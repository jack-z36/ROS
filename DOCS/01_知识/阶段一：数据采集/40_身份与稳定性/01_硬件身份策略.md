# 硬件身份策略

本页记录阶段一如何保证"同一物理传感器始终映射到同一 ROS topic"。这是阶段四模型部署的核心痛点，也是数据可复现的前提。

## 定位

本页回答：设备枚举顺序会变（`/dev/ttyUSB0` 和 `/dev/ttyUSB1` 互换、USB 口位置变），怎么保证每次采集时同一物理设备都发布到同一 topic？

本页是阶段一对阶段四最有复用价值的知识之一——阶段四部署同样面临"同一传感器必须读到同一 topic"的问题。

## 核心问题

物理设备的操作系统枚举顺序不稳定：

- `/dev/ttyUSB0` 和 `/dev/ttyUSB1` 可能在重启后互换。
- `/dev/video4` 在 USB 口位置变化后会指向不同设备。

如果直接用这些易漂移的路径做身份，会导致"今天左手传感器发到 `/pressure/left_hand/*`，明天发到 `/pressure/right_hand/*`"，数据彻底混乱。

阶段一对三类硬件采用不同的稳定身份策略：

## 触觉传感器：HWK_CHIP_UID 身份映射

这是阶段一最完善的身份策略，核心是**用芯片唯一 ID 而非串口路径做身份**。

### 机制

```text
每个 HWK 传感器有唯一的 HWK_CHIP_UID
  → 节点启动时通过串口协议查询每个设备的 HWK_CHIP_UID
  → 查 hardware_identity_map.yaml，把 UID 映射到固定的逻辑身份(hand/gripper)和 topic
  → 预创建 publisher，按映射结果发布
```

### identity_map.yaml 结构

```yaml
pressure:
  <logical_name>:
    match:
      HWK_CHIP_UID: "<芯片唯一ID>"
    target:
      hand: "left_hand"
      gripper: "gripper_1"
      topic: "/pressure/left_hand/gripper_1"
      frame_id: "pressure_sensor/left_hand/gripper_1"
    required: true
```

关键原则：**publisher 先按 UID target 创建，而不是按 `/dev/ttyUSB*` 创建。** 设备枚举顺序变化只影响"从哪个串口读到该 UID"，不影响最终 topic。

### 失败语义

| 情况 | 行为 |
|---|---|
| 未知 UID（不在映射表） | 报错并忽略，不发布到任何 topic |
| 重复 UID（两个设备同 UID） | 抛异常，避免同一硬件被绑定两次 |
| strict_identity=true 且无任何 target | 致命错误（ConfigError），节点无法启动 |
| 所有 `_sensors` 为空 | 抛 RuntimeError，节点退出（避免假启动成功） |

### 配置层防护

`config.py` 在解析阶段还检测：重复串口名、重复真实串口 realpath、非法 device_addr（0..15）、非法 package_id（0..63）、空 topic、重复 topic。

## 相机与串口设备：by-path / by-id 稳定路径

v4l2 相机和串口设备用**基于硬件拓扑或序列号的稳定路径**，而非 `/dev/video4`、`/dev/ttyUSB0` 这类易漂移路径。

### 相机（v4l2）

- 使用 `/dev/v4l/by-path/...`，路径基于 PCI/USB 拓扑（如 `pci-0000:00:0d.0-usb-0:3.2:1.0-video-index0`）。
- 只要相机插在同一 USB 口（同一拓扑位置），路径就稳定。
- **明确禁用** `/dev/video4` 这类裸设备号——它在 USB 口变动后会指向错误设备。

### 串口（触觉驱动扫描）

- `serial_port_globs` 配置为 `/dev/ttyUSB*`、`/dev/ttyACM*` 用于自动发现。
- 但最终身份由 HWK_CHIP_UID 决定（见上节），串口只是"从哪读 UID"的物理通道。
- 可选：udev rules（如 `99-hwk-pressure.rules`）创建 `/dev/hwk_pressure_*` 软链接，进一步稳定。

### by-id（序列号）

- `/dev/serial/by-id/` 基于设备序列号，是最稳定的路径形式。
- 阶段一目前主要用 by-path（相机）和 UID（触觉），by-id 作为备选。

## Baton Mini：固定 IP 身份

Baton Mini 是网络相机，身份由**固定 IP** 保证：

- 设备 IP 固定为 `192.168.1.10`。
- 本机通过 `local_ip`（默认 `192.168.1.18`）与之通信。
- 左右两台设备通过 launch 参数的 namespace 区分（`baton_mini_left`、`baton_mini_right`），各自需要独立的物理网络连接或 IP 配置。

网络身份天然稳定，不涉及设备路径漂移问题。

## 三类策略对比

| 硬件 | 身份锚点 | 稳定性来源 | 易漂移的陷阱 |
|---|---|---|---|
| 触觉（HWK） | `HWK_CHIP_UID` | 芯片唯一 ID + 映射表 | 无（UID 是硬件级唯一） |
| 相机（v4l2） | USB 拓扑位置 | `/dev/v4l/by-path/...` | `/dev/video4` 裸设备号 |
| Baton Mini | 固定 IP | `192.168.1.10` | 无（IP 配置级稳定） |

## 对阶段四的意义

阶段四模型部署时，推理程序同样需要读取传感器数据。这套身份策略可直接复用：

- 触觉：读取 `hardware_identity_map.yaml`，按 UID 绑定 topic。
- 相机：用 by-path 稳定路径接入。
- 关键：**部署代码不应假设 `/dev/ttyUSB0` 是左手传感器**，必须走 UID 或 by-path。
