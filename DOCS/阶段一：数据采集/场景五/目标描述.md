# 场景五目标描述：传感器序列号与固定 topic 的稳定绑定

## 1. 核心目标

场景五的最终目标保持不变：让真实硬件传感器无论插入顺序、USB 临时枚举编号或串口路径如何变化，都能把自己的数据稳定发布到规定 ROS2 topic。

本场景的触觉传感器实现路径修正为：

```text
传感器协议内序列号 -> topic 名称
```

也就是说，触觉传感器不再以“序列号 -> 现实 id -> topic”作为主路径，而是由 `hwk_pressure_driver` 在运行中读取每个传感器的序列号，并把“本次取回的触觉数据”与“本次确认的传感器序列号”关联起来。驱动按独立配置文件中的序列号到 topic 映射表，直接把数据发布到对应 topic。

例如：

```text
HWK_CHIP_UID=00600012-3035510B-3735333
    -> /pressure/right_hand/gripper_1
```

现实名称 `r1` 仍可作为人工标定和文档记录中的含义，但运行时分发逻辑的关键依据应是传感器序列号，而不是 `/dev/ttyUSBX`、USB 插口路径或人工现实 id。

## 2. 目标操作流程

触觉传感器侧的理想使用流程是：

```text
接入 4 个 HWK 触觉传感器
    ↓
启动 hwk_pressure_driver
    ↓
驱动打开当前可用串口或配置中的候选串口
    ↓
驱动按协议读取触觉压力数据
    ↓
驱动同时读取或确认该传感器的协议内序列号
    ↓
驱动把压力数据整理为标准 PressureFrame 消息
    ↓
驱动根据“序列号 -> topic”配置表选择发布 topic
    ↓
发布到固定 ROS2 topic
```

目标效果是：哪怕 Linux 把同一只触觉传感器枚举成不同 `/dev/ttyUSBX`，只要驱动能从传感器协议中读到同一个序列号，它的数据仍然发布到同一个固定 topic。

GoPro 侧仍属于场景五范围，但当前修正重点是触觉传感器。GoPro 采集卡后续仍需要根据可用硬件身份或人工标定结果，保证 `/gopro_right/image_raw` 和 `/gopro_left/image_raw` 稳定。

## 3. 目标绑定关系

触觉目标 topic 保持不变：

| 现实含义 | 绑定依据 | 目标 topic |
| --- | --- | --- |
| 左手第 1 台触觉传感器 | 传感器协议内序列号 | `/pressure/left_hand/gripper_1` |
| 左手第 2 台触觉传感器 | 传感器协议内序列号 | `/pressure/left_hand/gripper_2` |
| 右手第 1 台触觉传感器 | 传感器协议内序列号 | `/pressure/right_hand/gripper_1` |
| 右手第 2 台触觉传感器 | 传感器协议内序列号 | `/pressure/right_hand/gripper_2` |

序列号与 topic 的绑定应放在一个独立配置文件中，由 `hwk_pressure_driver` 加载。该配置文件至少需要表达：

```text
传感器序列号
目标 topic
hand / gripper 或等价消息字段
可选 frame_id / 备注现实名称
```

当前已知示例：

```text
00600012-3035510B-3735333 -> /pressure/right_hand/gripper_1
```

GoPro 目标 topic 保持不变：

| 逻辑含义 | 目标 topic |
| --- | --- |
| 右手 GoPro | `/gopro_right/image_raw` |
| 左手 GoPro | `/gopro_left/image_raw` |

## 4. 目标驱动行为

`src/hwk_pressure_driver` 的目标行为需要调整为：

```text
1. 继续负责从 HWK 触觉传感器读取压力数据；
2. 继续按现有数据模板组织 PressureFrame 消息；
3. 新增读取传感器协议内序列号的能力；
4. 每次取回压力数据时，同时取得或确认该数据对应的传感器序列号；
5. 将序列号作为该帧数据的身份依据；
6. 根据独立配置文件中的“序列号 -> topic”映射选择 publisher；
7. 将数据发布到对应固定 topic；
8. 如果序列号缺失、未知、重复或未配置，驱动必须明确报错或拒绝发布，不能按串口枚举顺序猜测 topic。
```

因此，驱动不应再把“某个串口配置项天然等于某个 gripper topic”作为唯一依据。串口路径可以用于打开设备，但不能作为最终决定发布到哪个 topic 的身份依据。

## 5. 成功标准

场景五触觉部分完成时，应满足：

```text
1. 驱动能读取每个 HWK 触觉传感器的协议内序列号；
2. 驱动能读取每个 HWK 触觉传感器的压力数据；
3. 每帧待发布压力数据都能关联到明确的传感器序列号；
4. 序列号与 topic 的绑定由独立配置文件管理；
5. 已配置序列号的数据会发布到对应固定 topic；
6. 未配置、重复或无法读取序列号的数据不会被错误发布到任意 topic；
7. 改变 `/dev/ttyUSBX` 枚举顺序后，同一个序列号仍发布到同一个 topic；
8. `ros2 topic list` 能看到四个固定触觉 topic；
9. 场景三 Octopus 仍能按固定 topic 采集数据并写入 MCAP；
10. 场景四 UI 仍能按固定 topic 展示目标触觉数据。
```

只靠 udev 按 USB 插口路径创建固定名称，或只靠当前 `pressure_sensors.yaml` 中的串口顺序发布，不算完成触觉部分的最终目标。

## 6. 与前序场景的关系

场景一和场景二解决传感器节点如何启动。

场景三解决 Octopus 订阅固定 topic、录制并输出 MCAP。

场景四解决 Octopus UI 中目标数据如何展示。

场景五解决更底层的身份稳定性：让触觉传感器的数据根据传感器自身序列号直接分发到固定 topic，使 Octopus 和 UI 不需要关心底层串口枚举和插线顺序。

## 7. 一句话总结

场景五触觉部分要实现的是：`hwk_pressure_driver` 运行时读取传感器序列号，并按“序列号 -> topic”的独立配置表，把对应传感器数据直接发布到固定 ROS2 topic。
