# L2-05 验收机制

> [!info] 文档契约
> - 消费对象：L3 生成 Agent、验收 Agent、L2 Gate 主 Agent。
> - 权威性：本文定义 AI 侧 Gate；人类操作见 `05_人类验收机制.md`。
> - 上游来源：`01_L2功能边界.md`、`03_ACT微元设计与协作.md`。
> - 不负责范围：不把设计期未实现命令伪装为已通过，不自动授权真机。
> - 读取时机：生成 acceptance card、执行 L2 Gate、判断下游/合入前。
> - 冲突处理：结构 validator 通过不等于语义 Gate 通过；必须逐项核对下表证据。

## 1. Gate 目标

证明 L2-05 在不拥有调度或硬件驱动的前提下，能把 L2-04 安全通过的 16D `[TCP7,TCP7,gripper,gripper]` action 映射为正确 ROS 输出，并严格执行 dry/shadow/safe 模式、最终授权、四路本地构造门、夹爪防刷和真实 status 语义。

## 3. Gate 验收矩阵

| ID | 验证层级 | 测试输入 | 观察点 | 通过现象 | 失败现象 |
|---|---|---|---|---|---|
| G01 | import/unit | 无 ROS 环境 import types/service/ui | pytest | lazy ROS import；types/service 可用 | ImportError 或 import 时创建 ROS 资源 |
| G02 | unit | valid SafetyResult + 16D | ActionPublishPlan | 左右 TCP 段、frame、quat 顺序正确 | 左右交换/欧拉角/单位漂移 |
| G03 | unit | gripper 0/0.5/1 | CommandTargets | 0/50/100 | 旧 300/1000 或反向映射 |
| G04 | negative unit | `accepted=False`、action=None、gripper=50/100 的伪 safe | exception/result + publisher mocks | 整批拒绝，四路 command=0 | 猜测尺度或绕过 safety |
| G05 | mock | dry-run | 六 publisher 调用 | ROS 调用=0，RAM result 明确 | 任何 command publish |
| G06 | mock/shadow | shadow-run、command_allowed 任意 | topic calls | policy/status=1；四路 command=0 | shadow 命令泄漏 |
| G07 | mock | safe-run + command_allowed=False | calls/status | policy/status=1；command=0；reason 可读 | gate 被忽略 |
| G08 | mock | safe-run + command_allowed=True | messages/calls | 2 PoseStamped + 2 Float64；全部先构造；按计划发 | 构造中途已发布 |
| G09 | failure injection | 右臂消息构造失败 | publisher calls | 四路 command=0 | 左臂已被主动发布 |
| G10 | failure injection | 第 n 个 publish 抛异常 | result/status | partial count、sent=false、无伪回滚 | 报 success 或硬件到位 |
| G11 | multi-tick mock | 重复/高频 gripper 目标 | gripper calls/state | deadband/min interval 生效；只在成功后更新 state | 无界刷写或失败也更新 last |
| G12 | static | UI 源码 | rg/AST | 无 subscription/timer/workspace/IK/厂商 SDK | 职责越界 |
| G13 | ROS shadow | fake safe action stream | ros2 topic | policy/status 可见；四路 command 0 | 任一真实 command 出现 |
| G14 | hardware | safe-run 真机 | driver/status/现场 | 仅经人工授权执行 | 默认自动执行或无急停 |

## 5. 阻断状态

| 状态 | 适用情况 | 当前可继续什么 | 不得声称什么 |
|---|---|---|---|
| `PASS_LOCAL` | G01-G12 全过 | 可进入 ROS shadow | 不代表 ROS/hardware 已通过 |
| `BLOCKED_ENV` | 无 rclpy/ROS graph | 可用 mock 完成本地 Gate | 不得把 G13 写成 PASS |
| `BLOCKED_HARDWARE_EXPECTED` | 无 RM65/F100/现场授权 | 可完成 shadow 与设计合入前审查 | 不得把 G14 写成 PASS |
| `FAIL_CONTRACT` | L2-04 仍输出 gripper 0..100 或 L1 仍未同步 | 可局部开发，但不能通过集成 Gate | 不得做双尺度兼容掩盖问题 |

## 6. 下游放行与 Git 合入

- L3 生成：本设计包 validator 与语义审计通过后允许生成。
- L2-06 mock 开发：`ActionPublishRequest/Result` 契约冻结后可并行使用 mock port。
- ROS shadow：必须先 `PASS_LOCAL`。
- safe-run/real-robot：必须先 shadow 证据、人工授权、急停就绪、driver readiness 可观察。
- 合入 `model_deploy`：必须 `PASS_LOCAL`，当前 L1 边界漂移和 L2-04 gripper 域已同步，人类验收签字完成；硬件项可以按规则记录 `BLOCKED_HARDWARE_EXPECTED`，不能伪造通过。

## 7. 失败排查入口

| 现象 | 首查 |
|---|---|
| 左右/frame/量纲错误 | `09_service层设计.md` 与 `types/action_spec.py` |
| shadow 出现 command | `build_publish_plan` mode 矩阵、UI 门控 |
| 未授权仍发 command | PublishAuthorization 构造方 L2-06 + L2-05 二次门控 |
| gripper 被放大 | 上游是否传 0..100；`map_gripper_command` 是否只接 `[0,1]` |
| 部分消息后报 success | UI publish 计数与异常处理 |
| publish 成功却硬件未动 | 外部 driver/gate/status；禁止改成“硬件到位” |
