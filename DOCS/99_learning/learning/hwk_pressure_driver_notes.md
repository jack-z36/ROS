## 二、知识点详解

### 第一层：操作系统基础

#### 1.1 进程与线程

**进程** = 操作系统分配资源的基本单位，类比为一个独立的工厂。

- 每个进程有自己独占的内存空间（车间、仓库）
- 进程之间互相隔离，一个崩了不影响别的
- 例：微信是一个进程，浏览器是另一个进程

**线程** = 进程内部的执行单元，类比为工厂里的工人。

- 同一进程内的所有线程共享内存（共享车间和仓库）
- 每个线程也有自己的一小块私有工作空间
- 多个线程可以同时干活

**为什么 driver 用线程而不是进程？**

driver 需要同时读多个串口（不能等串口 1 读完再读串口 2），而且多个串口收上来的数据需要发布到同一个 ROS 节点的 topic 上——共享内存最方便，所以用多线程。

```
driver 进程（1 个工厂）
  ├── 主线程（工人A）：拿着配置单，定时向传感器发请求
  ├── 线程1（工人B）：盯着串口1，不停读字节
  └── 线程2（工人C）：盯着串口2，不停读字节
```

### 第二层：串口通信

#### 2.1 串口是什么

串口（Serial Port）是一种最简单的通信方式：一根线，逐位传输二进制数据（0 和 1）。

通信过程：

```
上位机（电脑）  ──── 串口线 ────  传感器芯片

1. 上位机发送请求："6号传感器，给我数据"
2. 传感器收到请求，把压力数据按协议打包成二进制
3. 传感器通过串口线把二进制数据发回上位机
4. 上位机按协议解码，还原出压力数值
```

这是一种**请求-响应**模式：上位机主动问，传感器被动答。

#### 2.2 USB 转串口与设备文件

触觉传感器通过 USB 接口连接电脑，但通信方式是串口协议，所以需要 **USB 转串口**。

Linux 系统会自动识别 USB 转串口设备，并在 `/dev/` 目录下创建设备文件：

```
插一根 USB 转串口线 → 系统自动创建 /dev/ttyUSB0
再插一根           → 系统自动创建 /dev/ttyUSB1
拔掉第一根         → /dev/ttyUSB0 消失
```

- `/dev/ttyUSB*`：USB 转串口设备
- `/dev/ttyACM*`：另一种 USB 串口设备（如 Arduino）
- 不是所有 USB 设备都会出现这里（鼠标、U盘不会）

#### 2.3 串口通信协议

协议就是双方约定的"暗号"，确保发送方和接收方能互相理解。

本项目中的协议要点：

| 协议要素 | 值 | 含义 |
|---|---|---|
| 帧头 | `0x3C 0x3C` | 数据包的开头标记 |
| 帧尾 | `0x3E 0x3E` | 数据包的结尾标记 |
| CRC16 | 校验和 | 检测数据在传输中是否出错 |
| device_addr | 0-15 | 一条线上多个传感器的地址编号 |

driver 的工作就是：按协议**组装请求包**发出去 → 按协议**拆解响应包**拿到数据。

#### 2.4 udev 别名规则

`/dev/ttyUSB0` 这个名字不稳定——拔插顺序变了，编号可能变。为了让名字固定，Linux 提供 **udev 规则**，根据硬件特征（如序列号）给设备起别名：

```
原始名字（可能变）：/dev/ttyUSB0
        │
        │  udev 规则（根据硬件序列号自动创建别名）
        ▼
固定别名（不会变）：/dev/hwk_pressure_left_gripper_1
```

这样 YAML 配置里写别名就行，不用担心插拔顺序。

#### 2.5 GoPro HDMI 采集卡识别

GoPro 相机和触觉传感器的识别方式本质上一样——都是 USB 设备，都有硬件序列号。区别在于设备类型不同：

| 传感器类型 | 接入方式 | 设备文件 | 识别命令 |
|---|---|---|---|
| 触觉传感器 | USB 转串口 | `/dev/ttyUSB*` | `ls /dev/ttyUSB*` |
| GoPro 相机 | HDMI 采集卡（USB） | `/dev/video*` | `v4l2-ctl --list-devices` |

GoPro 不是直接插 USB 的，它通过 **HDMI 采集卡**（一个 USB 设备）把视频信号传给电脑。采集卡本身也是一个 USB 设备，同样有硬件序列号。

查看所有视频采集设备：

```bash
v4l2-ctl --list-devices
```

输出示例：

```
USB Video (usb-0000:00:14.0-1):        ← 采集卡1
    /dev/video0
    /dev/video1

USB Video (usb-0000:00:14.0-2):        ← 采集卡2
    /dev/video2
    /dev/video3
```

#### 2.6 硬件序列号与设备固定命名

无论是触觉传感器的 USB 转串口芯片，还是 GoPro 的 HDMI 采集卡，每个 USB 设备都有出厂时烧录的**硬件序列号**——类似身份证号，全球唯一，不会重复。

`/dev/ttyUSB0`、`/dev/video0` 这些名字不稳定（依赖插入顺序和 USB 口位置），但硬件序列号是固定的。udev 规则就是利用这一点来创建固定别名。

**固定命名的完整流程：**

```
1. 只插一个设备 → 记下它出现在哪个 /dev/xxx
2. 再插另一个 → 记下另一个
3. 用排除法（拔一个看谁消失）确定哪个序列号对应哪个物理设备
4. 写 udev 规则：序列号 → 固定别名
5. 以后不管插哪个口，别名都不变
```

查看串口设备序列号的命令：

```bash
udevadm info --name=/dev/ttyUSB0 --property=ID_SERIAL_SHORT
```

### 第三层：ROS 2 消息与通信

#### 3.1 interfaces 包 = 消息模板

`hwk_pressure_interfaces` 这个包**不干任何实际工作**，它只定义了一个消息类型 `PressureFrame`，告诉 ROS 2 世界"触觉传感器的数据长什么样"。

类比：它是一张空白的表格模板，定义了有哪些字段、每个字段填什么类型的数据。

PressureFrame 的字段结构：

```
PressureFrame（一张数据表单）
┌──────────────────────────────────────┐
│ header         时间戳 + 坐标系       │
│ hand           哪只手（如 left_hand）│
│ gripper        哪个夹爪（如 gripper_1）│
│ device_addr    传感器地址（0-15）     │
│ package_id     包序号（0-63 循环）    │
│ total_packets  总包数                │
│ packet_index   当前包序号            │
│ rows           传感器阵列行数         │
│ cols           传感器阵列列数         │
│ data[]         压力数据矩阵          │
│ raw_payload[]  原始字节（调试用）     │
└──────────────────────────────────────┘
```

构建后产生的 `.so` 文件，是 ROS 2 为不同编程语言和通信中间件自动生成的"翻译版本"，让各组件都能读懂这个消息格式。

#### 3.2 topic 与 publisher

- **topic**：ROS 2 中的数据通道，像一个广播频道。发的人往里面放数据，收的人从里面取数据。
- **publisher**：发布者，往 topic 里放数据的组件。
- **subscriber**：订阅者，从 topic 里取数据的组件。

```
driver 节点（publisher）
    │
    │  发布 PressureFrame 消息
    ▼
topic: /pressure/left_hand/gripper_1
    │
    ├── Octopus（subscriber）→ 录制成 MCAP 文件
    ├── RViz（subscriber）   → 可视化压力分布
    └── 其他算法节点（subscriber）→ 抓取控制等
```

### 第四层：驱动工作原理

#### 4.1 数据流全景

```
物理传感器
    │ 串口线
    ▼
SerialWorker（一个串口一个线程）
    │ 读字节流 → 找帧头帧尾 → CRC 校验 → 拆出有效数据
    ▼
PressureDriverNode（主线程）
    │ 按 PressureFrame 模板填入数据
    │ 发布到 topic
    ▼
ROS 2 topic
    │
    ▼
下游消费者（Octopus、RViz 等）
```

#### 4.2 YAML 配置文件的作用

YAML 是 driver 的"快递发货单"，driver 启动时读取它，才知道：

- 去哪个串口收数据（`port`）
- 上面挂着什么传感器（`hand`、`gripper`）
- 一条线上怎么区分多个传感器（`device_addr`）
- 数据阵列多大（`rows`、`cols`）
- 收到的数据发到哪个 topic

**driver 不会自动发现串口或传感器，YAML 里写了什么，它就做什么。没写，它就不知道。**

#### 4.3 多传感器如何对应

通过两个维度唯一确定一个传感器：

```
(串口路径, device_addr) → 唯一确定一个传感器 → 对应一个 topic
```

- **不同串口**上的传感器，`device_addr` 可以重复（因为不在同一条总线上）
- **同一串口**上的多个传感器，`device_addr` 必须不同（像同一间教室里的学生学号不能重复）

#### 4.4 四个源文件的协作模式

驱动包（`hwk_pressure_driver`）的核心逻辑由四个 Python 文件组成，各自职责清晰，互不越界。

**文件一览：**

| 文件 | 角色 | 类比 |
|---|---|---|
| `pressure_driver_node.py` | 站长（总调度） | 看发货单、雇快递员、定时派活、收货后发布 |
| `config.py` | 发货单 | 读 YAML、校验参数、返回配置 |
| `serial_worker.py` | 快递员 | 跑到串口收发货，按协议打包拆包 |
| `protocol.py` | 包装规则 | 二进制帧的组装和拆解 |

**调用关系（从上到下，上层调用下层）：**

```
pressure_driver_node.py（站长）
    │
    │  启动时：
    ├── 调用 config.py           → 读 YAML 配置，拿到所有参数
    │
    │  根据配置，为每个串口创建：
    └── 调用 serial_worker.py    → 创建 SerialWorker 实例（每个串口一个）
          │
          │  SerialWorker 内部：
          └── 调用 protocol.py   → 组帧（发请求时）、拆帧（收响应时）
```

**每个文件的职责边界：**

```
protocol.py（包装规则）
  │  只管二进制帧的组装和拆解
  │  不做的事：不知道串口是什么，不知道 ROS 是什么，不知道传感器是什么
  │

serial_worker.py（快递员）
  │  管一个串口的全生命周期：打开、读线程、写请求、关闭
  │  收到有效帧后，回调通知 pressure_driver_node
  │  不做的事：不知道 ROS 是什么，不知道数据该怎么组装成消息
  │

config.py（发货单）
  │  读 YAML 文件 → 校验参数 → 返回结构化的配置对象
  │  不做的事：不做任何运行时逻辑
  │

pressure_driver_node.py（站长）
  │  唯一的入口点，程序从它的 main() 开始跑
  │  读配置 → 建 Publisher → 建 SerialWorker → 启动定时器
  │  定时向传感器发请求
  │  收到帧回调后：匹配传感器 → 解析载荷 → 填 PressureFrame → 发布到 topic
  │  监控传感器超时
```

### 第五层：系统运行与排查

#### 5.1 构建产物（build 目录）

`colcon build` 之后，两个包的 build 目录内容截然不同：

| 包 | build 目录内容 | 原因 |
|---|---|---|
| `hwk_pressure_interfaces` | 大量 `.so` 文件和代码生成目录 | C++ 编译型包，ROS 2 为每种语言/协议生成了支持库 |
| `hwk_pressure_driver` | 只有 `egg-info` 和几个日志 | Python 解释型包，不需要编译 |

#### 5.2 串口排查流程

```
串口不存在的错误
  │
  ├── ls /dev/ttyUSB* 有没有？
  │     ├── 没有 → 线没插、线坏了、驱动没装
  │     └── 有 ↓
  │
  ├── ls /dev/hwk_pressure_* 有没有？（别名）
  │     ├── 没有 → udev 规则没配或没生效
  │     └── 有 ↓
  │
  ├── 别名和 YAML 里写的名字是否一致？
  │     ├── 不一致 → 改 YAML 或改 udev 规则
  │     └── 一致 → 问题不在这里
  │
  └── 临时方案：把 YAML 里的 port 直接改成 /dev/ttyUSB0 先跑起来
```

常用命令：

```bash
# 查看原始串口设备
ls /dev/ttyUSB* /dev/ttyACM* 2>/dev/null

# 查看别名
ls /dev/hwk_pressure_* 2>/dev/null

# 插拔对比（先不插，看一次；插上，再看一次）
ls /dev/ttyUSB* 2>/dev/null

# 查看视频采集设备（GoPro 用）
v4l2-ctl --list-devices

# 查看某个串口设备的硬件序列号
udevadm info --name=/dev/ttyUSB0 --property=ID_SERIAL_SHORT
```

## 三、两个包的职责总结

```
hwk_pressure_interfaces（模板定义者）
  │  只定义 PressureFrame 消息的结构
  │  不运行、不处理数据、不知道串口是什么
  │  构建后生成 .so 库，供其他包引用
  │

hwk_pressure_driver（数据搬运工）
  │  读 YAML 配置 → 知道去哪收数据、发给谁
  │  开串口线程 → 从传感器收二进制数据
  │  按协议解码 → 还原出压力数值
  │  填入 PressureFrame → 发布到 topic
  │  不定义消息格式，只使用 interfaces 提供的模板
```
