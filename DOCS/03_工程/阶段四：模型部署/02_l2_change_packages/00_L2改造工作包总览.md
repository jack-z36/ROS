## 0. 划分方法论

本总览的 L2 划分经过两轮迭代：

1. **第一轮（代码耦合 + 验证阶梯）**：按「改 A 必须同时改 B 否则编译不过」理出代码簇，按「改完能独立验证」拆层。得到初步 5 个 L2。
2. **第二轮（分层架构审计）**：用通用分层架构（Types → Config → Repo → Service → Runtime → UI，C5-1 单向依赖）当**边界检查器**，审查第一轮 L2 是否跨层污染。修正后边界更干净。

**核心原则**：分层架构是「边界检查器」，不是「划分模板」。L2 数量按实际控制（5 个），但每个 L2 内部的代码不得跨层污染。

## 1. 分层映射（Pi05 部署项目的 6 层对应）

通用 6 层架构映射到本项目：

| 通用层 | Pi05 部署对应 | AS-IS 文件 |
|---|---|---|
| **Types** | 数据结构定义（state/action 的物理语义、维度常量） | `common/data/state_codec.py`、`common/robot/action_spec.py`、`common/data/action_codec.py` |
| **Config** | 运行参数、topic 名、维度、安全配置 | `deploy/config/schema.py` |
| **Repo** | 数据获取（ROS 订阅 callback、bundle 文件加载） | `deploy_node._create_subscriptions`/各 `_xxx_cb`、`policy_loader.load_policy_runtime` 的文件读取部分 |
| **Service** | 业务逻辑（snapshot 装配、batch 构建、安全检查、推理） | `observation_collector.snapshot`、`policy_loader._build_batch`/`predict_action_chunk`、`safety_guard.filter_action`、`control_loop.tick` |
| **Runtime** | 节点装配与驱动（timer、executor、生命周期） | `pi05_vla_deploy_node.__init__`、`inference_worker`（后台线程）、`_control_tick` 的调度部分 |
| **UI** | 对外接口（ROS topic 发布） | `_create_publishers`、`_control_tick` 的发布部分、`_publish_metrics` |

## 2. 第一轮 L2 的跨层污染（审计发现）

| 旧 L2 | 包含代码 | 污染问题 |
|---|---|---|
| 旧 L2-01 | state_codec(Types) + action_spec(Types) + action_codec(Types) + config/schema(Config) | 🚨 混 Types + Config。按 C5-1，Types 不依赖 Config，Config 依赖 Types，是两层。 |
| 旧 L2-02 | collector(Service) + deploy_node订阅(Repo+Runtime) + policy_loader(Service) | 🚨 混 Repo + Service + Runtime。 |
| 旧 L2-03 | deploy_node发布(Runtime+UI) + safety_guard(Service) | 🚨 混 Service + Runtime + UI。 |

结论：粒度对，边界脏。修正目标——让每个 L2 只覆盖**同一层或严格相邻层**，且层间依赖单向。

## 3. 修正后的 L2（5 个，边界干净）

| 修正 L2 | 对应分层 | 包含代码 | 关联 Delta | 验证阶梯 | 真机风险 |
|---|---|---|---|---|---|
| **L2-01** | Types | state_codec、action_spec、action_codec | D8/D9/D11 | 单测（不依赖任何层） | 低 |
| **L2-02** | Config | config/schema（topic/维度/safety 配置） | D2/D7 | 单测（依赖 Types） | 低 |
| **L2-03** | Repo + Service（输入侧） | observation_collector、policy_loader._build_batch、deploy_node 订阅侧 | D3/D7/D8/D10 | dry-run（依赖 01/02） | 低 |
| **L2-04** | Service + Runtime + UI（输出侧） | safety_guard、deploy_node 发布侧、policy_action publisher、mode/gate 逻辑 | D12/D13/D17/D18 | dry-run + shadow-run（依赖 01） | 中 |
| **L2-05** | 独立新节点（自含分层） | command_bridge_sender_node、rm65_driver_node 适配、elephant_gripper_node 适配、新 launch | D1/D2/D5/D6/D14/D15/D16/D19 | shadow-run + real-robot | **高** |

### 为什么这么组合（边界干净性的证明）

**L2-01（Types）只含 Types 层**：state_codec / action_spec / action_codec 全是数据结构定义 + 编解码函数。不依赖 Config / Repo / Service。改完可纯单测（喂数据看输出）。

**L2-02（Config）只含 Config 层**：config/schema 是配置定义。它依赖 Types（引用 `ACTION_DIM`/`STATE_DIM`），但不依赖 Repo/Service。改完可单测（校验 config 加载）。

**L2-03（Repo+Service 输入侧）覆盖相邻两层**：observation_collector（Service：装配 snapshot）+ deploy_node 订阅（Repo：ROS callback）+ policy_loader._build_batch（Service：batch 构建）。这三者**共同隐藏「ROS 数据 → 模型 batch」的装配逻辑**，变化原因一致（数据语义变了），验证阶梯一致（dry-run）。Repo→Service 是相邻层、单向依赖，合并不违反 C5-1。

**L2-04（Service+Runtime+UI 输出侧）覆盖相邻三层**：safety_guard（Service：安全检查）+ deploy_node 发布（Runtime+UI：发布 policy_action）+ mode/gate 逻辑。这三者**共同隐藏「模型输出 → policy_action 发布」的逻辑**，变化原因一致（action 语义+发布出口变了），验证阶梯一致（dry-run+shadow）。这里跨了三层，但都是**输出链路的紧密耦合**——safety 检查的结果直接决定 `_control_tick` 发不发，强耦合，拆开反而增加协调成本。Service→Runtime→UI 单向依赖成立。

**L2-05（硬件栈）是独立子系统**：command_bridge + rm65 + gripper + launch。和前 4 个 L2 只通过 `/pi05/policy_action` topic 解耦（UI 层的对外接口）。它内部自含分层（Types: 无 / Config: launch 参数 / Repo: 订阅 policy_action+arm状态 / Service: IK检查+width→angle转换 / Runtime: 节点生命周期 / UI: 发布 command topic）。必须真机，验证阶梯不同，独立成包。

## 4. 依赖关系（单向，符合 C5-1）

```text
L2-01 Types （地基，不依赖任何层）
   ↓ Config 依赖 Types
L2-02 Config
   ↓ Repo/Service 依赖 Types+Config
L2-03 Repo+Service（输入侧）          L2-04 Service+Runtime+UI（输出侧）
   ↓                                    ↓
   └──→ /pi05/policy_action ←───────────┘  （UI 对外接口 = 契约边界）
              ↓ （topic 解耦，非代码依赖）
        L2-05 硬件执行栈（独立子系统）
```

- L2-01 → L2-02 → L2-03：严格单向（Types→Config→Repo+Service）。
- L2-04 依赖 L2-01（Types，因为 safety_guard 用 action 结构），但**不依赖** L2-02/L2-03（它消费的是模型输出，不关心 observation 怎么来的）。所以 L2-03 ∥ L2-04 可并行。
- L2-05 不依赖前 4 个的**代码**，只依赖 `/pi05/policy_action` 的**契约定义**（16D 段序）。

### 建议执行顺序

```text
第一波：L2-01（Types 地基）
第二波：L2-02（Config，紧跟地基）
第三波：L2-03 ∥ L2-04（并行，都依赖 01，彼此解耦）
第四波：L2-05（接真机，最高风险）
```
