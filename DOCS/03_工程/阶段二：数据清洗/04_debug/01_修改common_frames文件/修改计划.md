# 修改计划总览：解耦 common_frame 错误链路

## 1. 本次问题的宏观背景

当前阶段二位姿链路曾按统一 `common_frame` 推进：

```text
raw Baton Mini 相机位姿
-> common-frame camera/TCP pose
-> 场景二滤波、MCAP_A
-> common_frame 到 robot_base 的后置转换
-> IK / MCAP_B / 关节限制检查
```

这个方向与最终数据集的新定义冲突。新的最终语义是：

- 左手位姿数据描述在左手机械臂基坐标系下。
- 右手位姿数据描述在右手机械臂基坐标系下。
- 不再把左右手位姿统一描述到同一个机器人基坐标系下。
- 当前后续主线放弃 IK / MCAP_B / 关节限制检查，改为直接对 MCAP_A 做数据对齐并导出 LeRobot v3。

## 2. 新目标链路

以左手为例：

```text
原始 Baton Mini 相机数据（左手相机自身参考系）
-> TCP 位姿（左手相机自身参考系）
-> TCP 位姿（左手机械臂基坐标系）
-> 滤波处理
-> TCP 位姿（左手机械臂基坐标系）
```

右手同理：

```text
原始 Baton Mini 相机数据（右手相机自身参考系）
-> TCP 位姿（右手相机自身参考系）
-> TCP 位姿（右手机械臂基坐标系）
-> 滤波处理
-> TCP 位姿（右手机械臂基坐标系）
```

## 3. 局部问题之间的关系

本次修正拆成五个局部问题：

1. 旧的位姿转换配置生成模块应删除。
   - 原模块围绕 `FrameAlignmentConfig` / `common_anchor` 生成 common frame 配置。
   - 新方案不再由程序生成这类配置。
   - 后续由用户直接输入“工作坐标系在机械臂基坐标系下的位姿”。

2. 位姿转换计算应改为调用官方函数。
   - 原位姿转换功能模块不是整体删除，它需要继续承担两段职责。
   - 第一段：实现相机位姿到 TCP 位姿的转换。
   - 第二段：实现相机坐标系到机械臂基坐标系的转换。
   - 第二段必须使用睿尔曼官方 API：输入 TCP 在相机坐标系下的位姿 + 工作坐标系在基坐标系下的位姿，输出 TCP 在机械臂基坐标系下的位姿。
   - 该原子文档还必须说明如何搭建可正常使用官方 API 的 Python SDK 环境。

3. 场景二后半段路线调整。
   - 暂不修改 IK 求解、MCAP_B、关节限制检查相关模块。
   - 这些内容不进入当前修正范围。
   - 后续主线转为 `MCAP_A -> 数据对齐 -> LeRobot v3`。

4. 数据定义文件需要单独改造。
   - 旧数据定义中存在 common-frame pose、common->base 后置转换、IK / MCAP_B / 关节限制路线的契约。
   - 后续应把主位姿数据定义改为左右独立的 arm-base TCP pose。
   - 本次只生成修改计划，不直接修改现有 L2 数据定义文件。

5. 开发者端最终验收交互需要单独说明。
   - 修复完成后，用户应通过开发者引导菜单逐项验收场景一和场景二。
   - 验收文档需要明确每个菜单项进入后看到什么、执行后输出什么、什么现象代表功能完善。
   - 本次只生成验收交互文档，不实现菜单代码。
