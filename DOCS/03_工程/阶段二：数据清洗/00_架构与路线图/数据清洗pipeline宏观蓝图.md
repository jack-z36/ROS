# 数据清洗 pipeline 宏观蓝图

## 文档定位

本文是阶段二数据清洗 pipeline 的最高层蓝图。它只固定目标、数据主链路、产物边界、交互闭环和验收方式；不提前冻结源码文件名、类名、函数名或内部模块拆分。

旧版 canonical dataset 路线图已归档到：

```text
DOCS/归档/2026-05-28_阶段二旧宏观路线图_五场景canonical方案/
```

## 一、最终目标

阶段二最终目标是：

```text
把阶段一采集得到的 raw MCAP，处理成 LeRobotDataset v3 数据集，
用于 LeRobot 框架执行 ACT 模型训练。
```

阶段二的交付结果必须满足：

1. 能从真实 MCAP 小样本跑通端到端数据处理链路。
2. 输出的数据集能被 LeRobot 的数据读取与 ACT 训练前检查流程消费。
3. 每次处理都有独立 run 目录、配置快照、输入样本清单、运行日志和输出产物。
4. 用户不需要记忆内部脚本路径，只通过统一入口进入开发调试或生产处理。

## 二、主数据流

新版主链路为：

```text
raw MCAP
  -> [场景一] cleaned MCAP
  -> [场景二] MCAP_A / validated MCAP
  -> [场景三] aligned MCAP
  -> [场景四] LeRobotDataset v3
  -> [阶段三] LeRobot ACT training
```

与旧路线相比，关键变化是：

| 旧路线 | 新路线 |
|---|---|
| `cleaned -> validated -> aligned -> canonical_dataset_mcap -> exports` | `cleaned -> MCAP_A / validated -> aligned -> LeRobotDataset v3` |
| 场景一中间路径（旧 common frame）已降级为历史兼容 | 场景一主路径直接服务机械臂 base 坐标系位姿表达 |
| `validated MCAP` 包含 IK、关节限位、MuJoCo 仿真标注 | `MCAP_A / validated MCAP` 只输出主数据清洗、滤波、补全后的 MCAP，不做仿真与关节限位标注 |
| 场景四构建自定义 canonical dataset | 场景四构建 LeRobotDataset v3 |
| 场景五负责通用训练格式导出 | 阶段二主线不再维护通用 exporter；只保证 LeRobotDataset v3 可用于 ACT |

## 三、五个场景的新定位

| 场景 | 新定位 | 输出 |
|---|---|---|
| 场景一：提取夹爪开合以及位姿转换 | 从 raw MCAP 生成 cleaned MCAP，补齐夹爪开合语义，并把位姿转换到后续机械臂 base 坐标系链路所需表达。 | cleaned MCAP（含 arm-base TCP pose + raw pose）、清洗报告、位姿转换/标定配置。 |
| 场景二：硬件数据可靠性验证 | 从 cleaned MCAP 生成 MCAP_A / validated MCAP。P0 只做主数据滤波、补全、异常标记和可追溯写出，不做 IK、关节限位和 MuJoCo 仿真标注。 | MCAP_A、异常/修复/滤波报告、写出摘要。 |
| 场景三：MCAP 多 topic 时间轴对齐 | 从 MCAP_A / validated MCAP 生成 aligned MCAP，统一图像、触觉、位姿、夹爪等 topic 到 step 时间轴。 | aligned MCAP、alignment report、对齐索引或 sidecar。 |
| 场景四：构建 LeRobotDataset v3 | 从 aligned MCAP 直接构建 LeRobotDataset v3，形成阶段三 ACT 训练输入。 | LeRobotDataset v3 数据集、dataset meta、转换报告、读取校验结果。 |
| 场景五：训练入口验证与数据集交付 | 验证 LeRobotDataset v3 能进入 LeRobot ACT 数据读取和训练前检查。若后续需要多格式导出，再作为扩展，不作为当前主线。 | ACT 训练前检查结果、数据集交付报告。 |

## 四、交互闭环

本文中的用户交互逻辑分为两类：

- **开发者端交互逻辑**：程序开发完成后，开发者如何使用入口程序检验某个场景或功能模块是否正确。它服务于功能检验，不以生产整批数据集为目标。
- **用户端生产交互逻辑**：最终使用者如何使用已经开发好的 pipeline 完成全流程或单场景数据清洗。它服务于稳定生产 cleaned、MCAP_A / validated、aligned 和 LeRobotDataset v3。

交互组织粒度统一以阶段二五个场景为主，不以底层脚本文件为主。具体功能检验项由每个场景真正开发时再定义并写入对应场景文档；本文只规定统一交互规范。

### 1. 开发者端交互逻辑

开发者端通过统一入口进入开发调试模式：

```text
./start_data_clean.sh --dev
```

`--dev` 表示进入开发者引导界面，不直接执行正式生产流程。开发者引导界面的一级菜单固定对应阶段二五个场景：

```text
开发者引导界面
  1. 场景一：提取夹爪开合以及位姿转换
  2. 场景二：硬件数据可靠性验证
  3. 场景三：MCAP 多 topic 时间轴对齐
  4. 场景四：构建 LeRobotDataset v3
  5. 场景五：训练入口验证与数据集交付
```

选择某个场景后，进入该场景的功能检验菜单。该菜单按功能组织，不按脚本文件组织。具体有哪些功能检验项，在该场景实际编码时再确定；但每个场景至少必须保留一个“场景完整 smoke test”选项，用于按该场景内部主要处理链路跑通一次最小样本。

开发者端每个功能检验或场景 smoke test 的输出只要求两类：

- **测试产物**：用于判断该功能是否按预期运行的调试输出、中间结果、小样本结果。
- **运行日志**：记录输入、配置、执行步骤、关键状态、错误信息和输出位置。

开发者端输出必须与正式生产输出隔离。每次功能检验应保留独立运行目录，目录内至少包含测试产物和运行日志。调试产物不写入正式 LeRobotDataset v3 目录，也不污染正式生产输出。

开发者端默认读取用户端生产配置，以保证功能检验接近真实生产契约；同时允许在引导界面临时覆盖部分参数。临时覆盖只对本次开发调试运行生效。只有开发者明确选择“保存到配置文件”时，才允许把覆盖结果写回正式配置。

开发者端交互闭环为：

```text
./start_data_clean.sh --dev
  -> 选择场景
  -> 选择该场景下的功能检验项或完整 smoke test
  -> 选择小样本输入和调试输出位置
  -> 可选：临时覆盖配置
  -> 执行检验
  -> 查看测试产物和运行日志
  -> 判断功能是否正确
```

开发者端交互应呈现为“页面/终端向导调用脚本”的体验，而不是要求开发者记住每个内部脚本的路径和参数。开发者只需要知道自己要检验哪个场景、哪个功能；入口程序负责根据选择调用对应脚本、传递配置、创建调试输出目录并写入运行日志。

#### 开发者端通用交互剧本

开发者端每次检验的通用交互逻辑如下：

```text
启动入口
  -> 进入开发者引导界面
  -> 选择一个阶段二场景
  -> 进入该场景的功能检验菜单
  -> 选择要检验的功能或场景完整 smoke test
  -> 系统展示本次检验需要的输入、配置和输出
  -> 开发者确认或临时覆盖输入/配置/输出目录
  -> 系统调用对应功能脚本
  -> 系统写出测试产物和运行日志
  -> 开发者根据测试产物和运行日志判断功能是否正确
  -> 选择继续检验同场景其他功能、运行场景 smoke test、返回场景列表或退出
```

开发者端不要求每个功能检验都生成正式报告，但运行日志必须足够回答四个问题：

- 本次检验调用了哪个场景和功能。
- 本次检验读取了哪些输入和配置。
- 本次检验生成了哪些测试产物。
- 本次检验失败时失败在哪一步，错误摘要是什么。

#### 场景一开发者交互示例

场景一用于检验“提取夹爪开合以及位姿转换”相关能力。下面示例只用于说明整体交互逻辑，不代表其他场景必须提前固定同样的菜单项。

```text
$ ./start_data_clean.sh --dev

开发者引导界面
  1. 场景一：提取夹爪开合以及位姿转换
  2. 场景二：硬件数据可靠性验证
  3. 场景三：MCAP 多 topic 时间轴对齐
  4. 场景四：构建 LeRobotDataset v3
  5. 场景五：训练入口验证与数据集交付

请选择要检验的场景：1

场景一功能检验菜单
  1. 检验提取夹爪开合
  2. 检验实现左右位姿转换到机械臂 base 坐标系链路
  3. 填写/校验夹爪开合配置文件参数
  4. 填写/校验位姿转换配置文件参数
  5. 运行场景一完整 smoke test
  0. 返回上一级
```

如果开发者选择“检验提取夹爪开合”，交互语义如下：

```text
请选择功能：1

系统展示：
  - 本功能目标：从样本图像或 MCAP 图像 topic 中提取左右夹爪开合宽度
  - 默认读取：生产配置中的夹爪开合相关配置
  - 需要输入：小样本 raw MCAP 或图像样本
  - 输出位置：开发调试输出目录下的本次独立 run 目录

开发者确认或填写：
  - 输入样本路径
  - 调试输出目录
  - 是否临时覆盖生产配置中的夹爪标定参数
  - 是否保存临时覆盖到配置文件

系统执行：
  - 创建本次开发调试运行目录
  - 调用夹爪开合提取功能
  - 写出测试产物
  - 写出运行日志

运行结束后展示：
  - 测试产物路径
  - 运行日志路径
  - 返回场景一菜单 / 继续检验下一个功能 / 运行场景一完整 smoke test / 退出
```

如果开发者选择“填写/校验夹爪开合配置文件参数”，交互语义如下：

```text
请选择功能：3

系统展示：
  - 当前夹爪开合配置状态
  - 缺失项或空值
  - 每个配置项的含义和预期输入

开发者填写或修改配置：
  - 填写夹爪开合相关参数
  - 系统立即校验字段是否为空、类型是否正确、路径或数值是否合理
  - 开发者选择仅用于本次调试，或保存回正式配置文件

运行结束后展示：
  - 配置校验结果
  - 配置文件路径或本次临时覆盖记录
  - 运行日志路径
```

如果开发者选择“运行场景一完整 smoke test”，系统应按场景一内部主要链路执行一次最小样本闭环：

```text
运行场景一完整 smoke test
  -> 检查场景一必需配置
  -> 读取小样本 raw MCAP
  -> 提取夹爪开合
  -> 执行位姿转换到机械臂 base 坐标系链路
  -> 写出场景一测试产物
  -> 写出运行日志
  -> 返回测试产物路径和运行日志路径
```

场景一以外的其他场景，后续真正编码时也应遵循同一类交互结构：场景入口、功能菜单、输入确认、配置确认、执行、测试产物、运行日志、下一步选择。具体功能菜单不在本文提前冻结。

### 2. 用户端生产交互逻辑

用户端生产模式通过无参数入口进入：

```text
./start_data_clean.sh
```

无参数时默认进入用户生产引导界面，而不是直接开始处理。生产引导界面首页只提供三个选择：

```text
用户生产引导界面
  1. 配置配置文件
  2. 运行全流程（默认）
  3. 运行单个流程
```

#### 配置配置文件

“配置配置文件”是统一配置入口，内部按五个场景分组：

```text
配置配置文件
  1. 场景一配置
  2. 场景二配置
  3. 场景三配置
  4. 场景四配置
  5. 场景五配置
```

用户端允许进入某个场景下的单个配置填写功能，例如只填写或修改某个场景内的某一类配置参数。配置填写完成后必须立即校验：

- 字段是否为空。
- 类型、范围、路径或枚举值是否合理。
- 该配置是否能被所属场景读取。
- 该场景配置是否已经满足运行条件。

配置缺失时，系统应自动逐项引导用户补齐，同时允许用户跳过、返回或退出。配置项按语义分为：

- **必需配置**：缺失时，对应流程不能运行。
- **可选配置**：缺失时，可以使用默认值或关闭对应增强功能。
- **调试配置**：只影响开发者端检验，不影响用户端生产流程。

如果用户跳过必需配置，系统不允许运行受影响的流程，但允许保存当前配置草稿并返回首页。若用户手动指定了不依赖该缺失配置的下游产物，可以从对应下游场景继续运行。

#### 运行全流程

“运行全流程”是用户端默认选项，目标是从 raw MCAP 依次执行阶段二五个场景，最终得到 LeRobotDataset v3，并完成 ACT 训练前检查。

用户选择运行全流程后，系统必须先自动检查：

- 配置文件是否存在。
- 五个场景所需的关键配置是否为空。
- 输入 raw MCAP 是否存在且可读取。
- 输出目录是否可写，是否存在覆盖风险。

如果配置文件缺失或关键取值为空，不继续执行全流程，而是自动跳转到“配置配置文件”流程，并定位到缺失配置所在的场景分组。配置完成并校验通过后，再回到全流程执行。

#### 运行单个流程

用户端“运行单个流程”只允许选择单个场景的完整流程，不暴露场景内部的单个处理功能。场景内部单功能执行只属于开发者端。

运行单个流程前必须做前置检查：

```text
选择单个场景
  -> 检查该场景所需输入产物是否存在
  -> 检查该场景所需配置是否完整
  -> 缺输入：提示先运行上游流程或手动指定输入
  -> 缺配置：跳转到对应配置分组
  -> 都满足：执行该场景完整流程
```

### 3. 运行进度与结束反馈

用户端生产模式运行时应提供可视化进度条。全流程运行时，进度条至少表达两层信息：

```text
全流程进度：当前处于五个场景中的哪一个
当前场景进度：当前处于读取输入、检查配置、执行处理、写出产物、写入日志中的哪一步
```

示例语义：

```text
全流程进度：2/5 硬件数据可靠性验证
当前步骤：异常检测
进度：80%
```

生产模式运行完成后，结束页保持简洁，只显示：

- 运行状态：成功、失败或部分成功。
- 输出路径：本次生成的 cleaned、MCAP_A / validated、aligned、LeRobotDataset v3 或 ACT 训练前检查结果路径。
- 运行日志路径。
- 下一步可选动作：查看输出目录、重新运行单个流程、配置配置文件、返回首页或退出。

运行失败时，进度条停在失败场景和失败步骤，并显示：

- 失败发生在哪个场景和步骤。
- 一行失败原因摘要。
- 运行日志路径。
- 下一步选择：重新配置、重新运行当前流程、返回首页或退出。

## 五、产物职责

| 产物 | 语义 | 是否主线保留 |
|---|---|---|
| raw MCAP | 阶段一采集原始数据，外部只读输入源。 | 是，作为输入。 |
| cleaned MCAP | 场景一输出，补齐夹爪与位姿语义。 | 是。 |
| MCAP_A / validated MCAP | 场景二输出，滤波、补全、主数据整理后的 MCAP。 | 是。 |
| aligned MCAP | 场景三输出，统一 step 时间轴后的 MCAP。 | 是。 |
| LeRobotDataset v3 | 阶段二目标产物，供 LeRobot ACT 训练。 | 是，最终产物。 |
| canonical_dataset_mcap | 旧方案中间标准产物。 | 否，仅归档复盘。 |
| exports | 旧方案通用导出层。 | 否，当前主线只面向 LeRobotDataset v3。 |

## 六、配置与追溯原则

1. 配置从生产配置读取，开发者模式允许临时覆盖。
2. 临时覆盖只对本次 run 生效，只有用户明确选择保存时才写回配置。
3. 影响坐标系、step 对齐、action 生成、LeRobot 字段映射的配置必须进入 manifest。
4. 真实 MCAP 不进 Git，L3 开发验证默认从本机外部 raw MCAP 目录读取。
5. 调试输出、中间产物和日志必须进入独立 run 目录。

## 七、完成定义

阶段二完成不是“文档写完”或“脚本能启动”，而是满足以下闭环：

1. 能用至少一个真实 raw MCAP 小样本，从场景一跑到 LeRobotDataset v3。
2. LeRobotDataset v3 能被 LeRobot 数据读取流程加载。
3. ACT 训练前检查能识别 observation、action、episode、时间步和必要 metadata。
4. 每个中间产物都有来源、配置、处理步骤和失败原因记录。
5. 用户能通过 `./start_data_clean.sh --dev` 对每个场景进行人工最终验收。
