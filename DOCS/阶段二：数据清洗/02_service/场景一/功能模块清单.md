# 阶段二场景一：功能模块清单

## 一句话总结

场景一按“已有实现改造并纳入阶段二架构”的方式拆为 6 个 L2 功能模块，目标是把 raw MCAP、浏览器标定配置、frame alignment 配置和 cleaned MCAP 输出契约稳定下来，让场景二能消费统一坐标系下的夹爪和 TCP 位姿。

## 接口稳定结论

- 输入：raw MCAP + [[Scene1Config]]。
- 默认输出：`asset/阶段二：数据清洗/dev/mcap_cleaned/*.mcap`。
- raw pose 保留：`/baton_mini_left/fast_odom`、`/baton_mini_right/fast_odom` 仍按 raw Baton Mini pose 追溯，不再把“替换原 payload”作为长期契约。
- arm-base TCP pose 输出：场景一输出 [[ArmBaseTcpPose]]，frame_id = `<hand>_arm_base_link`；旧 `tcp_common` / `camera_common` 字段保留为历史兼容。
- 夹爪宽度：新增 `/gopro_left/gripper_width`、`/gopro_right/gripper_width`，消息类型为 `std_msgs/msg/Float32`，值为归一化 `[0, 1]` 的 [[GripperWidthSample]]。
- 配置生成：已有浏览器标定程序 `src/data_clean/ui/mcap_calibration_wizard.py` 是夹爪开合配置和旧 frame_alignment 配置生成的现实入口；后续 L3 只做接口改造和阶段二契约对接。
- 清洗报告：第一轮先定义 [[Scene1CleanReport]] 契约，代码暂不强制生成独立 JSON 报告文件；现有终端摘要和 `DATA_CLEAN_RAW_JSON=1` 输出后续应对齐该契约。

## 开发者验收范式

场景一最终验收必须能通过统一开发者入口触发：

```text
./start_data_clean.sh --dev
  -> 场景一：提取夹爪开合以及位姿转换
  -> 选择功能检验项或场景完整 smoke test
```

本轮只定义场景一需要暴露的 dev 功能检验项，不实现 `--dev` 统一入口。`--dev` 入口后续由 Runtime/公共能力实现。

### 场景一 dev 输出契约

- 每次功能检验创建独立 [[Scene1DevRun]]。
- 每次功能检验至少输出一个 [[Scene1DevArtifact]] 和一个 [[Scene1DevRunLog]]。
- 默认读取生产 [[Scene1Config]]，临时覆盖通过 [[Scene1DevConfigOverride]] 记录，默认不写回正式配置。
- 调试产物写入 `asset/阶段二：数据清洗/dev_runs/scene1/...`，不得污染正式 canonical dataset 或生产输出目录。

## 01 cleaned MCAP 契约稳定

- 一句话目标：定义场景一对场景二公开的 [[CleanedMcap]] 接口和相关配置、报告数据概念。
- 模块类别：数据定义类。
- 输入：场景一目标描述、现有 `src/data_clean` 行为、阶段二产物架构约束。
- 输出：`L2数据定义/` 原子定义、cleaned MCAP topic 语义、报告契约和后续 L3 任务边界。
- 上游依赖：阶段一 raw MCAP topic 日志。
- 下游消费者：场景二功能模块清单、位姿滤波器、触觉滤波器、异常值检测器、后续 Runtime 接入任务。
- 后续 L3 方向：补齐接口数据定义、同步场景一和场景二上游契约。

## 02 夹爪开合配置生成

- 一句话目标：把已有浏览器 GoPro 标定程序纳入场景一正式配置生成入口。
- 模块类别：工具对接类。
- 现实代码入口：`src/data_clean/ui/mcap_calibration_wizard.py`。
- 输入：终端启动脚本、左右 GoPro live image、网页点击或采样结果。
- 输出：[[L2数据定义/GripperCalibrationConfig|GripperCalibrationConfig]]，写入 [[Scene1Config]] 的 `gripper_streams` 和 `calibration.gripper`。
- 上游依赖：GoPro live topic、浏览器标定 UI、已有 YAML 写回逻辑。
- 下游消费者：[[夹爪宽度提取]]、[[Scene1CleanReport]]。
- 后续 L3 方向：对接浏览器夹爪配置生成接口，明确命令行入口、输出路径、字段名和机器可读摘要。

## 03 夹爪宽度提取

- 一句话目标：从左右 GoPro 图像流生成左右夹爪宽度 topic。
- 模块类别：数据计算类。
- 输入：raw MCAP 中的 `/gopro_left/image_raw`、`/gopro_right/image_raw` 和 [[L2数据定义/GripperCalibrationConfig|GripperCalibrationConfig]]。
- 输出：`/gopro_left/gripper_width`、`/gopro_right/gripper_width`，每帧图像对应一个归一化 [[GripperWidthSample]]。
- 上游依赖：raw MCAP 图像 topic、夹爪 marker 标定参数。
- 下游消费者：场景二异常检测、后续 canonical observation/action 构建。
- 后续 L3 方向：补充 gripper 输出字段测试、把 `Scene1CleanReport` 中的检测帧数和插值帧数字段对齐代码输出。

## 04 位姿转换配置生成

> ⚠️ **Deprecated since 2026-06 debug-common-frames L3 001**。配置生成路线（基于 `FrameAlignmentConfig.common_anchor`）已废弃。新链路使用 `camera_from_tcp` + [[WorkFrameInBaseConfig]] + `work_frames` 直接提供。配置示例保留为"历史参考"段，不删除。

- 一句话目标：生成以单侧 UMI 初始坐标系作为公共坐标系的 [[L2数据定义/FrameAlignmentConfig|FrameAlignmentConfig]]。
- 模块类别：工具对接类。
- 默认策略：`common_anchor: left`，即 `common_frame = left_umi_start_frame`。
- 输入：左右 UMI 固定底座外参、camera 到 TCP 外参、raw pose topic 映射。
- 输出：[[L2数据定义/FrameAlignmentConfig|FrameAlignmentConfig]]，包含 `common_from_left_start`、`common_from_right_start` 和 [[CameraFromTcpExtrinsic]]。
- 上游依赖：已有 `mcap_calibration_wizard.py` 旧 common frame 配置写回逻辑、底座 CAD/测量/标定结果。
- 下游消费者：[[arm-base 位姿转换]]、场景二位姿滤波和 IK 前置输入。
- 后续 L3 方向：把旧 `start_from_common` 配置生成改造为 `frame_alignment` 契约，并保留旧配置迁移兼容。

## 05 arm-base 位姿转换

- 一句话目标：把左右 TCP in camera 位姿经 `Algo.rm_algo_workframe2base` 转换为机械臂基坐标系下的 [[ArmBaseTcpPose]]。
- 模块类别：数据计算类。
- 输入：[[TcpInCamera]]（由 `compute_tcp_in_camera` 产出）、[[WorkFrameInBaseConfig]]（work frame in base 配置）。
- 输出：[[ArmBaseTcpPose]]，frame_id = `<hand>_arm_base_link`；raw pose 保留为附加大字段。
- 上游依赖：raw MCAP pose topic、[[CameraFromTcpExtrinsic]]（用于 TCP in camera 推导）、[[WorkFrameInBaseConfig]]。
- 下游消费者：场景二位姿滤波、异常检测、IK 前置输入；场景四 action 构建的上游语义。
- 后续 L3 方向：实现 TCP in camera 产出、arm-base TCP pose 输出和数量契约测试。

## 06 基础校验与输出契约检查

- 一句话目标：让场景一失败能定位到 topic、schema、配置或输出契约问题。
- 模块类别：数据计算类。
- 输入：raw MCAP summary、[[Scene1Config]]、清洗后的输出统计。
- 输出：校验结果、失败原因、[[Scene1CleanReport]] 可承载的 topic 和消息计数摘要。
- 上游依赖：场景一配置加载、配置生成工具和 MCAP 读写。
- 下游消费者：Runtime 预检查、场景二接口对齐、人工复查。
- 后续 L3 方向：补充配置来源检查、规范路径迁移后的输入输出检查、输出 contract 测试。
