# L2 能力模块说明：输入产物预检查模块

## 1. 能力名称

```text
Runtime MVP / 输入产物预检查模块
```

## 2. 所属位置

阶段：阶段二：数据清洗  
L1：`runtime_mvp`  
场景：Runtime MVP，不归入 `02_service` 的具体业务场景  
模块类别：数据计算类  
来源功能模块清单：[[功能模块清单]]

## 3. 一句话目标

```text
在调度 Service 前，检查当前目标场景依赖的上游输入产物是否存在、可读并满足最小文件/目录边界。
```

## 4. 能力角色

```text
本能力是 Runtime MVP 的输入边界守门能力，负责把“缺哪个上游产物、路径在哪里、是否阻塞调度”变成结构化预检查结果。
```

它消费 [[EffectiveRuntimeConfig]]、目标 [[SceneName]] 和后续配置预检查结果，产出 [[InputArtifactPrecheckSummary]]。它不负责读取 MCAP topic、解析 Parquet schema 或修复缺失数据。

## 5. 上游关系

- 来自 [[03_配置加载与配置快照模块]] 的 [[EffectiveRuntimeConfig]]。
- 来自功能模块清单中功能4“配置预检查模块”的通过/失败前提；该 L2 尚未落盘，因此当前标记为上游接口缺定义。
- 来自阶段二产物架构设计中的 raw、cleaned、validated、aligned、canonical dataset 和 exports 产物边界。
- 来自 [[SceneName]] 的目标场景选择。
- 已按 `$grill-me` 约束完成意图澄清：本能力不替代功能4做配置合法性判断，只做输入产物最小边界检查。

## 6. 下游关系

- 场景注册与 Service 调度模块必须在 [[InputArtifactPrecheckSummary]] 成功后才能调用 fake service 或真实 service。
- 结构化日志模块记录每个 [[InputArtifactCheckResult]]。
- Manifest 与错误摘要模块消费失败时的 [[RuntimeErrorRef]]。
- Runtime smoke test 模块验证合法输入、缺失输入和错误摘要路径。

开发本能力前，必须先按 `DOCS/阶段二：数据清洗/约束文件/上游依赖接口对齐约束.md` 检查直接上游功能。

| 上游功能 | 上游接口 / 产物 | 本能力如何依赖 | 对齐状态 | 处理方式 |
| --- | --- | --- | --- | --- |
| [[03_配置加载与配置快照模块]] | [[EffectiveRuntimeConfig]] 中的 `effective_data`、[[RuntimeConfigSource]] 和 [[ConfigSnapshot]] | 从最终生效配置解析候选输入路径，并保证预检查消费的是同一份运行配置 | 已对齐 | 复用 |
| 功能4：配置预检查模块 | 预期输出“配置已通过，可进入输入产物预检查”的结果对象或状态 | 本能力应只在配置预检查通过后执行；若配置字段缺失，应由功能4失败 | 缺定义 | 当前 L2 记录依赖；生成 L3 时先拆数据定义与占位规则，不直接消费未稳定接口 |

## 8. 职责边界

本能力负责：

1. 根据目标 [[SceneName]] 和 [[RunMode]] 确定本次需要检查的 [[InputArtifactRequirement]]。
2. 从 [[EffectiveRuntimeConfig]] 中解析每个需求的候选输入路径。
3. 检查候选路径是否存在、可读且类型匹配。
4. 生成 [[InputArtifactCheckResult]] 和 [[InputArtifactPrecheckSummary]]。
5. 缺输入时生成可被错误摘要消费的 [[RuntimeErrorRef]]。

本能力不负责：

1. 校验配置字段是否完整、类型是否正确或取值范围是否合法。
2. 读取 MCAP 内部 topic、检查 topic schema 或统计消息数量。
3. 校验 canonical dataset 的 schema、dataset index、masks 或 reports 完整性。
4. 自动运行上游场景来补齐缺失产物。
5. 调用 fake service、真实 service、日志写入器或 manifest 写入器。

## 9. 计算职责

本能力负责的判断或计算：

| 计算项 | 输入 | 输出 | 影响下游 |
| --- | --- | --- | --- |
| 场景输入需求解析 | 目标 [[SceneName]]、[[RunMode]]、阶段二产物架构 | [[InputArtifactRequirement]] 列表 | 决定要检查哪些路径 |
| 候选路径解析 | [[EffectiveRuntimeConfig]]、[[InputArtifactRequirement]].`path_config_key` | 候选路径 | 决定文件系统检查目标 |
| 单项产物边界检查 | 候选路径、`required_kind` | [[InputArtifactCheckResult]] | 决定某个输入是否阻塞 |
| 汇总阻塞错误 | 多个 [[InputArtifactCheckResult]] | [[InputArtifactPrecheckSummary]] | 决定是否允许 Service 调度 |

## 10. 计算规则

| 规则 | 触发条件 | 计算 / 判断方式 | 结果表达 |
| --- | --- | --- | --- |
| 场景一输入检查 | 目标场景为场景一 | 检查 raw MCAP 输入路径存在、可读且为文件或配置声明的输入目录存在、可读且为目录 | 成功或缺 raw 输入错误 |
| 场景二输入检查 | 目标场景为场景二 | 检查 cleaned MCAP 输入路径存在、可读且类型匹配 | 成功或缺 cleaned 输入错误 |
| 场景三输入检查 | 目标场景为场景三 | 检查 validated MCAP 输入路径存在、可读且类型匹配 | 成功或缺 validated 输入错误 |
| 场景四输入检查 | 目标场景为场景四 | 检查 aligned MCAP 输入路径存在、可读且类型匹配；第一版不深查 report 内容 | 成功或缺 aligned 输入错误 |
| 场景五输入检查 | 目标场景为场景五 | 检查 canonical dataset 目录存在、可读且为目录 | 成功或缺 canonical dataset 错误 |
| 缺候选路径 | 配置中找不到需求对应路径 | 不做文件系统猜测，直接失败 | [[RuntimeErrorRef]]，建议补配置或指定输入 |
| 路径类型不匹配 | 期望文件但得到目录，或期望目录但得到文件 | 标记 `kind_matches=false` | 阻塞调度 |

## 11. 输出结果结构

| 字段 | 类型 | 含义 | 有效性要求 | 下游使用方式 |
| --- | --- | --- | --- | --- |
| `requirements` | list of [[InputArtifactRequirement]] | 本场景需要的输入产物需求 | 至少覆盖目标场景直接输入 | 调度和日志解释本次检查范围 |
| `results` | list of [[InputArtifactCheckResult]] | 每个需求的检查结果 | 与 `requirements` 一一对应或可追溯 | 调度判断是否可继续 |
| `summary` | [[InputArtifactPrecheckSummary]] | 汇总状态与阻塞错误 | 任一失败必须进入 `blocking_errors` | 调度、日志、错误摘要消费 |

## 12. 异常与边界输入

| 边界情况 | 预期结果 | reason / error 表达 | 是否阻塞下游 |
| --- | --- | --- | --- |
| 配置未通过预检查 | 本能力不执行或返回上游未满足 | `config_precheck_required` | 是 |
| 配置中缺输入路径 | 单项检查失败 | `input_path_missing_in_config` | 是 |
| 路径不存在 | 单项检查失败 | `input_artifact_not_found` | 是 |
| 路径不可读 | 单项检查失败 | `input_artifact_not_readable` | 是 |
| 文件/目录类型不匹配 | 单项检查失败 | `input_artifact_kind_mismatch` | 是 |
| 路径存在但业务内容未知 | 第一版不深查，交给 Service 或 contract test | 无，或后续扩展 warning | 否，除非后续 L2 明确要求 |

## 13. 可验证样例

| 样例 | 输入特征 | 预期输出 | 验证方式 |
| --- | --- | --- | --- |
| 合法输入 | 场景二配置指向存在且可读的 cleaned MCAP 文件 | [[InputArtifactPrecheckSummary]] 成功，允许调度 | 单元测试创建临时文件并检查汇总状态 |

| 边界输入 | 场景五期望 canonical dataset 目录，但配置给出文件路径 | 汇总失败，包含 `input_artifact_kind_mismatch` | 单元测试检查类型判断 |

## 17. 给 L3 任务生成的约束

后续从本 L2 生成 L3 任务时，必须遵守：

1. 每个 L3 只能解决一个核心目标。
2. 每个 L3 必须先判断任务类别，并使用对应 L3 类别模板。
3. 每个 L3 必须有明确输入、输出、修改边界、验收命令和成功标准。
4. 每个 L3 必须写明“本次不做什么”。
5. 每个 L3 不能跨越本 L2 的能力边界。
6. 如果需要修改本 L2 之外的模块，必须在 L3 文档中显式说明原因。
