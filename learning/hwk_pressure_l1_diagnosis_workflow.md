# l1 触觉全 0 排查协作工作流

## 协作目标

- 确认 l1 全 0 数据的直接原因。
- 区分软件轮询/初始化问题、拓扑接线问题、地址/绑定问题。
- 找到可稳定复现、可稳定验证、可稳定修复的方案。

## 协作分工

用户负责：

- 切换硬件拓扑。
- 确认当前 l1/l2 接线状态。
- 在实验采样期间按压对应触觉片。
- 观察 Octopus 热力图是否有明显反馈。

Codex 负责：

- 每条命令执行前说明：命令做什么、为什么现在运行、期望看到什么。
- 运行或指导运行软件实验。
- 整理 `frames_ok`、`peak_max`、`nonzero_frames`、`avg_hz`、topic hz 等关键指标。
- 根据实验结果更新判断和下一步动作。

## 单轮实验流程

1. 固定一个硬件拓扑，不同时改变多个变量。
2. 记录当前 `/dev/ttyUSBx` 与 l1/l2 地址、UID 对应关系。
3. Codex 说明即将执行的命令含义、运行原因、期望结果。
4. 用户按要求按压指定触觉片。
5. 采集关键指标：`frames_ok`、`peak_max`、`nonzero_frames`、`avg_hz`、topic hz、Octopus 观察。
6. 更新实验状态表和诊断文档实验记录表。
7. 按收敛规则决定继续、转向或停止。

## 收敛规则

- 若独立 CH340 下强制 `serialized_polling` 后 l1 从 0 变非 0：根因优先锁定为 driver 轮询/读取模式差异。
- 若共用 CH340 下只请求 l1 仍非 0，但独立 CH340 raw 全 0：根因优先锁定为拓扑带来的初始化或总线状态副作用。
- 若 raw 采样非 0、ROS topic 全 0：根因锁定在 driver 解析/发布路径。
- 若所有软件对照都全 0，但恢复某条公共连接后非 0：根因锁定在接线公共条件。
- 一旦单变量实验让 l1 从 0 变非 0，就强证据收敛，不机械跑完整矩阵。

## 关键判定指标

| 指标 | 含义 | 判定方式 |
|---|---|---|
| `frames_ok` | 成功收到并解析的压力帧数量 | 大于 0 表示串口和协议链路可用 |
| `peak_max` | 采样窗口内最大压力值 | 大于 0 表示 MCU 返回了非零压力数据 |
| `nonzero_frames` | 非零压力帧数量 | 大于 0 表示按压反馈进入 payload |
| `avg_hz` | raw 采样实际频率 | 用于判断是否存在明显延迟或吞吐瓶颈 |
| topic hz | ROS topic 发布频率 | 用于判断 driver 发布链路是否稳定 |
| Octopus 观察 | 热力图实际显示 | 只作为最终用户体验验证，不作为底层根因的唯一证据 |
