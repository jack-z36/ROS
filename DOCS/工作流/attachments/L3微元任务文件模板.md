# L3 微元任务模板系统

本文件是 L3 模板系统入口，不再是唯一的大而全模板。生成 L3 微元任务时，必须先判断任务类别，再拼装对应模板组件。

L3 微元任务的目标是让短上下文 Agent 独立完成一次小 PR：

```text
位置、目标、任务类别、执行对象、执行依赖、上游接口确认、必读上下文、约束文档索引、修改边界、验收命令、成功标准、完成后交接。
```

代码类 L3 执行时必须使用 `$tdd` 技能，并遵守 `DOCS/阶段二：数据清洗/约束文件/L3执行TDD与归档约束.md`。该约束负责规定 TDD 垂直切片、相关 L3 历史记录读取、成功标准勾选、执行摘要和 `task/active/<功能组>/` 到 `task/completed/<功能组>/` 的归档动作。

## 模板拼装方式

```text
L3 文件 =
L3_common_header.md
+
一个 L3 类别主体模板
+
L3_common_footer.md
```

模板组件目录：

```text
DOCS/工作流/attachments/templates/
```

## 四类 L3 模板

| 任务类别 | 本质问题 | 适合任务 | 主体模板 |
|---|---|---|---|
| 数据定义类 | 定义一个可被下游使用的数据结构 | `RunStatus`、`RunContext`、`SceneResult`、schema 字段 | `templates/L3_data_definition.md` |
| 数据读写类 | 实现一个可验证的读写动作 | run 目录创建、JSON 写入、config snapshot 保存 | `templates/L3_data_io.md` |
| 数据计算类 | 实现一个可测试的判断或计算 | 配置缺失字段检查、输入路径存在性检查、scene 依赖判断 | `templates/L3_data_compute.md` |
| 流程编排类 | 实现一个可观察的调用顺序 | 单场景 runner、fake pipeline runner、失败停止并写 error summary | `templates/L3_orchestration.md` |

## 通用字段

所有 L3 都必须包含：

1. 任务定位
2. 任务类别
3. 本次唯一目标
4. 本次不做
5. 执行对象
6. 执行依赖
7. 上游接口确认
8. 预期改动形态
9. 类别专用内容
10. 必读上下文
11. TDD 执行要求
12. 允许修改
13. 禁止修改
14. 验收命令
15. 成功标准
16. 完成后交接

这些字段由以下组件承载：

- `templates/L3_common_header.md`
- 类别主体模板
- `templates/L3_common_footer.md`

## 类别选择规则

### 数据定义类

选择信号：

- 任务目标是定义类型、枚举、schema、字段或原子数据定义文档。
- 验收重点是能 import、能实例化、字段类型正确、非法值被拒绝或文档链接完整。

### 数据读写类

选择信号：

- 任务目标是创建目录、读写文件、保存配置快照、写日志或写 manifest。
- 验收重点是真实生成文件、目录结构正确、重复运行不污染旧结果。

### 数据计算类

选择信号：

- 任务目标是实现检查、判断、统计、转换或依赖判断。
- 验收重点是合法输入通过、缺失输入失败、错误信息清楚。

### 流程编排类

选择信号：

- 任务目标是组织多个模块的调用顺序。
- 验收重点是调用顺序正确、失败行为正确、状态或日志正确。

## 填写原则

- 一个 L3 只能解决一个核心目标。
- 一个 L3 默认只选一个任务类别；如果一个 L3 需要两个类别，优先拆成两个 L3。
- 同一个 L2 功能模块拆出的所有 L3 必须放入同一个 `DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/` 目录。
- 必读上下文只列完成当前任务必须读的文档、代码、相关 L3 任务和执行记录。
- 通用编程规则、文件存放规则、Git 同步规则、TDD 规则、归档规则和技术栈规则不复制进 L3 卡片，而是放入“必读约束文档”。
- 输出必须可检查，不能只写“处理完成”。
- 修改边界必须明确，防止顺手重构。
- 验收命令和成功标准必须具体。
- Python 命令必须写成 `python3`，不得写成 `python`。
- 仓库内文件和目录必须使用相对仓库根目录路径，不得写入开发者本机绝对路径。
- 外部 Agent 技能只写技能名，例如 `$tdd`，不写技能在某台机器上的安装路径。
- 完成后必须说明如何交接、如何勾选成功标准、如何移动到 `task/completed/<功能组>/`。

## 必读约束文档默认项

每个 L3 的 `必读约束文档` 默认包含：

```md
1. `DOCS/阶段二：数据清洗/约束文件/L3编码执行原则.md`
2. `DOCS/阶段二：数据清洗/约束文件/L3执行TDD与归档约束.md`
3. `DOCS/阶段二：数据清洗/约束文件/上游依赖接口对齐约束.md`
4. `DOCS/阶段二：数据清洗/约束文件/文件存放规范.md`
5. `<对应 L1 / 场景的执行约束.md>`
6. `<如涉及特定技术栈，补充技术栈约束文档>`
```

常见约束入口包括：

```text
DOCS/阶段二：数据清洗/约束文件/L3编码执行原则.md
DOCS/阶段二：数据清洗/约束文件/L3执行TDD与归档约束.md
DOCS/阶段二：数据清洗/约束文件/上游依赖接口对齐约束.md
DOCS/阶段二：数据清洗/约束文件/文件存放规范.md
DOCS/git操作约束.md
DOCS/阶段二：数据清洗/01_runtime_mvp/执行约束.md
DOCS/阶段二：数据清洗/02_service/执行约束.md
DOCS/阶段二：数据清洗/02_service/场景一/执行约束.md
```

## 使用流程

1. 读取来源 L2 能力模块说明。
2. 确认本次 L3 只解决一个核心目标。
3. 判断 L3 任务类别。
4. 读取 `templates/L3_common_header.md`。
5. 读取对应类别主体模板。
6. 读取 `templates/L3_common_footer.md`。
7. 确认来源 L2 对应的功能组目录，例如 `runtime-g1` 或 `service-s1-g1`。
8. 拼装并填写正式 L3 task，写入 `DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/`。

## 合格 L3 文件判断

写完后必须能回答：

1. Agent 是否知道自己属于哪个阶段、场景和 L2 能力？
2. Agent 是否知道本次任务类别？
3. Agent 是否知道这次只做一个目标？
4. Agent 是否知道执行对象、执行依赖和上游接口确认点？
5. Agent 是否知道开始前要读哪些任务文档、相关 L3 记录、约束文档和代码？
6. Agent 是否知道能改和不能改哪些文件？
7. Agent 是否知道代码类任务必须使用 `$tdd` 技能？
8. Agent 是否知道 Python 命令必须使用 `python3`？
9. Agent 是否知道怎么验收？
10. Agent 是否知道本任务属于哪个 `task/active/<功能组>/`？
11. Agent 是否知道完成后要勾选成功标准、追加执行摘要并移动到 `task/completed/<功能组>/`？
