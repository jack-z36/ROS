
## 1. 框架一句话

```text
AS-IS Contract → TO-BE Contract → Contract Delta =
先描述“现有部署程序的运行契约”，
再描述“目标部署程序的运行契约”，
最后描述“两个契约之间的变更集”。
```

它适合你的场景：

```text
不是从零开发部署程序，
而是在同事已有部署程序上做定向改造。
```

---

# 2. AS-IS Contract：现有运行契约

## 2.1 它回答什么问题

```text
同事现在的部署程序，在真实运行时到底是怎么工作的？
```

注意：

```text
AS-IS 不是“当前功能列表”，
而是“现有系统已经形成的运行规则、接口约定和依赖边界”。
```

---

## 2.2 AS-IS 需要描述什么

```markdown
# AS-IS Contract：现有运行契约

## 1. Runtime Entry

- 程序入口：
- 启动命令：
- 主循环位置：
- 配置文件：
- 运行环境：
- 是否需要连接真实硬件：

## 2. External Dependencies

- 依赖的模型：
- 依赖的 ROS topic：
- 依赖的机械臂 SDK：
- 依赖的夹爪接口：
- 依赖的配置文件：
- 依赖的硬件设备：

## 3. Input Contract

- 当前输入来源：
- 当前输入字段：
- 当前输入格式：
- 当前输入单位：
- 当前输入坐标系：
- 当前输入频率：
- 输入缺失时如何处理：

## 4. Internal Data Model

- 内部如何表示 observation：
- 内部如何表示 action：
- 内部如何表示 robot_state：
- 是否有统一数据结构：
- 是否存在隐式约定：

## 5. Policy / Model Contract

- 当前如何调用模型：
- 模型输入是什么：
- 模型输出是什么：
- 推理频率：
- 推理失败时如何处理：

## 6. Output Contract

- 输出给机械臂的命令格式：
- 输出给夹爪的命令格式：
- 单位：
- 坐标系：
- 相对动作 / 绝对动作：
- 命令发送频率：
- 阻塞 / 非阻塞：
- 返回值如何处理：

## 7. Failure Semantics

- 模型推理失败时怎么办：
- 输入缺失时怎么办：
- SDK 返回错误时怎么办：
- 机械臂超时时怎么办：
- 是否停止：
- 是否重试：
- 是否继续发送上一帧动作：

## 8. Observability

- 当前记录哪些日志：
- 是否记录 observation：
- 是否记录模型输出 action：
- 是否记录最终 robot command：
- 是否记录 SDK 返回码：
- 是否方便复现问题：

## 9. Existing Guarantees

- 当前已经能稳定工作的能力：
- 当前不能破坏的能力：
- 当前被其他模块依赖的接口：
- 当前真机可运行的最小路径：
```

# 3. TO-BE Contract：目标运行契约

## 3.1 它回答什么问题

```text
改造完成后，部署程序必须对外承诺什么行为？
```

注意：

```text
TO-BE 不是“我想新增哪些功能”，
而是“改造后系统必须满足的新运行规则、接口约定和安全约束”。
```

---

## 3.2 TO-BE 需要描述什么

```markdown
# TO-BE Contract：目标运行契约

## 1. Target Runtime Contract

- 程序入口是否保持不变：
- 是否新增运行模式：
  - dry-run
  - fake-policy
  - real-policy
  - real-robot
- 每种模式允许做什么：
- 每种模式禁止做什么：

## 2. Target Input Contract

目标 observation 应包括：

- image：
- robot_state：
- tcp_pose：
- gripper_width：
- tactile，可选：
- language_instruction，可选：

每个字段必须说明：

- shape：
- dtype：
- unit：
- frame：
- frequency：
- missing policy：

## 3. Target Policy Contract

统一 Policy 接口：

- 输入：
- 输出：
- 是否支持 DummyPolicy：
- 是否支持真实模型：
- 推理失败返回什么：
- 推理超时如何处理：

## 4. Target Action Contract

目标 action 应包括：

- tcp_delta：
- gripper_target：
- 左右臂顺序：
- 单位：
- 坐标系：
- 值域：
- 最大单步变化：

## 5. Target Safety Contract

任何 action 发给机械臂前，必须通过：

- NaN / Inf 检查
- 单步位移限幅
- 单步旋转限幅
- workspace 检查
- IK / 可执行性检查
- SDK 返回码检查
- 急停检查

检查失败时：

- 不发送动作
- 记录失败原因
- 进入安全状态

## 6. Target Output Contract

最终发给机械臂 / 夹爪的命令必须说明：

- command 类型：
- 参数格式：
- 单位：
- 坐标系：
- 阻塞 / 非阻塞：
- 返回值：
- 超时处理：

## 7. Target Observability Contract

每一轮控制循环必须记录：

- timestamp
- observation summary
- policy action
- safe_action
- robot_command
- safety_check_result
- SDK return code
- error reason

## 8. Target Compatibility Contract

- 哪些旧接口保持不变：
- 哪些旧行为保持不变：
- 哪些模块只允许包一层 adapter，不直接改：
- 哪些接口允许破坏性修改：
- 如何回滚到同事原始版本：
```

# 4. Contract Delta：契约变更集

## 4.1 它回答什么问题

```text
从 AS-IS 到 TO-BE，哪些运行契约发生了变化？
这些变化影响谁？
是否兼容？
如何实现？
如何验收？
如何回滚？
```

注意：

```text
Delta 不是简单的任务列表，
而是“契约变更集”。
```

# 6. 这个框架怎么指导编程任务拆解

```text
AS-IS Contract
用于读懂同事代码，防止误改。

TO-BE Contract
用于定义你最终要承诺的新系统行为。

Contract Delta
用于拆解具体开发任务。
```

开发任务不是从“我想实现什么功能”拆出来，而是从 Delta 拆出来。

例如：

```text
D2：Policy Interface 发生变化
↓
开发任务：
新增 PolicyAdapter，让原部署程序可以统一调用 predict(observation)
↓
验收：
DummyPolicy 能在 dry-run 模式下输出固定 action，并被 RuntimeLogger 记录
```

# 7. 这个框架的核心原则

```text
1. 先描述运行契约，不先写代码。
2. 先保护已有可运行路径，再做新改造。
3. 每一个变更都必须说明影响范围。
4. 每一个变更都必须有验收方式。
5. 每一个高风险变更都必须有回滚方式。
6. 能用 Adapter 包一层，就不要直接重写同事核心逻辑。
```

---

# 8. 一句话总结

```text
框架一不是“当前功能 → 目标功能 → 修改任务”，
而是：

现有运行契约
→ 目标运行契约
→ 契约变更集。

它最适合你现在这种：
在同事已有部署程序上做低风险、可验收、可回滚的定向改造。
```
