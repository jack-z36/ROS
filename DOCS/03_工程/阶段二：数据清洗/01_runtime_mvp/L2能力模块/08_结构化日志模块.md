# L2 能力模块说明：结构化日志模块

## 1. 能力名称

```text
Runtime MVP / 结构化日志模块
```

## 2. 所属位置

阶段：阶段二：数据清洗  
L1：`runtime_mvp`  
场景：Runtime MVP，不归入 `02_service` 的具体业务场景  
模块类别：数据读写类  
来源功能模块清单：[[功能模块清单]]

## 3. 一句话目标

```text
把 Runtime 运行过程中的上下文、步骤、调度事件、结果和错误写成可机器读取的 run_log.json。
```

## 4. 能力角色

```text
本能力是 Runtime MVP 的运行追溯入口，负责把分散的运行事实统一落盘为结构化日志。
```

它消费 [[RunContext]]、[[RuntimeStepRecord]]、[[SceneDispatchEvent]]、[[SceneResult]]、[[PipelineResult]] 和 [[RuntimeErrorRef]]，形成 [[RuntimeLogEvent]] 列表并写入 [[RunLogFile]]，最后返回 [[RuntimeLogWriteResult]]。它不负责写 manifest 或 error summary。

已按 `$grill-me` 约束完成意图澄清：仓库现有功能模块清单、Runtime 六件套、功能6/功能7 L2 和相关数据定义已经能回答功能8的目标、输入、输出、上下游和边界；本轮无需额外追问。

## 5. 上游关系

- 来自 [[01_Runtime运行上下文定义]] 的 [[RunContext]]、[[RuntimeStepRecord]]、[[SceneResult]]、[[PipelineResult]] 和 [[RuntimeErrorRef]]。
- 来自 [[02_Run目录管理模块]] 的 [[RunDirectory]]、[[RunDirectoryLayout]] 和 [[RunArtifactPath]]，用于确定 `run_log.json` 的写入位置。
- 来自 [[03_配置加载与配置快照模块]] 的配置快照路径语义，日志只记录路径引用，不复制完整配置。
- 来自 [[06_场景注册与Service调度模块]] 的 [[SceneDispatchEvent]]，用于记录调度计划、场景开始、成功、失败和停止。
- 来自 [[07_Fake Service模块]] 的 [[FakeServiceResult]]，通过 [[SceneResult]] 或事件摘要进入日志。

## 6. 下游关系

- Manifest 与错误摘要模块读取 [[RunLogFile]] 或 [[RuntimeLogWriteResult]]，用于追溯成功处理过程或失败定位。
- Runtime smoke test 模块检查 `run_log.json` 是否存在、是否可解析、是否包含关键事件。
- 人工排错时通过 `run_log.json` 查看输入、配置路径、场景顺序、结果和错误。

## 8. 职责边界

本能力负责：

1. 定义 [[RunLogFile]]、[[RuntimeLogEvent]] 和 [[RuntimeLogWriteResult]] 的日志语义。
2. 将 [[RuntimeStepRecord]]、[[SceneDispatchEvent]]、[[SceneResult]]、[[PipelineResult]] 和 [[RuntimeErrorRef]] 转换为可序列化日志事件。
3. 将结构化日志写入 [[RunDirectoryLayout]].`run_log_path` 指向的 `run_log.json`。
4. 在成功和失败路径中尽量保留可追溯日志。
5. 返回 [[RuntimeLogWriteResult]]，供后续结果汇总、manifest、error summary 和 smoke test 使用。

本能力不负责：

1. 创建 [[RunDirectory]]。
2. 写入 `config_snapshot.yaml`、`processing_manifest.json`、`error_summary.json` 或 `run_result.json`。
3. 实现场景一到场景五的真实业务算法。
4. 决定调度顺序、失败停止策略或重试策略。
5. 保存完整 MCAP、Parquet、HDF5、Zarr 或大型业务数据内容。

## 9. 读写职责

本能力负责的读写动作：

| 动作 | 读取来源 | 写入目标 | 格式 | 下游消费者 |
| --- | --- | --- | --- | --- |
| 生成日志事件 | [[RuntimeStepRecord]]、[[SceneDispatchEvent]]、[[SceneResult]]、[[PipelineResult]]、[[RuntimeErrorRef]] | 内存中的 [[RuntimeLogEvent]] 列表 | JSON 可序列化对象 | [[RunLogFile]] |
| 写出结构化日志 | [[RunContext]]、[[RunDirectoryLayout]].`run_log_path`、[[RuntimeLogEvent]] | `src/data_clean/runs/{run_id}/run_log.json` | JSON | Manifest 与错误摘要模块、Runtime smoke test |
| 返回写入结果 | 文件写入状态、事件数量、错误引用 | [[RuntimeLogWriteResult]] | 结构化对象 | [[PipelineResult]]、Manifest 与错误摘要模块 |

## 10. 路径与命名规则

| 文件 / 目录 | 路径来源 | 命名规则 | 是否允许覆盖 | 创建时机 |
| --- | --- | --- | --- | --- |
| `run_log.json` | [[RunDirectoryLayout]].`run_log_path` | 固定文件名 `run_log.json` | 只允许覆盖同一次新建 [[RunDirectory]] 内的临时/半成品日志，不允许覆盖旧 run | Runtime 开始后初始化，运行结束或失败时补全 |
| 临时日志文件 | `run_log_path` 同目录 | 可使用临时后缀，例如 `run_log.tmp.json` | 允许在同一次 run 内替换 | 写入原子性需要时创建 |

## 11. 文件格式与内容契约

| 文件 | 格式 | 必填内容 | 可选内容 | 校验方式 |
| --- | --- | --- | --- | --- |
| [[RunLogFile]] | JSON | `run_id`、`run_dir`、`status`、`target_scenes`、`events` | `config_snapshot_path`、`scene_results`、`pipeline_result`、`errors` | JSON 可解析；`run_id` 与 [[RunContext]] 一致；事件数量大于 0 |

## 12. 覆盖策略与幂等性

- 重复运行时如何处理：重复运行应由 [[02_Run目录管理模块]] 创建新的 [[RunDirectory]]，本能力只写当前 run 目录下的 `run_log.json`。
- 是否允许覆盖已有文件：不允许覆盖旧 run 的 `run_log.json`；同一新建 run 内为补全日志可重写同一路径。
- 如何避免污染旧 run：所有写入目标必须来自当前 [[RunContext]].`run_dir` 或 [[RunDirectoryLayout]].`run_log_path`。
- 临时文件或半成品如何处理：如果采用临时文件，成功后原子替换；失败时保留可排查半成品或返回 [[RuntimeLogWriteResult]].`error`。

## 13. 失败处理

| 失败情况 | 判断方式 | 处理策略 | 错误信息要求 | 是否写入报告 |
| --- | --- | --- | --- | --- |
| 缺少 `run_log_path` | [[RunDirectoryLayout]] 中没有日志路径 | 返回失败 [[RuntimeLogWriteResult]] | `runtime_log_path_missing`，说明缺哪个路径 | 进入后续错误摘要 |
| 日志路径逃逸 run 目录 | `run_log_path` 不在 [[RunDirectory]] 下 | 拒绝写入 | `runtime_log_path_escape`，说明目标路径 | 进入后续错误摘要 |
| 事件不可 JSON 序列化 | 写入前序列化失败 | 返回失败 [[RuntimeLogWriteResult]]，保留错误事件摘要 | `runtime_log_not_serializable`，指出事件类型 | 进入后续错误摘要 |
| 文件写入失败 | 文件系统写入异常 | 返回失败 [[RuntimeLogWriteResult]] | `runtime_log_write_failed`，包含路径和简短原因 | 进入后续错误摘要 |

## 17. 给 L3 任务生成的约束

后续从本 L2 生成 L3 任务时，必须遵守：

1. 每个 L3 只能解决一个核心目标。
2. 每个 L3 必须先判断任务类别，并使用对应 L3 类别模板。
3. 每个 L3 必须有明确输入、输出、修改边界、验收命令和成功标准。
4. 每个 L3 必须写明“本次不做什么”。
5. 每个 L3 不能跨越本 L2 的能力边界。
6. 如果需要修改本 L2 之外的模块，必须在 L3 文档中显式说明原因。
