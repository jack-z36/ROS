## 3. 身份识别规则

本场景的核心约束是优先使用硬件身份，而不是临时枚举顺序。

禁止把以下信息作为最终稳定身份：

```text
/dev/video0
/dev/video1
/dev/ttyUSB0
/dev/ttyUSB1
```

以下信息可作为候选身份来源，但需要标明可靠性：

| 信息来源 | 可靠性要求 |
| --- | --- |
| `ID_SERIAL` / `ID_SERIAL_SHORT` | 优先使用；必须确认每台设备唯一。 |
| 设备协议内序列号 | 优先使用；必须确认能从真实传感器读出且唯一。 |
| `/dev/serial/by-id`、`/dev/v4l/by-id` | 可用作稳定路径；必须确认每台设备区分明确。 |
| V4L2 card / bus info | 可辅助识别；如果同型号重复，不能单独作为唯一身份。 |
| `ID_PATH`、`by-path` | 只能作为 USB 拓扑 fallback；不能宣称为“无论怎么接入都稳定”。 |

如果硬件没有可区分身份，系统必须明确报告“需要人工标定”，不能自动猜测左右手或 l1/l2/r1/r2。

## 4. 映射边界

硬件映射层负责：

- 扫描已连接设备；
- 读取硬件身份；
- 匹配现实编码；
- 生成运行配置需要的设备路径；
- 在缺失、重复、冲突时失败并提示。

ROS 节点负责：

- 按已经解析好的设备路径启动；
- 发布固定 topic；
- 不在运行中猜测硬件真实身份。

Octopus 负责：

- 订阅固定 topic；
- 显示和录制固定 topic；
- 不关心底层硬件插在哪个 USB 口。

## 5. 验证边界

场景五不以“当前插法能启动”为最终成功。

必须验证：

```text
1. 插入全部目标硬件后，硬件扫描能列出每个候选设备的身份信息；
2. 映射结果能明确显示 l1、l2、r1、r2、gopro_left、gopro_right；
3. 启动前检查能发现缺失设备、重复设备或无法唯一识别设备；
4. 变更插入顺序或 USB 口后，仍能得到同样的逻辑映射；
5. 启动 ROS2 节点后，目标 topic 名称不变；
6. `ros2 topic list` 能看到目标 topic；
7. 如涉及场景三验收，MCAP 中 topic 名称仍为固定目标 topic。
```

## 6. 不算成功的情况

以下情况不算完成场景五：

- 只把 `/dev/ttyUSB0` 改成 `/dev/ttyUSB1`；
- 只把 `/dev/videoX` 改成当前机器上的某个 by-path；
- 只在 udev 里按 USB 插口路径命名，但没有验证硬件自身唯一身份；
- 设备插到不同 USB 口后映射失效，却仍宣称完成；
- 同型号设备无法区分时仍默认按枚举顺序分配左右手；
- 输出 topic 改名导致场景三、场景四或 Octopus 配置不一致。

## 7. topic 一致性规则

本场景不得随意改动场景三和场景四已经约定的目标 topic。

触觉目标 topic：

```text
/pressure/left_hand/gripper_1
/pressure/left_hand/gripper_2
/pressure/right_hand/gripper_1
/pressure/right_hand/gripper_2
```

GoPro 目标 topic：

```text
/gopro_right/image_raw
/gopro_left/image_raw
```

如果将来确实需要改 topic 名称，必须同步更新：

```text
DOCS/阶段一：数据采集/场景三
DOCS/阶段一：数据采集/场景四
DOCS/阶段一：数据采集/场景五
config/all_sensor_nodes.yaml
scripts/configure_octopus_scanner.py
```

## 8. 状态记录要求

场景五当前进度必须区分：

- 已部署：硬件映射脚本 / 配置是否已实际写入并用于启动；
- 已测试：是否运行过硬件扫描和节点启动；
- 已验证：是否通过插拔顺序或 USB 口变化后的稳定映射验证。
