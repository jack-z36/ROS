# 阶段四模型部署程序开发工作流

## 1. 适用范围

- 阶段：阶段四：模型部署
- 任务模式：规划、拆分、开发、验收第一版 ACT 部署程序
- 适用对象：ACT 部署程序的功能模块、模块协作架构、L2/L3 任务拆解、验收和合入
- 当前代码根目录：`src/model_deploy/act/`
- 源码主参考：同事 Pi0.5 部署程序 `DOCS/03_工程/阶段四：模型部署/pi05_old/pi05_test/pi05/`
- 当前修改路径：`src/model_deploy/act/`

本工作流不再以旧版「Contract Delta 聚类 L2 改造包」为主线。新版主线是：

```text
规划功能模块责任边界
-> 规划功能模块协作架构
-> 每个功能模块成为一个 L2
-> 线性开发 L2
-> 每个 L2 内先对照 Pi0.5 源码做功能范围匹配
-> 按用户 3.5 层认知框架拆解源码微元和 class 封装
-> 设计 ACT 版六层代码落点和文件内函数 / class
-> 拆 L3 微元任务
-> 执行与验收 L3
-> L2 Gate + 人类验收
-> 合入 model_deploy
-> 进入下一个 L2
```

## 2. 核心概念

### 2.1 L1

L1 是整个 ACT 部署程序的开发总目标。L1 必须按消费对象产出 4 类工程产物，全部落在 `DOCS/03_工程/阶段四：模型部署/02_l2_change_packages/`：

| 产物 | 消费对象 | 目的 | 推荐文件名 |
|---|---|---|---|
| 任务文档 MD | Agent | 定义 L1 总目标、L2 清单与稳定 ID、线性开发顺序、L2 依赖关系、L1 验收口径。 | `00_L1_ACT部署程序任务文档.md` |
| 功能模块边界 MD | Agent | 完整定义每个 L2 的功能边界：功能定义、输入、输出、负责/不负责、完成判据、代码层落点。 | `01_L1_ACT功能模块边界.md` |
| 功能模块协作架构 MD | Agent | 完整定义模块间协作关系：数据流、调用关系、RAM 对象所有权、同步/异步边界、失败传播、metrics、不变量。 | `02_L1_ACT功能模块协作架构.md` |
| 架构可视化 HTML | 人类 | 可视化整体架构、模块协作和模块边界，便于人类指挥 Agent 做 L2/L3 设计和代码落地。 | `ACT架构交互可视化.html` |

L1 文档不是代码设计细节全集。它负责把程序拆成可线性开发的 L2 功能模块，并按消费对象把上下文分别交付给 Agent 和人类。

四个产物的职责边界：

- 任务文档只承担任务管理属性，不展开模块边界或协作细节。
- 边界 MD 只定义单模块边界，不展开模块间协作（指向协作 MD）。
- 协作 MD 只定义模块间协作关系，不重复定义单模块边界（指向边界 MD）。
- HTML 是人类简化视图，刻意降低信息密度，不作为 L3 生成依据。

### 2.2 L2

L2 是一个功能模块闭环。每个 L2 必须回答：

```text
这个功能模块接收什么输入？
输出什么对象或外部效果？
负责哪些事情？
明确不负责哪些事情？
和上下游模块通过什么对象、队列、topic 或接口协作？
怎样才算本 L2 完成？
```

L2 不按 `types / config / repo / service / runtime / ui` 命名。一个 L2 可以横跨多个代码层。

### 2.3 L3

L3 是 L2 内部的最小实现任务。每个 L3 必须：

- 只服务于当前 L2 的一个最小目标。
- 声明涉及的 `types / config / repo / service / runtime / ui` 产物落点。
- 有局部验收方式。
- 能回滚。
- 不越过当前 L2 的责任边界。

## 3. L1 阶段：功能模块规划

### 3.1 目标

先把程序拆成一组功能模块，明确每个模块的责任边界。阶段四 ACT 第一版建议使用以下 7 个 L2：

```text
L2-01 外部参数加载与契约校验闭环
L2-02 传感器订阅与 ObservationSnapshot 组装闭环
L2-03 ObservationSnapshot 到 ACT ActionChunk 推理闭环
L2-04 ActionChunk 时间对齐与平滑融合闭环
L2-05 单步 Action 安全检查闭环
L2-06 单步 Action 到执行器 Topic 适配发送闭环
L2-07 ControlLoop 中央运行调度闭环
```

如后续项目语义变化，允许重新设计 L2，但必须保持以下原则：

- L2 按运行时功能闭环拆分。
- L2 责任边界必须显式写出「负责」和「不负责」。
- `ControlLoop` 是中央总控，不是普通加工函数。
- 每个 L2 都必须能被 Gate 验收。

### 3.2 L1 任务文档必含内容

L1 任务文档（`00_L1_ACT部署程序任务文档.md`）只承担任务管理属性，必须包含：

- L1 总目标。
- 全部 L2 清单与稳定 L2 ID。
- L2 线性开发顺序。
- L2 之间的依赖关系。
- L1 验收口径。

任务文档不展开单模块边界（指向 `01_L1_ACT功能模块边界.md`），不展开模块间协作（指向 `02_L1_ACT功能模块协作架构.md`）。

### 3.3 L1 架构协作包必含内容

L1 架构协作包不是单一文档，而是按消费对象拆分的三个配套产物：边界 MD（Agent）、协作 MD（Agent）、可视化 HTML（人类）。三者共同覆盖"模块边界 + 模块协作 + 人类可视化"三个维度。

| 产物 | 消费对象 | 内容定位 | 权威文件 |
|---|---|---|---|
| 功能模块边界 MD | Agent | 完整定义每个 L2 的功能边界、输入输出、负责/不负责、完成判据、代码层落点。 | `01_L1_ACT功能模块边界.md` |
| 功能模块协作架构 MD | Agent | 完整定义模块间协作关系、数据流、对象所有权、同步/异步边界、失败传播、metrics、不变量。 | `02_L1_ACT功能模块协作架构.md` |
| 架构可视化 HTML | 人类 | 可视化整体架构、模块协作、模块边界，便于人类指挥 Agent。 | `ACT架构交互可视化.html` |

权威关系：

- 两个 Agent MD 是权威上下文；HTML 与 MD 冲突时以 MD 为准。
- 边界 MD 不展开模块间协作（指向协作 MD）；协作 MD 不重复定义单模块边界（指向边界 MD）。
- 架构语义变化时，三个产物必须同步更新；如果来不及更新 HTML，必须在边界或协作 MD 中标记 HTML 已过期。
- L2 设计 Agent 和 L3 生成 Agent 必须同时读取边界 MD 和协作 MD，不得只读取 HTML。

#### 3.3.1 Agent 消费版：功能模块边界 MD

边界 MD（`01_L1_ACT功能模块边界.md`）目标是让后续 Agent 在不猜测的情况下回答：

```text
当前 L2 的功能定义是什么？
当前 L2 接收什么输入？输出什么对象或外部效果？
当前 L2 负责哪些事情？明确不负责哪些事情？
当前 L2 怎样才算完成？
当前 L2 允许落到哪些代码层？不能越过哪些边界？
```

边界 MD 必须包含：

- 消费者声明：说明本文是 Agent 边界权威上下文，不展开模块间协作。
- 全局边界原则：代码落点边界（types/config/repo/service/runtime/ui）、数据与控制边界（三类运行角色）。
- 每个 L2 的统一卡片：
  - 功能定义。
  - 输入（来自配置/topic/RAM/队列/上游 L2）。
  - 输出（对象/队列/topic/metrics）。
  - 负责内容。
  - 不负责内容（关键，明确边界）。
  - 完成判据。
  - 代码层落点。
  - 上下游模块（指向协作 MD 看协作细节）。
- 模块边界不变量：每个 L2 明确不能做什么，尤其是 `ControlLoop` 不能吞并 service 实现。

边界 MD 不承担以下职责：

- 不展开模块间协作关系（指向协作 MD）。
- 不展开任务管理属性（指向任务文档）。
- 不存放 Pi0.5 源码盘点（属于 L2 内部产物）。

#### 3.3.2 Agent 消费版：功能模块协作架构 MD

协作 MD（`02_L1_ACT功能模块协作架构.md`）目标是让后续 Agent 在不猜测的情况下回答：

```text
每个 L2 的上下游是谁？
每个关键 RAM 对象由谁创建、谁维护、谁消费？
哪些边界是同步调用，哪些边界是异步 queue / latest buffer / ROS topic？
ControlLoop.tick() 每轮有哪些决策点？
每类失败如何传播到 fallback、status 或 blocked？
每个 L2 能落到哪些代码层，不能越过哪些层？
生成 L2 设计和 L3 微元任务时必须继承哪些不变量？
```

协作 MD 必须包含：

- 消费者声明：说明本文是 Agent 协作权威上下文，不重复定义单模块边界。
- 模块协作总览：7 个 L2 的职责、上下游关系。
- 关键 RAM 对象与所有权：对象名、创建方、维护方、消费者、生命周期、是否 latest-only。
- 宏观数据流契约：外部配置、bundle、ROS topic、ObservationSnapshot、InferenceRequest、ActionChunk、SafetyResult、status / metrics 的流转。
- ControlLoop 调控契约：每个 tick 的读取、判断、提交、收集、调用、fallback、发布、metrics 更新步骤。
- 启动阶段协作：配置、bundle、service、worker、publisher、timer 的装配顺序和启动失败条件。
- 稳态运行协作：Observation 事件轴、Inference 后台轴、Control Tick 调度轴。
- 同步 / 异步边界：函数调用、queue、latest buffer、ROS topic、hardware gate 的区别。
- 成功路径时序：从第一帧 observation 到第一条 action 发布的端到端路径。
- 失败传播关系：配置失败、observation stale、inference error、chunk invalid、safety reject、hardware gate closed、driver failure。
- Metrics / status 汇总方式：每个 L2 贡献哪些状态字段，最终由谁发布。
- 模块协作不变量：模块间协作必须保持的约束。
- L2 与 `types / config / repo / service / runtime / ui` 的关系。
- 面向 L2/L3 的使用说明：后续 Agent 如何用本文生成 L2 设计和 L3 微元任务，哪些信息仍需到具体 L2 文档中补齐。
- 歧义与待确认项：仍未确定的 topic、action 语义、bundle 结构、hardware gate、真机验收条件等。

协作 MD 可以包含 Mermaid 图，但图只是辅助；关键契约必须用文字或表格写清楚，保证 Agent 能稳定引用。

#### 3.3.3 人类消费版：HTML 架构可视化

人类版 HTML（`ACT架构交互可视化.html`）目标是让用户在低信息负载下回答：

```text
这个程序由哪些功能模块组成？
外部数据如何进入程序？
关键 RAM 对象如何流转？
ControlLoop.tick() 到底在调控什么？
动作如何经过 safety、adapter 和 topic 输出？
失败时如何进入 fallback？
status / metrics 从哪里来？
每个模块的边界是什么（输入、输出、负责、不负责）？
```

人类版 HTML 必须满足：

- 自包含，可直接用浏览器打开，不依赖本地 dev server。
- 第一屏展示整体架构，不要求用户先读长文。
- 至少包含：模块协作、宏观数据流、ControlLoop 调控、失败传播、Metrics / status、模块边界 六类视图。
- 每个视图只展示关键模块、关键 RAM 对象和关键边界，不展开 Pi0.5 源码映射、函数签名、L3 列表或完整配置 schema。
- 必须区分 `data`、`control`、`queue`、`topic`、`metrics`、`failure` 这些关系类型。
- 必须支持查看每个模块的边界：功能定义、输入、输出、负责、不负责。
- 必须明确 `ControlLoop.tick()` 是中央调度器，不是数据加工函数。

人类版 HTML 不承担以下职责：

- 不作为 L3 生成依据。
- 不存放完整字段契约。
- 不解释每个文件该怎么写。
- 不替代 L2 内部的 Pi0.5 源码盘点。

## 4. L2 阶段：基于 Pi0.5 源码的功能模块交互式设计

每个 L2 开始前，必须先与 Agent 交互式设计该功能模块的内部产物。不得直接让 Agent 生成 L3。

L2 内部设计的第一任务不是自由设计新程序，而是先理解同事 Pi0.5 源码中如何实现相同或相近的运行时功能。Agent 必须先完成源码范围匹配、3.5 层微元拆解和 class 封装盘点，再推荐 ACT 版设计。

L2 设计阶段属于固定产出流程，优先使用仓库内 skill：

```text
skills/stage4-l2-designer/
```

仓库内所有可复用 skill 默认存放在 `skills/` 目录下。`stage4-l2-designer` 只负责 L2 设计固定产物，不负责生成或执行 L3；L3 调度仍由 `skills/stage4-l3-orchestrator/` 负责。

### 4.1 代码范围匹配

先明确当前 L2 的功能边界，再去源码中寻找对应代码范围。

#### 4.1.1 L2 设计前置校验

进入任意 L2 具体功能设计前，必须先完成以下校验：

| 校验项 | 要求 |
|---|---|
| L2 ID | 必须属于新版 7 个功能闭环 L2：`l2-01-external-contract`、`l2-02-observation-snapshot`、`l2-03-act-inference`、`l2-04-action-smoothing`、`l2-05-safety-guard`、`l2-06-action-publisher`、`l2-07-control-loop`。 |
| 设计目录 | 必须落到 `02_l2_change_packages/<l2_id>_<中文短名>/`，不得落到 `_legacy_layer_based_act/`。 |
| 功能边界来源 | 必须来自 `01_L1_ACT功能模块边界.md`。 |
| 协作关系来源 | 必须来自 `02_L1_ACT功能模块协作架构.md`。HTML 只作人类理解入口，不作为 Agent 权威上下文。 |
| 旧资料状态 | Contract Delta、旧 layer-based L2 卡片、旧 dispatch、旧 acceptance 均不得作为当前 L2 边界。 |

如果 L2 ID 无法确认，或者用户给出的目标仍是旧 `l2-01-types` / `l2-02-config` / `l2-03-assembly` / `l2-04-publish` / `l2-05-hardware`，必须先停止并澄清，不得进入 Pi0.5 源码盘点。

#### 4.1.2 参考材料降权规则

L2 设计阶段允许读取参考材料，但必须遵守以下优先级：

```text
阶段四新版工作流
-> L1 任务文档
-> L1 Agent 架构 Markdown
-> 当前 L2 设计目录
-> 01_contracts/ 参考语义
-> Pi0.5 源码结构参考
-> legacy 历史材料
```

- `01_contracts/` 只能补充 topic、shape、bundle、硬件接口和安全语义，不得作为 L2 拆解权威。
- Pi0.5 源码只能用于源码微元拆解、class 封装盘点和结构复用判断，不得覆盖当前 ACT L1/L2 责任边界。
- 旧 layer-based L2 卡片只能作为人工迁移素材，不得作为当前 L2 的负责 / 不负责边界。
- `ACT架构交互可视化.html` 只服务人类理解，Agent 设计必须以 `01_L1_ACT功能模块边界.md` 和 `02_L1_ACT功能模块协作架构.md` 为准。

代码范围匹配是 Agent 的内部工作过程，不作为独立文档产物生成。Agent 必须在工作过程中形成一张「Pi0.5 源码范围匹配表」，但只把有用结论折叠进后续 `01_pi05源码3.5层微元拆解.md`、`02_ACT微元设计与协作.md` 和六层设计文档中。

| 字段 | 要求 |
|---|---|
| 当前 L2 宏观功能 | 用一句话说明本 L2 在 ACT 部署程序中的运行时职责。 |
| L2 输入 | 写清来自配置、topic、RAM 对象、队列、模型或上游 L2 的输入。 |
| L2 输出 | 写清输出对象、队列写入、topic 发布、status、metrics 或副作用。 |
| Pi0.5 对应文件 | 具体到 `DOCS/03_工程/阶段四：模型部署/pi05_old/pi05_test/pi05/` 下的文件路径。 |
| Pi0.5 对应 class / 函数 | 具体到 class、函数、常量、配置或入口。 |
| Pi0.5 已有能力 | 说明源码已经解决了什么问题。 |
| 与 ACT 目标差距 | 说明维度、模型框架、topic、bundle、动作格式、runtime 语义等差异。 |
| 复用判断 | `直接复用 / 结构复用 / 参考理解 / 不复用`。 |
| 风险 | 写清照搬会导致什么错误，或缺少什么上下文。 |

没有完成源码范围匹配，不得进入 ACT 版六层设计，也不得生成 L3。

### 4.2 源码 3.5 层微元拆解

结合 `DOCS/02_约束/认知偏好/用户认知框架与讲解偏好.md` 的第 3.5 层，Agent 必须解释：Pi0.5 源码用哪些文件内功能微元实现当前 L2 的宏观功能。

源码微元拆解必须使用以下分类：

| 3.5 层微元 | 判断标准 |
|---|---|
| 数据 | 变量名、常量、字段、维度、segment、状态对象、配置对象。 |
| 计算函数 | 输入和输出都在 RAM 内，负责转换、归一化、校验、构造、推理前后处理。 |
| 内部状态更新函数 | 修改 buffer、queue、cache、metrics、运行状态或 class 内部字段。 |
| 数据读写函数 | 跨进程边界读取或写出文件、ROS topic、模型权重、硬件、网络资源。 |
| 编排函数 | 决定什么时候调谁、按什么顺序调、是否并发、失败后怎么办。 |

每个 L2 必须产出「Pi0.5 源码 3.5 层微元拆解表」：

| 源码文件 | class / 函数 / 数据 | 3.5 层微元类型 | 输入 | 输出或副作用 | 与其他微元的协作关系 | 对 ACT 设计的启发 |
|---|---|---|---|---|---|---|
|  |  | 数据 / 计算函数 / 内部状态更新函数 / 数据读写函数 / 编排函数 |  |  |  |  |

协作关系必须说明：

- 谁持有状态。
- 谁调用谁。
- 谁只负责加工 RAM 对象。
- 谁跨越外部边界。
- 谁负责 runtime 时序或失败处理。

### 4.3 源码 class 封装盘点

Agent 必须继续回答：Pi0.5 源码中哪些微元被 class 封装了，为什么需要 class。

每个 L2 必须产出「Pi0.5 class 封装盘点表」：

| class | 源码路径 | 封装了哪些 3.5 层微元 | 内部状态 | 生命周期 / 并发特征 | 为什么适合 class | ACT 中的处理建议 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

判断原则：

- 保存内部状态、cache、queue、metrics 或 buffer：通常适合 class。
- 需要线程、timer、启动 / 停止生命周期：通常适合 class。
- 需要 ROS node 生命周期：使用 ROS node class。
- 只是纯输入到输出转换：优先函数。
- 只是为了“看起来面向对象”：不得封装为 class。

### 4.4 ACT 版微元设计推荐

在完成 Pi0.5 源码盘点后，Agent 再推荐当前 L2 在 ACT 程序中应该包含哪些微元功能模块、哪些应该封装为 class、各模块如何协作。

这一部分由 Agent 先给出推荐设计，用户负责审核、优化和调整。没有经过用户确认的 ACT 版微元设计，不得进入 L3 生成。

ACT 版设计必须产出以下表：

| ACT 微元 | 3.5 层微元类型 | 推荐落点 | 输入 | 输出或副作用 | 函数 / class 判断 | 推荐理由 | 对应 Pi0.5 参考 |
|---|---|---|---|---|---|---|---|
|  | 数据 / 计算函数 / 内部状态更新函数 / 数据读写函数 / 编排函数 | types / config / repo / service / runtime / ui |  |  |  |  |  |

还必须产出一段协作说明：

```text
当前 L2 内部微元协作关系：
1. 哪个对象先被创建？
2. 哪个函数或 class 持有状态？
3. 哪些函数只做 RAM 内计算？
4. 哪些函数跨越文件、topic、模型或硬件边界？
5. 哪个 runtime 编排点负责调用这些微元？
6. 失败时错误如何向上游或下游传播？
```

### 4.5 六层设计文档目录

每个 L2 必须生成一个 L2 设计目录。推荐落点：

```text
DOCS/03_工程/阶段四：模型部署/02_l2_change_packages/<l2_id>_<l2_name>/
```

其中：

- `l2_id` 用于 branch、dispatch、cards、acceptance 和状态摘要，例如 `l2-01-external-contract`。
- `l2_design_dir` 用于 L2 设计包目录，例如 `l2-01-external-contract_外部参数加载与契约校验闭环`。
- L3 / dispatch / acceptance 使用纯 `l2_id`，不得使用带中文短名的设计目录名。

六个子文件夹必须与 `src/model_deploy/act/` 的六层代码落点对应。每个子文件夹中包含一个或多个 `.md` 文件，用来说明该层下函数与 class 的设计。

如果某个 L2 不涉及某一层，也保留对应子文件夹，并在 `README.md` 中说明：

```text

原因：
验收如何确认：
```

每个六层设计 `.md` 至少包含：

| 字段 | 要求 |

| 目标源码路径 | 未来落到 `src/model_deploy/act/<层>/` 下的文件路径。 |
| 文件职责 | 本文件负责什么，不负责什么。 |

| 验收覆盖 | 哪些 L3 或 L2 Gate 会验证该文件设计。 |
| 边界来源 | 必须说明该文件服务当前 L1/L2 功能边界，不从旧 layer-based L2 卡片继承任务边界。 |

### 4.6 六层产物拆分

对当前 L2，先逐项确认是否需要以下产物：

| 层 | 需要回答的问题 |
|---|---|
| `types/` | 是否需要新的数据结构、常量、维度定义、枚举、codec、result 对象？ |
| `config/` | 是否需要新的配置 schema、默认值、合法性校验？ |
| `repo/` | 是否需要读取外部文件、bundle、checkpoint、normalizer、manifest？ |
| `service/` | 是否需要纯业务计算、转换、校验、构造函数？ |
| `runtime/` | 是否需要队列、线程、timer、状态机、调度器、生命周期管理？ |
| `ui/` | 是否需要 ROS node、subscription、publisher、message adapter、launch 入口？ |

输出一份当前 L2 的「六层产物设计表」。表中必须写明：

- 文件路径。
- 该文件的职责。
- 输入。
- 输出。
- 不做什么。
- 依赖哪些上游层。
- 本 L2 的验收如何覆盖它。

### 4.7 文件内功能微元设计

继续细化每个文件内部需要哪些功能微元：

| 功能微元 | 需要回答的问题 |
|---|---|
| 数据定义 | 是否需要 dataclass、TypedDict、常量、segment 定义、字段说明？ |
| 计算函数 | 输入和输出是什么？是否只在 RAM 内计算？ |
| 内部状态更新函数 | 是否修改 buffer、queue、cache、metrics、状态机？ |
| 数据读写函数 | 是否跨进程边界读取文件、ROS topic、硬件、网络？ |
| 编排函数 | 是否决定何时调用谁、失败后怎么办、是否并发？ |

如果一个文件内同时出现多类微元，必须说明它们之间的边界，避免把所有逻辑塞进一个大函数。

### 4.8 class 封装判断

是否封装为 class，按以下原则判断：

- 需要保存内部状态：可以封装为 class。
- 需要多次调用并共享配置：可以封装为 class。
- 只是纯输入到输出转换：优先函数。
- 涉及线程、queue、timer、生命周期：优先 class。
- 涉及 ROS node：使用 ROS node class。

禁止为了“看起来面向对象”而无状态封装。

### 4.9 L2 验收机制设计

每个 L2 在拆 L3 前必须先设计 Gate。Gate 至少包含：

- required L3 清单。
- 验收运行目录。
- 最低验证层级：unit / import / mock / dry-run / shadow-run / real-robot。
- 运行命令。
- 测试输入。
- 观察点。
- 通过现象。
- 失败现象与排查入口。
- 未验证项处理方式。
- 是否允许进入下游 L2。
- 是否允许触发 Git 合入。

经用户交互修正后的 L2 设计必须额外产出 `04_人类验收机制.md`，用于描述人类可执行的验收清单、命令、输入、观察点、通过现象、失败现象、真机风险和签字位置。

### 4.10 L2 设计澄清机制

如果出现以下情况，Agent 必须先向用户提问，不得自行进入 L3：

- 当前 L2 功能边界与 Pi0.5 源码边界不一致，无法判断应该拆分还是合并。
- Pi0.5 源码中同一段代码横跨多个 L2，无法确定本 L2 的修改边界。
- ACT 目标与 Pi0.5 行为冲突，例如维度、topic、模型输入、动作语义或安全策略不同。
- 无法判断某个微元应该是函数还是 class，且该选择会影响状态、并发、生命周期或测试方式。
- 验收需要真实 ROS、bundle 或硬件，但当前环境只能做 mock / dry-run。
- 用户提出的 L2 目标会破坏 `types / config / repo / service / runtime / ui` 的依赖方向。

### 4.11 L2 设计输出前自检

生成或更新 L2 设计包后，进入 L3 生成前必须确认：

- 当前 L2 ID 属于新版 7 个功能闭环 L2。
- 当前 L2 设计目录不在 `_legacy_layer_based_act/`。
- `00_L2功能边界.md` 写明 L1 任务文档和 L1 Agent 架构文档。
- 当前 L2 设计包未把 `ACT Contract Delta`、`AS-IS Contract -> TO-BE Contract -> Contract Delta` 或旧 L2 ID 写成任务来源。
- 当前 L2 设计包未引用阶段二 L2 模板作为模板来源。
- `types / config / repo / service / runtime / ui` 六个子目录均包含设计文件或 README。
- 若引用 `01_contracts/`，必须写明引用目的：topic / shape / bundle / hardware semantics。

L3 生成前必须满足：

```text
L2 功能边界已明确
L2 协作接口已明确
Pi0.5 源码范围匹配已明确
Pi0.5 源码 3.5 层微元拆解已明确

L2 Gate 已明确

```

L3 的生成与执行机制沿用旧阶段四工作流的调度和验收纪律，但不再沿用旧版 AS-IS / TO-BE / Contract Delta 作为 L2 主线。旧模板中的源码盘点、dispatch、验收卡片、执行 / 验收 agent 分离、最多 3 轮迭代、L2 Gate、人类验收签字和合入规则必须保留；旧模板中与新版 L2 功能模块主线冲突的字段，替换为：

```text
L2 功能边界
Pi0.5 源码范围匹配
Pi0.5 源码 3.5 层微元拆解
ACT 版微元设计与协作
L2 六层设计文档
```

L3 必须使用 `attachments/L3微元改造任务模板.md`，并且每个 L3 必须同时生成：

- L3 任务文件。
- `dispatch` YAML。
- 验收卡片。
- 执行 agent 输入边界。
- 验收 agent 输入边界。
- 当前 L3 对 L2 Gate 的贡献说明。

每个 L3 任务文件必须包含：

- L3 编号。
- 所属 L2。
- 本次唯一目标。
- 对应 Pi0.5 源码参考。
- 对应 ACT 六层设计文档。
- 允许修改路径。
- 禁止修改路径。
- 产物落点。
- 依赖关系。
- `dispatch` 元数据。
- 本地验收命令。
- 验收模式。
- 验收卡片路径。
- 最多 3 轮执行-验收迭代限制。
- L2 Gate 贡献场景。
- 人类验收签字入口。
- 回滚方式。

L3 应尽量小，但不能小到无法验收。一个 L3 的合适粒度是：

```text
一次提交可以完成
能单独解释价值
能被局部测试或 L2 Gate 覆盖
失败后能回滚
```

## 6. L3 执行与验收

L3 执行采用执行与验收分离：

| 角色 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|
| 执行 Agent | L3 任务文件、上下文、允许修改路径 | 代码、测试、执行摘要 | 不改验收结论，不做 Git 合入 |
| 验收 Agent | 验收卡片、L3 文件、diff、日志 | PASS / FAIL / BLOCKED / DEFER | 不改源码，不替执行 Agent 修代码 |
| 主 Agent | dispatch、L3 状态、验收反馈 | 调度、迭代、L2 Gate 判断 | 不跳过验收 |

每个 L3 最多执行-验收迭代 3 轮。3 轮后仍失败，停止自动推进并请求人工判断。

### 6.1 L3 调度产物

每个 L3 必须有 `dispatch` 元数据，用于主 Agent 判断串行、并行、依赖、冲突范围和验收模式。`dispatch` 至少包含：

- `task_id`
- `task_file`
- `group`
- `branch`
- `integration_branch: model_deploy`
- `acceptance_dir`
- `acceptance_card`
- `acceptance_mode`
- `acceptance_round_limit: 3`
- `depends_on`
- `can_run_parallel_with`
- `conflict_scope`
- `robot_risk`
- `dispatch_status`

缺少 `dispatch` 的 L3 不得执行。

### 6.2 验收卡片

每个 L3 必须生成独立验收卡片。验收卡片供验收 Agent 使用，至少说明：

- 要检查的 L3 任务文件。
- 允许查看的 diff、日志和验收证据。
- 验收模式：`direct-local / static-review / downstream-l2 / env-blocked / hardware-blocked`。
- 必跑命令或必须解释为什么不能跑。
- PASS / FAIL / BLOCKED / DEFER 判断标准。
- 本 L3 是否影响 L2 Gate。

执行 Agent 不得自行修改验收结论。

### 6.3 迭代限制

单个 L3 的执行-验收最多 3 轮：

```text
执行 Agent 实现
-> 验收 Agent 检查
-> FAIL_LOCAL 时返回执行 Agent 修正
-> 最多重复 3 轮
-> 仍失败则停止自动推进，请用户判断
```

`downstream-l2`、`env-blocked`、`hardware-blocked` 不是免验收，而是要求写清：

- 当前能验证什么。
- 缺少什么环境或硬件。
- 由哪个 L2 Gate 场景补验。
- 是否允许继续进入下游 L3。

## 7. L2 Gate、人类验收与合入

一个 L2 的 required L3 全部达到可解释状态后，启动 L2 Gate：

```text
PASS_LOCAL
DEFER_TO_L2_GATE
BLOCKED_ENV
BLOCKED_HARDWARE_EXPECTED
```

L2 Gate 通过后，必须进入人类验收关卡。人类验收规则见 `attachments/人类验收关卡规则.md`。

只有满足以下条件，才允许合入 `model_deploy`：

```text
L2 Gate 通过
人类验收签字通过
真机风险记录完整
Git 状态符合阶段四 Git 操作规则
```

合入流程以 `DOCS/02_约束/Git协作/阶段四：模型部署 Git操作规则.md` 为准。

## 8. 真机与环境边界

默认开发环境可能没有 ROS、模型 bundle、机械臂、夹爪或传感器。阶段四验收必须遵守：

- 能在本地跑的 unit/import/config/mock 测试必须跑。
- 无真实 bundle 时，模型链路使用 fake-policy 验收接口形状和调度行为。
- 无 ROS 时，ROS 行为可以先用 adapter/mock 验收，标记 `env-blocked`。
- 无硬件时，真机行为必须标记 `hardware-blocked`。
- 禁止把未运行的 real-robot smoke test 写成通过。
- 真机发送必须经过 shadow-run、gate、急停准备和人工授权。
