## 0. 本次调整背景

第一版部署程序内部模型确定为 **ACT**（lerobot 框架训练），消费阶段二《数据清洗交付说明.md》的 LeRobotDataset v3。

- 维度：observation.state = **16D**（双臂 TCP 7D + 夹爪 1D，不含触觉）；action = **16D**（TCP+width，绝对动作）。与阶段二数据同构、零转换。
- 代码：新建 `src/model_deploy/act/` 独立代码树，不抽象 PolicyBackend 接口，Pi0.5 代码零改动。
- 验收：每个 L2 在 AI 侧 Gate 通过后，必须经**人类验收关卡**（人类亲自运行测试 + 签字）才允许合入 `model_deploy` 并删除三级分支。规则见 `DOCS/02_约束/工作流/阶段四开发工作流/attachments/人类验收关卡规则.md`。

## 0.5 同事源码复用边界

> [!info] 背景
> 同事已交付一套可运行的 Pi0.5 部署源码（`pi05_old/pi05_test/pi05/`，下称「同事源码」）。第一版虽切换为 ACT，但同事源码中**与模型解耦的调度骨架、数据结构、ROS 接线**是已验证的工程成果，必须复用以避免重新踩坑。各 L2 在执行时按本节对照表从同事源码搬运或参考，不重复造轮子。

### 核心发现：调度层与模型唯一耦合点是 `predict_action_chunk`

同事源码的调度层（control_loop / inference_worker / shared_buffer）**完全不依赖 Pi0.5**。整个调度层与模型的唯一契约是 `inference_worker.py:67` 的一个方法调用：

```python
self.policy_runtime.predict_action_chunk(request.observation)  # → np.ndarray, shape (chunk_size, action_dim)
```

**结论**：只要新写的 `act/repo/policy_loader.py` 的 `ACTPolicyRuntime` 保持这个方法签名（输入 `ObservationSnapshot`，输出 shape `(chunk_size, 16)` 的 float32 numpy），**shared_buffer / control_loop / inference_worker 可以一行不改地直接复用**。

### 复用方式定义

| 方式 | 含义 |
|---|---|
| **直接复用** | 文件几乎原样搬到 ACT 目录，只改包名/import 路径（`pi05.` → `act.`），不改逻辑 |
| **结构复用** | 保留类的骨架/方法签名/校验框架，修改具体维度、字段、默认值或检查项 |
| **重写，保持接口** | 内部完全重写（换模型），但对外方法签名不变，保证下游复用方零改动 |
| **部分复用** | 文件中部分类/函数保留，部分剥离或替换 |
| **参考** | 不搬运，只读同事实现学习思路（ROS 接线方式、消息处理），新代码独立写 |
| **不复用** | 模型强耦合，ACT 用不到 |

## 1. 分层映射（ACT 部署项目的 6 层对应）

通用 6 层架构映射到 ACT 项目：

| 通用层 | ACT 部署对应 | 新建文件 |

| **Config** | 运行参数、topic 名、维度、安全配置 | `act/config/schema.py` |

## 2. 修正后的 L2（5 个，边界干净）

| L2 | 对应分层 | 包含代码 | 关联 ACT Delta | 验证阶梯 | 真机风险 |
|---|---|---|---|---|---|
| **L2-01** | Types | state_codec（16D 分组段序）、action_spec、action_codec（16D 交替段序） | A2/A3 | 纯单测 | 低 |
| **L2-02** | Config | config/schema（`/act/*` topic、维度 16/16、bundle、safety） | A4 | 单测 | 低 |
| **L2-03** | Repo + Service（输入侧） | observation_collector、policy_loader（ACT checkpoint 加载）、`_build_batch` | A5/A6 | dry-run | 低 |
| **L2-04** | Service + Runtime + UI（输出侧） | safety_guard、deploy_node 发布侧、`/act/policy_action`、control_loop、mode/gate、metrics | A7/A8/A9/A10 | dry-run + shadow-run | 中 |
| **L2-05** | 独立新节点（自含分层） | command_bridge_sender_node、rm65_driver_node、elephant_gripper_node、新 launch | A11/A12 | shadow-run + real-robot | **高** |

### 边界干净性说明

- **L2-01（Types）只含 Types 层**：state_codec / action_spec / action_codec 全是数据结构定义 + 编解码。不依赖 Config/Repo/Service。改完可纯单测。
- **L2-02（Config）只含 Config 层**：依赖 Types（引用 `ACTION_DIM`/`STATE_DIM`），但不依赖 Repo/Service。
- **L2-03（Repo+Service 输入侧）**：observation_collector + policy_loader + `_build_batch`，共同隐藏「ROS 数据 → ACT batch」的装配逻辑。验证阶梯一致（dry-run）。
- **L2-04（Service+Runtime+UI 输出侧）**：safety_guard + deploy_node 发布 + control_loop，共同隐藏「ACT 输出 → policy_action 发布」的逻辑。验证阶梯一致（dry-run+shadow）。
- **L2-05（硬件栈）是独立子系统**：和前 4 个 L2 只通过 `/act/policy_action` topic 解耦。

## 3. 依赖关系（单向，符合分层约束）

```text
L2-01 Types （地基，不依赖任何层）
   ↓ Config 依赖 Types
L2-02 Config
   ↓ Repo/Service 依赖 Types+Config
L2-03 Repo+Service（输入侧）          L2-04 Service+Runtime+UI（输出侧）
   ↓                                    ↓
   └──→ /act/policy_action ←─────────────┘  （UI 对外接口 = 契约边界）
              ↓ （topic 解耦，非代码依赖）
        L2-05 硬件执行栈（独立子系统）
```

- L2-01 → L2-02 → L2-03：严格单向。
- L2-04 依赖 L2-01（Types，safety_guard 用 action 结构），不依赖 L2-02/L2-03。L2-03 ∥ L2-04 可并行。
- L2-05 不依赖前 4 个的代码，只依赖 `/act/policy_action` 的 16D 契约。

### 建议执行顺序

```text
第一波：L2-01（Types 地基）
第二波：L2-02（Config，紧跟地基）
第三波：L2-03 ∥ L2-04（并行，都依赖 01，彼此解耦）
第四波：L2-05（接真机，最高风险）
```

## 4. 人类验收关卡（每个 L2 必须通过）

每个 L2 必须依次通过以下两道关卡才能合入 `model_deploy`：

1. **L2 Gate（AI 侧自动化）**：运行 L2 整体验收卡片中的自动化测试（单测/dry-run/shadow-run），产出 `05_acceptance/<l2>/验收结果.md` 和 `L2整体验收报告.md`。
2. **人类验收关卡**：AI 暂停，向用户交付《人类验收清单》（`05_acceptance/<l2>/人类验收清单.md`），用户亲自运行清单中的测试并签字。只有签字通过，才允许执行 Gate 后合入流程。

规则见 `DOCS/02_约束/工作流/阶段四开发工作流/attachments/人类验收关卡规则.md`。
