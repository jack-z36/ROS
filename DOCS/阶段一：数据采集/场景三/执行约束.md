## 3. 启动边界约束

- 场景三不把 Octopus 录制逻辑塞进传感器启动 launch。
- `start_all_sensor.sh` 是目标数据源启动入口，第二阶段最终应自动启动 2 个 Baton Mini、2 个 GoPro 和 4 路触觉传感器数据源。
- Octopus 必须有独立启动入口，建议后续实现为 `/home/hit/ROS/start_octopus.sh`。
- 相机和触觉传感器节点只负责发布 ROS2 topic。
- Octopus 负责图形化开始采集、结束采集和输出 `.mcap` 文件。
- 验证时必须先确认 8 个目标 topic 在 ROS2 图中可见，再启动或刷新 Octopus 订阅配置。
- 若普通 ROS_DOMAIN 中存在远端 topic 干扰，需要明确记录当前使用的 ROS discovery 范围和环境变量。
- 两个脚本必须使用兼容的 ROS discovery 配置，否则 Octopus 可能看不到 `start_all_sensor.sh` 启动的数据源。

## 4. 8 个节点 / 8 路数据口径约束

- 场景三默认验收口径是 8 路可采集 topic / 数据源，而不是必须存在 8 个独立 ROS 进程。
- 当前触觉驱动可以由一个 `pressure_driver_node` 管理多个串口并发布多个触觉 topic；第二阶段目标是发布 4 个触觉 topic。
- 如果后续明确要求“8 个 ROS 节点进程”，需要将触觉传感器拆成多个独立节点或多个独立 launch 实例，并同步更新本场景文档。

## 5. Octopus 配置约束

- Octopus 的录制 topic 列表必须包含 8 个目标 topic。
- 理想目标是用户能在 Octopus 图形化界面选择要导出的 topic，并导出一个总 `.mcap` 文件。
- 如果当前 Octopus 只能通过 `scanner.json` 固定 topic 列表，应先记录为功能差距，再决定是否修改 Octopus。
- 修改 Octopus 录制 topic 时，优先记录实际修改位置，例如 `/home/hit/.config/scanner.json` 或源码默认配置。
- 不把旧的 `/realsense/*`、`/inspire/*` 默认 topic 当作本场景成功标准。
- 如果 UI 只能显示部分 topic，不能直接判定录制失败；必须结合 MCAP 文件内容验证。

## 6. MCAP 验证约束

每次声称场景三采集成功时，至少需要记录：

```text
1. 采集开始和结束方式；
2. 生成的总 .mcap 文件路径；
3. .mcap 文件大小；
4. .mcap 中包含的 topic 列表；
5. 每个目标 topic 是否有消息写入；
6. 是否存在 unsupported type、schema 为空或读取失败等问题。
```

可优先使用：

```bash
ros2 bag info <mcap文件路径>
```

若 `ros2 bag info` 对当前 MCAP 文件不适用，应记录替代验证工具和输出结论。

## 7. 已知风险约束

- Octopus 当前录制器已知显式支持 `sensor_msgs/msg/Image`、`sensor_msgs/msg/CompressedImage`、`sensor_msgs/msg/JointState` 的 schema definition。
- 场景三需要录制的 `nav_msgs/msg/Odometry` 和 `hwk_pressure_interfaces/msg/PressureFrame` 必须作为优先风险点验证。
- 如果 MCAP 能生成但无法被后续工具正确解析，优先排查 Octopus 的 `McapRecorder::get_message_definition()`。
- 未完成 MCAP 内容验证前，不能把“Octopus 界面点击成功”视为场景三完成。
