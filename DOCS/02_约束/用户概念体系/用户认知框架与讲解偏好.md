## 第二层：文件夹架构

| 概念        | 当前理解                                                                                                                                                                                                                                                                                                                                                                                                | 简单例子 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `types`   | 定义数据长什么样，它只负责回答一个问题：程序里被传来传去的数据，应该长什么样。<br />具体包括：这个数据有哪些字段、每个字段是什么类型、如果是数组则有多少维、每一维或每一段分别代表什么、哪些取值是固定选项、什么样的数据一眼就算非法。<br />`types/` 是程序架构中最上游的数据语言层。<br />它不关心配置从哪里来、不关心文件怎么读、不关心业务怎么处理、不关心运行时怎么调度、不关心 UI/ROS 怎么交互。 | 定义 `Action` 必须是 14 个 `float`，例如 `[0.1, -0.2, 0.0, ...]` |
| `config`  | `config/` 是程序架构中的运行参数语言层。它位于 `types` 之后，依赖 `types` 提供的数据语言，用来定义程序运行时有哪些可配置参数、这些参数是什么类型、默认值是什么、哪些配置值明显非法。<br />它不负责存放某次运行的具体配置值；<br />具体值放在 `config_files/`。<br />它的职责是把外部配置值整理成后续层可以稳定使用的配置对象。                                                                  | 定义 `control_hz` 是 `float`，本次配置值可以是 `30.0` |
| `repo`    | `repo/` 是程序架构中的外部资源读取层。它位于 `config` 之后，依赖 `types` 和 `config`。它负责根据配置找到进程外部的资源，读取、解析、校验这些资源，并把它们变成当前 Python 进程 RAM 里的内部对象，供后续层直接使用。它不负责业务处理、运行时调度或 UI/ROS 交互。相关基础概念见 `Python代码运行的计算机基础.md`。                                                                               | 从 `/models/act/checkpoint.pt` 读取模型权重到 RAM 里的 `policy` 对象 |
| `service` | `service/` 是程序架构中的业务计算层。它位于 `repo` 之后，依赖 `types`、`config` 和 `repo`。<br />从输入输出角度看，`service/` 接收已经在当前 Python 进程 RAM 里的输入对象，调用计算函数，按照程序目标把它们加工成新的内部对象或判断结果。<br /><br />它不负责把外部资源读进 RAM，不负责安排循环、线程或执行时机，也不负责直接和 ROS/硬件交互。                                              | 输入 observation，输出 action，例如把 26D 状态和 3 路图像加工成 14D action |
| `runtime` | `runtime/` 是程序架构中的运行流程组织层。它位于 `service` 之后，依赖 `types`、`config` 和 `service`。<br />它负责根据时间、状态、事件和失败条件，调度计算函数、内部状态更新函数以及必要的数据读写函数，把一次性的处理能力组织成持续运行的程序流程。<br />它关心的是“什么时候调谁、多久调一次、谁先谁后、是否并发、失败后怎么办”，而不是具体业务怎么算。                                     | 每 `1/30` 秒调用一次取动作和发布动作流程 |
| `ui`      | `ui/` 是程序架构中的外部交互层。它位于最下游，依赖前面的 `types`、`config`、`repo`、`service`、`runtime`。<br />它负责让程序和外部世界交换数据：把外部输入转换成 Python 进程 RAM 里的内部对象，也把内部对象转换成外部系统能接收的消息、命令或输出。<br />在 ROS 项目中，`ui/` 主要负责 ROS Node、topic 订阅、topic 发布和 message 转换。它不负责核心业务计算，也不负责内部运行流程编排。  | 从 `/camera/color/image_raw` 收到图像消息，把 `/action_cmd` 发布给机械臂 |

### class、实例与实例化

| 概念 | 当前理解 | 简单例子 |
|---|---|---|
| class | 创建某类对象的模板，规定实例内部可以拥有哪些属性和函数能力；class 本身不是某次运行产生的具体业务对象 | `ActInferenceService` 是推理服务的 class 模板 |
| 实例 | Python 根据 class 模板在 RAM 中创建的具体对象，是程序运行时真正被保存和操作的对象 | `ActInferenceService(...)` 得到一个具体推理服务实例 |
| 实例化 | 使用 `class名(...)` 创建并初始化一个实例的过程 | `inference_service = ActInferenceService(...)` |
| `__init__()` | 实例化时由 Python 自动调用的初始化函数；它不负责返回实例，而是把外部传入的数据绑定为新实例的内部属性 | `ActInferenceService.__init__()` 保存 config、normalizer、policy 和 input spec |
| 实例化流程 | class 模板 → 执行 `class名(...)` → RAM 中创建具体实例 → Python 自动调用 `__init__()` → 实例内部属性完成初始化 | `ActInferenceService` → `ActInferenceService(...)` → 推理服务实例 |

### 从公开接口理解 class

| 概念 | 当前理解 | 简单例子 |
|---|---|---|
| 公开接口 | class 设计给外部代码使用的方法和属性。按 Python 的命名约定，不以 `_` 开头的方法通常视为公开方法；`@property` 也能提供公开属性。这个约定帮助我们从外部使用者的视角理解 class。 | `service.predict_action_chunk(...)` 是公开方法；`service.input_spec` 是公开属性 |
| 从公开函数定位核心能力 | 对以业务计算为目的的 class，可以先看公开函数的输入和输出。公开函数通常表达该 class 对外提供的核心能力。 | `ActInferenceService.predict_action_chunk(observation)` 的输入是观测，输出是动作块 |
| 内部辅助内容 | 内部属性、内部函数和构造期保存的依赖，通常为公开函数服务：保存长期数据、准备输入、计算派生信息或检查约束。 | `_policy` 保存模型；`_device` 保存设备；`_resolve_device()` 计算设备 |
| 单一公开函数的 class | 如果 class 主要只有一个公开的业务函数，可以把它理解为“带长期保存依赖的函数能力包”：先创建实例并保存依赖，以后可多次调用同一个能力。 | `ActInferenceService` 创建后，可多次调用 `predict_action_chunk(...)` |
| 与普通函数的区别 | 普通函数主要使用本次调用传入的参数；这类 class 的实例还能长期持有属性。因此 class 本身不是一种特殊函数，而是把一个或多个函数能力与长期状态封装在一起的模板。 | 同一个推理服务实例持续保存 policy、normalizer 和 config |
| 不能一概而论 | class 可以没有公开函数、只有一个公开函数，或有多个公开函数和公开属性。判断核心功能时，要看全部公开接口以及这个 class 所属的职责，而不能机械地只看第一个公开函数。 | `input_spec` 是公开属性，但它不是 `ActInferenceService` 的主要业务计算 |

## 第 3.375 层：文件内编排函数

| 概念 | 当前理解 | 简单例子 | 描述规范（后续讲解时按此格式输出） |
| ---- | -------- | -------- | --- |
| 编排函数 | 编排函数是对第 3.5 层基础功能微元（计算函数、数据读写函数、内部状态更新函数、数据）的封装与编排。<br />它不引入新的计算逻辑，而是决定：按什么顺序调用哪些功能微元、在什么条件下调用、失败后如何处理。<br />编排函数位于 class（3.25）和基础功能微元（3.5）之间——class 打包编排函数和基础微元，编排函数封装和调度基础微元。 | 每 0.033 秒依次执行"取观测 -> 推理 -> 发布动作" | 讲清<b>编排逻辑</b>：①按什么顺序调用哪些功能微元 ②调用条件（什么时候调、什么时候跳过） ③失败后怎么办（抛异常 / fallback / 重试） |

## 第 3.5 层：文件内基础功能微元

| 功能微元         | 当前理解                                                                                                                                                                             | 简单例子 | 描述规范（后续讲解时按此格式输出） |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | --- |
| 数据             | 定义变量的 变量名、内部数据结构以及各个部分存储的数值类型的那部分代码。                                                                                                              | `ACTION_DIM = 14`，其中变量名是 `ACTION_DIM`，数值是 `14` | 讲清三个维度的信息：①<b>变量名</b> ②<b>内部存储结构</b>（是常量、dict、list、dataclass 还是 tuple 等） ③<b>内部存储的数值类型</b>（int、float、str、bool 等） |
| 计算函数         | 输入是 RAM 里的数据；<br />输出是新的 RAM 内部数据或判断结果。<br />它不直接读写进程外部资源。理解计算函数，重点是看清楚输入数据和输出数据的特征边界。                               | 输入 `[1.0, 2.0]`，输出归一化后的 `[0.1, 0.2]` | 讲清：①<b>输入</b>是什么（对象类型 + shape/结构） ②<b>输出</b>是什么（对象类型 + shape/结构）或抛出什么异常。不直接读写进程外部资源。 |
| 内部状态更新函数 | 输入是 RAM 里的已有对象和新值；<br />输出不是一个全新的业务结果，而是 RAM 里已有对象的状态被更新。<br />它修改的是进程内部对象，例如 buffer、queue、cache。                          | 把最新 action `[0.1, -0.2]` 写入 `latest_action` | 讲清：①<b>修改了哪个内存对象</b>（变量名） ②<b>如何修改</b>（写入新值 / 追加到队列 / 替换缓存 / 累积计数器等） |
| 数据读写函数     | 输入通常是路径、topic、硬件句柄或待写出的数据；<br />输出是从进程外部读入的数据，或进程外部资源被写入后的结果。<br />它的边界特征是发生了文件、ROS topic、网络、硬件等进程边界交互。 | 输入路径 `config.yaml`，输出 RAM 里的配置字典 `{“control_hz”: 30}` | 讲清：①<b>从哪里读取数据</b>（文件路径 / ROS topic 名 / 硬件句柄） ②<b>读出了什么</b>（对象类型 + shape/结构），或<b>写入了哪个外部资源</b> |

## 第四层：变量

| 概念 | 当前理解 | 简单例子 |
|---|---|---|
| RAM 对象 | 当前 Python 进程中真正存在的数据实体；可以把它理解为“客观实在” | 一个 `DeployConfig` 实例、一个列表或一个字符串 |
| 变量名 | 代码中给 RAM 对象使用的名字，可以把它理解为对象的“标签”；变量名不是 RAM 地址本身 | `config`、`inference_service` |
| 引用 | 变量名或属性与 RAM 对象之间的连接关系；Python 负责管理底层实际地址 | `inference_service` 引用一个 `ActInferenceService` 实例 |
| 绑定 | 建立“名字指向对象”关系的过程；`=` 常用于完成绑定 | `action = [0.1, -0.2]` |
| 变量 | 一个在特定作用域内可见的名字，以及这个名字当前绑定的 RAM 对象；理解变量时仍需看对象的数据结构和内部数值类型 | `action` 绑定一个内部为 `float` 的列表对象 |
| 实例属性 | 通过 `self.属性名` 绑定在某个具体实例内部的名字 | `self._config` 是推理服务实例的内部属性 |
| 同一对象的多个标签 | 多个变量名、参数或实例属性可以同时引用同一个 RAM 对象；一次普通绑定通常不会复制对象 | `config` 和 `self._config` 可以引用同一个 `DeployConfig` 实例 |
| 作用域 | 描述一个变量名在哪些代码边界内可见、可使用；它描述的是名字的可见范围，不等于对象的生存范围 | 函数局部变量只在该函数内部可见 |
| 局部变量 | 在函数内部创建，只在该函数作用域内可直接使用的变量名 | `main()` 中的 `inference_service` |
| 名字—引用—对象关系 | 变量名通过引用连接到 RAM 对象；变量名不是对象，也不是底层地址本身 | `inference_service` → 引用 → RAM 中的 `ActInferenceService` 实例 |
| 多标签关系 | 不同作用域中的不同名字可以共同引用同一个对象 | `inference_service` 与 `worker._service` → 同一个 RAM 实例 |
| 作用域与对象寿命 | 变量名离开作用域后会变得不可见；只要仍有其他名字引用对象，对象就可以继续存在 | `main()` 的局部名字消失后，`worker._service` 仍可引用该实例 |

## 第五层：基本语法

### Python 函数头

| 语法单元 | 含义 |
|---|---|
| 完整结构 | `def 函数名(参数) -> 返回值类型:` |
| `def` | 开始定义一个函数 |
| `函数名` | 给函数绑定的名字，后续通过这个名字调用函数 |
| `(` `)` | 包围函数的参数列表；`)` 表示参数列表到此结束 |
| `参数名: 类型` | 参数类型标注，说明该参数预期接收什么类型的对象；例如 `policy: object` |
| `-> 返回值类型` | 返回值类型标注，用来说明函数预期返回什么类型；`-> None` 表示函数不返回业务结果 |
| `:` | 函数头结束；下一行开始进入函数体 |
| 向右缩进的代码 | 属于这个函数的函数体 |
| `"""..."""` | 文档字符串，写在 class 或函数内部，说明其用途、输入、输出或异常 |
| 多行写法 | 参数较多时，一个函数头可以拆成多行；`def say_hello(` 与 `) -> None:` 是同一个函数头的开头和结尾，不是两个并列语句 |
| 多行示例 | <code>def say_hello(<br>&nbsp;&nbsp;&nbsp;&nbsp;name,<br>) -> None:<br>&nbsp;&nbsp;&nbsp;&nbsp;print("你好", name)</code> |
| 单行等价写法 | `def say_hello(name) -> None:` 与上面的多行函数头含义相同 |

### `__init__()`、`self` 与实例属性

| 语法单元 | 含义 |
|---|---|
| 完整示例 | <code>class Person:<br>&nbsp;&nbsp;&nbsp;&nbsp;def __init__(self, name) -> None:<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;self.name = name</code> |
| `__init__` | Python 规定的特殊初始化函数；`init` 来自 initialize |
| 前后双下划线 `__` | 表示 Python 规定的特殊名称 |
| `self` | 当前正在被初始化或操作的具体实例 |
| `self.name` | 当前实例内部名为 `name` 的属性 |
| `self.name = name` | 把参数 `name` 当前引用的对象绑定给实例属性 `self.name` |
| 实例化表达式 | `person = Person("小明")` |
| 执行顺序 | Python 创建 `Person` 实例 → 自动调用 `__init__()` → `self` 指向新实例 → 参数 `name` 指向字符串“小明” → `self.name` 绑定同一个字符串对象 → `person` 绑定初始化完成的实例 |
| `__init__() -> None` | `__init__()` 负责修改当前实例的内部属性，不负责返回业务结果；严格名称是“初始化函数”，日常也常称“构造函数” |

### 属性绑定、内部方法加工与检查

| 写法 | 含义 |
|---|---|
| `self._config = config` | 把外部参数引用的对象直接绑定为实例属性，通常不复制对象 |
| `self._device = self._resolve_device()` | 先调用实例内部方法计算结果，再把结果绑定为 `_device` 属性 |
| `self._validate_contract()` | 只调用实例内部方法进行检查；因为没有 `=`，所以这行本身不创建新属性 |
| `__init__()` 常见顺序 | 外部 RAM 对象 → 绑定为实例属性 → 调用内部方法 → 计算派生属性或校验已有属性能否一起工作 |

### 内部属性、`@property` 与公开读取入口

| 语法单元 | 含义 |
|---|---|
| 内部保存示例 | `self._input_spec = input_spec` |
| 公开读取定义 | <code>@property<br>def input_spec(self) -> PolicyInputSpec:<br>&nbsp;&nbsp;&nbsp;&nbsp;return self._input_spec</code> |
| `_input_spec` | 实例内部真正保存对象引用的属性 |
| 下划线 `_` | 属性名以下划线开头，表示“供实例内部使用”；这是命名约定，不是绝对访问限制 |
| `@property` | 让外部使用 `service.input_spec` 读取，而不是调用 `service.input_spec()` |
| `return self._input_spec` | 返回内部属性当前引用的同一个对象，不复制、不重新推导 |
| 没有 setter | 外部不能通过 `service.input_spec = ...` 替换该公开属性；实例内部仍可管理 `_input_spec` |
| 保存与读取关系 | 第一步执行 `self._input_spec = input_spec` 保存对象引用；第二步通过 `service.input_spec` 读取同一个对象 |
| 读取边界 | 只有已经获得该实例引用的变量、参数或属性，才能通过公开入口读取数据；另一个文件即使导入 class 模板，也不会自动获得某次运行创建的具体实例 |
