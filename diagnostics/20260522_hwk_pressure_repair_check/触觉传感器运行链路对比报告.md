# 触觉传感器运行链路对比报告

生成时间：2026-05-22  
诊断目录：`/home/hit/ROS/diagnostics/20260522_hwk_pressure_repair_check`

## 1. 报告目的

本报告说明两件事：

1. 正常情况下，阶段一触觉传感器从硬件到 ROS topic 的运行链路应该怎样工作。
2. 本次维修后检测中，当前实际链路运行到了哪一步，在哪一层失败。

本报告只基于本次隔离诊断产物生成，不修改现有代码、配置、启动脚本或系统规则。

## 2. 正常运行链路

正常情况下，触觉传感器链路应按以下顺序贯通：

```text
4 路触觉传感器硬件
  -> 4 个 CH340 USB 串口设备枚举
  -> Linux 生成 /dev/ttyUSB*
  -> udev / by-path 提供稳定设备身份
  -> HWK 协议查询每个传感器的 HWK_CHIP_UID
  -> hardware_identity_map.yaml 将 UID 映射到逻辑夹爪与 topic
  -> pressure_driver_node 绑定 publisher
  -> 发布 4 路 /pressure/... topic
  -> start_all_sensor.sh 的 postlaunch 检查通过
  -> Octopus 可显示/录制触觉 topic
```

## 3. 正常链路分层说明

| 层级 | 正常表现 | 关键证据 |
|---|---|---|
| 硬件供电与连接 | 4 路触觉传感器均上电，USB 线、Hub、维修接头稳定 | 插拔后设备稳定存在，不反复断开 |
| USB 枚举 | `lsusb` 能看到 4 个 `1a86:7523 QinHeng Electronics CH340 serial converter` | `CH340 count: 4 / expected 4` |
| Linux 串口节点 | 系统生成 4 个 `/dev/ttyUSB*` 或 `/dev/ttyACM*` | `/dev/ttyUSB0` 到 `/dev/ttyUSB3` 或等价串口存在 |
| 稳定路径 | `/dev/serial/by-path/...` 或 `/dev/hwk_pressure_*` 可定位每个物理触觉设备 | 4 个预期 by-path 均为 `OK` |
| HWK 协议通信 | 每个串口能在 `460800` 波特率下返回 `HWK_CHIP_UID` | `result: OK`，并输出 `value: <UID>` |
| 身份映射 | 4 个 UID 与 `config/hardware_identity_map.yaml` 中的 `l1/l2/r1/r2` 对应 | `hardware_identity_scan.py validate` 返回 0 |
| ROS 驱动绑定 | `pressure_driver_node` 能打开串口、识别 UID、绑定 topic | 日志出现 `HWK identity detected` 和 `Bound HWK sensor by UID` |
| ROS topic 发布 | 4 路 topic 出现并持续有真实 `PressureFrame` 消息 | `ros2 topic list` 可见 4 路 topic，`ros2 topic echo --once` 成功 |

## 4. 正常情况下应出现的 4 路 topic

```text
/pressure/left_hand/gripper_1
/pressure/left_hand/gripper_2
/pressure/right_hand/gripper_1
/pressure/right_hand/gripper_2
```

这 4 路 topic 的来源不是固定 `/dev/ttyUSB0`、`/dev/ttyUSB1` 顺序，而是由 `HWK_CHIP_UID` 经过 `hardware_identity_map.yaml` 映射出来。也就是说：

- 串口路径只负责“找到设备并打开串口”。
- `HWK_CHIP_UID` 才负责“确定这是哪一个夹爪触觉传感器”。
- topic 名称来自身份映射表，而不是 USB 枚举顺序。

## 5. 当前实际运行链路

本次检测中，当前实际链路如下：

```text
触觉硬件接入
  -> 系统只枚举到 1 个 CH340
  -> 生成 /dev/ttyUSB1
  -> 生成 /dev/hwk_pressure_left_gripper_1 -> ttyUSB1
  -> 对 /dev/ttyUSB1 查询 HWK_CHIP_UID
  -> 查询超时，无 ACK
  -> hardware_identity_map.yaml 无法匹配任何目标传感器
  -> pressure_driver_node 无法绑定任何 publisher
  -> 节点退出
  -> 4 路 /pressure/... topic 全部缺失
```

## 7. 当前唯一可见设备

当前系统只看到一个 CH340 触觉候选串口：

```text

/dev/hwk_pressure_left_gripper_1 -> ttyUSB1
```

对应 by-path：

```text
/dev/serial/by-path/pci-0000:00:14.0-usb-0:2.4.3.2.2:1.0-port0 -> ../../ttyUSB1
```

对应 udev 属性显示：

```text

ID_PATH=pci-0000:00:14.0-usb-0:2.4.3.2.2:1.0

```

这说明这一路 USB 串口枚举层是存在的，但不代表触觉传感器协议通信正常。

## 8. 缺失的预期设备

当前缺失以下三个预期 by-path：

```text
/dev/serial/by-path/pci-0000:00:14.0-usb-0:2.4.3.2.4:1.0-port0
/dev/serial/by-path/pci-0000:00:14.0-usb-0:2.4.1.1:1.0-port0
/dev/serial/by-path/pci-0000:00:14.0-usb-0:2.4.4.2:1.0-port0
```

这表示至少 3 路触觉 USB 串口当前没有被系统稳定识别。

## 9. UID 查询结果

对当前唯一可见串口 `/dev/ttyUSB1` 执行 UID 查询：

```text
port: /dev/ttyUSB1
baudrate: 460800
addr: 6
package_id: 29
cmd: 0x05 (chip_uid)
request_hex: 3C 3C 61 75 01 00 05 C0 03 3E 3E
result: timeout/no matching ACK
```

判断：

- 串口设备能被打开。
- 查询命令能被发送。
- 但传感器侧没有返回符合 HWK 协议的 ACK。

这说明问题不只是“少了 3 个串口”，当前唯一枚举出来的这一路也没有完成触觉板通信。

## 10. ROS 驱动当前表现

`pressure_driver_node` 启动日志显示：

```text
Serial port opened: name=discovered_ttyUSB1_0, port=/dev/ttyUSB1
HWK identity query failed: serial=discovered_ttyUSB1_0, port=/dev/ttyUSB1, device_addr=6
RuntimeError: No HWK pressure sensors were bound to publishers.
```

这表示 ROS 驱动本身做了正确动作：

1. 找到了当前唯一串口 `/dev/ttyUSB1`。
2. 尝试查询该串口上的触觉传感器 UID。
3. 因为 UID 查询失败，所以无法判断它对应哪个夹爪。
4. 在严格身份映射模式下，驱动不发布假 topic、不发布空数据，而是退出。

因此，4 路 `/pressure/...` topic 缺失是硬件/协议通信失败后的结果，不是根因。

## 11. 内核日志线索

内核日志显示：

```text
10:08:19  ch341-uart converter now attached to ttyUSB0
10:08:20  ch341-uart converter now attached to ttyUSB1
10:12:32  ch341-uart converter now disconnected from ttyUSB0
```

判断：

- 至少有另一只 CH340 曾经短暂出现过。
- 它随后断开，说明某一路 USB 连接、Hub 分支、供电或维修接头可能不稳定。
- 当前最终只剩 `/dev/ttyUSB1`。

## 12. 当前故障定位

当前最可能的失败层级排序如下：

1. **USB/硬件枚举层**
   - 证据：只看到 1 个 CH340，期望是 4 个。
   - 影响：驱动根本没有机会访问另外 3 路传感器。

2. **触觉板协议通信层**
   - 证据：唯一可见 `/dev/ttyUSB1` 查询 UID 超时。
   - 影响：即使这一路 USB 串口存在，也无法绑定到任何逻辑 topic。

3. **udev 稳定命名层**
   - 证据：`/etc/udev/rules.d/99-hwk-pressure.rules` 与仓库规则不同。
   - 判断：这是后续需要处理的问题，但不是当前第一断点。因为设备还没有完整枚举，且唯一设备不返回 UID。

4. **ROS 启动链路**
   - 证据：节点能启动、能打开串口、能报出明确失败。
   - 判断：ROS 驱动行为符合预期，不是当前根因。

## 13. 为什么现在不应优先改代码

当前失败发生在 ROS 代码之前：

```text
缺少 USB 设备
  -> 无法查询 UID
  -> 无法身份映射
  -> 无法发布 topic
```

如果此时修改 `pressure_driver_node`、`pressure_sensors.yaml` 或 `start_all_sensor.sh`，大概率只会掩盖真实硬件故障，无法恢复触觉数据。

当前正确策略是先恢复硬件枚举和 HWK UID 响应。

## 14. 建议下一步排查顺序

### 第一步：恢复 4 个 CH340 枚举

先只关注：

```text
CH340 count: 4 / expected 4
```

建议检查：

- 4 路触觉传感器是否都上电。
- USB Hub 是否供电稳定。
- 维修过的接头是否虚焊、反接、接触不良。
- 当前断开的那一路是否与内核日志中的 `ttyUSB0` 对应。
- 插拔后是否会短暂出现又消失。

### 第二步：确认每个串口能返回 UID

恢复 4 个 CH340 后，再逐个确认：

```text
result: OK
value: <HWK_CHIP_UID>
```

如果某个串口仍然 `timeout/no matching ACK`，说明该路虽然 USB 转串口正常，但触觉板侧通信仍异常。

### 第三步：确认 UID 与映射表一致

四路 UID 都返回后，再运行身份映射校验，目标是：

```text
validation passed
```

这一步确认每个真实硬件 UID 都能映射到：

```text
left_gripper_1
left_gripper_2
right_gripper_1
right_gripper_2
```

### 第四步：再启动 `pressure_driver_node`

当 UID 校验通过后，再启动触觉 driver，正常日志应出现：

```text
HWK identity detected
Bound HWK sensor by UID
First valid pressure frame received
```

### 第五步：最后再运行全量 `start_all_sensor.sh`

触觉单独闭环通过后，再回到阶段一最终产物：

```bash
./start_all_sensor.sh
```

届时再验证 GoPro、Baton Mini、pressure 三类传感器的完整联动。

## 15. 一句话结论

正常链路应该是：4 个 CH340 稳定枚举，4 个 HWK UID 成功返回并匹配身份映射，`pressure_driver_node` 绑定 4 个 publisher，最终发布 4 路 `/pressure/...` topic。

当前链路是：只枚举到 1 个 CH340，且该串口 UID 查询无 ACK，导致身份映射失败、触觉 ROS 节点退出、4 路 pressure topic 全部缺失。

当前优先修复方向是硬件供电、USB/Hub 连接、维修接头和触觉板协议响应，不是修改 ROS 代码。
