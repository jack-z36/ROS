# 场景二目标描述：一键启动全部相机 ROS 节点

## 1. 核心目标

场景二的核心目标是：

```text
运行一个 .sh 脚本，由该脚本调用 ROS2 launch.py 文件，一键启动当前全部相机 ROS 节点。
```

当前需要启动的节点包括：

```text
1. 两个 Baton Mini 节点；
2. 两个 GoPro 节点。
```

后续还会继续加入：

```text
4 个传感器节点。
```

因此，本场景不只是临时启动 4 个相机节点，而是要形成一个可扩展的一键启动入口。

## 2. 目标运行方式

期望的使用方式是：

```bash
./start_all_sensor.sh
```

该脚本负责准备运行环境并调用总 launch 文件，例如：

```text
start_all_sensor.sh
    ↓
all_sensor_nodes.launch.py
    ↓
启动 Baton Mini / GoPro / 后续传感器节点
```

职责划分如下：

| 文件                   | 职责                                                      |
| ---------------------- | --------------------------------------------------------- |
| `.sh` 脚本           | 作为用户入口，负责 source 环境、执行必要检查、调用 launch |
| `launch.py` 文件     | 负责组织和启动多个 ROS2 节点                              |
| 配置文件或 launch 参数 | 负责保存设备参数、topic 名称、namespace 等可变配置        |

## 3. 解耦要求

后续 topic 名称还会继续调整，因此 topic 命名不能硬编码在启动脚本里。

本场景要求做到：

```text
启动入口与 topic 命名解耦；
节点启动逻辑与设备配置解耦；
后续修改 topic 名称时，不需要大改 .sh 脚本或重写整体 launch 结构。
```

优先采用的方式是：

```text
在 launch 参数、YAML 配置或独立配置文件中维护 topic / namespace / 设备参数；
.sh 脚本只负责调用；
launch.py 负责读取配置并启动节点。
```

也就是说，后续如果要改：

```text
/baton_mini_right/imu
/gopro_left/image
```

这类 topic 名称，应尽量只修改配置层，而不是修改一堆启动命令。

## 4. 成功标准

场景二完成时，应满足：

```text
1. 运行一个 .sh 脚本即可启动当前 4 个相机节点；
2. 两个 Baton Mini 节点和两个 GoPro 节点能同时运行；
3. ROS2 topic 名称清晰、互不冲突；
4. topic 名称后续可通过配置或 launch 参数集中修改；
5. 结构能继续扩展到后续 4 个传感器节点；
6. Octopus 能看到目标 topic，并可用于后续 MCAP 录制。
```

## 5. 与最终采集链路的关系

场景二服务于 FASTUMI 数据采集链路：

```text
一键启动全部相机 / 传感器 ROS 节点
    ↓
稳定发布 ROS2 topic
    ↓
Octopus 选择并录制目标 topic
    ↓
输出 MCAP 文件
    ↓
进入后续 FASTUMI 数据处理流程
```

## 6. 一句话总结

场景二要实现的是：通过一个 `.sh` 用户入口调用总 `launch.py`，一键启动当前 2 个 Baton Mini 和 2 个 GoPro 节点，并把 topic 命名、设备参数和启动入口解耦，方便后续继续修改 topic 名称和增加 4 个传感器节点。
