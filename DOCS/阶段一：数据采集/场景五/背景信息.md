## 2. 为什么需要本场景

当前系统已经能通过配置启动 8 个目标 topic，但设备路径仍带有明显的硬件接入顺序和 USB 拓扑依赖。

当前例子：

- GoPro 使用 `/dev/v4l/by-path/...video-index0` 形式的路径；
- 触觉传感器部分使用 `/dev/hwk_pressure_left_gripper_1` 这类 udev symlink，部分仍使用 `/dev/serial/by-path/...`；
- udev 规则当前基于 `ID_PATH`、vendor id 和 model id；
- `ID_PATH` 能稳定某个 USB 插口路径，但不能天然代表“这台真实传感器就是 l1 / l2 / r1 / r2”。

用户希望更进一步：不管怎么接入相机和触觉传感器，都能先识别硬件自身信息，再映射为规定设备名称和规定 topic 名称。

## 4. 触觉传感器映射背景

用户给出的现实编码是：

```text
l1：左手第 1 台触觉传感器
l2：左手第 2 台触觉传感器
r1：右手第 1 台触觉传感器
r2：右手第 2 台触觉传感器
```

当前触觉驱动通过 `pressure_sensors.yaml` 配置串口、传感器地址、hand、gripper 和 topic。

当前四路目标 topic 为：

| 现实编码 | 当前 logical 配置 | topic |
| --- | --- | --- |
| `l1` | `left_hand/gripper_1` | `/pressure/left_hand/gripper_1` |
| `l2` | `left_hand/gripper_2` | `/pressure/left_hand/gripper_2` |
| `r1` | `right_hand/gripper_1` | `/pressure/right_hand/gripper_1` |
| `r2` | `right_hand/gripper_2` | `/pressure/right_hand/gripper_2` |

当前已知触觉设备使用 CH340 串口芯片，udev 规则中 vendor / model 为：

```text
ID_VENDOR_ID=1a86
ID_MODEL_ID=7523
```

关键未知项：

- 每个 CH340 转串口设备是否暴露唯一 `ID_SERIAL` 或等价硬件序列号；
- 触觉传感器协议本身是否能读出设备唯一序列号；
- 如果四个 CH340 没有唯一序列号，只靠 vendor / model 无法区分 l1、l2、r1、r2；
- 当前 `device_addr` 在四个独立串口上都可以相同，不能单独作为跨串口唯一身份。

因此场景五需要先实测硬件身份来源，再决定是用硬件序列号、协议内身份、还是一次性人工标定生成映射表。

用户补充的协议内身份查询方式：

```text
CHANNEL=0x01
GET FLAGS 低 2 位 = 0x01
ACK FLAGS 低 2 位 = 0x03
CMD=0x01 查询应用版本号
CMD=0x05 查询芯片 UID / 序列号
CMD=0x06 查询设备地址
```

该协议已用于新增脚本 `/home/hit/ROS/scripts/hwk_query_device_info.py`。当前实测中，已接入的 `r1` 能响应设备信息通道 `CHANNEL=0x01` 的 `CMD=0x05`，返回 UID：

```text
00600012-3035510B-3735333
```

注意：用户文档描述 ACK 低 2 位为 `0x03`，但当前 `r1` 固件实测设备信息响应低 2 位为 `0x02`。脚本已兼容 `0x02` 和 `0x03` 两种设备信息响应类型。

## 5. GoPro 采集卡映射背景

GoPro 侧实际被 Linux 看到的是 HDMI 采集卡对应的 V4L2 设备，而不是 GoPro 本体。

当前 GoPro 配置在 `/home/hit/ROS/config/all_sensor_nodes.yaml` 中记录：

| 逻辑侧 | 当前设备字段 | 目标 topic |
| --- | --- | --- |
| right | `video_device` | `/gopro_right/image_raw` |
| left | `video_device` | `/gopro_left/image_raw` |

当前 `gopro_camera_launch` 通过 `video_device` 启动 `v4l2_camera_node`，再由 namespace 和 topic 设置输出固定 topic。

需要重点确认的硬件身份来源包括：

```text
udevadm info -q property -n /dev/videoX
v4l2-ctl --list-devices
/dev/v4l/by-id/
/dev/v4l/by-path/
```

优先级应是硬件自身可识别信息高于 USB 插口路径。只有当采集卡没有唯一硬件身份时，才把 by-path 作为临时 fallback，并在文档中标记风险。

## 6. 建议的映射层

场景五后续实现时，建议把“硬件身份映射表”和“节点运行配置”分清楚。

建议职责划分：

| 层级 | 作用 |
| --- | --- |
| 硬件身份扫描 | 枚举 `/dev/video*`、`/dev/ttyUSB*`、`/dev/serial/*` 并读取 udev / V4L2 / 协议内信息。 |
| 映射表 | 记录硬件唯一身份到现实编码，如 `l1`、`l2`、`r1`、`r2`、`gopro_left`、`gopro_right`。 |
| 运行配置生成 | 根据映射表生成当前启动需要的 `video_device`、串口 `port`、node name 和 topic。 |
| 启动前检查 | 在节点启动前验证所有 required 逻辑设备都已识别，且没有重复或缺失。 |
| ROS 节点启动 | 只消费已经解析好的稳定配置，不在节点内部猜测左右手身份。 |

映射表已建立模板：

```text
/home/hit/ROS/config/hardware_identity_map.yaml
```

该模板目前记录 `l1`、`l2`、`r1`、`r2`、`gopro_left`、`gopro_right` 的目标 topic 和配置归属。`pressure.r1` 已绑定协议内 `HWK_CHIP_UID`，`gopro.right` 暂时绑定 USB 拓扑 `ID_PATH`；其余设备仍需在目标硬件接入后，通过扫描结果填入可唯一识别设备的字段。

## 7. 与 Octopus 的关系

场景五不直接修改 Octopus，但它影响 Octopus 能否稳定看到同一批 topic。

Octopus 和 MCAP 侧应继续只关心固定 topic：

```text

/gopro_left/image_raw
/pressure/left_hand/gripper_1
```

硬件如何插入、如何被 Linux 枚举、如何映射为这些固定 topic，应由场景五解决。

## 8. 当前风险和未知项

已知风险：

- 多个同型号 CH340 设备可能没有唯一序列号。
- 多个同型号 HDMI 采集卡也可能没有唯一序列号。
- `/dev/videoX`、`/dev/ttyUSBX` 绝不能作为稳定身份。
- `/dev/serial/by-path` 和 `/dev/v4l/by-path` 依赖 USB 插口和拓扑，不等同于真实设备身份。
- 如果无法从硬件自动识别真实编码，系统必须要求人工标定，不能静默猜测。

待验证：

- 四个触觉传感器或其串口转换器是否有可用 `ID_SERIAL`。
- 触觉协议是否支持读取设备序列号或可配置编码。
- 两个 GoPro 采集卡是否有不同的 `ID_SERIAL`、`ID_SERIAL_SHORT`、`ID_MODEL` 或 V4L2 card name。
- 当前系统是否存在 `/dev/v4l/by-id` 和 `/dev/serial/by-id` 可用稳定链接。
- 是否需要新增一个硬件扫描 / 映射生成脚本，并在 `start_all_sensor.sh` 启动前调用。
