# Pi0.5 源码 3.5 层微元拆解：L2-03

> [!info] 说明
> - Pi0.5 源码只作为结构参考，不覆盖当前 ACT L2-03 边界。
> - 本文目标：讲清 Pi0.5 部署代码中与 L2-03（ObservationSnapshot→ActionChunk 推理）对应的功能模块**是如何运作的**。
> - 第一版已去除独立 action smoothing L2；Pi0.5 中 `control_loop.py` 的 `smoothstep_alpha`、`_blend_next_action`、`blend_steps` 平滑逻辑**不进入本 L2 设计**（这些归 L2-06，且第一版整体不做平滑）。
> - 路径基于实际源码树（src-layout），文件位于 `pi05_test/pi05/<deploy|common>/src/pi05/...`。

## 0. L2-03 对应 Pi0.5 的哪一部分

L2-03 的运行时职责是「把 `ObservationSnapshot` 加工成 batch，调用 policy 推理，输出 `ActionChunk`」。Pi0.5 部署代码中完成同一件事的功能模块是**推理链路**，分布在两个包：

| Pi0.5 文件（真实路径） | 对应 L2-03 的哪部分 |
|---|---|
| `deploy/src/pi05/deploy/models/policy_loader.py` | policy runtime 加载 + 统一推理接口 `predict_action_chunk`（repo + service 层） |
| `deploy/src/pi05/deploy/runtime/inference_worker.py` | 后台推理 actor：消费 request→推理→写 result + metrics（runtime 层） |
| `deploy/src/pi05/deploy/runtime/shared_buffer.py` | `ActionChunk`/`InferenceRequest`/`ObservationSnapshot`/`SharedBuffer`/`LatestQueue`/`RuntimeMetrics` 数据结构（runtime 层） |
| `common/src/pi05/common/data/normalization.py` | `ActionStateNormalizer`（state normalize / action unnormalize，service 层使用） |
| `common/src/pi05/common/runtime/bundle.py` | bundle/normalizer 读取（repo 层，L2-01 已设计，本 L2 复用） |
| `common/src/pi05/common/model/builder.py` | Pi0.5 模型构建 + action projection resize（repo 层参考） |
| `deploy/src/pi05/deploy/runtime/control_loop.py` | **仅参考其消费 chunk 的部分**；其中的 `smoothstep_alpha`/`_blend_next_action`/`blend_steps` 平滑逻辑**不继承** |

> [!important] 维度差异（决定不能照搬）
> Pi0.5 是 **26D state / 14D action**（`ARM_DOF=6`、`HAND_DOF=1`，关节角表示），`DEFAULT_STATE_DIM=26`、`DEFAULT_ACTION_DIM=14`，且 `action_dim` 被死锁为 14（`builder.py` 第 68-69 行强制校验）。
> ACT 第一版是 **16D state / 16D action**（TCP pose 7D + gripper width 1D，左右各一组）。
> 因此 Pi0.5 的维度常量、normalizer 长度、action projection resize 都只能作为结构参考，数值必须重写。

> [!important] 模型框架差异（决定不能照搬）
> Pi0.5 是 **VLA（PaliGemma + Gemma expert + LoRA）**，用 `PI05Policy.predict_action_chunk` 推理，preprocessor 用 `make_pi05_pre_post_processors`。
> ACT 是 **Transformer-based CVAE action chunking 模型**（LeRobot `lerobot.policies.act`）。
> 两者模型类、preprocessor、batch key 完全不同。Pi0.5 的 `Pi05PolicyRuntime` 封装思路（持有 model/policy/preprocessor/normalizer/device）可结构复用，但内部调用必须替换为 ACT。

## 0.5 给计算机小白的白话开场

如果你不熟悉模型推理术语，先读这段，再往下看。

L2-03 这部分代码做的事，可以用一句话概括：**像一个"后台厨师"——前面（L2-06）下单说"这盘观测数据给我做成一批动作"，厨师就在后台默默把食材（snapshot）处理成模型能吃的样子（batch），喂给模型（policy），等模型吐出一串动作（action chunk），再装盘递回前面（result queue）。** 全程不卡住前台（control tick），因为厨师在独立的后厨（后台线程）干活。

理解下面几个词就够了（用《用户认知框架与讲解偏好.md》的概念体系解释）：

| 术语 | 白话解释 |
|---|---|
| **ObservationSnapshot** | "一盘刚拍好的食材"——某一瞬间所有传感器数据（图像 + 状态）冻结成一个完整对象。由 L2-02 准备好放那儿，本 L2 只负责拿来做菜。 |
| **batch** | "模型能吃的标准化摆盘"。模型不直接吃原始 snapshot，要先把 state 归一化到 [-1,1]、把图像整理成指定格式、贴上标签（task）。这一步是纯 RAM 内的数据变换（认知框架第 3.5 层"计算函数"）。 |
| **policy**（策略模型） | "厨师的大脑"——一个训练好的神经网络。给它一盘标准化的观测，它就预测接下来应该怎么动。本 L2 不训练它，只调用它。 |
| **predict_action_chunk** | "厨师做一次菜"——调用模型一次，产出一串动作（不是单个动作）。比如一次产出 chunk_size=30 步连续动作。 |
| **normalize / unnormalize** | 模型只认 [-1,1] 区间的数。**normalize** 是把传感器原始物理值"压"到 [-1,1]（推理前做）；**unnormalize** 是把模型输出的 [-1,1] 值"还原"回物理尺度（推理后做）。两个方向都要做，否则动作幅度全错。 |
| **InferenceWorker**（推理工人） | 一个在后台不停转的线程。它的循环很简单：看队列里有没有新订单（request）→ 有就拿去做（推理）→ 做好放结果队列（chunk）→ 继续看。它和前台（ControlLoop）通过两个队列通信，互不阻塞。 |
| **latest-only queue**（只留最新的队列） | 一个特殊的队列：新订单来了，旧的直接扔掉。因为推理要低延迟，过时的观测做了也没意义。 |
| **fake-policy**（假模型） | 一个"假装是模型"的替身——不加载真实权重，直接返回一个 shape 正确的假动作块。它存在的唯一目的：在没有 GPU / 没有真实 bundle 时，也能验证"从下单到出菜"整条链路是否通。 |
| **async 解耦** | "前台点完单就能去干别的，不用等厨师做完"。control tick 每 1/30 秒跑一次，不能卡在等模型（可能要几十毫秒）。所以推理放后台线程，前台只管下单和取菜。 |

### 一次推理走完全流程的例子

假设 L2-06 在 tick 时决定要新 chunk，它创建一个 `InferenceRequest`（带着当前 snapshot），丢进 `inference_request_queue`。跟着这个 request 走一遍：

```text
① L2-06 创建 request（含 snapshot、obs_time、request_id）  [L2-06 职责]
② request 写入 inference_request_queue（latest-only，旧的被丢）  [队列 · 内部状态更新]
③ InferenceWorker 后台线程循环 get_latest_or_none()  → 拿到 request  [编排函数 · 后台线程]
④ 按 inference_hz 限速（避免空转过载）  [编排函数]
⑤ policy_runtime.predict_action_chunk(request.observation)  [编排函数 · 调核心推理]
   5a. _build_batch: state normalizer.normalize(encoded_state) → batch  [计算函数 · RAM 内]
   5b. preprocessor(batch): LeRobot processor 处理 batch  [计算函数 · RAM 内]
   5c. batch move to device (cuda)  [内部状态更新 · 跨设备]
   5d. policy.predict_action_chunk(batch) → norm_chunk [−1,1]  [数据读写函数 · GPU 推理]
   5e. norm_chunk.cpu() + clamp(−1,1)  [计算函数 · RAM 内]
   5f. action_normalizer.unnormalize(norm_chunk) → 物理尺度 chunk  [计算函数 · RAM 内]
   5g. 校验 shape[1]==16, 截断到 output_chunk_size  [计算函数 · RAM 内]
⑥ 构造 ActionChunk（含 obs_time/infer_start/ready_time/action_dt/request_id）  [数据]
⑦ 写入 chunk_result_queue + record metrics（latency/count）  [内部状态更新函数]
⑧ L2-06 下一个 tick 从 result_queue 收集 chunk  [L2-06 职责]
```

如果第 ⑤ 步模型抛异常：`InferenceWorker._run_request` 用 `try/except` 捕获 → `record_inference_error(message)` → 继续下一个 request，不崩溃。这就是"推理失败记录 inference_error，L2-06 继续 hold/safe_stop"。

## 1. 运行机制：Pi0.5 这部分是怎么运作的

L2-03 对应的 Pi0.5 代码有两个核心入口：

### 1.1 启动期：加载 policy runtime（`policy_loader.py`）

```text
load_policy_runtime(config: DeployConfig) -> Pi05PolicyRuntime
  1. 校验 multi_gpu_strategy == "none"（第一版不支持模型分片）  [计算函数]
  2. _validate_bundle(bundle_dir): 检查 manifest/normalizers/experiment_config 存在  [数据读写函数]
  3. load_bundle_manifest(bundle_dir)  [数据读写函数 · 复用 L2-01]
  4. _load_bundle_experiment_config: 加载 + 覆写 device/dtype/chunk/dim  [数据读写函数 + 计算]
  5. build_pi05_with_lora: 构建 Pi0.5 模型 + LoRA  [数据读写函数 · 加载权重]
  6. _load_adapter: 加载 LoRA adapter 权重  [数据读写函数]
  7. model.to(device) + model.eval()  [内部状态更新]
  8. _configure_cuda_runtime: flash SDP 等优化  [内部状态更新]
  9. _resolve_policy: 从 PEFT 包裹层找到 predict_action_chunk  [计算函数]
  10. make_pi05_pre_post_processors: 构建 LeRobot processor  [计算函数]
  11. load_bundle_normalizers: 加载 state/action normalizer  [数据读写函数 · 复用 L2-01]
  12. _manifest_image_names: 从 manifest 取相机名  [计算函数]
  13. 构造 Pi05PolicyRuntime(...) 并返回  [数据]
```

### 1.2 稳态推理：predict_action_chunk（`Pi05PolicyRuntime.predict_action_chunk`）

```text
predict_action_chunk(observation) -> np.ndarray (chunk_size, 14)
  1. batch = self.preprocessor(self._build_batch(observation))  [计算函数]
  2. batch = _move_tensors_to_device(batch, device)  [内部状态更新 · 跨设备]
  3. with torch.inference_mode(): norm_chunk = self._predict_fn(batch)  [数据读写函数 · GPU]
  4. norm_chunk = norm_chunk.detach().cpu().float()[0]  [内部状态更新]
  5. if clamp_normalized_action: norm_chunk.clamp_(-1, 1)  [计算函数]
  6. action_chunk = action_normalizer.unnormalize(norm_chunk).numpy()  [计算函数]
  7. 校验 shape[1]==action_dim → 否则 ValueError  [计算函数]
  8. return action_chunk[:output_chunk_size]  [计算函数]
```

`_build_batch` 内部：`state_normalizer.normalize(encoded_state)` → 拼 `observation.state`/`task`/`observation.images.*`（CPU float tensor）。

### 1.3 后台调度：InferenceWorker（`inference_worker.py`）

```text
InferenceWorker(threading.Thread).run()  [编排函数 · 后台线程]
  while not _stop_event.is_set():
    1. request = request_queue.get_latest_or_none()  [内部状态更新函数]
    2. if request is None: wait 0.001s, continue  [编排函数]
    3. 按 inference_hz 限速: remaining = period_s - (now - last_start)  [编排函数]
    4. if remaining > 0: wait, continue  [编排函数]
    5. self._run_request(request)

_run_request(request)  [编排函数]
  1. infer_start = time.monotonic()
  2. try: actions = policy_runtime.predict_action_chunk(request.observation)
     except: record_inference_error + log + return  [失败传播]
  3. chunk = ActionChunk(actions, obs_time, infer_start, ready_time, action_dt, request_id)
  4. record_inference_latency(ready_time - infer_start)  [内部状态更新函数]
  5. record_chunk_result()  [内部状态更新函数]
  6. result_queue.put_latest(chunk)  [内部状态更新函数]
```

关键协作关系：

- **谁持有状态**：`Pi05PolicyRuntime`（持有 model/policy/preprocessor/normalizer/device，启动期创建后稳定）；`InferenceWorker`（持有 `_stop_event`、`_last_infer_start_s`、`period_s`、`action_dt`，后台线程生命周期）；`SharedBuffer.metrics`（全局计数器，锁保护）。
- **谁调用谁**：`InferenceWorker._run_request` 调 `policy_runtime.predict_action_chunk`；后者调 `_build_batch` + `preprocessor` + `_predict_fn` + `unnormalize`。
- **谁只负责加工 RAM 对象**：`_build_batch`、`normalize`/`unnormalize`、`clamp`、shape 校验、`_move_tensors_to_device`（device 内移动）。
- **谁跨越外部边界**：`policy.predict_action_chunk`（跨进程边界到 GPU 计算）；`load_*` 系列（启动期跨文件边界读 bundle，复用 L2-01）。稳态推理中，GPU 计算是一次跨"进程-设备"边界的读写。
- **谁负责 runtime 时序或失败处理**：`InferenceWorker.run`（后台循环、限速、停止）；失败用 `try/except` 捕获并 `record_inference_error`，不崩溃。

## 4. class 封装盘点

| class | 源码路径 | 封装了哪些 3.5 层微元 | 内部状态 | 生命周期 / 并发特征 | 为什么适合 class | ACT 中的处理建议 |
| --- | --- | --- | --- | --- | --- | --- |
| `Pi05PolicyRuntime` | `models/policy_loader.py` | 数据 + 计算函数 + 编排函数（predict/build_batch） | model/policy/preprocessor/normalizer/device/task/action_dim/chunk_size/image_names/_predict_fn | 启动期创建一次，稳态被 InferenceWorker 串行调用，无并发（单后台线程） | 持有大量稳定状态（模型权重、normalizer），多次调用 predict 共享这些状态 | 结构复用为 `ActPolicyRuntime`（替换模型为 ACT） |
| `InferenceWorker` | `runtime/inference_worker.py` | 编排函数 + 内部状态更新函数（run/_run_request/stop） | _stop_event/_last_infer_start_s/period_s/action_dt/queues/policy_runtime | 后台 daemon 线程，独立生命周期，与 ControlLoop 并行 | 需要线程生命周期 + 持有 queue 句柄 + 限速状态 | 直接复用 |
| `ActionChunk` | `runtime/shared_buffer.py` | 数据 + 计算函数（aligned_index） | actions/obs_time/infer_start_time/ready_time/action_dt/request_id/cursor | frozen，单次创建，被多个消费者只读 | 聚合多个字段的值对象，frozen 保证不变 | 直接复用（14→16） |
| `InferenceRequest` | `runtime/shared_buffer.py` | 数据 | observation/obs_time/request_id/trigger_step | frozen，单次创建 | 值对象，frozen | 直接复用 |
| `ObservationSnapshot` | `runtime/shared_buffer.py` | 数据 | images/state/encoded_state/captured_at_s | frozen，单次创建 | 值对象，frozen | 直接复用（L2-02 也持有） |
| `LatestQueue` | `runtime/shared_buffer.py` | 内部状态更新函数 + 数据 | _items(deque)/_lock | 长生命周期，多线程读写 | 需要 deque + 锁保证线程安全 | 直接复用 |
| `SharedBuffer` | `runtime/shared_buffer.py` | 数据 + 内部状态更新函数 | _latest_observation/queues/metrics/_lock | 长生命周期，多线程读写 | 聚合跨模块共享状态 + 锁 | 直接复用 |
| `RuntimeMetrics` | `runtime/shared_buffer.py` | 数据 + 计算函数 | 各计数器/latency EMA/last_error | 长生命周期 | 计数器集合 + EMA 计算 | 直接复用 |
| `ActionStateNormalizer` | `data/normalization.py` | 数据 + 计算函数（normalize/unnormalize） | min_vals/max_vals/range_vals/non_zero_mask/identity_mask/vector_dim | bundle 加载后稳定持有 | 持有归一化参数，多次调用 | 直接复用（长度 16） |

> 其余函数（`load_policy_runtime`、`_validate_bundle`、`_build_batch`、`_move_tensors_to_device`、`_resolve_policy` 等）**只做纯转换、单次读盘或无状态编排**，按判断原则应优先**函数**，不封装为 class。其中 `load_policy_runtime` 虽是编排函数，但无内部状态，返回 `ActPolicyRuntime` 对象即可。

## 5. 禁止继承的 Pi0.5 行为

- 不继承 Pi0.5 的 26D/14D 旧维度作为 ACT 当前 16D/16D 维度。
- 不继承 Pi0.5 的 `PI05Policy`/`make_pi05_pre_post_processors`/`build_pi05_with_lora` 作为 ACT 模型构建方式；ACT 用 LeRobot ACT 实现。
- 不继承 `control_loop.py` 的 `smoothstep_alpha`、`_blend_next_action`、`blend_steps`、`_start_blend_or_switch` 平滑逻辑作为本 L2 或第一版能力。
- 不继承 Pi0.5 的 `blend_steps=3` 配置字段。
- 不把 `_blend_next_action`（跨 chunk 加权融合）塞进 `InferenceWorker` 或 `predict_action_chunk`。
- 不在 `predict_action_chunk` 内部做单步选择或 cursor 推进（那是 L2-06 的事）。
- 不在 `InferenceWorker` 内部决定何时提交推理请求（那是 L2-06 的事；worker 只被动消费 queue）。
