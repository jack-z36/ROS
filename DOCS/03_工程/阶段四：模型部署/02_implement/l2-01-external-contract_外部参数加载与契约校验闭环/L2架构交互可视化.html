这一节用白话讲。每个专业术语第一次出现时都会解释，点开"术语词典"可以随时查。看不懂任何一步，回到「术语词典」对一下就行。

① 这部分代码整体在干什么（一句话）

把一个写满运行参数的 deploy.yaml 文件（人写、人能读的文本），变成程序内存里一个"只读、不会变、随时可查"的配置对象——就像把一份纸质表格誊抄进一块刻好的石碑：誊抄时逐栏检查有没有填错，刻完之后谁都改不动，后面所有人只能读、不能改。

这一步在程序刚启动时只做一次，做完就不再碰。后面所有模块（L2-02 ~ L2-06）都从这块"石碑"上读参数，不会再去翻原始文件，也不用自己判断参数对不对。

📖 术语词典（点开随时查，用《用户认知框架与讲解偏好》的概念体系解释）
yaml 文件对应认知框架第 3.5 层"数据"（写在文件里的）。一个用缩进表示层级的文本文件，里面写满 键: 值，比如 control_hz: 30。人能直接读，程序也能读。这里它就是那张"纸质表格"。
raw mapping
（原始映射）		对应认知框架第 3.5 层"数据读写函数"的产物。程序把 yaml 文件读进内存后，得到的"一整坨还没检查过的键值对"。它还没有任何类型保证——control_hz 可能是数字 30，也可能是手误写成字符串 "三十"。
校验
（validate）		对应认知框架第 3.5 层"计算函数"（输入输出都在 RAM 内）。检查每个值是不是"该有的样子"：该是数字的是不是数字、是不是正数、是不是在允许的选项里。查出一个错就立刻报错停下。
类型化校验器
（typed validator）		对应认知框架第 3.5 层"计算函数"。一个个"专门检查某一类值"的小函数。比如 _positive_float 专门负责"必须是正的小数"，_choice 专门负责"必须是这几个选项之一"。
typed 值
（类型确定的值）		对应认知框架第 4 层"变量"。经过校验器检查通过后的值。程序拿到它时已确定它是某种类型（比如确定是正小数），后面不用再担心它变成别的东西。
dataclass对应认知框架第 3.25 层"class 打包函数"。一种"带固定字段的容器"，像一张预先印好栏位的卡片，每个栏位有名字。RuntimeConfig 就是这样一张卡片。
frozen dataclass
（冻结的 dataclass）		对应认知框架第 3.25 层"class"。一张"刻了就不能改"的卡片。一旦把值填进去，谁都不能再改它的字段。L2-01 要的效果——配置进内存后就锁死。
__post_init__对应认知框架第 3.5 层"计算函数"。dataclass 卡片填完值之后自动触发的一段检查代码。它检查字段之间的关系，比如"execute_horizon 不能大于 chunk_size"。
bundle
（模型包）		训练好的模型导出成一个目录，里面装着权重、清单、归一化参数等文件。部署程序不重新训练，只读这个包。
manifest.json
（清单）		bundle 目录里的一个文件，像快递箱上的发货单，写清楚这个包里有什么、维度是多少、什么时候打的包。
normalizers.json
（归一化参数）		bundle 里的另一个文件，记录怎样把传感器原始数值"压"到 [-1, 1] 区间（模型只认这个区间的输入）。
抛异常 / 报错中止程序发现配置不对时，不假装没事继续跑，而是当场报错退出。这比"带着错误配置勉强运行"安全得多。

② 整体流程：四个步骤

Pi0.5 这部分代码按严格顺序执行，只做一次。任一步出错，程序立刻停下，不会带着错误配置继续。

1

读入

把硬盘上的 deploy.yaml 读进内存，得到一坨"还没检查的键值对"（raw mapping）。跨进程边界：从硬盘到内存。
2

装配

按固定顺序逐个字段处理：bundle → runtime → image → topics → safety → bridge → mux。每个字段过对应校验器，得到"确定类型"的值。
3

关系校验

卡片填完后自动检查字段之间关系：hz>0？horizon≤chunk？不满足就报错中止。不会进入半初始化状态。
4

冻结

所有检查通过 → 装进 DeployConfig 这张"刻了不能改"的卡片 → 后续所有模块 import 它就能用，谁也改不动。

③ 跟一个配置项走完全流程

以 runtime: control_hz: 30 为例，看它怎么从 yaml 文本变成冻结的配置。这是理解整个机制最快的方式。

# deploy.yaml 里写着： # runtime: # control_hz: 30 ① # 程序把文件读进内存（数据读写函数，从硬盘到 RAM） raw = {"runtime": {"control_hz": 30}, ...} # raw mapping，还没检查 ② # 把 control_hz 交给校验器（计算函数，纯 RAM 内） control_hz = _positive_float(raw, "control_hz", default=30.0) # → 30 是数字 ✓、30 > 0 ✓ → 返回 typed 值 30.0 ③ # 填进 RuntimeConfig 卡片，卡片填完自动检查字段关系 runtime = RuntimeConfig(control_hz=30.0, ...) # → __post_init__ 检查: control_hz > 0 ? 通过 ✓ ④ # 装进 DeployConfig 并冻结，全生命周期只读 deploy_config.runtime.control_hz → 永远 30.0，谁也改不了 # ── 如果手误写成 control_hz: "abc" 会怎样？ ②' # _positive_float 尝试 float("abc") → 失败 raise DeployConfigError("control_hz must be a float") # 程序当场报错退出，不进入③④。这就是"非法配置在入口处失败"。

④ deploy.yaml 里写了什么

Pi0.5 的配置文件分七个段落，程序按固定顺序逐段读取、逐个字段校验。ACT 第一版只保留前五段，bridge 和 mux 去掉。

ACT 保留（5 段）

① bundle — 模型包放在哪个目录。必填，缺失直接报错。
② runtime — 控制频率、推理频率、chunk 大小、fallback 策略。关系校验最密集。
③ image — 图像尺寸、缩放方式、传输格式。
④ topics — 所有 ROS 话题名（订阅哪些、发布哪些）。
⑤ safety — 单步位移上限、夹爪值域。只定义参数，不执行检查。

ACT 去掉（2 段）

⑥ bridge — 适配老执行栈的转发开关。
⑦ mux — 遥操作 / VLA 命令复用器。

除此之外，Pi0.5 有 blend_steps: 3（平滑步数），ACT 第一版也删掉——因为不做平滑。

⑤ 模型包（bundle）里有什么

除了 yaml，程序还要读模型包目录（训练完成后导出，部署时只读不改）。Pi0.5 用三个函数各读一样：

pi05_pour_water_v1/ ← bundle_dir 指向这里 ├── manifest.json ← 清单：维度、模型信息、打包时间 ├── normalizers.json ← 归一化参数：state/action 的最大最小值 ├── experiment_config.yaml ← 训练配置（只读原值，做交叉校验） └── adapter/ ← 模型权重目录（后续 L2-03 加载，本 L2 只检查它存在）

三个读取函数 — load_bundle_manifest 读清单、load_bundle_normalizers 读归一化参数、resolve_bundle_adapter_dir 检查权重目录。读到的维度信息交 config 层做交叉校验。

⑥ 回答四个核心问题（谁持有状态、谁跨边界、谁加工、谁管时序）

❶ 谁持有状态？

两个对象持有"会长期存在"的状态：

  • DeployConfig：启动期创建一次，冻结，全生命周期只读。
  • ActionStateNormalizer：bundle 加载后稳定持有 min/max/range/identity_mask。

（除此之外没有 buffer、queue、cache 等会变化的状态）

❷ 谁跨越外部边界？

四个函数只读不写：

  • yaml.safe_load（读 yaml）
  • load_bundle_manifest（读 manifest）
  • load_bundle_normalizers（读 normalizers）
  • resolve_bundle_adapter_dir（检查目录）

本 L2 不写任何外部文件、不订阅任何 topic。

❸ 谁只负责加工 RAM 对象？

  • 类型化校验器（_str/_choice/_positive_float 等）
  • __post_init__ 关系校验
  • normalize/unnormalize（min-max 数值变换）

这些都是"输入在内存、输出也在内存"的纯计算。

❹ 谁负责 runtime 时序？

答：无。

这部分代码启动期同步调用一次就结束，不进入稳态 tick。失败方式只有"抛异常阻止启动"，没有 fallback、没有重试、没有并发。时序调度是 L2-06 的事。

校验器函数群（无 class，纯函数）

Pi0.5 校验器群结构复用。每个函数只做一类值的检查。

计算函数_positive_float(raw, key, default) — 输入 raw dict + 字段名str + 默认值float → 输出 正float值 或 DeployConfigError；_choice(raw, key, choices, default) — 输入 raw dict + 字段名 + 允许值set + 默认值 → 输出 str 或 DeployConfigError

文件：schema.py。配置实例：config_files/deploy.yaml。验收覆盖：合法 mapping 构造成功、缺字段/非法 hz/非法 mode/维度非 16 抛异常、rg 检查无平滑字段。
参考 Pi0.5：deploy/config/schema.py（去掉 bridge/mux 段 + blend_steps）。

repo/ · 外部资源读取层（4 个文件，全是函数，无 class）

这一层只做路径、文件存在性、格式读取，不做业务维度校验（业务校验交 config 层）。全是跨进程边界读取（从硬盘到内存）。Pi0.5 参考：common/runtime/bundle.py。

数据读写resolve_bundle_dir(bundle_dir) — 从 {bundle_dir} 路径读取 → 得到 Path 或 FileNotFoundError；resolve_bundle_adapter_dir(bundle_dir) — 从 {bundle_dir}/adapter/ 读取 → 得到 Path 或 FileNotFoundError
manifest_parser.py（函数）

为什么不封装成 class？因为这些函数无内部状态（不持有 buffer/queue/cache），每次读盘是独立的一次性调用。按你的认知框架第 3.25 层判断原则：纯输入到输出转换 → 优先函数，不封装 class。验收覆盖：合法文件可读、缺文件/坏 JSON·YAML 抛明确异常。
参考 Pi0.5：common/runtime/bundle.py。

原因：service 层负责 RAM 内业务计算、转换、校验（如 observation collector、batch builder、safety guard、action adapter）。L2-01 的类型化配置校验归 config/，外部文件读取归 repo/，数据规格归 types/，本 L2 不做 observation/batch/safety/action 业务计算。

与去平滑的关系：第一版没有独立 action smoothing service，本 L2 不创建 smoother/chunk blender/RTC aligner。

验收确认：L2-01 不产生 src/model_deploy/act/service/*.py 产物。

runtime/ · 本 L2 不落点
