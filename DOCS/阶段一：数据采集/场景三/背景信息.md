## 1. 文档定位

本文用于记录场景三需要知道的上下文：


## 2. Octopus 在本项目中的角色

Octopus 是 ROS2 + Qt 的桌面数据采集程序，当前项目最终需要通过它完成 FASTUMI 数据采集。

根据 `/home/hit/ROS/DOCS/Octopus_architecture.md`，Octopus 有两条需要区分的链路：

```text
显示链路：
ROS2 topic -> MainWindow subscriptions -> 页面组件 -> UI 渲染

录制链路：
OpDockWidget -> McapRecorder -> generic ROS2 subscriptions -> MCAP writer -> .mcap 文件
```

场景三的核心验收对象是录制链路：即使某些 topic 暂时没有专门 UI 面板显示，只要 Octopus 能按配置订阅并写入 MCAP，也可以作为本场景的关键进展。

## 3. 最终理想蓝图

用户明确的最终理想蓝图是：

```text
第一步：
运行 /home/hit/ROS/start_all_sensor.sh
    ↓
自动开启 8 路目标数据源
    ↓
8 个目标 topic 在 ROS2 图中稳定发布

第二步：
运行另一个 Octopus 启动脚本
    ↓
自动启动数据采集程序 Octopus
    ↓
打开图形化界面

第三步：
在 Octopus 图形化界面中
    ↓
实时查看 8 路数据情况
    ↓
选择需要导出的 topic
    ↓
开始采集 / 结束采集
    ↓
导出一个总 .mcap 文件
```

这里的“8 路目标数据源”以最终采集 topic 为准。当前触觉驱动的代码事实是：`hwk_pressure_driver` 可以用一个 `pressure_driver_node` 管理多个串口并发布多个触觉 topic。因此后续实现时需要明确：

```text
如果用户要求的是 8 个 ROS 进程：
需要把触觉传感器拆成多个独立节点或独立 launch 实例。

如果用户要求的是 8 路可采集数据：
同一个触觉驱动节点在配置四个串口后发布四个触觉 topic，也可以满足 8 路数据目标。
```

场景三文档默认按“8 路可采集 topic / 数据源”作为验收口径；若后续明确必须是 8 个 ROS 节点进程，需要再更新执行约束和启动脚本设计。

## 5. Octopus 启动脚本背景

场景三已经新增一个独立于 `start_all_sensor.sh` 的 Octopus 启动脚本：

```text
/home/hit/ROS/start_octopus.sh
```

该脚本的职责是：

```text
1. source ROS2 Jazzy 环境；
2. source Octopus 所需工作区或安装空间；
3. 设置与传感器节点一致的 ROS discovery 范围；
4. 启动 Octopus 图形化程序；
5. 不负责启动或停止传感器节点；
6. 不在脚本中硬编码临时采集动作。
```

当前脚本会在启动 Octopus 前调用：

```text
/home/hit/ROS/scripts/configure_octopus_scanner.py
```

第一阶段该脚本已用于确保 `/home/hit/.config/scanner.json` 的 `recording.mcap.topics` 包含场景三 6 个目标 topic，并将默认 MCAP 输出目录设为 `/home/hit/ROS/mcap`。第二阶段需要把该脚本和 Octopus 默认配置同步扩展为 8 个目标 topic。

## 6. Octopus 录制配置背景

Octopus 的本地配置文件名是：

```text
scanner.json
```

代码中通过 Qt 的 `QStandardPaths::GenericConfigLocation` 生成配置路径；在当前 Ubuntu 桌面环境中通常对应：

```text
/home/hit/.config/scanner.json
```

录制 topic 来自：

```text
recording.mcap.topics
```

也就是说，场景三第二阶段需要确保 `scanner.json` 或 Octopus 内部默认配置中的录制 topic 列表包含 8 个目标 topic。

理想状态下，用户能在 Octopus 图形化界面中选择需要导出的 topic；如果当前 Octopus 版本只能通过 `scanner.json` 固定录制 topic 列表，则该能力差距需要作为场景三后续实现项记录。

## 7. 当前已知风险

根据当前 Octopus 源码，`McapRecorder::get_message_definition()` 已知显式支持的消息类型包括：

```text
sensor_msgs/msg/Image
sensor_msgs/msg/CompressedImage
sensor_msgs/msg/JointState
```

而场景三需要录制的 8 个目标 topic 中还包含：

```text
nav_msgs/msg/Odometry
hwk_pressure_interfaces/msg/PressureFrame
```

因此场景三存在一个关键风险：

```text
Octopus 可能能创建 generic subscription 并写入消息，
但 MCAP schema definition 对 Odometry 和 PressureFrame 的支持需要实测确认；
如果 MCAP 回放或解析失败，需要扩展 Octopus 的 schema definition 支持。
```

这个风险不影响场景三目标，但会影响验收方式。若发现 MCAP 中缺少 topic、消息数为 0、schema 为空或读取工具报错，应优先排查 Octopus 录制器对消息类型的支持。
