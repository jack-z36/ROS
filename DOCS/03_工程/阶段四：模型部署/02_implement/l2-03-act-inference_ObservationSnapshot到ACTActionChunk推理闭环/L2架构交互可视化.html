① 这部分代码整体在干什么（一句话）

像一个"后台厨师"——前面（L2-06）下单说"这盘观测数据给我做成一批动作"，厨师就在后厨默默把食材（snapshot）处理成模型能吃的样子（batch），喂给模型（policy），等模型吐出一串动作（action chunk），再装盘递回前面（result queue）。全程不卡住前台，因为厨师在独立的后厨（后台线程）干活。

厨师循环很简单：看订单队列有没有新单 → 有就拿去做 → 做好放结果队列 → 继续看。和前台（ControlLoop）通过两个队列沟通，互不阻塞。

📖 术语词典（点开随时查）
ObservationSnapshot对应认知框架第 3.5 层"数据"。"一盘刚拍好的食材"——某一瞬间所有传感器数据（图像 + 状态）冻结成一个完整对象。由 L2-02 准备好，本 L2 只负责拿来做菜。
batch对应认知框架第 3.5 层"计算函数"的产物。"模型能吃的标准化摆盘"。模型不直接吃原始 snapshot，要先把 state 归一化到 [−1,1]、图像整理成指定格式。ACT 是纯视觉-动作模型，不需要注入语言指令（Pi0.5 VLA 需要 task 标签）。
policy（策略模型）"厨师的大脑"——一个训练好的神经网络。给它一盘标准化观测，它预测接下来该怎么动。本 L2 不训练它，只调用它。
predict_action_chunk对应认知框架第 3.5 层"编排函数"。"厨师做一次菜"——调模型一次，产出一串动作（不是单个）。比如一次产出 chunk_size 步连续动作。
normalize / unnormalize对应认知框架第 3.5 层"计算函数"（RAM 内）。模型只认 [−1,1]。normalize 把物理值压到 [−1,1]（推理前）；unnormalize 把模型输出的 [−1,1] 还原回物理尺度（推理后）。两个方向都要做。
InferenceWorker（推理工人）对应认知框架第 3.5 层"编排函数"+"内部状态更新函数"。一个后台不停转的线程。在 ACT 设计中完全归 L2-06；L2-03 只是被同步调用的纯函数。
latest-only queue一个特殊队列：新订单来了，旧的直接扔掉。推理要低延迟，过时观测做了也没意义。归 L2-06。
fake-policy（假模型）一个"假装是模型"的替身——不加载真实权重，直接返回 shape 正确的假动作块。在 ACT 设计中，fake-policy 的选择和构造归 L2-01；L2-03 只接收已注入的 policy（无论真假）。
async 解耦"前台点完单就能去干别的，不用等厨师做完"。control tick 每 1/30 秒跑一次，不能卡在等模型（可能几十毫秒）。所以推理放后台线程，前台只管下单和取菜。在 ACT 中归 L2-06。

② 整体流程：四个步骤（后台推理轴）

Pi0.5 这部分代码在后台线程里循环执行。任一次推理出错，记录后继续下一个，不崩溃。

1

取订单

从 inference_request_queue 取最新 request（取前先按 inference_hz 限速）。无单就等 1ms 再看。latest-only：旧订单被新订单覆盖。
2

备料+做菜

predict_action_chunk：snapshot→batch（normalize state）→preprocess→GPU 推理→unnormalize→校验 shape→截断。
3

装盘递回

构造 ActionChunk（含时间戳 + request_id），写入 chunk_result_queue。
4

记账

记录 metrics（延迟/计数）；失败则记 inference_error，不崩溃。

③ 跟一次推理走完全流程

假设 L2-06 在 tick 时决定要新 chunk，创建 InferenceRequest 丢进队列。跟着它走一遍：

④ 模型包（bundle）里有什么

推理链路启动时要读模型包目录（训练完成后导出，部署只读不改）。在 ACT 设计中，bundle 读取、normalizer 加载和 policy 构建全部归 L2-01。

act_pour_water_v1/ ← bundle_dir（L2-01 校验和管理） ├── manifest.json ← 清单：维度(16)、模型信息、相机名 ├── normalizers.json ← state/action 的 min/max（L2-01 加载并校验） ├── experiment_config.yaml ← ACT 训练配置（L2-01 只读交叉校验） └── policy/ ← ACT 策略权重（L2-01 加载到 GPU 后注入 L2-03）

L2-03 不接收 bundle 路径，不读取任何 bundle 文件。它只接收 L2-01 已加载并注入的 policy + normalizer 引用。

⑤ Pi0.5 推理链路的两个核心入口（ACT 归属对比）

启动期：load_policy_runtime

Pi0.5：一次性加载 bundle→模型构建（VLA+LoRA）→adapter→preprocessor→normalizer→构造 Pi05PolicyRuntime。
ACT 归属：全部归 L2-01。L2-03 只接收注入的 policy + normalizer 引用。

稳态：InferenceWorker.run

Pi0.5：后台 daemon 线程循环：取 request→限速→predict→构造 chunk→record→put。try/except 捕获失败。
ACT 归属：全部归 L2-06。L2-03 只是被同步调用的纯函数，不拥有线程/队列/metrics。

⑥ 回答四个核心问题

❶ 谁持有状态？

  • ActInferenceService（L2-03）：config 引用、两个 normalizer 引用、policy 引用、只读输入规格——启动期注入后稳定只读。
  • InferenceWorker / queue / metrics：全部归 L2-06。
  • L2-03 内部不持有 batch/raw tensor/chunk 缓存或跨调用状态。

❷ 谁跨越外部边界？

  • L2-01：启动期读 bundle + 加载权重到 GPU。
  • L2-03：policy.predict_action_chunk 调 GPU（跨设备边界，最耗时）。
  • L2-03 不订阅/不发布 topic，不读文件，不写硬件。

❸ 谁只负责加工 RAM 对象？

  • prepare_observation_batch（snapshot→batch，7 个计算微元）
  • run_act_inference（policy 前向）
  • postprocess_action_chunk（raw→ActionChunk，6 个微元）

❹ 谁负责 runtime 时序？

全部归 L2-06：后台循环、inference_hz 限速、stop 控制、失败策略、metrics。L2-03 只是被同步调用的纯函数，不决定被调用时机。

维度 3 · 开发建议与蓝图

📖 阅读路径：了解代码如何组织（service 层一个 class + 三个文件）→ 代码写完后用维度4检查产物清单

L2-03 是纯同步推理服务。按「一个 service class + 三个一级阶段函数」组织。types 层新增 ActionChunk（只含 actions）；config / repo / runtime / ui 层不新增产物——四项稳定依赖全部由 L2-01 注入。第一版不做 action 平滑。

图① L2-06 同步调用 L2-03 的运行时协作链

L2-06 每 tick 同步调用 service.predict_action_chunk(observation)，内部走 prepare_observation_batch → run_act_inference → postprocess_action_chunk → 返回 ActionChunk。成功则 L2-06 自行管理 chunk 生命周期；失败则异常向上传播给 L2-06。虚线=编译时注入，实线=运行时同步调用。

关键协作事实（对照图②）：
「模型与推理」predict_action_chunk 是编排函数（串联三段）；prepare_observation_batch 是编排函数（7 个计算微元）；run_act_inference 是计算函数（只调 policy chunk API）；postprocess_action_chunk 是编排函数（6 个微元）。
「归一化」state/action normalizer 由 L2-01 注入，在 ③normalize 和 ⑤unnormalize 两步各被调用恰好一次。两个 normalizer 是独立实例，不得交换。
「配置常量」state_dim / action_dim / chunk_size / device 均来自 L2-01 编译时注入的 DeployConfig，运行时只读。ACT 不需要 task 语言指令。
「设备」device 决定所有 tensor 计算位置；L2-01 只注入配置和已加载 policy，不参与运行时调用。
「驱动与失败」L2-06 是驱动方，每 tick 同步调用触发整条链；失败时异常直接在 L2-06 侧被 try/except 捕获。L2-03 不自行捕获异常。

repo/ · 本 L2 不新增源码产物

runtime/ · 本 L2 不落点

原因：L2-03 是一次性的同步 service，不新增 runtime 文件。runtime/ 负责时间、线程、queue、持续循环、运行状态和失败策略——全部归 L2-06。

明确归 L2-06 的运行对象：
• worker/thread/timer
• latest observation buffer
• request/in-flight/result records
• latest-only queues
• request_id、timestamps、latency、metrics
• active ActionChunk、cursor、selected raw step
• fallback/stop/retry policy
• ROS status/metrics publication

并发约束：L2-03 不创建 lock，不承诺同一 policy 实例可被并发调用。L2-06 应默认串行化调用。
验收确认：L2-03 不产生 runtime/*.py；service/types 中无 Thread/queue/timer/cursor/metrics/fallback 实现。
← 验收方式见维度4

ui/ · 本 L2 不落点

原因：L2-03 不跨越进程外 I/O。订阅 observation topic 归 L2-02；发布 policy_action/command 归 L2-05；启动 ROS node/timer 归 L2-06。L2-03 的 batch、raw tensor 和 service class 都是 Python 进程内对象，不能被表述为 ROS message、topic 或 node。

外部接口分工：observation ROS message 订阅/解码归 L2-06；observation 业务缓存/图像预处理/snapshot 组装归 L2-02；policy/status/metrics ROS publish 归 L2-05/L2-06；arm/gripper command publish 归 L2-05。
验收确认：L2-03 不产生 ui/*.py 或 launch 产物；静态扫描 types/service 不含 ROS/hardware import。

第一版不实现平滑：predict_action_chunk 只输出整个 chunk 的 actions ndarray，不做单步选择/cursor 推进/跨 chunk 融合。L2-06 若后续要引入平滑，必须重新设计并同步 L1/L2 文档与 Gate。
基础设施归 L2-06：InferenceWorker / LatestQueue / SharedBuffer / RuntimeMetrics / InferenceRequest / ActionChunk 运行元数据包装全部归 L2-06，L2-03 只暴露同步函数。
