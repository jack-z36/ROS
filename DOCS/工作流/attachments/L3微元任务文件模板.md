# L3 微元任务文件模板

本模板用于把一个已经稳定的 L2 能力模块拆成可由短上下文 Agent 独立完成的小任务。

L3 微元任务不是“尽量塞满上下文”，而是给 Agent 一个最小但完整的任务导航包：

```text
位置、目标、输入、输出、必读上下文、约束文档索引、修改边界、验收交接。
```

一句话定义：

```text
L3 = 让失忆 Agent 能独立完成一次小 PR 的最小导航单元。
```

## 最小信息集

一个 L3 任务文档必须引导 Agent 获取 8 类信息：

| 信息角度 | 作用 | 必须提供什么 |
|---|---|---|
| 1. 任务定位 | 让 Agent 知道自己在全局哪一小段 | 阶段、场景、L1、L2 能力、L3 编号 |
| 2. 本次目标 | 让 Agent 知道唯一目标 | 一句话目标，只解决一个问题 |
| 3. 输入信息 | 告诉 Agent 从哪里开始 | 数据输入、配置输入、已有代码输入、样本输入 |
| 4. 输出信息 | 告诉 Agent 交付什么 | 函数、文件、topic、报告、测试结果、字段契约 |
| 5. 必读上下文 | 引导 Agent 读取必要背景 | 当前任务必须读的文档、代码和约束文档 |
| 6. 修改边界 | 控制 Agent 动刀范围 | 允许修改文件、禁止修改文件 |
| 7. 验收方式 | 判断任务是否完成 | 验收命令、成功标准 |
| 8. 完成后交接 | 让后续 Agent 接得住 | 需更新文档、交接摘要要求 |

公式：

```text
L3 任务文档 =
任务坐标
+ 单一目标
+ 输入输出契约
+ 必读上下文索引
+ 约束文档索引
+ 修改边界
+ 验收命令
+ 交接要求
```

核心不是在 L3 卡片里复制所有规则，而是告诉 Agent：

```text
开始前该读哪些约束文档
该读哪些任务上下文
该改什么
不该碰什么
怎么证明完成
完成后怎么交接
```

## 填写原则

- 一个 L3 只能解决一个核心目标。
- 必读上下文只列完成当前任务必须读的文档、代码和约束文档。
- 通用编程规则、文件存放规则、Git 同步规则、技术栈规则不直接复制进 L3 卡片，而是放入“必读约束文档”。
- 不读全部场景历史，不读所有论文，不读所有执行记录。
- 输出必须可检查，不能只写“处理完成”。
- 修改边界必须明确，防止顺手重构。
- 验收命令和成功标准必须具体。
- 完成后必须说明如何交接。

## 字段填写要求

### 1. 任务定位

任务定位用于回答“我在哪”。必须写清：

```text
阶段二：数据清洗
场景一：raw MCAP -> cleaned MCAP
L2 能力：夹爪开合提取
L3 任务：S1-GRIP-02 单帧 ArUco marker 检测
```

它的作用是防止 Agent 只知道“写检测函数”，但不知道该函数服务于什么 pipeline。

### 2. 本次目标

本次目标必须只有一个。

推荐：

```text
实现一个可单元测试的单帧 ArUco marker 检测函数。
```

不推荐：

```text
完成夹爪开合提取功能。
```

后者太大，会诱导 Agent 同时修改配置、算法、MCAP 写入、报告和 smoke test。

### 3. 输入

输入必须明确，不要让 Agent 猜。

示例：

```text
数据输入：
- OpenCV 图像数组

配置输入：
- aruco_dict
- marker_id_0
- marker_id_1

已有代码输入：
- src/data_clean/core/gripper_width.py
- src/data_clean/core/mcap_process_config.py
```

如果任务涉及真实样本，再列样本输入。

### 4. 输出

输出必须可检查。

示例：

```text
代码输出：
- 新增 detect_gripper_markers(image, config) 函数

数据输出：
- GripperDetectionResult

测试输出：
- tests/service/test_gripper_marker_detection.py
```

输出字段应具体到可断言字段，例如：

```text
- ok: bool
- center_0: [x, y] | null
- center_1: [x, y] | null
- pixel_distance: float | null
- reason: str
```

### 5. 必读上下文

只列当前任务必须读的文件。必读上下文分三类：

1. 必读任务文档：解释本任务的业务目标、L2 来源、场景背景和当前进度。
2. 必读约束文档：承载文件存放、Git 同步、架构分层、技术栈、报告更新等规则。
3. 必读代码：当前任务真正需要理解或修改的代码入口。

约束文档应按任务需要选择，不要无差别堆满上下文。常见约束入口包括：

```text
DOCS/阶段二：数据清洗/文件存放规范.md
DOCS/git操作约束.md
DOCS/阶段二：数据清洗/01_runtime_mvp/执行约束.md
DOCS/阶段二：数据清洗/02_service/执行约束.md
DOCS/阶段二：数据清洗/02_service/场景一/执行约束.md
```

后续如果编程反馈暴露出新问题，例如依赖管理、测试环境、ROS2 topic 命名、schema 校验、UI 交互约束，应先沉淀为独立约束文档，再在具体 L3 的“必读约束文档”中引用。

原则：

```text
只读当前任务必要上下文。
不读五个场景全部历史。
不读所有论文。
不读所有执行记录。
不把通用约束复制进任务卡片。
```

### 6. 修改边界

必须写清允许修改和禁止修改。

示例：

```text
允许修改：
- src/data_clean/core/gripper_width.py
- tests/service/test_gripper_marker_detection.py

禁止修改：
- src/data_clean/core/mcap_io.py
- src/data_clean/core/tcp_transform.py
- start_data_clean.sh
- config/data_clean_calibrated.yaml
- 场景二到场景五代码
```

## 合格 L3 的判断标准

写完 L3 文档后，必须能回答：

1. Agent 是否知道自己属于哪个阶段、场景和 L2 能力？
2. Agent 是否知道这次只做一个目标？
3. Agent 是否知道输入和输出？
4. Agent 是否知道开始前要读哪些任务文档、约束文档和代码？
5. Agent 是否知道能改和不能改哪些文件？
6. Agent 是否知道怎么验收？
7. Agent 是否知道完成后怎么交接？

如果这些问题都能回答，L3 任务文档就足够用于短上下文 Agent 执行。
