# ui 层设计：L2-05

> [!info] 元信息
> - 消费对象：ROS UI 实现/验收 Agent。
> - 权威性：定义 B2、A1/B3 和 C8/C12-C21；编号以 `03a` 为准。
> - 上游来源：C2/C4/C7、用户确认的三编排函数与 CLI 总开关。
> - 不负责范围：不订阅、不拥有 node 生命周期/timer、不调用硬件 API。
> - 读取时机：实现或审查 ROS publisher 前。

## 1. 目标源码路径

```text
src/model_deploy/act/ui/action_publisher.py
src/model_deploy/act/ui/__init__.py       # 仅导出 ActionPublisher 与必要公共入口
```

不新增独立 ROS Node 或 launch。本组件由 L2-06/UI 装配入口创建。

## 2. 层职责与文件职责

ui 层承担两件事：

1. B2 把 transport-neutral C4 转为五个候选 ROS messages。
2. A1/B3 依据 CLI 总开关与 C1 permit 选择并写出 policy/可选 command，最后根据真实事实形成 result/status。

它是 ACT 内部唯一 action command publish 边界。

禁止：subscription、timer、thread、queue、SafetyGuard 算法、workspace/IK/TF、driver SDK、fallback、RuntimeConfig.mode。

## 3. ROS transport

| Topic | 类型 | 构造规则 |
|---|---|---|
| `/act/policy_action` | `Float32MultiArray` | C4 policy 16D 原样 float32。 |
| 两路 arm target | `PoseStamped` | request ROS stamp；共同 `pose_frame_id`；xyz + quaternion `xyzw`。 |
| 两路 gripper target | `Float64` | B1 已映射的 0..100。 |
| `/act/command/status` | `String` JSON | B3 根据最终 C6 构造；unknown 保留 null。 |

模块使用 lazy ROS import：无 ROS 时模块仍可 import，mock message/publisher 测试不要求 ROS graph；真实 ROS 验收缺环境时标记 `BLOCKED_ENV`。

## 4. C8 `_RosMessageBundle`（模块私有数据）

| 变量名 | 内部存储结构 | 内部存储的数据类型 |
|---|---|---|
| `policy_action_msg` | ROS object reference | `Float32MultiArray` |
| `left_arm_msg` | ROS object reference | `PoseStamped` |
| `right_arm_msg` | ROS object reference | `PoseStamped` |
| `left_gripper_msg` | ROS object reference | `Float64` |
| `right_gripper_msg` | ROS object reference | `Float64` |

C8 只在本模块内短生命周期使用，不从 `ui/__init__.py` 导出。它不含 status；ROS msg 本身可变，因此不得伪称为跨层 frozen 契约。

## 5. B2 `build_ros_messages`（编排函数）

```python
def build_ros_messages(
    payloads: TopicPayloadBundle,
    ros_time_s: float,
) -> _RosMessageBundle:
    ...
```

调用条件：B1 完整成功后由 B3 调用。

步骤：

1. C12：policy16 → `Float32MultiArray`。
2. C13 ×2：左右 C3 + stamp → `PoseStamped`。
3. C14 ×2：0..100 → `Float64`。
4. 完整构造 C8。

失败：任一 builder 异常时不返回部分 C8；B3 不调用 policy/command publisher，只形成 FAILED result/status。

禁止：不读取 CLI/permit，不做 deadband，不调用 publisher，不构造最终 status。

## 6. C12-C14 消息计算函数

### C12 `_build_policy_msg`

输入：RAM `tuple[float, ...]`，长度16。

输出：新的 RAM `Float32MultiArray`，data=16 个 float。

异常：长度/finite 错误。不直接读写进程外资源。

### C13 `_build_arm_msg`

输入：RAM C3 + finite `ros_time_s`。

输出：新的 RAM `PoseStamped`：header frame/stamp、position xyz、orientation xyzw。

异常：frame/长度/finite 错误。不执行 TF，不直接读写外部资源。

### C14 `_build_gripper_msg`

输入：RAM `float` 0..100。

输出：新的 RAM `Float64`。

异常：越域/finite 错误。不直接读写外部资源。

## 7. A1 `ActionPublisher` class

### 7.1 class 封装的 3.5 微元

| 3.5 微元 | 内容 |
|---|---|
| 数据 | C7、六 publisher handles、每侧 gripper target/time、last C6、env status。 |
| 计算函数 | C15/C16/C19/C20。 |
| 内部状态更新函数 | C18/C21。 |
| 数据读写函数 | C17。 |
| 编排函数 | B3。 |

### 7.2 constructor

```python
ActionPublisher(node, command_output_config, topics_config)
```

- 创建恰好六个 publisher：policy、left/right arm、left/right gripper、status。
- 不创建 metrics publisher；全局 metrics 属 L2-06。
- 不调用 `create_subscription`、`create_timer`。
- 不从 node clock 取时间；时间来自 C2。
- publisher 创建失败立即阻止可用状态，不能半初始化后接受 B3。

## 8. B3 `ActionPublisher.publish`（编排函数）

```python
def publish(self, request: ActionPublishRequest) -> ActionPublishResult:
    ...
```

唯一业务入口；禁止公开“直接发左臂/右臂”的 bypass method。

顺序：

```text
1. B1 build_topic_payloads(request.safety_result, self._config)
2. B2 build_ros_messages(payloads, request.ros_time_s)
3. C15 decide(enabled, request.command_permit)
4. C17 publish policy；失败则停止 command
5. 若 command 允许：
   a. C17 publish left arm
   b. C17 publish right arm
   c. C16 判断左右 gripper
   d. C17 publish 允许的 gripper
   e. 对成功 gripper 调 C18
6. C19 汇总 C6
7. C20 构造 status msg
8. C17 best-effort publish status
9. 若 status 失败，RAM C6.status_published=False
10. C21 保存最终 C6，返回 L2-06
```

若 B1/B2 失败，B3 捕获错误，构造 `FAILED/REJECTED` C6 并尽力发 status；policy/command 调用数为 0。

### 8.1 发布失败追因矩阵（deploy_060）

`ActionPublishResult` 新增 `failure_stage` / `failed_topic`，使 L2-06 只需保存并核验返回值即可 fail-closed，无需从 outcome 反推失败位置。每个 stage 必须在失败发生点显式记录；矩阵在 C6 构造层（types）不可违反：

| 故障点（B3 分支） | outcome | reason_code | failure_stage | failed_topic |
|---|---|---|---|---|
| B1 安全 REJECTED / 契约违例 | `REJECTED` | `SAFETY_REJECTED`（非空） | `safety` | `None` |
| B1 其它异常（payload 构建） | `FAILED` | `PAYLOAD_BUILD_ERROR` | `command_build` | `None` |
| B2 消息构建异常 | `FAILED` | `MESSAGE_BUILD_ERROR` | `command_build` | `None` |
| C17 policy 写出 I/O 失败 | `FAILED` | `POLICY_PUBLISH_IO_ERROR` | `policy_publish` | `/act/policy_action` |
| 某路 command 写出 I/O 失败（count>0 后中断） | `PARTIAL` | `COMMAND_PUBLISH_IO_ERROR` | `command_publish` | 该 command 的 public topic |
| 首路 command 写出 I/O 失败（count=0） | `FAILED` | `COMMAND_PUBLISH_IO_ERROR` | `command_publish` | 该 command 的 public topic |
| command 不允许（disabled / deny） | `OBSERVED` / `BLOCKED` | `COMMAND_OUTPUT_DISABLED` / permit.reason_code | `None` | `None` |
| 全成功 | `PUBLISHED` | `None` | `None` | `None` |

命令失败立即停止后续 command（已发消息不回滚），`failed_topic` 精确到失败那一路的 public topic（如 `/act/command/arm/right_target`）。

## 9. C15 发布决策

```python
def _decide_command_publish(
    command_output_enabled: bool,
    permit: CommandPermit,
) -> tuple[bool, str | None]:
    ...
```

| enabled | permit | allow command | 预期 outcome/reason |
|---|---|---|---|
| False | 任意 | False | OBSERVED / `COMMAND_OUTPUT_DISABLED` |
| True | False | False | BLOCKED / permit.reason_code |
| True | True | True | 继续 ROS command 写出 |

这是计算函数，不读取 argv/topic，不修改状态，不直接写 ROS。

## 10. C16/C18 夹爪防刷

每侧独立：

```text
publish gripper iff:
  no previous successful target
  OR (abs(target-last_target) >= deadband
      AND monotonic_s-last_time >= min_interval)
```

C16 是计算函数：只读 cache，输出 publish/skip + reason。

C18 是内部状态更新函数：

- 修改对象：对应 side 的 `_gripper_last_target/_gripper_last_time`。
- 如何修改：仅在 C17 publish 成功后替换；失败或 skip 不修改。

两臂不受 gripper deadband 影响。

## 11. C17 ROS 数据写出

```python
def _try_publish(label, publisher, message) -> None:
    ...
```

- 外部边界：对应 `/act/*` ROS topic publisher handle。
- 写出：一个已完整构造的 ROS message。
- 失败：抛带 topic label 的 `ActionPublishIoError`；B3 记录真实成功计数。
- command 首次失败后停止剩余 command；已发消息无法回滚。
- status 使用同一 C17，但为 best effort；失败只影响 RAM `status_published` 和 reason。
- `/act/command/status` 仍是 L2-05 唯一 writer；status C17 失败抛 `ActionPublishIoError(label="status")`，且**不能伪造**已发布 status 的 result（`status_published=False`），失败点不写入 `failure_stage`。

## 12. C19-C21 result/status

### C19 `_build_publish_result`（计算函数）

输入：request、config.enabled、permit、policy 事实、command count、skip、错误。

输出：新的 frozen C6；不写 ROS，不修改 class。

### C20 `_build_status_msg`（计算函数）

输入：C6。

输出：新的 `String(JSON)`；key 稳定，Enum 写字符串，unknown 写 null。

最低示例：

```json
{
  "action_id": "action-0042",
  "safety_status": "PASS",
  "command_output_enabled": false,
  "command_permitted": false,
  "outcome": "OBSERVED",
  "policy_action_published": true,
  "command_publish_count": 0,
  "gripper_skipped": [],
  "command_plan_completed": true,
  "reason_code": "COMMAND_OUTPUT_DISABLED",
  "failure_stage": null,
  "failed_topic": null,
  "driver_accepted": null,
  "hardware_reached": null
}
```

### C21 `_record_last_result`（内部状态更新函数）

- 修改对象：A1 `_last_result`。
- 如何修改：用本次最终 frozen C6 替换旧引用；每个 B3 调用最多一次最终替换。

## 14. 依赖关系

允许：types、config、service、ROS message packages、标准库。

禁止：runtime（UI 不反向依赖调度实现）、repo、SafetyGuard 实现、RM65/F100 SDK、MoveIt/IK/TF、Modbus/serial。A1 只读取 `SafetyResult` 数据契约，不 import L2-04 service。

## 15. Pi0.5 参考

- `_create_publishers`：只结构复用 publisher handle 生命周期。
- `_control_tick`：只参考 publish API，拒绝边构造边发和 mode 分支。
- Bridge/Mux：subscription、deadman、mode state 均不复用。
- JSON status transport 可参考，但当前 status 改为逐 action 发送回执。

## 16. 验收覆盖

- constructor 恰好 6 publisher、0 subscription、0 timer、无 metrics publisher。
- B2 五消息完整构造且不含 status。
- enabled/permit 三路径调用数与 outcome 准确。
- policy failure 时 command=0；第 n 路 command failure 返回 PARTIAL/真实 count。
- deadband 每侧独立，失败/skip 不更新 cache。
- frame/stamp/xyzw 与 gripper 0..100 正确。
- status 只在真实 result 形成后构造，不伪造 driver/hardware success。
- 发布失败追因（deploy_060）：六种 outcome 均带 `failure_stage`/`failed_topic`/`reason_code` 矩阵；status 失败不伪造 result。
- 无 ROS import 测试与 ROS observation 测试分层。

## 17. 边界继承声明

本文件继承当前 L2-05 唯一 ROS 输出边界，不从旧 layer-based publish/hardware 卡片或 Pi0.5 bridge/mux 继承。ui 只做消息适配与外部写出，不能吞并调度、安全或硬件驱动。
