## 一、这套系统整体是什么？（先打个比方）

把整套机器人系统想象成 **一个人在干活**：

| 比喻 | 实际组件 | 干什么的 |
|---|---|---|
| 🧠 大脑 | ACT 部署节点（AI 模型） | 看着眼前的画面，思考"下一步手臂该怎么动" |
| 👀 眼睛 | 双鱼眼相机（左右各一个） | 拍下眼前的画面，传给大脑 |

**干活流程**：眼睛拍照 → 大脑看图思考 → 大脑发出"手臂动一动、手抓一下"的指令 → 手臂和手照做。任何一个环节掉链子，整个流程就走不通。

另外还有一个"总管"：

| 比喻 | 实际组件 | 干什么的 |

## 三、每个问题的通俗解释

### 问题 1：👀 眼睛（相机）——"地址写错了，按老地址找不到人"【✅ 已修复】

**现象**：启动时报错"打不开设备"。

**原因**：
电脑里每个 USB 设备都有一个"门牌号"（插在哪个 USB 口上，就有对应的编号）。
配置文件里写的门牌号是当初写代码时随手填的**占位示例**（文件注释里也明说了"上线前必须按真机重新核对"）。
现在相机确实插上了，但插的位置和示例写的不一样，所以系统按老地址去敲门，当然找不到。

**已查明的事实**：电脑上确实识别到了两台相机，真实门牌号是：
- `pci-0000:00:14.0-usb-0:1:1.0`（对应 video2）
- `pci-0000:00:14.0-usb-0:5:1.0`（对应 video0）

**修法**：把配置文件 `src/model_deploy/dual_fisheye_camera/config/dual_fisheye_camera.yaml` 里的两个地址改成上面的真实地址。

**✅ 修复记录（2026-07-28）**：
- 用"拔插法"确认左右：拔掉一台后，剩下的（`usb-0:5` 口）是**右眼**，被拔掉的（`usb-0:1` 口）是**左眼**。
- 配置文件已改成真实地址，并重新编译生效。
- 修复过程中又发现一个隐藏 bug：启动文件嘴上说"默认读配置文件里的地址"，实际代码却拿一个**空地址**去覆盖配置——等于配置改得再对也没人看。已修好启动文件（空地址时回退去读配置文件），重启后两只眼睛点名 OK、正常拍照。
- ⚠️ 注意：地址绑定的是 **USB 插口的位置**，不是相机本身。左相机必须插回原来那个 USB 口（usb-0:1），不能和右相机换着插，否则左右画面会颠倒。

### 问题 2：✋ 手掌（夹爪）——"人到了，但还没办入职、没有工牌"【✅ 已修复】

**现象**：夹爪程序一直重试报错"找不到 /dev/elephant_gripper_left（左夹爪）"。

**原因**：
两个夹爪通过 USB 线插上了，电脑也识别到了它们（以"串口设备"的身份）。
但夹爪程序找它们时，用的是两个**固定的名字**：`elephant_gripper_left`（左手）和 `elephant_gripper_right`（右手）。
要让系统给设备贴上这两个名字标签，需要安装一个"起名规则文件"（术语叫 udev 规则）。这个规则文件仓库里已经写好了，只是**还没安装到系统里**，所以名字标签没贴上，程序自然找不到。

**✅ 修复记录（2026-07-28）**：
- 用"拔插法"确认左右：拔掉左手夹爪后，序列号 `5AF5008554` 消失 → **左手 = 5AF5008554，右手 = 5AF5010881**。
- 起名规则改成按**出厂序列号**认人（不是按插在哪个口）——所以夹爪的 USB 线**随便插哪个口都不会认错**，这点和相机不一样。
- 规则文件已安装到系统（`/etc/udev/rules.d/`），两个名字标签已验证贴上。
- 顺手修了一个隐藏 bug：夹爪连接成功的那一刻，程序在打印"连接成功"日志时会崩溃（ROS 日志系统不允许同一行代码一会儿喊警告、一会儿报喜）。已修复代码、补了自动化测试防止复发，重启后左右手掌点名 OK。

### 问题 3：💪 手臂（RM65 双臂）——"缺少厂商的说明书和工具包，控制程序压根没造出来"

**现象**：启动点名时，手臂节点直接缺席。

**原因**：
控制机械臂需要用**厂商（睿尔曼）官方提供的驱动程序包**（几个 `.so` 库文件和头文件）。
这些文件因为版权原因**不能放进代码仓库**，必须由使用者自己从官方 SDK 里拷进来。
现在存放它们的文件夹（`src/model_deploy/rm65_dual_arm/lib/`）里只有一份"如何拷贝"的说明书，真正的驱动文件还没放进去。
编译系统发现驱动缺失后，**按设计主动跳过了手臂控制程序的构建**——所以不是编译坏了，是根本没编（这是刻意设计的保护行为）。

**修法**：
1. 找到官方 RM_API2 SDK 包（需要你提供它在哪，或者去哪下载）；
2. 按 `lib/SDK_VENDOR_README.txt` 的说明把文件拷进去；
3. 运行一条安装命令（需要管理员密码）；
4. 重新编译手臂这个包。

### 问题 4：🧠 大脑（ACT 部署节点）——"办公环境缺零件 + 脑子里没装知识"【✅ 已修复】

**当初的现象**：启动后 1 秒内就退出了。

**当初的原因（两层）**：一是 conda 环境里没装 ROS 通信零件和一堆 AI 库的依赖；二是配置文件里"模型在哪"一栏是空的。

**✅ 修复记录（2026-07-29）**：

用户提供了训练好的模型：`/home/hit/模型权重/UMI_ACT/act_pretrained_model_20260702_13_010000`。修复分四步：

1. **环境零件补齐**：给 conda 环境装上缺的一堆 Python 库（其中两个库的版本必须按 lerobot 官方钉死，装太新会报错）；ROS 通信零件通过"借用系统 ROS"方式解决，验证可用。
2. **发现并解决了五处"训练↔部署对不上"的契约冲突**（最关键的侦察成果）：
   - 模型吃 32 维状态（含 16 维触觉），机器人没触觉传感器 → 触觉段用训练均值填充（归一化后恰好是 0）
   - **动作顺序陷阱**：训练时动作排序是"左臂7+左爪1+右臂7+右爪1"，部署侧是"左臂7+右臂7+左爪1+右爪1"，必须"换座位"，否则右臂指令会被当成夹爪指令（已用归一化统计数值实证）
   - 批次键名、归一化方式、图像尺寸（模型要 480×640）也都不同
   - 解法：写了一个"翻译官"包装层（`act/service/lerobot_policy.py`）站在模型门口，把以上差异全部翻译好，部署流水线的 16 维铁律一点没动
3. **制作了模型"知识包"（bundle）**：在权重旁边建了 `deploy_bundle/` 文件夹（清单+归一化说明+软链接），配置文件里填上了路径，并把动作块长度从 30 改成模型真实的 100
4. **顺手修了一个隐藏 bug**：节点建"闹钟"（定时器）时传错了参数类型，以前从没连真 ROS 跑过所以没暴露，一连真机就崩。已修复。

**验证结果**：离线端到端测试——真配置+真模型+真 GPU，模型加载 2.4 秒，推理暖机后每次 10 毫秒（要求每秒 10 次，绞绞有余），夹爪输出落在 0~1 合法范围（证明换座位正确）；自动化测试 878 个全部通过；一键启动点名 OK，心跳指标正常发布。

⚠️ 目前是 **dry-run（干跑）模式**：大脑照常思考，但不给手臂发真实命令——要真动手还需要手臂驱动修好后由操作员显式开启。

## 五、名词小词典（遇到看不懂的词查这里）

| 术语 | 大白话 |
|---|---|
| 节点（node） | 一个独立运行的小程序，比如"夹爪节点"就是专门管夹爪的程序 |
| ROS 2 | 机器人程序之间互相传话用的"通信系统" |
| 编译（build） | 把人写的代码翻译成电脑能直接执行的程序 |
| SDK | 厂商提供的"驱动+工具包"，用它才能指挥厂商的硬件 |
| udev 规则 | 告诉系统"这个 USB 设备叫什么名字"的登记规则 |
| conda 环境 | 一个独立的 Python 工具箱，不同项目用不同的箱子，互不干扰 |
| 模型 bundle | 训练好的 AI"知识包"文件夹 |
| fail-fast（快速失败） | 程序发现条件不对就立刻停下报错，而不是带病硬跑——是保护设计 |
| dry-run（干跑） | 只演习不真动手：大脑照常思考，但不给手臂发真实命令 |
