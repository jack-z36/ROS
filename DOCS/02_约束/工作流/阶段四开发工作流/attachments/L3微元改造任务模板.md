# 阶段四 L3 微元改造任务模板

本模板用于新版阶段四 ACT 部署工作流。L3 是某个 L2 功能模块内部的一次最小、可验证、可回滚实现任务。

## 使用前提

生成阶段四 L3 前，必须已经完成：

1. L1 任务文档。
2. L1 架构协作文档。
3. 当前 L2 的功能边界。
4. 当前 L2 的 Pi0.5 源码范围匹配已作为内部工作完成，并已折叠进 3.5 层微元拆解文档。
5. 当前 L2 的 Pi0.5 源码 3.5 层微元拆解。
6. 当前 L2 的 Pi0.5 class 封装盘点。
7. 当前 L2 的 ACT 版微元设计与协作关系。
8. 当前 L2 的 `agent_context/06_types层设计.md` 至 `agent_context/11_ui层设计.md` 六层设计文件。
9. 当前 L2 的 Gate 设计。

如果现有代码尚未盘点，不得生成正式 L3。

## 核心纪律

L3 的生成与执行机制沿用旧阶段四工作流的调度和验收纪律：

- L3 任务文件。
- `dispatch` YAML。
- 验收卡片。
- 执行 agent / 验收 agent 分离。
- 最多 3 轮执行-验收迭代。
- L2 Gate。
- 人类验收签字。
- 通过后合入 `model_deploy`。

新版不再使用旧版 AS-IS / TO-BE / Contract Delta 作为 L2 主线。旧字段中与新版冲突的部分，用「L2 功能边界 / Pi0.5 源码 3.5 层微元拆解 / ACT 微元设计 / 六层设计文档」替代。Pi0.5 源码范围匹配只作为内部工作过程，不作为独立 L2 文档。

## 新版 L2 身份白名单

阶段四 ACT L3 只能属于以下新版功能闭环 L2：

| L2 ID | L2 名称 |
|---|---|
| `l2-01-external-contract` | 外部参数加载与契约校验闭环 |
| `l2-02-observation-snapshot` | 传感器订阅与 ObservationSnapshot 组装闭环 |
| `l2-03-act-inference` | ObservationSnapshot 到 ACT ActionChunk 推理闭环 |
| `l2-04-safety-guard` | 单步 Action 安全检查闭环 |
| `l2-05-action-publisher` | 单步 Action 到执行器 Topic 适配发送闭环 |
| `l2-06-control-loop` | ControlLoop 中央运行调度闭环 |

旧 `l2-01-types`、`l2-02-config`、`l2-03-assembly`、`l2-04-publish`、`l2-05-hardware` 不得作为当前 L3 所属 L2、dispatch group、acceptance 目录或分支 topic。

## 改造类型

| 改造类型 | 适用任务 |
|---|---|
| `source-adaptation` | 根据 Pi0.5 源码结构实现 ACT 版对应微元。 |
| `contract-adapter` | 在旧接口外包一层 adapter，使其满足目标接口。 |
| `behavior-change` | 修改已有行为，但必须写明兼容或破坏性原因。 |
| `safety-gate` | 在真机发送链路前增加安全检查或阻断策略。 |
| `observability` | 增加日志、运行记录、status、metrics 或错误上下文。 |
| `compatibility` | 保留旧入口、旧参数、旧返回值或回滚开关。 |
| `test-coverage` | 为已有行为或新增改造补测试 / smoke 验证。 |
| `runbook-doc` | 补充 dry-run、fake-policy、real-policy、real-robot 运行说明。 |

如果一个 L3 同时符合多个类型，优先拆成多个 L3；只有拆分会破坏同一个最小行为闭环时，才允许写两个类型。

````md
`dispatch_status` 只允许 `ready`、`blocked`、`waiting_user`。如果 `robot_risk` 是 `real-robot`，必须在验收方式中写明人工确认、急停准备、限幅策略和回滚路径。

### Agent 执行 / 验收边界

- 执行 sub-agent 只负责本 L3 的实现、局部验证和执行摘要。
- 执行 sub-agent 可以阅读验收卡片理解通过标准，但不得替验收 sub-agent 修改验收结论。
- 验收 sub-agent 只能读取验收卡片、L3 文件、执行摘要、允许查看的 diff / 日志，并按 `acceptance_mode` 输出结论。
- 验收 sub-agent 不得改源码、测试、dispatch、任务状态或 Git。
- `FAIL_LOCAL` 反馈最多回到执行 sub-agent 迭代 3 轮；超过 3 轮必须由主 Agent 停止自动推进并要求人工介入。
- `downstream-l2`、`hardware-blocked`、`env-blocked` 不是免验收，而是要求写清由哪个 L2 场景覆盖、缺什么环境或缺什么硬件。

## 14. 执行要求

执行前必须完成任务文件身份校验：

```text
用户指定任务路径：

是否一致：
所属 L2 ID：

是否命中旧 L2 ID：
是否位于 legacy/archive 目录：
```

执行前必须读取 `dispatch` YAML，确认：

- `task_id` 与正文 L3 编号一致。
- `task_file` 与当前文件路径一致。
- `task_file` 位于 `03_tasks/task/active/<new-l2>/`。
- `group` 是新版 L2 ID。
- `branch` 是当前 L2 分支。
- `integration_branch` 是 `model_deploy`。
- `acceptance_dir` 指向所属 L2 的 `05_acceptance` 子目录。
- `acceptance_card` 指向当前 L3 的验收卡片。
- `acceptance_mode` 已明确。
- `acceptance_round_limit` 固定为 `3`。
- `depends_on` 已完成或明确无需等待。
- `dispatch_status` 不是 `blocked` 或 `waiting_user`。
- `robot_risk` 与验收方式一致。

执行前必须全文检查当前 L3 和 dispatch：

- 不得把 `ACT Contract Delta` 作为任务来源。
- 不得把 `AS-IS Contract -> TO-BE Contract -> Contract Delta` 作为当前主线。
- 不得引用旧 L2 ID 作为所属 L2、任务 group、分支 topic、dispatch 或 acceptance。

```

必须更新：

- 当前 L3 任务文件本身：勾选已验证成功标准，并在末尾追加执行摘要。
- 所属 L2 的 `05_acceptance/<l2>/验收结果.md`：登记本 L3 贡献的运行验收场景、实际命令、测试输入、观察点、通过 / 失败现象、证据链接、未验证项和是否影响 L2 Gate。
- 对应 L3 验收卡片：供验收 agent 独立评估；执行 agent 不得自行改验收结论。
- 不得擅自更新阶段级 `当前进度.md` 或共享 `执行记录.md`，除非当前 L3 明确要求。
- 执行 sub-agent 完成单个 L3 后不得自行提交或推送；主 Agent 在验收进入可提交终态后，按阶段四 Git 规则处理。所属 L2 Gate 通过后，才允许合入 `model_deploy`。

交接摘要必须包含：

1. 读取了哪些 L2 设计文档、Pi0.5 源码、ACT 源码和历史任务。
2. 任务文件身份校验结论。
3. 修改了哪些文件。
4. 新增或修改了哪些函数、class、配置、测试或脚本。
5. 如何验证，实际命令是什么。
6. 哪些成功标准已勾选，哪些未验证。
7. 是否影响 dry-run、fake-policy、real-policy、shadow-run 或 real-robot。
8. 回滚方式。
9. 本次明确没有做什么。
10. 后续建议生成或执行的 L3。
````

## 验收模式说明

| 模式 | 含义 |
|---|---|
| `direct-local` | 当前环境可直接运行 unit / import / config / mock 测试。 |
| `static-review` | 只能做结构、接口、边界评审。 |
| `downstream-l2` | 单个 L3 不构成闭环，由 L2 Gate 覆盖。 |
| `env-blocked` | 缺 ROS、bundle、依赖或环境变量。 |
| `hardware-blocked` | 依赖真机、传感器、夹爪、机械臂或 SDK 实机行为。 |

## 合格 L3 判断

生成完成后，必须能回答：

1. 这个 L3 属于哪个 L2？
2. 它参考了 Pi0.5 哪段源码？
3. Pi0.5 源码已经做到了什么？
4. 本次 ACT 版只实现什么？
5. 什么明确不能改？
6. 新增或修改的微元属于哪个 3.5 层类型？
7. 哪些微元封装为 class，为什么？
8. 是否有 dispatch 和验收卡片？
9. 是否有 dry-run、fake-policy 或 mock 验证路径？
10. 是否涉及 real-robot 风险？
11. 如何自动验收？
12. 如何回滚？

## 不合格 L3

- “实现整个模块”。
- “重构代码”但不说边界。
- 同时改多条不相关链路。
- 没有 Pi0.5 源码盘点。
- 没有六层产物落点声明。
- 没有 `dispatch`。
- 没有验收卡片。
- 没有验收方式。
- 没有回滚方式。
