# Agent 编程执行原则

## 适用范围

- 阶段：全局
- 任务模式：普通代码维护、Debug / Bugfix、代码类 L3、测试补充、配置调整
- 适用对象：Agent 对源码、测试、配置、脚本和代码相关文档的修改行为
- 不适用对象：纯知识查询、只读解释、历史归档整理

## 核心原则

Agent 写代码前必须先确认目标、边界和验收方式。对于明显的极小任务，可以保持说明简短，但不得绕过目标确认、最小修改和验证闭环。

## 一、先想清楚再编码

开始实现前，必须明确：

- 本次任务的唯一目标是什么。
- 本次任务明确不做什么。
- 允许修改哪些文件，禁止修改哪些文件。
- 直接依赖、上游接口和数据 shape 是否清楚。
- 验收命令、可观察结果和失败判据是什么。

如果目标、依赖、修改边界或验收方式不清楚，必须先停下说明缺口，不得靠猜测实现。

如果存在多种合理解释，必须说明解释差异和需要确认的点。不得静默选择会扩大影响面的方向。

## 二、简单优先

只实现当前任务明确要求的最小能力。

- 不添加未要求的功能。
- 不提前做未来扩展。
- 不为单次使用代码抽象新框架。
- 不添加未被验收标准覆盖的可配置项。
- 不为不在任务边界内的场景写复杂错误处理。

如果更少代码能满足同一验收，应优先选择更少代码。一个合格结果应让后续维护者能快速看出每段代码为什么存在。

## 三、外科手术式修改

每一处改动都必须能追溯到当前任务目标。

修改已有代码时：

- 只改必须修改的文件和行。
- 匹配现有代码风格、命名、错误处理和测试组织方式。
- 不顺手重构相邻代码。
- 不顺手格式化无关文件。
- 不删除或改写与当前任务无关的旧逻辑。

如果发现无关死代码、命名问题或结构问题，只在交接摘要或后续建议中说明；除非当前任务明确要求，不在本次处理。

如果本次修改制造了新的未使用 import、变量、函数、配置项或测试辅助对象，必须清理由本次修改造成的孤儿代码。

## 四、目标驱动与验收闭环

Agent 必须把任务转化为可验证目标。

常见转换方式：

- “添加校验”应落实为：先补无效输入测试，再实现校验并让测试通过。
- “修复 bug”应落实为：先用测试、日志或最小复现证明 bug，再修复并验证。
- “重构”应落实为：确认重构前后行为一致，并运行对应测试。
- “新增输出字段”应落实为：代码输出、数据样例或测试断言能观察到该字段。

多步任务开始前，应给出简短计划：

```text
1. 修改/新增什么 -> 用什么检查
2. 修改/新增什么 -> 用什么检查
3. 更新交接记录 -> 检查记录是否包含要求字段
```

执行完成后必须运行任务要求的验收命令。若因环境缺失无法运行，必须说明无法运行的具体原因、已完成的替代检查和剩余风险。

## 五、Debug / Bugfix 额外要求

修复前必须确认：

- 复现入口或最小失败现象。
- 失败影响的代码边界和数据边界。
- 本次修复是否需要把失败模式升级为单元测试、集成测试、结构测试、lint 或验收脚本。

如果同类失败可能重复出现，应优先把复现方式沉淀为测试或检查；暂时不能机械化时，在交接中说明原因和后续检查候选。

## 六、交接要求

完成后必须说明：

1. 修改了哪些文件。
2. 新增或修改了哪些函数、类、配置、脚本或测试。
3. 运行了哪些验收命令。
4. 哪些要求已验证，哪些未验证以及原因。
5. 当前明确没做什么。
6. 后续如果继续推进，下一步建议是什么。
