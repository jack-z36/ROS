
本模板用于把一个 L1 功能需求细化为可生成 L3 微元任务的能力模块说明书。

它不是代码任务，也不是完整设计文档。它的目标是稳定产出后续可拆分为 `L3 active task`、小 PR 或微元开发任务的说明依据。

## 使用原则

- L2 文件描述能力模块，不直接描述某一次代码执行任务。
- L2 文件必须说清输入、输出、核心数据语义、处理流程和可拆分的 L3 任务。
- L2 文件必须说明用户交互逻辑：开发者或用户如何调用该能力、入口在哪里、需要提供什么参数、会看到什么反馈。
- 用户交互逻辑必须参考 `DOCS/阶段二：数据清洗/00_架构与路线图/数据清洗pipeline宏观蓝图.md` 中的整体交互设计，不能脱离阶段二统一入口另起一套孤立交互。
- L2 文件不应提前锁死具体 `.py` 文件名、类名、函数名或配置文件名，除非这些对象已经存在并且必须被复用。
- 未知问题必须显式记录，不允许后续 Agent 自行猜测。

## 字段含义与填写要求

| 模板字段 | 含义 | 核心要提供什么信息 | 核心要提供什么约束 |
|---|---|---|---|
| 1. 能力名称 | 给这个 L2 模块命名 | 属于哪个场景、哪个能力 | 名称要具体，不能写成“数据处理”这类泛词 |
| 2. 所属位置与目标 | 说明它在 pipeline 中的位置 | 上游是谁，下游是谁，把什么变成什么 | 不能脱离场景边界，不能跨场景扩张 |
| 3. 输入 | 说明它吃什么 | 数据、配置、依赖、已有文件 | 输入必须明确，不能让 Codex 自己猜 |
| 4. 输出 | 说明它产出什么 | 数据文件、topic、报告、schema、mask | 输出必须可验收，不能只写“处理完成” |
| 5. 核心数据语义 | 说明输出数据的现实含义 | 单位、取值范围、坐标系、有效性 | 防止代码能跑但语义错误 |
| 6. 处理流程 | 描述从输入到输出的关键工序 | 主要步骤、顺序、数据流 | 不写具体代码实现，只写必要流程 |
| 7. 用户交互逻辑设计 | 说明开发者或用户如何调用该能力 | 调用入口、用户输入、交互步骤、反馈和可观测性 | 必须参考阶段二宏观蓝图中的整体交互设计，不能另起孤立入口 |
| 8. 配置需求 | 明确需要哪些配置项 | 配置名、类型、默认值、缺失处理 | 配置不能散落到代码里写死 |
| 9. 分层实现需求 | 说明各层职责 | Types / Config / Repo / Service / Runtime / UI 分别承担什么 | 防止把业务逻辑写进 Runtime 或 UI |
| 10. 失败情况与异常处理 | 预设可能失败的情况 | 失败原因、判断方式、处理策略 | 不能静默失败，必须有 reason / report |
| 11. 边界与不负责 | 明确不做什么 | 不属于本能力的内容 | 防止任务膨胀 |
| 12. 整体完成标准 | 判断 L2 是否完成 | 功能、报告、测试、smoke test | 必须可检查，不写空泛标准 |
| 13. L3 任务清单 | 生成后续 Codex 小任务 | L3 编号、输入、输出、验收方式 | 每个 L3 必须是小 PR 级别 |
| 14. 当前未知问题 | 记录未决策内容 | 不能确定的语义、配置、策略 | 未知问题不能让 Codex 擅自决定 |
| 15. L3 生成约束 | 约束后续任务拆分 | L3 的粒度规则 | 防止 L3 变成大任务 |

## 最核心的 4 个部分

如果需要压缩模板，最不能删除的是：

```text
输入
输出
核心数据语义
L3 任务清单
```

L2 的本质是：

```text
输入输出契约
+
语义定义
+
处理流程
+
L3 任务生成依据
```

## 合格 L2 文件的判断标准

写完后，必须能回答以下问题：

1. 这个能力在 pipeline 哪一段？
2. 它吃什么？
3. 它产出什么？
4. 产出的数据在现实世界中是什么意思？
5. 开发者或用户如何调用它？
6. 它不负责什么？
7. 失败时怎么处理？
8. 它能拆成哪些 L3 小任务？

如果这 8 个问题都能回答清楚，这个 L2 文件就够用于后续 L3 任务生成。
