# S1-7 执行约束 (Execution Constraints)

你在执行 execution plan 的具体任务时，必须遵循以下约束。

---

## 第五步约束：按分层原则设计程序架构

### C5-1 严格分层与单向依赖

架构必须将程序划分为固定层级，严格遵循以下顺序：

```text
Types → Config → Repo → Service → Runtime → UI
```

**各层职责：**

- **Types（类型层）**：最底层基座。定义数据结构、接口、数据传输对象、领域实体。不依赖后面任何一层。
- **Config（配置层）**：管理运行参数和环境设定（数据库连接串、密钥、超时常量）。将所有随环境变化的魔法数字集中管理。
- **Repo（仓储层）**：负责数据持久化和获取，直接与数据库、文件系统或外部接口打交道。隐藏底层存储细节。
- **Service（服务层）**：业务逻辑的"大脑"。调用 Repo 拿数据，按业务规则计算、转换、处理。不关心数据怎么存、怎么展示。
- **Runtime（运行时层）**：将各组件装配并驱动的"发动机"。管理依赖注入、生命周期钩子、事件循环、启动与终止机制。
- **UI（表现层）**：最外层，面向用户或外部调用方。网页前端、命令行界面或 API 端点。

**强制规则：**
- 依赖方向只能单向向前——后面的层可以调用前面的层，前面的层绝对不允许反向依赖后面的层
- 禁止跨层污染（如 UI 层直接写数据库查询代码）

### C5-2 横切关注点的统一入口

所有横切关注点（系统认证、结构化日志、遥测、连接器、功能标志等），必须通过单一且显式的统一接口进入系统。禁止在代码库中随处乱写底层系统调用。

### C5-3 边界校验与品味锁死

- **边界校验**：在系统边界处必须解析数据形状，绝不允许基于猜测操作未知数据（杜绝 YOLO 式探测）
- **品味锁死**：必须使用结构化日志，严格禁止裸 `print` 或 `console.log`；文件大小限制、Schema 与类型的命名约定必须严格校验

### C5-4 技术选型偏好

- 优先选择 API 极其稳定且在大型训练集中覆盖度极高的成熟技术（对智能体更易建模和组合）
- 对于上游行为不透明的技术库，倾向在自有代码中重新实现其关键子集，确保 100% 测试覆盖率和完全可预测的运行时行为

### C5-5 中央严格与局部自由

中央层面严格强制执行边界、正确性和可重复性；在这些不可逾越的护栏内部，允许在代码的具体表达和实现方式上拥有高度自主权。只要代码正确、可维护并符合上述扫描规则，即视为达标。
