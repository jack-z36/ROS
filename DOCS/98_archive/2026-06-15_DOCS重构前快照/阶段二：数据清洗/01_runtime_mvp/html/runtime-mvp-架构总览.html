阶段二：数据清洗 › runtime_mvp

Runtime MVP 程序架构

阶段二数据清洗 pipeline 的最小运行时骨架。把用户选择、配置、输入检查、run 目录、日志、manifest、错误摘要和 service 调用串成可运行闭环。不实现真实清洗算法。

架构分层

依赖方向（从左到右，不可反向依赖）
核心约束
Runtime 只编排流程，不写业务算法。Types/Config/Repo 是支撑层，不得反向依赖 Service/Runtime/UI。

Pipeline 数据流

10 个模块的输入输出串联

关键数据传递

传递环节传递什么谁用
01 → 所有RunContext（运行身份、模式、场景、路径）全部后续模块
02 → 3,8,9RunDirectory + RunDirectoryLayout配置快照、日志、manifest
03 → 4,5,6EffectiveRuntimeConfig + ConfigSnapshot配置预检、输入预检、调度
04 → 5,6ConfigPrecheckResult（通过/失败）输入预检、调度
05 → 6InputArtifactPrecheckSummary调度
06 → 7,8SceneDispatchPlan + SceneResultFake Service、日志
07 → 6,8,9FakeServiceResult调度汇总、日志、manifest
08 → 9RunLogFile + RuntimeLogWriteResultmanifest/错误摘要
09 → 外部processing_manifest / error_summary / run_resultUI、smoke test、后续 Agent

Run 目录布局

每次运行创建的独立目录结构
src/data_clean/runs/{run_id}/
├── outputs/                    ← 02 创建，Fake Service 调试输出
├── config_snapshot.yaml        ← 03 写入，最终生效配置快照
├── run_log.json                ← 08 写入，结构化运行日志
├── processing_manifest.json    ← 09 写入（成功路径）
├── error_summary.json          ← 09 写入（失败路径）
└── run_result.json             ← 09 写入（统一结果索引）
命名规则
单场景 {YYYY-MM-DD}_s{N} · 全流程 {YYYY-MM-DD}_all · 重复运行追加 _002、_003

01 · Runtime 运行上下文定义

1
运行上下文定义
P0

定义一次运行所需的最小数据语义，让所有后续模块共享同一份运行事实。

职责
  • 定义 RunContext、RunStatus、RunMode、SceneName、ServiceMode 等 9 个核心数据概念
  • 明确每个概念的字段、有效性规则、上下游关系
  • 为后续 L3 任务提供 Types 和状态流转的语义依据
输入 → 输出

入口参数（场景选择、配置路径、输入路径） → RunContext（所有模块共享的运行事实）

不做
  • 不创建目录、不读配置、不检查输入、不调 Service、不写任何文件
数据定义（9 个）

RunContext · RunStatus · RunMode · SceneName · ServiceMode · SceneResult · PipelineResult · RuntimeStepRecord · RuntimeErrorRef

02 · Run 目录管理模块

2
Run 目录管理模块
P0

为每次运行创建独立目录，向后续模块提供稳定的文件路径语义。

职责
  • 生成 run_id 和 RunDirectory，创建独立目录和 outputs/ 子目录
  • 声明 RunDirectoryLayout 中固定文件路径
  • 同一天同一场景重复运行时自动追加 _002、_003，不覆盖旧目录
输入 → 输出

RunContext（run_id、场景、模式） → RunDirectory + RunDirectoryLayout

不做
  • 不写任何文件内容（只声明路径）、不调 Service、不检查输入产物
数据定义（3 个）

RunDirectory · RunDirectoryLayout · RunArtifactPath

03 · 配置加载与配置快照模块

3
配置加载与配置快照
P0

读取配置 → 应用覆盖项 → 生成生效配置 → 写入 config_snapshot.yaml。

职责
  • 确定配置来源（默认/显式路径/环境变量），读取 YAML 配置
  • 应用临时覆盖项，生成 EffectiveRuntimeConfig
  • 将最终生效配置写入 run 目录的 config_snapshot.yaml
  • 回填 config_snapshot_path 到 RunContext
输入 → 输出

RunContext + YAML 配置文件 + 覆盖参数 → EffectiveRuntimeConfig + ConfigSnapshot

不做
  • 不校验配置字段是否满足场景业务要求、不检查输入产物、不调 Service
数据定义（4 个）

RuntimeConfigSource · ConfigOverrideSet · EffectiveRuntimeConfig · ConfigSnapshot

04 · 配置预检查模块

4
配置预检查模块
P0

配置放行闸门：判断生效配置是否满足 Runtime 继续执行的最低要求。

职责
  • 检查 EffectiveRuntimeConfig 是否存在、可消费、来源可追溯
  • 检查 ConfigSnapshot 是否指向本次 run 目录
  • 检查每个目标场景在生效配置中存在对应 Runtime 级配置块
  • 产出 ConfigPrecheckResult（passed + issues 列表）
输入 → 输出

EffectiveRuntimeConfig + ConfigSnapshot + 目标 SceneName → ConfigPrecheckResult

不做
  • 不读取配置文件、不检查输入产物、不校验 Service 业务参数
数据定义（4 个）

ConfigPrecheckRule · ConfigPrecheckIssue · ConfigPrecheckResult · SceneConfigRequirement

05 · 输入产物预检查模块

5
输入产物预检查模块
P0

输入边界守门：检查当前场景依赖的上游产物是否存在、可读、类型匹配。

职责
  • 根据目标 SceneName 确定需要检查哪些输入产物
  • 从 EffectiveRuntimeConfig 解析候选路径，检查存在性、可读性、类型
  • 汇总阻塞错误，产出 InputArtifactPrecheckSummary
输入 → 输出

EffectiveRuntimeConfig + 目标 SceneName → InputArtifactPrecheckSummary

不做
  • 不校验配置字段、不深查 MCAP topic 或 Parquet schema、不自动补齐缺失产物
数据定义（3 个）

InputArtifactRequirement · InputArtifactCheckResult · InputArtifactPrecheckSummary

06 · 场景注册与 Service 调度模块

6
场景注册与 Service 调度
P0

主调度枢纽：从注册表找到场景对应的 service，按顺序统一调度。

职责
  • 构建 ServiceRegistry，确认目标场景有可调用 ServiceBinding
  • 生成 SceneDispatchPlan（调度计划 + 顺序）
  • 预检都通过后，按顺序逐个调用 service
  • 汇总 SceneResult → PipelineResult，失败时停止后续场景
输入 → 输出

RunContext + ConfigPrecheckResult + InputArtifactPrecheckSummary + ServiceRegistry → SceneDispatchPlan → SceneResult → PipelineResult

不做
  • 不实现 fake/真实 service 业务行为、不读写业务产物、不写日志/manifest
数据定义（4 个）

ServiceRegistry · ServiceBinding · SceneDispatchPlan · SceneDispatchEvent

07 · Fake Service 模块

7
Fake Service 模块
P0

替身业务：提供可控的成功/失败假结果，验证调度、日志、manifest 和错误摘要链路。

职责
  • 根据 FakeServicePlan 的 behavior（success / controlled_failure）生成结果
  • 成功路径：声明假输出路径和执行耗时
  • 失败路径：生成可被下游消费的 RuntimeErrorRef
  • 输出路径只能位于本次 RunDirectory 或 outputs/ 内
输入 → 输出

FakeServicePlan + RunContext + RunDirectory → FakeServiceResult

不做
  • 不读取/写入真实 MCAP/Parquet、不实现任何业务算法、不决定调度顺序
数据定义（3 个）

FakeServicePlan · FakeServiceBehavior · FakeServiceResult

08 · 结构化日志模块

8
结构化日志模块
P0

运行追溯入口：把运行过程中的步骤、调度事件、结果和错误写成 run_log.json。

职责
  • 将步骤记录、调度事件、场景结果、PipelineResult、错误引用转换为 RuntimeLogEvent 列表
  • 写入 run 目录的 run_log.json
  • 返回 RuntimeLogWriteResult 供后续模块使用
输入 → 输出

步骤记录 + 调度事件 + 场景结果 + 错误引用 → run_log.json + RuntimeLogWriteResult

不做
  • 不创建 run 目录、不写 manifest/error summary、不保存大型业务数据内容
数据定义（3 个）

RunLogFile · RuntimeLogEvent · RuntimeLogWriteResult

09 · Manifest 与错误摘要模块

9
Manifest 与错误摘要
P0

结束态追溯：成功写 processing_manifest.json，失败写 error_summary.json，统一写 run_result.json。

职责
  • 成功路径：写入 processing_manifest.json（配置快照、场景结果、输入输出产物）
  • 失败路径：写入 error_summary.json（失败步骤、错误引用、日志路径、建议下一步）
  • 无论成功失败，都写入 run_result.json 作为统一结果索引
  • 所有文件只写在本次 RunDirectory 下
输入 → 输出

RunContext + ConfigSnapshot + SceneResult + PipelineResult + RuntimeErrorRef → processing_manifest / error_summary / run_result

不做
  • 不写 run_log.json、不创建 run 目录、不加载配置、不调 Service
数据定义（3 个）

ProcessingManifest · ErrorSummary · RunResultIndex

10 · Runtime smoke test 模块

10
Runtime smoke test
P0

验收层：用一组最小 smoke test 验证 1-9 模块串成的端到端闭环。

职责
  • 覆盖 5 条路径：单场景 fake 成功、fake 全流程成功、缺配置、缺输入、可控失败摘要
  • 为每个用例构造独立 RunContext、配置和输入前置条件
  • 断言期望状态、期望错误码、期望产物
  • 产出 RuntimeSmokeTestResult
输入 → 输出

RuntimeSmokeTestSuite → 执行 1-9 模块 → RuntimeSmokeTestResult

不做
  • 不实现真实业务算法、不定义日志/manifest 的完整 schema、不修改启动脚本
数据定义（3 个）

RuntimeSmokeTestCase · RuntimeSmokeTestSuite · RuntimeSmokeTestResult
