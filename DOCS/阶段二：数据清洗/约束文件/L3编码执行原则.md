# L3 编码执行原则

本文用于约束阶段二 L3 微元任务的代码执行方式。它服务于短上下文 Agent：当 Agent 只拿到一个 L3 任务文件时，必须先读取本文，再开始实现。

这些原则偏向谨慎和可验证。对于明显的极小任务，Agent 可以保持简短，但不得绕过目标确认、修改边界和验收。

## 零、执行期强制约束

执行代码类 L3 时，必须同时遵守：

- `DOCS/阶段二：数据清洗/约束文件/L3执行TDD与归档约束.md`
- `$tdd` 技能

只要任务涉及代码新增、代码修改、bug 修复或行为变更，就必须按 TDD 垂直切片推进：一个行为测试或最小复现 -> 最少实现 -> 验证通过 -> 必要整理 -> 下一个行为。

代码执行环境中的 Python 命令统一使用 `python3`。所有验收命令、示例命令和交接记录不得写成 `python`。

执行前必须先校验当前 L3 任务文件身份：用户指定路径、实际读取路径、文件名编号和正文 `L3 编号` 必须一致；找不到或不一致时必须停止，不得改读同目录其他 L3。随后确认当前分支是当前 L3 所属 L1 feature 分支，并读取当前 L3 文件明确列出的上下文；Runtime MVP 使用 `runtime-mvp`，Service 使用 `feature/stage2-service`。完成后必须勾选已验证成功标准、在当前 L3 文件末尾追加执行摘要，并将完成的 L3 文件从 `03_tasks/task/active/<功能组>/` 移动到 `03_tasks/task/completed/<L1归档目录>/<功能组>/`；如果原 active 功能组目录为空，必须删除该空目录。Ubuntu L3 执行端不得写集中执行记录或阶段进度文件。

Service 场景一到场景五的 L3 必须说明本任务对 `./start_data_clean.sh --dev` 开发者验收入口的影响。单个 L3 的自动化测试不能替代场景最终验收；场景最终验收必须由用户本人运行开发者入口、选择场景和功能检验项或场景完整 smoke test 后确认。

## 一、先想清楚再编码

开始实现前，Agent 必须先明确：

- 本 L3 的唯一目标是什么。
- 本 L3 明确不做什么。
- 执行对象、执行依赖、上游接口和成功标准是否足够清楚。
- 允许修改哪些文件，禁止修改哪些文件。
- 验收命令和可观察结果是什么。

如果目标、依赖、修改边界或验收方式不清楚，必须先停下说明缺口，不得自行猜测实现。

如果存在多种合理解释，必须先列出解释差异，并说明需要用户确认的点。不得静默选择一个方向。

如果存在更简单的实现方式，必须优先选择更简单的方式；如果用户要求的方案明显过重，应先说明取舍。

## 二、简单优先

只实现 L3 明确要求的最小能力。

- 不添加 L3 未要求的功能。
- 不提前做未来扩展。
- 不为单次使用代码抽象新框架。
- 不添加未被验收标准覆盖的可配置项。
- 不为不可能或不在本任务边界内的场景写复杂错误处理。

如果实现明显可以用更少代码完成，应先简化。一个合格的 L3 结果应让后续维护者能快速看出每段代码为什么存在。

## 三、外科手术式修改

每一处改动都必须能追溯到本 L3 的目标。

修改已有代码时：

- 只改必须修改的文件和行。
- 匹配现有代码风格。
- 不顺手重构相邻代码。
- 不顺手格式化无关文件。
- 不删除或改写与本 L3 无关的旧逻辑。

如果发现无关死代码、命名问题或结构问题，只在交接摘要中说明，不在本 L3 中处理。

如果本次修改导致新的未使用 import、变量、函数或测试辅助对象，必须清理由本次修改制造的孤儿代码；不得清理本次任务前已经存在的死代码，除非 L3 明确要求。

## 四、目标驱动与验收闭环

Agent 必须把 L3 任务转化为可验证目标。

常见转换方式：

- “添加校验”应落实为：补充无效输入测试，再实现校验并让测试通过。
- “修复 bug”应落实为：先用测试或最小复现证明 bug，再修复并验证。
- “重构”应落实为：确认重构前后行为一致，并运行对应测试。
- “新增输出字段”应落实为：代码输出、数据样例或测试断言能观察到该字段。

多步任务开始前，应给出简短计划：

```text
1. 修改/新增什么 -> 用什么检查
2. 修改/新增什么 -> 用什么检查
3. 更新交接记录 -> 检查记录是否包含要求字段
```

执行完成后必须运行 L3 指定的验收命令。若因环境缺失无法运行，必须说明无法运行的具体原因、已完成的替代检查和剩余风险。

## 五、交接要求

完成 L3 后，交接摘要必须说明：

1. 执行前读取了哪些相关 L3 任务文件或执行记录。
2. 修改了哪些文件。
3. 新增或修改了哪些函数、类、配置或测试。
4. TDD red / green / refactor 如何执行；如果无法完整执行，说明具体原因。
5. 运行了哪些验收命令，命令必须使用 `python3`。
6. 哪些成功标准已勾选，哪些未勾选以及原因。
7. Service 场景 L3 对 `./start_data_clean.sh --dev` 开发者入口、功能检验项或场景完整 smoke test 的影响。
8. 当前明确没做什么。
9. 后续如果继续推进，下一步建议是什么。

如果需要阶段级汇总或规划记录，只能在当前 L3 执行摘要中提出建议，由 Win 主机后续统一整理。
