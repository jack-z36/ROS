# 阶段四模型部署程序改造工作流

## 适用范围

- 阶段：阶段四：模型部署
- 任务模式：在同事已有模型部署程序基础上进行修改、适配、加固和验证
- 适用对象：模型部署入口、模型推理调用、observation 构造、action 转换、安全检查、机械臂 / 夹爪命令发送、运行日志和回滚路径
- 不适用对象：阶段二数据清洗 pipeline 的从零开发范式、阶段二 L2/L3 模板、阶段二功能模块清单

## 核心判断

阶段四不是从零开发。阶段四的主线是：

```text
现有代码契约盘点
→ 目标运行契约定义
→ 契约差异识别
→ 按差异聚合 L2 改造工作包
→ 拆成最小 L3 代码改造任务
→ 按 dry-run / fake-policy / real-policy / real-robot 阶梯验证
```

阶段四中的 `L1`、`L2`、`L3` 只表示任务层级：

- `L1`：模型部署程序改造总目标。
- `L2`：围绕一组相关 Contract Delta 的改造工作包。
- `L3`：对已有代码的一次最小、可验证、可回滚改造动作。

不得把阶段二的 `功能模块清单`、`L2能力模块模板`、`L3微元任务模板` 或 Service / Runtime 分类直接套用到阶段四。

## 强制原则

1. 先读现有代码，再定义改造任务。
2. 先写 AS-IS Contract，再写 TO-BE Contract。
3. 每个改造任务必须能追溯到 Contract Delta。
4. 默认保护同事原始可运行路径。
5. 能用 adapter 包装的，不直接重写核心逻辑。
6. 任何真机相关改造必须有 dry-run 或 fake-policy 验证路径。
7. 每个高风险改造必须写明回滚方式。
8. L3 不得空泛描述“实现某功能”，必须写清现有代码盘点和真实改造边界。

## 机械约束优先级

阶段四代码类 L3 必须读取并遵守：

- `DOCS/02_约束/编程执行/Agent编程执行原则.md`
- `DOCS/02_约束/编程执行/架构边界与机械约束原则.md`

如果某条架构、分层、命名、schema、日志或平台可靠性规则已经被脚本、lint、结构测试或验收命令表达，执行和验收以机械检查结果为准；文档用于解释规则意图和修复方向。

尚未机械化的规则先按文档执行。反复违反、影响面大或可稳定判定的规则，应在执行摘要或验收反馈中登记为后续 lint、结构测试或验收脚本候选。

## 阶段四执行约束

### Git 同步约束

阶段四模型部署改造采用 L2 分支制：

- 集成分支固定为 `model_deploy`。
- 每个 L2 使用独立三级分支，从 `model_deploy` 创建，命名为 `feat/model_deploy/<topic>`，例如 `feat/model_deploy/l2-01-types`。三级分支合入 `model_deploy` 后删除。
- 普通执行 sub-agent 不得提交或推送；Ralph / OpenCode 循环工程中，主 Agent 在单个 L3 验收进入可提交终态后，必须在所属 L2 分支执行 L3 原子提交并尝试小包 push。
- L2 Gate 通过 **且 人类验收签字通过** 后，AI 才可合入 `model_deploy`。合入流程：确认 L2 分支已提交 / 推送，切回 `model_deploy`，执行 `git pull --ff-only`，再用 `git merge --no-ff <三级分支>` 合入并推送，最后删除三级分支。人类验收关卡规则见 `attachments/人类验收关卡规则.md`。
- 遇到冲突、远端分叉、非预期变更、Gate 未通过、人类验收未签字或真机风险记录缺失，必须停止同步。
- 通用 Git 底线以 `DOCS/02_约束/Git协作/Git操作规则.md` 为准；阶段四分支、L3 原子提交、L2 Gate 后合入和 `model_deploy` 合并规则以 `DOCS/02_约束/Git协作/阶段四：模型部署 Git操作规则.md` 为准。Ralph / OpenCode 循环行为约束以 `DOCS/02_约束/循环工程/` 为准。

### 代码和产物落点约束

阶段四代码根目录按当前主线模型确定：

- 第一版（ACT）当前代码根目录：`src/model_deploy/act/`
- 历史保留：`src/model_deploy/pi05/` 是 Pi0.5 旧实现，原地保留不动，只作 AS-IS 参考，不得作为当前修改路径

生成或修改产物必须按以下规则存放（以 ACT 主线为例）：

- 可维护源码、配置、launch、运行脚本：放在 `src/model_deploy/act/` 下既有分层目录。
- 可维护测试：放在 `src/model_deploy/act/tests/` 下对应测试目录。
- **分层与产物落点细则**：ACT 代码树必须按 `types / config / repo / service / runtime / ui` 六层目录组织，每类产物（源码、配置实例、launch、单测、集成测试、验收脚本）有唯一落点。权威细则见 `attachments/ACT代码树分层与产物落点约束.md`，L2 / L3 执行时必须遵守。
- L2 / L3 验收专用脚本：放在 `DOCS/03_工程/阶段四：模型部署/05_acceptance/<l2>/scripts/`；只有复杂或重复运行场景才需要新增脚本。
- L2 / L3 验收日志、命令输出和人工记录：放在 `DOCS/03_工程/阶段四：模型部署/05_acceptance/<l2>/logs/`。
- L2 运行验收说明、实际执行记录和 Gate 结论：写入 `DOCS/03_工程/阶段四：模型部署/05_acceptance/<l2>/验收结果.md`。
- `src/model_deploy/third_party/` 默认只读，除非 L3 明确授权。
- `DOCS/03_工程/阶段四：模型部署/pi05_old/` 是历史源码快照，只能作为 AS-IS 参考，不得作为当前修改路径。

任何阶段四 L3、dispatch、验收命令或回滚命令中，当前代码路径不得写成 `pi05_test/pi05/...`。如果必须引用该路径，只能作为 `pi05_old` 历史源码引用并显式说明。

### L2 Gate 约束

每个 L2 改造工作包必须定义 L2 Gate。L2 Gate 不是单纯检查 required L3 是否完成，而是确认本 L2 改造后能按预期运行、可观察、可判断通过。L2 Gate 至少包含：

- required L3 清单。
- 当前 L2 分支名。
- 验收运行目录。
- 最低验证层级。
- 运行命令：cwd、命令、必要环境变量、输入文件或 ROS topic。
- 测试输入：mock 数据、配置、topic、shadow-run 或 real-robot 条件。
- 观察点：stdout、日志、topic、生成文件、metrics 或机器人行为。
- 通过现象：明确写出看到什么输出、日志、topic、shape、状态或人工现象才算 OK。
- 失败现象与排查入口。
- 未验证项处理方式。
- 是否允许进入下游 L2。
- 是否允许触发 L2 Git 自动同步。

每个 L2 必须额外定义**人类验收清单**（写入 `05_acceptance/<l2>/人类验收清单.md`），由人类在 Gate 通过后亲自运行。人类验收清单必含：验收项编号、运行命令（cwd/命令/env）、测试输入、观察点、通过现象、失败现象与排查入口、验收性质（`机械` 或 `人工`）。人类验收清单设计原则和签字格式见 `attachments/人类验收关卡规则.md`。

L3 只负责本任务局部验收，并说明自己贡献到哪个 L2 运行验收场景；L2 Gate 是 AI 侧判断整个 L2 是否完成的工程依据；**人类验收签字是是否允许批量同步和是否允许下游开工的最终依据**。

### L3 验收卡片与双 Agent 约束

阶段四 L3 执行 / 验收采用执行 agent 与验收 agent 分离：

- 执行 agent 读取 L3 任务文件，负责实现、局部验证和执行摘要。
- 验收 agent 读取对应 L3 验收卡片，负责评估完成度、运行无硬件可执行检查、输出反馈，不得改源码。
- 主 Agent 读取 dispatch 和 `skills/stage4-l3-orchestrator/SKILL.md`，负责分配 sub-agent、控制最多 3 轮执行-验收迭代。

每个 L3 必须有验收卡片：

```text
DOCS/03_工程/阶段四：模型部署/03_tasks/cards/<l2>/<deploy_id>_验收卡片.md
```

每个 L2 必须有整体验收卡片：

```text
DOCS/03_工程/阶段四：模型部署/03_tasks/cards/<l2>/<l2>_整体验收卡片.md
```

每个 L3 必须声明 `acceptance_mode`：

| 模式 | 含义 |
|---|---|
| `direct-local` | Ubuntu 22.04 无硬件下可直接跑 unit/import/config/mock/dry-run |
| `static-review` | 只能或更适合做代码结构、diff、接口、边界评审 |
| `downstream-l2` | 单个 L3 不构成完整运行闭环，依赖后续 L3 或 L2 Gate |
| `hardware-blocked` | 真实验收依赖机械臂、夹爪、传感器或 SDK 实机行为 |
| `env-blocked` | 理论可本地跑，但当前 Ubuntu 缺 ROS、bundle、SDK 或依赖 |

不是每个 L3 都强制有独立运行命令。能本地验收的必须验收；不能独立验收的必须被静态评审、下游 L2 场景覆盖或硬件 blocked 记录覆盖。禁止把无硬件环境下未验证的真机行为写成通过。

#### 角色职责

阶段四 L3 调度必须拆成四类职责，避免同一个 agent 既实现又验收：

| 角色 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|
| 主 Agent | dispatch、L3 文件、验收卡片、`skills/stage4-l3-orchestrator/SKILL.md` | 执行 sub-agent prompt、验收 sub-agent prompt、迭代决策、L2 Gate 决策 | 不直接替代验收 agent 给自己放行 |
| 执行 sub-agent | 单个 L3 文件及其列出的上下文 | 代码 / 测试 / 文档改造、局部命令结果、执行摘要 | 不改 dispatch、不做 Git 同步、不改验收卡片结论 |
| 验收 sub-agent | L3 验收卡片、L3 文件、执行摘要、允许查看的 diff / 日志 | `PASS_LOCAL` / `FAIL_LOCAL` / `BLOCKED_ENV` / `BLOCKED_HARDWARE_EXPECTED` / `DEFER_TO_L2_GATE` 和反馈 | 不改源码、不改测试、不提交、不移动任务 |
| L2 验收 agent | L2 整体验收卡片、L2 `验收结果.md`、全部 L3 执行和验收记录 | `L2整体验收报告.md`、是否允许进入下游 L2、是否允许 Git 自动同步 | 不伪造未运行命令、不把真机 blocked 写成通过 |

#### 单个 L2 的执行-验收流程

一个 L2 工作包执行时，主 Agent 按以下顺序调度：

1. 读取本 L2 的 dispatch，确认 required L3、依赖关系、`conflict_scope`、分支名和验收目录。
2. 读取本地 skill：`skills/stage4-l3-orchestrator/SKILL.md`。
3. 运行或等价执行 skill 校验逻辑，确认 L3、dispatch、验收卡片三者一致。
4. 按 wave、依赖和冲突范围挑选可执行 L3；冲突文件相同或互相依赖的 L3 不并行。
5. 为每个可执行 L3 生成执行 sub-agent prompt；执行 sub-agent 只按该 L3 文件工作。
6. 执行 sub-agent 完成后，运行该 L3 文件要求的本地验证命令；无法运行时必须记录环境缺口。
7. 主 Agent 再用对应验收卡片生成验收 sub-agent prompt。
8. 验收 sub-agent 按 `acceptance_mode` 判断：
   - `direct-local`：必须运行卡片中的本地命令并检查通过现象。
   - `static-review`：必须完成静态检查清单。
   - `downstream-l2`：必须指出由哪个 L2 场景最终覆盖。
   - `hardware-blocked`：只评估软件侧和真机风险，不允许宣称真机通过。
   - `env-blocked`：记录缺失依赖和未验证范围。
9. 如果结论是 `FAIL_LOCAL`，主 Agent 把反馈交回执行 sub-agent，最多迭代 3 轮。
10. 如果 3 轮后仍失败，主 Agent 停止该 L3 自动推进，要求人工介入。
11. 当 L2 required L3 都达到 `PASS_LOCAL`、`DEFER_TO_L2_GATE`、`BLOCKED_ENV` 或 `BLOCKED_HARDWARE_EXPECTED` 的可解释状态后，启动 L2 整体验收。
12. L2 验收 agent 按 L2 整体验收卡片和 `05_acceptance/<l2>/验收结果.md` 运行或记录 Gate，生成 `L2整体验收报告.md`。
13. 只有 L2 Gate 通过，且未验证项、blocked 项和真机风险记录都符合预期，才允许进入人类验收关卡。
14. **人类验收关卡**：主 Agent 暂停自动推进，向用户报告 Gate 结果并交付《人类验收清单》（`05_acceptance/<l2>/人类验收清单.md`）。用户亲自运行清单中的测试并签字（在 `验收结果.md` 的「人类验收」段勾选通过 + 用户名 + 日期）。只有人类验收签字通过，才允许触发阶段四 Git 同步规则。若用户不通过，反馈给执行 sub-agent 修正，最多 3 轮，仍不通过则停止并向用户报告。规则见 `attachments/人类验收关卡规则.md`。

#### 三个 L3 的最小示例

假设某个 L2 只有三个微元任务：

| L3 | 目标 | 验收模式 | 典型结论 |
|---|---|---|---|
| `deploy_101` | 定义 action 数据结构和值域 | `direct-local` | 单测通过后 `PASS_LOCAL` |
| `deploy_102` | 把配置文件接入 action 参数 | `direct-local` | 合法配置通过、非法配置失败后 `PASS_LOCAL` |
| `deploy_103` | 把 action 交给后续发布链路 | `static-review` + `downstream-l2` | 接口和边界评审通过，最终由 L2 dry-run 场景覆盖 |

该 L2 的运行方式如下：

```text
主 Agent 读取 dispatch
→ 发现 deploy_101 和 deploy_102 无文件冲突，可以并行执行
→ 分别生成两个执行 sub-agent prompt
→ 两个执行 sub-agent 完成代码和局部测试
→ 主 Agent 分别生成两个验收 sub-agent prompt
→ deploy_101 / deploy_102 验收 agent 运行本地命令并给出 PASS_LOCAL
→ 主 Agent 发现 deploy_103 依赖前两者，开始执行 deploy_103
→ deploy_103 执行 sub-agent 完成接线改造
→ deploy_103 验收 agent 做静态评审，并标记 DEFER_TO_L2_GATE
→ 主 Agent 启动 L2 整体验收卡片
→ L2 验收 agent 运行 dry-run 场景，确认三项能力在同一运行链路中闭合
→ 生成 L2整体验收报告.md
```

这个例子里，`deploy_103` 没有被强行要求提供独立命令；它必须被评估，但真正证明它有效的是 L2 dry-run 场景。无硬件条件下，真机发送行为如果出现在该链路中，只能记录为 blocked 或 shadow-run 通过，不能写成 real-robot 通过。

#### 验收结论处理

验收 sub-agent 只能输出以下结论之一：

| 结论 | 含义 | 主 Agent 后续动作 |
|---|---|---|
| `PASS_LOCAL` | 无硬件本地验收通过 | 记录通过，允许进入依赖它的下游 L3 |
| `FAIL_LOCAL` | 本地命令、静态检查或任务完成度失败 | 反馈给执行 sub-agent，最多 3 轮 |
| `BLOCKED_ENV` | 缺 ROS、依赖、模型 bundle、SDK 或环境变量 | 记录环境缺口，由主 Agent 判断是否可继续 L2 |
| `BLOCKED_HARDWARE_EXPECTED` | 真机、夹爪、传感器或 SDK 实机行为无法在当前环境验证 | 记录 blocked，不作为失败，但禁止宣称真机通过 |
| `DEFER_TO_L2_GATE` | 单个 L3 不构成运行闭环，需由 L2 场景证明 | 进入 L2 Gate 待验收清单 |

#### Ubuntu 22.04 无外设边界

当前默认开发环境是 Ubuntu 22.04 主机且没有任何外联设备。阶段四验收必须遵守：

- 每个 L3 必须被评估，但不强制每个 L3 都有独立可运行命令。
- unit、import、config、codec、mock、dry-run、shadow-run 能在本地跑的，必须在本地跑。
- ROS、模型 bundle、SDK、真机设备缺失时，必须写成 `env-blocked` 或 `hardware-blocked`，不能写成通过。
- 真机 smoke test 只允许写安全前置条件、人工观察点和 blocked 记录；没有硬件时不得伪造日志或结果。
- L2 Gate 是“这一组 L3 是否形成可运行阶段成果”的最终判断点。

## 阶段零：定位与边界确认

开始阶段四开发前，先确认：

- 阶段命名使用 `阶段四：模型部署`。
- 同事原始部署程序所在仓库路径。
- 原始启动命令、配置文件、模型文件、ROS topic、机械臂 SDK 和夹爪接口。
- 哪些文件允许修改，哪些文件只能包 adapter。
- 是否需要保留一条可直接回退到同事原始版本的运行路径。

输出：

```text
阶段四边界说明
同事源码入口清单
禁止破坏的原始可运行路径
```

## 阶段一：AS-IS Contract

阅读同事源码后，必须先写出现有运行契约。AS-IS Contract 回答：

```text
同事现在的部署程序，在真实运行时到底是怎么工作的？
```

AS-IS Contract 至少包含：

- Runtime Entry：程序入口、启动命令、主循环、配置文件、运行环境。
- External Dependencies：模型、ROS topic、机械臂 SDK、夹爪接口、硬件设备。
- Input Contract：输入来源、字段、格式、单位、坐标系、频率、缺失处理。
- Internal Data Model：observation、action、robot_state 的内部表示和隐式约定。
- Policy / Model Contract：模型调用方式、输入、输出、推理频率、失败处理。
- Output Contract：机械臂和夹爪命令格式、单位、坐标系、发送频率、阻塞语义。
- Failure Semantics：输入缺失、推理失败、SDK 错误、机械臂超时后的行为。
- Observability：现有日志、可复现信息、SDK 返回码记录情况。
- Existing Guarantees：当前稳定能力、不能破坏的能力、被其他模块依赖的接口。

出口标准：

```text
不看源码的后续 Agent 能通过 AS-IS Contract 说清现有程序怎么启动、怎么取输入、怎么推理、怎么发命令、失败时怎么处理。
```

## 阶段二：TO-BE Contract

TO-BE Contract 回答：

```text
改造完成后，部署程序必须对外承诺什么行为？
```

TO-BE Contract 至少包含：

- Target Runtime Contract：运行入口、dry-run、fake-policy、real-policy、real-robot 等模式边界。
- Target Input Contract：目标 observation 字段、shape、dtype、单位、坐标系、频率、缺失策略。
- Target Policy Contract：统一 policy 接口、DummyPolicy、真实模型、超时和失败语义。
- Target Action Contract：tcp_delta、gripper_target、左右臂顺序、值域、最大单步变化。
- Target Safety Contract：NaN / Inf、限幅、workspace、IK、急停、SDK 返回码等发送前检查。
- Target Output Contract：最终机器人命令类型、参数格式、阻塞语义、返回值、超时处理。
- Target Observability Contract：每轮控制循环必须记录的信息。
- Target Compatibility Contract：旧接口保留、adapter 包装边界、允许破坏性修改的接口、回滚方式。

出口标准：

```text
TO-BE Contract 能作为验收依据，而不是愿望清单。
```

## 阶段三：Contract Delta

Contract Delta 是 AS-IS 到 TO-BE 的契约变更集。每条 Delta 必须说明：

| 字段       | 含义                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| 编号       | 例如 `D1`、`D2`                                                                                     |
| 变更对象   | Runtime Mode、Input Contract、Policy Interface、Action Format、Safety Check、Output Command、Logging 等 |
| AS-IS 契约 | 当前真实行为                                                                                            |
| TO-BE 契约 | 目标承诺行为                                                                                            |
| 变更类型   | 新增 / 修改 / 删除                                                                                      |
| 影响范围   | 入口、模型调用链、控制链路、真机发送链路、日志系统等                                                    |
| 是否兼容   | 兼容 / 需适配 / 破坏性修改                                                                              |
| 实现方式   | adapter、参数扩展、包装旧调用、插入 gate、补日志等                                                      |
| 验收方式   | dry-run、单元测试、fake-policy、真实模型离线推理、真机 smoke test                                       |
| 回滚方式   | 默认关闭、切回旧入口、移除 adapter、关闭 safety gate 等                                                 |

出口标准：

```text
每个后续 L2 / L3 都能追溯到一个或多个 Delta。
```

## 阶段四：L2 改造工作包

L2 不是阶段二意义上的功能模块说明，也不要求生成 `功能模块清单.md`。阶段四 L2 是：

```text
围绕一组相关 Contract Delta，在已有代码某个边界上进行的一组可控改造。
```

每个 L2 改造工作包必须包含：

- 对应的 Contract Delta 编号。
- 涉及的现有代码文件、入口、类、函数或配置。
- 已有能力盘点。
- 必须保留的原始行为。
- 本 L2 的真实改造边界。
- 优先采用 adapter 还是允许直接修改。
- 真机风险等级。
- 验收路径。
- 回滚方式。
- 可拆分的 L3 改造任务草案。

### L2 改造工作包划分原则

L2 聚类方式不得预设。必须先阅读 AS-IS Contract、TO-BE Contract 和 Contract Delta，再根据底层设计原则生成当前项目自己的 L2 改造工作包。

注意：最终生成的工作包，不得超过5个。

本工作流采用以下原则：

1. 按设计决策聚类，不按执行时序聚类。

   - 不要因为运行链路是 `输入 → 推理 → 动作 → 发送`，就机械地生成四个 L2。
   - 应先识别哪些设计决策最难、最可能变化、最需要隔离，例如模型接口、动作语义、坐标系、真机发送策略、失败处理。
2. 按信息隐藏边界聚类。

   - 如果一组 Delta 共同依赖同一种内部知识，就应优先放进同一个 L2。
   - 例如“真实模型 checkpoint 怎么加载”“模型输出张量如何解释”“SDK 返回码如何转成失败语义”都属于应被隐藏的内部知识。
   - L2 的目标不是让所有细节暴露给下游，而是把不稳定知识封装在一个改造边界内。
3. 按变化原因聚类。

   - 同一类变化原因应尽量进入同一个 L2。
   - 不同变化原因不要强行合并，即使它们在运行时相邻。
   - 例如“更换模型结构”和“调整真机安全限幅”通常是两类变化原因，不应为了控制链路连续而塞进同一个 L2。
4. 按外部接口最小化聚类。

   - 一个好的 L2 应有尽量小、稳定、清晰的对外契约。
   - 如果某个 L2 需要让下游知道太多内部字段、临时状态、文件布局或算法细节，说明聚类边界可能错了。
   - L2 内部可以复杂，但暴露给其他 L2 / L3 的接口必须简单。
5. 按依赖方向聚类。

   - L2 之间应形成清晰的单向依赖，不应互相知道对方内部实现。
   - 如果两个候选 L2 之间需要频繁互相读取内部状态，应考虑合并，或先抽出一个更稳定的 adapter / contract。
   - 如果一个 L2 同时依赖多个未稳定上游，应先生成接口对齐类 L2，而不是直接进入实现类 L2。
6. 按验证阶梯聚类。

   - 能用同一类验证方式验收的一组 Delta，可以优先放在同一个 L2。
   - 只需要 dry-run 验证的改造，不应和必须 real-robot 验证的改造混在同一个 L2。
   - 一个 L2 如果同时跨越 dry-run、real-policy 和 real-robot，通常过大，应继续拆分。
7. 按回滚边界聚类。

   - 可以用同一个开关、同一条旧路径或同一层 adapter 回滚的一组 Delta，可以优先聚成一个 L2。
   - 如果某组 Delta 的回滚方式完全不同，不应为了表面相关而放在同一个 L2。
8. 代码位置只是辅助判断，不是主判断。

   - 同一个文件里的改动不一定属于同一个 L2。
   - 分散在多个文件里的改动也可能属于同一个 L2，只要它们隐藏同一个设计决策，并共享同一外部契约。
9. 每个 L2 只承载一个主要抽象。

   - 一个 L2 必须能用一句话说明它隐藏了什么复杂性。
   - 如果一句话中同时出现多个“并且”，通常说明它混合了多个抽象，应拆分。
10. 优先生成深 L2，避免浅 L2。

    - 深 L2：内部处理较完整，对外接口简单，下游使用成本低。
    - 浅 L2：只是给每个小步骤起一个名字，对外仍泄露大量内部细节。
    - 阶段四改造应避免为了“看起来颗粒度细”而制造大量浅 L2。

生成 L2 改造工作包时，必须先回答以下问题：

```text
1. 这组 Delta 共同隐藏了什么设计决策？
2. 这组 Delta 是否有共同变化原因？
3. 这组 Delta 对外暴露的最小契约是什么？
4. 下游是否需要知道它的内部细节？
5. 它和其他 L2 的依赖方向是否单向、清晰？
6. 它的验证阶梯是否一致？
7. 它的回滚方式是否一致？
8. 它是否只是按运行步骤切出来的浅边界？
```

只有这些问题回答清楚后，才能生成具体的 L2 改造工作包列表。

出口标准：

```text
每个 L2 都能回答：为什么改、改哪里、不能改哪里、怎么验收、怎么回滚。
```

## 阶段五：L3 微元改造任务

L3 是对已有代码的一次最小改造动作。每个 L3 必须满足：

- 单个 Agent 在一轮任务中可以读完上下文、完成改造、执行验证并交接。
- 只解决一个核心目标。
- 明确写出已有代码盘点。
- 明确写出本次真实改造边界。
- 明确写出禁止修改内容。
- 明确写出验收命令或人工验收路径。
- 真机相关任务必须说明不触发真机动作的验证方式。
- 高风险任务必须说明回滚方式。

正式生成阶段四 L3 时，可以参考阶段二 L3 模板的结构骨架，但必须读取并使用阶段四专用模板：

```text
DOCS/02_约束/工作流/阶段四开发工作流/attachments/L3微元改造任务模板.md
```

阶段四 L3 模板保留任务定位、调度元数据、唯一目标、必读上下文、修改边界、验收方式和完成后交接这些通用结构；删除或替换阶段二专属的数据清洗任务类别、Service 开发者入口、阶段二开工自检和功能组归档规则。

L3 不得写成：

```text
实现模型部署程序
完善安全逻辑
接入机械臂
优化日志系统
```

L3 应写成：

```text
为现有部署入口增加 dry-run 参数，并保持默认启动行为不变
实现 DummyPolicy adapter，并接入 dry-run 控制循环
在发送机器人命令前插入 NaN / Inf 检查
记录每轮 policy_action 和 robot_command
```

每个 L3 建议包含以下章节：

```text
任务目标
来源 Delta
所属 L2 改造工作包
必读文档
必读代码
现有程序盘点
真实改造边界
禁止修改
实施步骤
验收方式
回滚方式
完成后交接
```

## 阶段六：工程记录

阶段四开发过程中，工程记录应放在：

```text
DOCS/03_工程/阶段四：模型部署/
```

建议后续按需要建立：

```text
01_contracts/
02_l2_change_packages/
03_tasks/
04_debug/
05_acceptance/
```

其中：

- `01_contracts/` 放 AS-IS Contract、TO-BE Contract、Contract Delta。
- `02_l2_change_packages/` 放 L2 改造工作包。
- `03_tasks/` 放 L3 微元改造任务、active / completed / dispatch。
- `04_debug/` 放调试记录。
- `05_acceptance/` 放 L2 运行验收说明、L2 Gate 结论、L2/L3 验收专用脚本和日志。

阶段四已建立上述工程目录时，后续 L2/L3 必须遵守对应落点；如果新增其他工程目录，必须先更新本工作流或阶段四工程索引。

## 禁止事项

- 禁止把阶段四当作阶段二从零开发流程处理。
- 禁止跳过 AS-IS Contract 直接写 TO-BE 或任务。
- 禁止在没有现有代码盘点的情况下生成 L3。
- 禁止把阶段二 `功能模块清单.md` 作为阶段四必需产物。
- 禁止直接套用阶段二 L2 / L3 模板生成阶段四任务；阶段二 L3 模板只能作为结构参考，正式生成必须使用阶段四 L3 微元改造任务模板。
- 禁止让后续 Agent 自行猜测同事源码中哪些能力必须保留。
- 禁止将真机发送链路改造和模型接口重构揉进同一个 L3。
- 禁止没有 dry-run / fake-policy 验证路径就直接进入 real-robot。

## 输出要求

使用本工作流生成阶段四开发文档或任务时，必须说明：

- 当前产物属于 AS-IS、TO-BE、Delta、L2 改造工作包还是 L3 微元改造任务。
- 目标路径。
- 涉及的现有代码路径。
- 尚未确认的问题。
- 是否存在真机风险。
- 本次是否会创建工程文件、任务文件或只做规划讨论。
