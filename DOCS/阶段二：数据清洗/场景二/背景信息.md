# 阶段二场景二：背景信息

## 场景定位

cleaned MCAP 已经补齐夹爪宽度和 common frame 位姿表达，但它仍可能包含硬件噪声、跟踪跳变、触觉异常、缺失段或机器人不可执行的轨迹。

如果这些问题直接进入时间对齐和 canonical dataset，后续模型会学习到错误动作，甚至在部署阶段带来硬件风险。因此本场景在时间对齐之前，先做数据可靠性验证。

## 输入数据形态

本场景输入为 cleaned MCAP，通常包含：

- 图像数据。
- 左右 common frame 相机 pose，后续可扩展为 TCP pose。
- 左右触觉数据。
- 左右夹爪宽度。
- 场景一产生的清洗报告和标定/转换参数。

## 可靠性验证的两个维度

### 信号可靠性

硬件信号可能出现：

- 位姿高频噪声。
- 位姿跳变或跟踪丢失。
- 触觉尖峰或异常突变。
- 局部缺失段。
- 非法数值或明显超出合理范围的数据。

本场景需要通过滤波、异常检测和补全策略，将这些问题变成可追溯的处理结果。

### 机器人执行可行性

阶段二最终服务于机器人模仿学习和部署，因此位姿轨迹不仅要看起来连续，还需要满足机器人约束。

需要关注：

- IK 是否可解。
- 关节角是否在限制内。
- 关节速度和加速度是否安全。
- workspace 是否合理。
- 仿真中是否出现明显不可行情况。

具体机器人模型、约束参数和仿真实现方式应在进入实现时确定，并记录到对应输出清单和架构文档中。

## 输出数据形态

validated MCAP 应代表“已经通过可靠性处理的数据版本”。它可以包含修复后的数据，也可以保留问题标记，但不能让异常片段失去追溯。

配套报告应回答：

- 哪些地方被判定为异常。
- 哪些异常被修复。
- 哪些异常只能标记为不可用。
- 哪些轨迹不满足机器人约束。
- 哪些判断来自仿真或约束检查。

## 与后续场景的关系

场景三会基于 validated MCAP 生成统一时间轴。如果场景二没有把异常和不可执行片段标清楚，场景三只能对错误数据做对齐，场景四也无法生成可靠 masks。

## 风险与未知

- 滤波参数和异常阈值需要根据真实数据调优。
- IK 求解可能有多解，需要考虑轨迹连续性。
- MuJoCo 或等价仿真依赖准确的机器人模型和约束参数。
- 长时间缺失或严重异常可能无法修复，只能交给 masks 标记为不可训练。
