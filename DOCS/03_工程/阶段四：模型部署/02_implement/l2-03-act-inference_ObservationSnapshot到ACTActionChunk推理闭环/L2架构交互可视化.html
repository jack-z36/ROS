① 这部分代码整体在干什么（一句话）

像一个"后台厨师"——前面（L2-06）下单说"这盘观测数据给我做成一批动作"，厨师就在后厨默默把食材（snapshot）处理成模型能吃的样子（batch），喂给模型（policy），等模型吐出一串动作（action chunk），再装盘递回前面（result queue）。全程不卡住前台，因为厨师在独立的后厨（后台线程）干活。

厨师循环很简单：看订单队列有没有新单 → 有就拿去做 → 做好放结果队列 → 继续看。和前台（ControlLoop）通过两个队列沟通，互不阻塞。

📖 术语词典（点开随时查，用《用户认知框架与讲解偏好》的概念体系解释）
ObservationSnapshot对应认知框架第 3.5 层"数据"。"一盘刚拍好的食材"——某一瞬间所有传感器数据（图像 + 状态）冻结成一个完整对象。由 L2-02 准备好放那儿，本 L2 只负责拿来做菜。
batch对应认知框架第 3.5 层"计算函数"的产物。"模型能吃的标准化摆盘"。模型不直接吃原始 snapshot，要先把 state 归一化到 [−1,1]、图像整理成指定格式、贴标签（task）。纯 RAM 内数据变换。
policy
（策略模型）		"厨师的大脑"——一个训练好的神经网络。给它一盘标准化观测，它预测接下来该怎么动。本 L2 不训练它，只调用它。
predict_action_chunk对应认知框架第 3.5 层"编排函数"。"厨师做一次菜"——调模型一次，产出一串动作（不是单个）。比如一次产出 chunk_size=30 步连续动作。
normalize
unnormalize		对应认知框架第 3.5 层"计算函数"（RAM 内）。模型只认 [−1,1]。normalize 把物理值压到 [−1,1]（推理前）；unnormalize 把模型输出的 [−1,1] 还原回物理尺度（推理后）。两个方向都要做，否则动作幅度全错。
InferenceWorker
（推理工人）		对应认知框架第 3.5 层"编排函数"+"内部状态更新函数"。一个后台不停转的线程。循环：看队列有无新单 → 有就拿去做 → 做好放结果队列 → 继续。和前台通过两个队列通信。
latest-only
queue		一个特殊队列：新订单来了，旧的直接扔掉。推理要低延迟，过时观测做了也没意义。LatestQueue。
fake-policy
（假模型）		一个"假装是模型"的替身——不加载真实权重，直接返回 shape 正确的假动作块。目的：无 GPU / 无 bundle 时也能验证"从下单到出菜"整条链路是否通。
async 解耦"前台点完单就能去干别的，不用等厨师做完"。control tick 每 1/30 秒跑一次，不能卡在等模型（可能几十毫秒）。所以推理放后台线程，前台只管下单和取菜。

② 整体流程：四个步骤（后台推理轴）

Pi0.5 这部分代码在后台线程里循环执行。任一次推理出错，记录后继续下一个，不崩溃。

1

取订单

从 inference_request_queue 取最新 request。无单就等 1ms 再看。latest-only：旧订单被新订单覆盖。
2

备料+做菜

predict_action_chunk：snapshot→batch（normalize state）→preprocess→GPU 推理→unnormalize→校验 shape→截断。
3

装盘递回

构造 ActionChunk（含时间戳 + request_id），写入 chunk_result_queue。
4

记账+限速

记录 metrics（延迟/计数）；按 inference_hz 限速，避免空转过载。失败则记 inference_error，不崩溃。

③ 跟一次推理走完全流程

假设 L2-06 在 tick 时决定要新 chunk，创建 InferenceRequest 丢进队列。跟着它走一遍：

# L2-06 在 tick 时创建 request（L2-06 职责，不是本 L2） ① # InferenceWorker 后台线程从队列取最新 request（编排函数，后台线程） request = request_queue.get_latest_or_none() # latest-only，旧的被丢 ② # 按 inference_hz 限速（编排函数） remaining = period_s - (now - last_start) # if remaining > 0: wait，continue（避免空转过载） ③ # 调核心推理（编排函数 → 调 repo/service） actions = policy_runtime.predict_action_chunk(request.observation) # 3a. build_batch: state normalizer.normalize(encoded_state) → batch [计算函数] # 3b. preprocessor(batch) [计算函数] # 3c. batch move to cuda [内部状态更新] # 3d. policy.predict(batch) → norm_chunk [−1,1] [GPU 推理，最耗时] # 3e. cpu() + clamp(−1,1) [计算函数] # 3f. action_normalizer.unnormalize → 物理尺度 [计算函数] # 3g. 校验 shape[1]==16, 截断 chunk_size [计算函数] ④ # 构造 ActionChunk 并写回（内部状态更新函数） chunk = ActionChunk(actions, obs_time, infer_start, ready_time, action_dt, request_id) shared_buffer.record_inference_latency(ready_time - infer_start) result_queue.put_latest(chunk) # ── 如果第③步模型抛异常会怎样？ ③' # _run_request 用 try/except 捕获 except Exception: shared_buffer.record_inference_error(message) # 记 error_count++ + last_error，worker 继续下一个 request，不崩溃 # L2-06 下个 tick 发现长期无新 chunk / error 增长 → 进入 fallback

④ 模型包（bundle）里有什么（推理需要读的外部资源）

推理链路启动时要读模型包目录（训练完成后导出，部署只读不改）。L2-03 复用 L2-01 的四个读取函数（bundle_reader/manifest_parser/normalizer_loader/experiment_config_loader）：

act_pour_water_v1/ ← bundle_dir 指向这里（L2-01 已校验） ├── manifest.json ← 清单：维度(16)、模型信息、相机名、打包时间 ├── normalizers.json ← state/action 的 min/max/identity_indices（长度须 16，L2-01 已校验） ├── experiment_config.yaml ← ACT 训练配置（只读原值，做交叉校验，不覆写维度） └── policy/ ← ACT 策略权重（L2-03 加载到 GPU；fake 模式跳过）

fake-policy 模式下只读 manifest 拿相机名与维度，不加载权重，直接返回 shape 正确的假动作块——保证无 bundle/GPU 也能验收整条推理链路。

⑤ Pi0.5 推理链路的两个核心入口

启动期：load_policy_runtime

一次性加载：bundle 校验→模型构建（Pi0.5 VLA + LoRA）→adapter 权重→preprocessor→normalizer→构造 Pi05PolicyRuntime。

ACT 差异：模型替换为 LeRobot ACT；无 LoRA 包裹；增加 fake-policy 分支。

稳态：InferenceWorker.run

后台 daemon 线程循环：get_latest_or_none→限速→_run_request（predict→构造 chunk→record→put）。try/except 捕获失败。

ACT 差异：几乎完全一致，直接复用。

⑤ 回答四个核心问题

❶ 谁持有状态？

  • Pi05PolicyRuntime：model/policy/preprocessor/normalizer/device，启动期创建后稳定只读。
  • InferenceWorker：_stop_event/period_s，后台线程生命周期。
  • SharedBuffer.metrics：全局计数器，锁保护。

❷ 谁跨越外部边界？

  • 启动期：load_policy_runtime 读 bundle + 加载权重到 GPU。
  • 稳态：policy.predict_action_chunk 调 GPU（跨进程-设备边界，最耗时）。
  • 本 L2 不订阅/不发布 topic。

❸ 谁只负责加工 RAM 对象？

  • _build_batch（snapshot→batch dict）
  • normalize/unnormalize（min-max 变换）
  • clamp、shape 校验、截断

❹ 谁负责 runtime 时序？

InferenceWorker.run：后台循环、inference_hz 限速、stop 控制。失败用 try/except 捕获并 record_inference_error，不崩溃。不进入 ControlLoop.tick()（那是 L2-06）。

维度 3 · 开发建议与蓝图

📖 阅读路径：了解代码如何组织 → 代码写完后用维度4检查产物清单

L2-03 是后台推理角色。建议按「repo 加载 policy runtime → service 做 batch → runtime 跑 InferenceWorker」三层开发。fake-policy 是 Gate 必选项。

图① 一次推理请求的运行时协作调用链

这张图回答"运行起来后，各层模块怎么协作"——按步骤①→⑥看箭头方向：L2-06 是驱动方（tick 提交 request），runtime worker 取 request 后调 repo 推理，repo 内部调 service 做 batch，成功则写回 result_queue，失败则记录错误并停止。每一步都标了对应的 3.5 层微元类型，可与图②对照。L2-01 只在编译时注入配置，不参与运行时调用（虚线）。

关键协作事实（对照图②）：① L2-06 是驱动方，tick 提交 request 触发整条链；②③ runtime worker 的 run() 是编排函数，消费 request、调 repo、写 chunk；④ repo 的 predict_action_chunk 是编排函数（内部编排 batch→GPU→unnormalize），service 的 build_act_batch 是计算函数（纯 RAM 变换），GPU predict 是数据读写函数（跨进程/设备边界）；⑤ runtime 的 put_latest 是内部状态更新函数（覆盖 latest chunk）；⑥ 下游 L2-06 在独立 tick 内读取。L2-01 只注入配置，运行时不参与调用。失败时 worker 不崩溃，记录 error 后继续循环。

service/ · batch 构造层（函数，无 class）

把 ObservationSnapshot 加工成 ACT batch（纯 RAM 内 dict 构造）+ normalizer 使用。不安排线程、不持有 queue。Pi0.5 参考：Pi05PolicyRuntime._build_batch。

batch_adapter.py（函数，无 class）

为什么无 class？batch 构造是无状态纯转换（不持有 buffer/queue/cache），每次调用独立。按认知框架第 3.25 层判断原则：纯输入到输出转换 → 优先函数。

计算函数build_act_batch(observation, state_normalizer, task, image_names) — 输入 ObservationSnapshot + ActionStateNormalizer + str + tuple → 输出 dict[str, CPU float Tensor]（含 observation.state(16,) normalized、observation.images.*、task）。调 state_normalizer.normalize(encoded_state)。缺图像 key 抛 KeyError
计算函数normalize_state(state, normalizer) / unnormalize_action_chunk(norm_chunk, normalizer)（可选薄封装）— 纯 RAM 内 min-max 变换。或直接复用 repo 持有的 ActionStateNormalizer method

文件：service/batch_adapter.py（可选 service/normalizer.py）。验收覆盖：合法 snapshot→正确 batch dict；缺 key 抛 KeyError；normalize→unnormalize 往返一致。
参考 Pi0.5：Pi05PolicyRuntime._build_batch（落点可选 method 或独立函数，推荐独立函数保持六层清晰）。

runtime/ · 后台推理层（2 个文件，多个 class）

承载共享数据结构 + 后台推理线程。被 L2-02/L2-03/L2-06 共同使用。Pi0.5 参考：deploy/runtime/shared_buffer.py + inference_worker.py（直接复用）。

InferenceWorker（class，继承 threading.Thread）

后台 daemon 线程，异步消费 request→推理→写 chunk+metrics。与 ControlLoop 并行。Pi0.5 直接复用。

数据变量名：policy_runtime/request_queue/result_queue/shared_buffer/period_s/action_dt/log_info/log_debug/log_warning | 存储结构：Thread 实例字段
编排函数run() — 顺序：循环 ①get_latest_or_none ②无则 wait 0.001s continue ③按 inference_hz 限速 ④调 _run_request；调用条件：daemon 线程启动后持续循环；失败处理：_stop_event 触发时退出循环_run_request(request) — 顺序：①infer_start ②try predict_action_chunk ③except record_inference_error+return ④构造 ActionChunk ⑤record latency/count ⑥result_queue.put_latest；调用条件：有 request 且未超 inference_hz；失败处理：异常被 try/except 捕获，记录 error 后返回，不崩溃

shared_buffer.py 数据结构（frozen dataclass + queue + buffer）

跨模块共享的 RAM 对象。第一版由 L2-03 落地，L2-02/L2-06 import 复用。

数据ActionChunk（frozen dataclass）— 结构：actions (chunk_size,16) + obs_time + infer_start_time + ready_time + action_dt + request_id + cursor；数值类型：np.ndarray float32 + float + int；含 __post_init__ 校验 rank-2 + action_dt>0InferenceRequest（frozen dataclass）— 结构：observation + obs_time + request_id + trigger_step；数值类型：ObservationSnapshot + float + intObservationSnapshot（frozen dataclass）— 结构：images + state + encoded_state (16,) + captured_at_s；数值类型：dict + ObservationState + np.ndarray float + float
内部状态更新LatestQueue[T] — 修改对象：内部 deque + lock；如何修改：put_latest 追加并覆盖旧值，get_latest_or_none 返回最新或 None（latest-only 语义）SharedBuffer — 修改对象：聚合 latest_observation/request_queue/result_queue/metrics；如何修改：record_* 方法更新对应计数器（inference_count/error_count/request_count）RuntimeMetrics — 修改对象：inference_count/error_count/request_count + latency EMA + last_error；如何修改：record_latency 更新 EMA，record_error 更新 last_error + error_count

文件：runtime/inference_worker.py、runtime/shared_buffer.py。验收覆盖：ActionChunk 非法 rank 抛异常；LatestQueue latest-only；record_* 计数；worker 消费→写 chunk→metrics→不阻塞；异常→error_count→不崩溃；inference_hz 限速。
参考 Pi0.5：deploy/runtime/{shared_buffer,inference_worker}.py（直接复用，14→16）。

ui/ · 本 L2 不落点

原因：L2-03 是后台计算角色，只消费 RAM 内 request、产出 RAM 内 chunk，不直接与外部世界交换数据。订阅 observation topic 归 L2-02；发布 policy_action/command 归 L2-05；启动 ROS node/timer 归 L2-06。InferenceWorker 是普通 threading.Thread，不是 ROS node。

与去平滑的关系：不定义 /act/smoothed_action、/act/blended_action 或 RTC 平滑相关 topic。

验收确认：L2-03 不产生 ui/*.py 或 launch 产物；rg 检查无 import rospy/rclpy。

维度 4 · 人类验收标准

📖 阅读路径：功能承诺来源见维度1 → 下面验收动作逐个执行，每个都告诉你「做什么 → 看到什么 → 意味着什么」

人类验收只做两件事：① 跑一个 .sh 脚本，它会自动执行所有子功能模块的测试并在终端分层分组打印结果；② 用下面的「终端输出翻译表」对照终端每一行，搞清楚含义、出了问题该查哪个模块。核心目标：无 ROS / 无 GPU / 无真实 bundle 条件下，L2-03 能从 ObservationSnapshot 输入经 fake-policy 产出 shape 正确的 ActionChunk，且后台 worker 异步解耦、异常不崩溃。

# /home/hit/ROS，无 ROS / 无 GPU / 无真实 bundle 环境 bash src/model_deploy/act/scripts/l2_03_verify.sh
