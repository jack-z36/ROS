## 三、项目边界

本项目当前关注从数据采集到数据清洗的链路打通，并以阶段二 canonical dataset 为当前重点；不把目标扩展为重新设计 Octopus、重构全部 ROS 节点或提前实现模型训练/部署。

核心边界如下：

- 数据来源：FASTUMI 相关 ROS2 节点输出的话题数据。
- 采集平台：公司的 Octopus 程序。
- 采集产物：可被后续处理、回放或验证的 `.mcap` 文件。
- 清洗产物：由 `data_clean` 生成或后续扩展生成的 `canonical_dataset_mcap`，包括 `data.mcap`、schema、step index、masks、report、manifest、夹爪宽度结果和坐标/TCP 配置。
- 关键验证：Octopus 能看到需要的 ROS2 topic，并能把选定 topic 正确录制进 MCAP；清洗程序能读取原始 MCAP 并输出符合配置约束的清洗结果。

## 六、架构文档要求

除输出清单中的简表外，每个程序、脚本或独立模块必须配备一份独立的架构说明文档（`*_architecture.md` 或 `*_架构说明.md`），放在该程序所属的代码包目录下。

架构文档必须包含以下内容，使毫无上下文记忆的后续 Agent 能够快速理解该程序的设计与运行方式：

1. 概述：该程序的用途、所属阶段/场景、解决什么问题。
2. 目录结构：源码文件清单及每个文件的职责。
3. 数据流：输入来源、内部工作机理、处理逻辑、输出目标。
4. 依赖与运行：依赖的系统环境、ROS2 包、Python 库等；启动命令和参数说明。
5. 配置项说明：关键配置参数、默认值、可调范围和含义。
6. 与上下游的关系：该程序被谁调用、调用了谁、共享哪些 topic 或文件。

更新规则：

- 新增程序或脚本时，必须在对应场景的输出清单中追加条目，并同步创建架构文档。
- 修改已有程序的行为时，必须同步更新其架构文档。
- 架构文档的文件名和路径必须在输出清单表格中明确列出。
