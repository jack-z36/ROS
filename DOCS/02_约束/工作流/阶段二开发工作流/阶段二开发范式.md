# 工作流：阶段二开发范式

本工作流适用于 Win 主机上的阶段二数据清洗 pipeline L1/L2/L3 开发范式整理。它负责把阶段二的开发想法逐层清洗为功能模块清单、数据定义文件、L2 能力模块说明和可执行任务文档，终点是生成 `03_tasks/task/active/<功能组>/` 下的 L3 微元任务；不负责直接执行代码开发、测试修复、Git 提交或任务归档。

当用户提到“阶段二 pipeline”“L1/L2/L3”“功能模块拆解”“功能模块说明文档”“微元任务”“根据模块说明生成任务”等信号时，必须加载本工作流。

## 核心分层

### L1：阶段二一级开发任务

阶段二 L1 固定为以下六条任务线：

1. `runtime_mvp`：Runtime MVP 开发。
2. `service_s1`：Service 场景一，提取夹爪开合以及位姿转换。
3. `service_s2`：Service 场景二，硬件数据可靠性验证。
4. `service_s3`：Service 场景三，MCAP 多 topic 时间轴对齐。
5. `service_s4`：Service 场景四，构建标准 canonical dataset。
6. `service_s5`：Service 场景五，模型训练格式导出器。


### L2：功能模块说明文档

L2 是某个 L1 内部的功能模块说明。L2 阶段不只产出单个功能模块说明文件，还必须先产出该 L1 一共需要实现多少个功能模块的清单，再围绕这些功能模块定义必要的数据契约、schema、types 和 config，最后才逐个生成能力模块说明文件。

L2 模板不再使用单一大模板。生成 L2 时必须先判断模块类别，再使用模板组件拼装：

```text
L2 文件 =
DOCS/02_约束/工作流/原工作流/attachments/templates/L2_common_header.md
+
一个或多个 L2 类别主体模板
+
DOCS/02_约束/工作流/原工作流/attachments/templates/L2_common_footer.md
```

四类 L2 模板固定为：

| 模块类别 | 本质问题 | 适合任务 | 主体模板 |
|---|---|---|---|
| 数据定义类 | 数据长什么样 | `RunContext`、`SceneResult`、schema、枚举、配置对象 | `templates/L2_data_definition.md` |
| 数据读写类 | 数据从哪里来、写到哪里 | run 目录、配置快照、日志、manifest、MCAP/JSON/YAML/Parquet 读写 | `templates/L2_data_io.md` |
| 数据计算类 | 输入如何变成新结果 | 配置校验、输入检查、统计、转换、异常检测、mask 生成 | `templates/L2_data_compute.md` |
| 流程编排类 | 谁先做、谁后做、失败怎么办 | `SceneRunner`、`PipelineRunner`、fake pipeline、入口调度 | `templates/L2_orchestration.md` |
 
所有 L2 都必须包含：能力名称、所属 L1、模块类别、一句话目标、能力角色、上游关系、下游关系、职责边界、完成标准、可拆分 L3 清单和未知问题。具体字段、路径、读写动作、计算规则或调用顺序由类别主体模板承载，不放进通用头部。

Service 场景一到场景五的 L2 / L3 必须遵守 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/开发者验收入口约束.md`。所有 Service 功能设计必须能说明它如何通过 `./start_data_clean.sh --dev` 下的场景菜单、功能检验项或场景完整 smoke test 被最终人工验收。

L2 阶段的产出分三类：

1. `功能模块清单.md`：说明该 L1 下需要实现多少个功能模块、每个模块的名称、目标、上下游和优先级。
2. `数据定义文件`：说明上游/下游数据产物契约、机器可读 schema、程序内部 types、配置项和配置 schema。
3. `能力模块说明文件`：说明某个功能模块的输入、输出、数据语义、处理流程、交互逻辑、边界和可拆分 L3 任务。

功能模块清单统一命名为：

```text
功能模块清单.md
```

单个能力模块说明文件建议放入 `L2能力模块/` 子目录，按功能命名，例如：

```text
L2能力模块/夹爪开合提取.md
L2能力模块/common_frame位姿转换.md
L2能力模块/夹爪开合配置文件自动生成.md
L2能力模块/位姿转换配置文件自动生成.md
```

落点规则：

- Runtime 功能模块清单：`DOCS/03_工程/阶段二：数据清洗/01_runtime_mvp/功能模块清单.md`
- Runtime 能力模块说明：`DOCS/03_工程/阶段二：数据清洗/01_runtime_mvp/L2能力模块/<能力名称>.md`
- Service 场景功能模块清单：放入对应场景目录，例如 `DOCS/03_工程/阶段二：数据清洗/02_service/场景一/功能模块清单.md`
- Service 场景能力模块说明：放入对应场景的 `L2能力模块/` 子目录，例如 `DOCS/03_工程/阶段二：数据清洗/02_service/场景一/L2能力模块/夹爪开合提取.md`

生成 L2 时，不要在交互一开始加载模板。只有当 Agent 已经和用户完成深入交流、整理出某个 L2 功能蓝图，并准备把蓝图落成正式 L2 能力模块说明文件时，才加载 `DOCS/02_约束/工作流/原工作流/attachments/L2能力模块说明文件模板.md` 作为模板系统入口，再按模块类别读取 `DOCS/02_约束/工作流/原工作流/attachments/templates/` 下的通用头部、类别主体和通用尾部。如果用户在当前任务中提供新版 L2 模板，以用户提供的模板为准；如果模板字段仍不足以填写，围绕目标、能力角色、上下游关系、职责边界、验收和风险继续追问。

### 数据定义文件

每开发一个功能模块前，必须先定义清楚它依赖和产出的数据。不要把所有数据定义都放进 types 目录，应分为三类：

| 类别          | 内容                                                                               | 建议位置                       | 使用者          |
| ----------- | -------------------------------------------------------------------------------- | -------------------------- | ------------ |
| 数据产物契约      | raw MCAP、cleaned MCAP、validated MCAP、aligned MCAP、canonical dataset 等文件/数据产物长什么样 | `DOCS/阶段二：数据清洗/01_数据产物契约/` | 人、Agent、后续设计 |
| 机器可读 schema | JSON Schema / YAML Schema，描述字段、topic、单位、必填项和配置结构                                 | `schemas/` 或 `contracts/`  | 程序、测试、Agent  |
| 代码 Types    | Python dataclass / Pydantic model / TypedDict 等程序内部对象                            | `src/data_clean/types/`    | 程序内部         |


判断规则：

- raw MCAP 应该有哪些 topic：写入数据产物契约。
- cleaned MCAP 比 raw 多哪些 topic：写入数据产物契约。
- 某个功能模块吃什么、吐什么：写入该模块的 L2 能力模块说明。
- topic 名、marker id、标定参数、failure policy：写入 config 和 schema。
- `GripperWidthSample`、`PoseSample`、`Report` 等程序内部对象：写入 `src/data_clean/types/`。
- 如何读写 MCAP：属于 Repo 层。
- 如何计算夹爪宽度、位姿转换、异常检测：属于 Service 层。
- 如何调度整个流程：属于 Runtime 层。

定义流程固定为：

```text
1. 定义上游数据产物契约
2. 定义下游数据产物契约
3. 根据模块类别定义本模块的专用契约
4. 定义需要的 Types
5. 定义需要的 Config / Schema
```

### L3：微元任务文档

L3 是交给一个没有长期上下文、上下文窗口有限的 Agent 执行的任务文件。一个 L3 微元任务应满足：单个 Agent 在一轮任务中可以读完上下文、完成实现或文档动作、执行验收并更新必要记录。

L3 文档统一放入：

```text
DOCS/03_工程/阶段二：数据清洗/03_tasks/task/active/<功能组>/
```

`<功能组>` 对应当前 L3 来源 L2 功能模块，例如：

```text
DOCS/03_工程/阶段二：数据清洗/03_tasks/task/active/runtime-g1/
DOCS/03_工程/阶段二：数据清洗/03_tasks/task/active/service-s1-g1/
```

同一个 L2 功能模块拆出的所有 L3 必须放入同一个功能组目录。

命名规则按 L1 前缀编号：

```text
runtime_mvp_001_<短任务名>.md
service_s1_001_<短任务名>.md
service_s2_001_<短任务名>.md
service_s3_001_<短任务名>.md
service_s4_001_<短任务名>.md
service_s5_001_<短任务名>.md
```

同一 L1 内编号递增，不同 L1 之间编号互不共享。

L3 模板也不再使用单一大模板。生成 L3 时必须先判断任务类别，再使用模板组件拼装：

```text
L3 文件 =
DOCS/02_约束/工作流/原工作流/attachments/templates/L3_common_header.md
+
一个 L3 类别主体模板
+
DOCS/02_约束/工作流/原工作流/attachments/templates/L3_common_footer.md
```

四类 L3 模板固定为：

| 任务类别 | 本质问题 | 适合任务 | 主体模板 |
|---|---|---|---|
| 数据定义类 | 定义一个可被下游使用的数据结构 | `RunStatus`、`RunContext`、`SceneResult`、schema 字段 | `templates/L3_data_definition.md` |
| 数据读写类 | 实现一个可验证的读写动作 | run 目录创建、JSON 写入、config snapshot 保存 | `templates/L3_data_io.md` |
| 数据计算类 | 实现一个可测试的判断或计算 | 配置缺失字段检查、输入路径存在性检查、scene 依赖判断 | `templates/L3_data_compute.md` |
| 流程编排类 | 实现一个可观察的调用顺序 | 单场景 runner、fake pipeline runner、失败停止并写 error summary | `templates/L3_orchestration.md` |

生成 L3 时，不要在交互一开始加载模板。只有当某个 L2 能力模块说明已经稳定，并准备从它拆出正式 L3 task 时，才加载 `DOCS/02_约束/工作流/原工作流/attachments/L3微元任务文件模板.md` 作为模板系统入口，再按任务类别读取 `DOCS/02_约束/工作流/原工作流/attachments/templates/` 下的通用头部、类别主体和通用尾部。如果用户在当前任务中提供新版 L3 模板，以用户提供的模板为准；如果模板字段仍不足以填写，先整理待确认问题。

## 上游依赖接口对齐

阶段二功能是一条顺序链路。开发功能 X 前，必须先确认它直接依赖的上游功能 Y 及其接口，避免上下游各自实现后无法对接。

所有 L2/L3 生成与执行都必须遵守：

- 先识别直接上游功能。
- 先读取上游 L2 能力模块说明、相关 `L2数据定义/` 原子文档，以及接口相关 L3 记录。
- 当前功能不得重新定义一个与上游相似但字段不同的数据对象。
- 如果上游接口尚未稳定，必须写入未知问题，或先拆出上游接口定义/对齐任务。
- L3 验收必须尽量覆盖至少一个上游接口兼容性检查。

详细规则见：

- `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/上游依赖接口对齐约束.md`

## 工作流步骤

### 步骤一：定位 L1

根据用户描述判断任务属于哪个 L1：

- 提到 Runtime、调度、run 目录、manifest、入口菜单、fake service，优先归入 `runtime_mvp`。
- 提到夹爪开合、位姿转换、raw 到 cleaned，归入 `service_s1`。
- 提到滤波、异常值、IK、MuJoCo、可靠性验证，归入 `service_s2`。
- 提到多 topic、时间轴、step 时间戳、插值、对齐，归入 `service_s3`。
- 提到 episode、step index、canonical dataset、schema、mask、manifest，归入 `service_s4`。
- 提到 HDF5、LeRobot、Zarr、训练格式、export，归入 `service_s5`。

如果用户描述跨多个 L1，先确认主 L1；不要在一个 L3 微元任务中混合多个 L1 的实现目标。

### 步骤二：追问并生成 L2 功能模块说明

如果用户要求生成或完善 L2，必须按以下顺序执行：

1. 先与用户交互，确认该 L1 下总共需要实现多少个功能模块，并生成 `功能模块清单.md`。
	   例如：场景一可拆为：夹爪开合提取、common frame 位姿转换、夹爪开合配置文件自动生成、位姿转换配置文件自动生成。
2. 编写任意 L2 能力模块说明前，必须遵守 `DOCS/02_约束/编程执行/架构边界与机械约束原则.md`，确认当前能力属于 Types、Config、Repo、Service、Runtime、Web 或入口层中的哪一层。
3. 编写任意 L2 能力模块说明前，必须遵守 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/L2能力模块与数据定义约束.md`：先使用 `grill-me` 技能澄清用户意图；意图未稳定前不得直接落盘正式 L2 文档。
4. 编写任意 L2 能力模块说明前，必须遵守 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/上游依赖接口对齐约束.md`：先识别当前功能的直接上游功能，读取上游 L2、相关 `L2数据定义/` 和接口相关 L3 记录；如果上游接口未稳定，必须写入未知问题或先拆出上游接口任务。
4. 围绕功能模块清单，定义必要的数据文件：上游数据产物契约、下游数据产物契约、本模块类别专用契约、需要的 Types、需要的 Config / Schema。
5. L2 能力模块文件中提到的每一个数据概念，都必须先在对应 `L2数据定义/` 目录下创建或复用独立原子文档，并在能力模块文件中用 Obsidian 双向链接引用，例如 `[[RunContext]]`、`[[SceneResult]]`。不得只用反引号或普通文本提到数据概念。
6. 与用户深入交流，整理出某个功能模块的功能蓝图；此阶段只围绕目标、模块类别、能力角色、上下游关系、上游接口对齐状态、职责边界、成功标准、禁止事项和验收方式追问，不加载 L2 模板全文。字段、路径、读写动作、计算规则、调用顺序等类别专用问题，在确定模块类别后再追问。
7. 当功能蓝图已经稳定、准备写入正式 L2 文档时，先判断模块类别：数据定义类、数据读写类、数据计算类或流程编排类。复合模块最多使用两个类别模板；如果需要三个以上类别，优先拆成多个 L2。
8. 读取 `DOCS/02_约束/工作流/原工作流/attachments/L2能力模块说明文件模板.md`，再读取 `templates/L2_common_header.md`、对应类别主体模板和 `templates/L2_common_footer.md`；如果用户提供新版模板，则使用新版模板。
9. 根据模板检查功能蓝图是否缺字段；如有缺口，只追问缺口字段。
10. 将确认后的内容写入对应 `L2能力模块/<能力名称>.md`。
11. L2 文档可以说明能力、边界和验收，但不得在用户未要求时提前锁死具体 `.py` 文件名、类名、函数名或配置文件名。

### 步骤三：根据 L2 生成 L3 微元任务

如果用户要求从某个功能模块生成 L3：

1. 先读取对应 L2 能力模块说明文件。
2. 读取 `DOCS/02_约束/编程执行/架构边界与机械约束原则.md`，确认要拆出的每个 L3 所属层次、依赖方向和数据 shape 边界。
3. 根据 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/上游依赖接口对齐约束.md`，确认要拆出的每个 L3 是否直接消费上游接口；若消费，上游接口定义文档必须列入 L3 的必读任务文档或必读代码。
4. 与用户确认要拆出的 L3 任务边界，确保每个 L3 只解决一个核心目标。
5. 确认每个 L3 的任务类别：数据定义类、数据读写类、数据计算类或流程编排类。一个 L3 默认只使用一个类别模板；如果需要两个类别，优先拆成两个 L3。
5. 当准备写入正式 L3 task 时，再读取 `DOCS/02_约束/工作流/原工作流/attachments/L3微元任务文件模板.md`，再读取 `templates/L3_common_header.md`、对应类别主体模板和 `templates/L3_common_footer.md`；如果用户提供新版模板，则使用新版模板。
6. 读取与该 L1 对应的 Harness 文档和当前进度。
7. 将功能模块拆成一个或多个“一轮 Agent 可完成”的任务。
8. 为当前 L2 功能模块确定唯一功能组目录，例如 `runtime-g1` 或 `service-s1-g1`；功能组序号必须与 `功能模块清单.md` 中的功能模块序号一致，详细规则见 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/L3功能组目录约束.md`。该 L2 拆出的所有 L3 必须写入同一个 `03_tasks/task/active/<功能组>/`。
9. 根据 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/L3调度元数据约束.md`，先为该功能组拆出 L3 任务 DAG，确定每个 L3 的 `wave`、`parallel_group`、`depends_on`、`blocks` 和 `conflict_scope`。
10. 生成每个 L3 时必须在任务文件中填写 `dispatch` YAML 调度元数据。
11. 同步生成或更新 `DOCS/03_工程/阶段二：数据清洗/03_tasks/task/dispatch/<功能组>.yaml`，供主 Agent 调度该功能组任务池。
12. 如果 L3 是在已有程序基础上的改造、对接、补测或契约稳定，必须遵守 `DOCS/02_约束/文档体系/阶段二任务体系/约束文件/L3现有实现盘点约束.md`，在任务文件中写清“现有程序盘点”和“真实改造边界”。
13. Service 场景一到场景五的 L3 必须写明它对应或影响 `./start_data_clean.sh --dev` 下哪个场景菜单、功能检验项或场景完整 smoke test。
14. 代码类 L3 必须在任务文件中写明使用 `$tdd` 技能、先运行 `bash scripts/init_data_clean_dev.sh` 开工自检、读取相关 L3 历史任务和必要历史记录、完成后勾选成功标准并从 `task/active/<功能组>/` 移动到 `task/completed/<L1归档目录>/<功能组>/`，并在原 active 功能组目录为空时删除该空目录。
15. L3 中所有 Python 验收命令必须使用 `python3`；仓库内文件和目录必须使用相对仓库根目录路径。
16. L3 自动化验收命令只证明局部实现正确；`bash scripts/init_data_clean_dev.sh` 只证明工作区具备基本开发前提，不替代 L3 自己的验收命令；完成一个 Service 场景的全部 L3 后，场景最终验收必须由用户本人运行 `./start_data_clean.sh --dev` 并查看测试产物和运行日志确认。

L3 文档只列必读链接、必要任务边界和类别专用契约，不完整复制上游文档。
L3 文档不得把通用实现约束、文件存放规则、Git 同步规则、TDD 归档规则或技术栈规则整段复制进任务卡片；这些规则必须沉淀为独立约束文档，并在 L3 的“必读约束文档”中引用。具体 L3 只保留与本任务强相关的目标、执行对象、类别专用契约、修改边界、验收命令和交接要求。
L3 执行由 Ubuntu 主机完成。Win 主机只生成任务文件，不要求在生成阶段写执行记录、移动任务或更新代码。

### 步骤四：投递到功能组任务池

生成的 L3 文档必须写入：

```text
DOCS/03_工程/阶段二：数据清洗/03_tasks/task/active/<功能组>/
```

写入前先确认或创建功能组目录。功能组命名规则：

```text
runtime-g<序号>/
service-s1-g<序号>/
service-s2-g<序号>/
service-s3-g<序号>/
service-s4-g<序号>/
service-s5-g<序号>/
```

功能组序号必须与该 L1 / 场景下的 L2 功能模块顺序对应。写入前检查该功能组目录下最大 L3 编号，按 L1 前缀递增。

写入前必须再次执行 `L3功能组目录约束.md` 的检查：读取当前 L1 / 场景的 `功能模块清单.md`，确认 L3 来源 L2 功能模块及其序号，不得把不同功能模块的 L3 混放到同一个 `gN` 目录。

写入 L3 后必须同步写入或更新调度索引：

```text
DOCS/03_工程/阶段二：数据清洗/03_tasks/task/dispatch/<功能组>.yaml
```

调度索引必须覆盖该功能组下所有新生成 L3 的 `task_id`、文件路径、执行波次、并行组、硬依赖和冲突范围。

代码类 L3 的“验收命令”必须先列出：

```bash
bash scripts/init_data_clean_dev.sh
```

随后再列出当前 L3 自己的测试、最小复现或验收命令。不得把开工自检当成当前 L3 的唯一验收。

写入后，向用户报告：

- 新增了哪些 L3 任务文件。
- 每个任务对应哪个 L1 和哪个 L2 功能模块。
- 生成或更新了哪个 `task/dispatch/<功能组>.yaml` 调度索引。
- 哪些模板字段仍为空或被标记为待确认。

本工作流到此结束。后续实际执行 L3 任务时，应按 `03_tasks/README.md` 的 `task/active/<功能组>/` 到 `task/completed/<L1归档目录>/<功能组>/` 机制处理。
