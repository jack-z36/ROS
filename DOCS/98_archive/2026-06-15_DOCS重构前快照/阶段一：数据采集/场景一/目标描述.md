# 场景一目标描述：逐个启动 4 个相机 ROS 节点

## 1. 场景名称

逐个启动 4 个相机 ROS 节点，并让 Octopus 数据采集平台能够采集 FASTUMI 数据、输出 MCAP 文件。

## 2. 根本目的

本场景的根本目的不是实现最终的一键启动，而是先完成单节点验证：

```text
4 个相机节点各自能否独立启动；
4 个相机节点各自能否稳定发布 ROS2 topic；
Octopus 能否看到并订阅这些 topic；
Octopus 能否把这些 topic 录制为 MCAP 文件。
```

因此，本场景是整个 FASTUMI 数据采集链路的单节点验证阶段。

## 3. 本场景要启动的 4 个相机节点

当前需要逐个启动并验证的 4 个相机节点包括：

```text
1. BatonMini right 节点
2. BatonMini left 节点
3. GoPro right v4l2 节点
4. GoPro left v4l2 节点
```

其中：

```text
BatonMini 相机：
用于发布 IMU、里程计、快速里程计、双目图像等 ROS2 topic。

GoPro 相机：
通过采集卡接入 Ubuntu 上位机，再通过 v4l2_camera 节点发布图像与相机信息 topic。
```

## 4. 本场景最终目标

本场景最终要达到的状态是：

```text
用户可以分别手动启动 4 个相机节点；
每个节点启动后，都能在 ROS2 中看到对应 topic；
Octopus 可以识别并订阅这些 topic；
用户可以在 Octopus 中点击开始录制和停止录制；
最终成功输出包含相机数据的 .mcap 文件。
```

核心成功判断标准：

```text
4 个相机节点可以分别手动启动，并且它们发布的 ROS2 topic 可以被 Octopus 订阅和录制成 MCAP 文件。
```

## 5. 本场景暂时不做什么

本场景暂时不追求：

```text
1. 不追求一条命令启动所有节点；
2. 不追求自动识别所有设备；
3. 不追求自动录制 MCAP；
4. 不追求自动同步所有数据；
5. 不追求完整 FASTUMI 数据处理流水线；
6. 不追求触觉传感器节点接入；
7. 不追求机械臂控制或训练模型。
```

本场景只解决一个问题：

```text
每个相机节点单独启动时，是否能正常给 Octopus 提供可采集的 ROS2 topic。
```

## 7. 当前代码事实

### 7.1 BatonMini 当前默认话题

`src/data_collection/baton_mini_sdk_demo` 当前源码默认发布：

```text
/baton_mini/imu
/baton_mini/odometry
/baton_mini/fast_odom
/baton_mini/image_left
/baton_mini/image_right
```

本项目最终希望区分 right/left，因此需要在执行阶段确认是通过参数、remap、namespace，还是复制 launch 配置来形成：

```text
/baton_mini_right/...
/baton_mini_left/...
```

### 7.2 GoPro 当前默认话题

`src/data_collection/gopro_camera_launch` 当前 launch 文件启动单个 `v4l2_camera_node`，默认发布：

```text
/gopro/image_raw
/gopro/camera_info
```

其中：

```text
/gopro/image_raw    sensor_msgs/msg/Image
/gopro/camera_info  sensor_msgs/msg/CameraInfo
```

本项目最终希望区分 right/left，因此需要在执行阶段确认是通过参数、remap、namespace，还是不同 launch 配置来形成：

```text
/gopro_right/image_raw
/gopro_right/camera_info
/gopro_left/image_raw
/gopro_left/camera_info
```

## 8. 验收标准

### 8.1 ROS2 层验收

逐个启动 4 个节点后，执行：

```bash
ros2 topic list
```

至少应能看到对应节点的 topic。

BatonMini right 期望看到：

```text
/baton_mini_right/imu
/baton_mini_right/odometry
/baton_mini_right/image_left
/baton_mini_right/image_right
```

BatonMini left 期望看到：

```text
/baton_mini_left/imu
/baton_mini_left/odometry
/baton_mini_left/image_left
/baton_mini_left/image_right
```

GoPro right 期望看到：

```text
/gopro_right/image_raw
/gopro_right/camera_info
```

GoPro left 期望看到：

```text
/gopro_left/image_raw
/gopro_left/camera_info
```

如果 GoPro 尚未完成 right/left 命名区分，则单节点验证时至少应看到：

```text
/gopro/image_raw
/gopro/camera_info
```

### 8.2 topic 数据验收

能够通过 ROS2 命令确认 topic 有数据流动。

示例：

```bash
ros2 topic echo /baton_mini_right/imu
ros2 topic echo /baton_mini_left/imu
ros2 topic hz /gopro_right/image_raw
ros2 topic echo /gopro_right/camera_info --once
ros2 topic hz /gopro_left/image_raw
ros2 topic echo /gopro_left/camera_info --once
```

如果 GoPro 尚未完成 right/left 命名区分，则先使用：

```bash
ros2 topic hz /gopro/image_raw
ros2 topic echo /gopro/camera_info --once
```

只要 topic 能稳定输出数据，就说明该节点在 ROS2 层基本可用。

### 8.3 Octopus 层验收

打开 Octopus 后，应该能够：

```text
1. 在 topic 列表中看到这些相机 topic；
2. 选择需要录制的 topic；
3. 点击开始录制；
4. 点击停止录制；
5. 得到一个 .mcap 文件。
```

说明：Octopus 的录制路径使用独立的 MCAP recorder，写入的是 ROS2 serialized message，不依赖显示面板是否成功渲染。

### 8.4 MCAP 文件验收

录制完成后，应该能够确认：

```text
1. .mcap 文件真实生成；
2. 文件大小不是 0；
3. 回放或检查时能看到录制的 topic；
4. 至少包含一个相机图像 topic；
5. 最好包含 BatonMini 的位姿或 IMU topic。
```

可以用类似命令检查：

```bash
ros2 bag info <mcap文件路径>
```

## 9. 本场景完成后的产物

本场景完成后，应该留下以下产物：

```text
1. 每个相机节点的单独启动命令；
2. 每个相机节点对应的 topic 名称；
3. 每个相机节点启动时需要传入的参数；
4. 每个节点是否成功启动的记录；
5. Octopus 是否能识别对应 topic 的记录；
6. 至少一个由 Octopus 成功录制出的 MCAP 文件；
7. 若失败，需要记录失败原因和错误日志。
```

这些产物应沉淀到场景一的背景信息、执行记录和当前进度文档中。

## 10. 本场景与场景二的关系

场景一是场景二的前置验证。

```text
场景一：
一个一个启动 4 个相机节点，验证每个节点本身能跑通。

场景二：
把已经验证成功的 4 个节点，统一放进一键启动脚本或 launch 文件中，实现一键启动。
```

因此，场景一的重点是：

```text
先确认每个节点能独立工作。
```

场景二的重点才是：

```text
把这些已经能独立工作的节点组织成一个统一启动系统。
```
