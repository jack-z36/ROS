# 场景二背景信息：双 Baton Mini 上位机发布 topic 方案

## 1. 文档定位

本文用于说明：

```text
为什么需要场景二；
场景二从 FASTUMI 原始设计中继承了什么；
为什么本项目要用 Baton Mini / RoboBaton MINI 替代 T265；
为什么选择“Ubuntu 上位机运行 SDK 节点并发布 ROS2 topic”这条路线。
```

本文不是启动教程，也不是目标验收文档，而是背景说明文档。

说明：本文中关于 FASTUMI 论文和原始系统的内容，来自当前项目理解与用户提供的背景总结；若后续需要写成可引用论文说明，应再补充正式论文来源和原文出处。

## 2. FASTUMI 原始系统背景

FASTUMI 是对 Stanford UMI 系统的改进。它主要想解决两个问题：

```text
1. 原始 UMI 对特定硬件依赖较强；
2. 原始 UMI 使用复杂的 VIO / SLAM 流程，部署和调试成本较高。
```

当前项目理解中，FASTUMI 的核心改进之一是：用现成的追踪模块替代复杂的视觉惯性里程计 / SLAM 流程，从而降低部署复杂度，并提升数据采集的稳定性。

因此，本项目关注的不是先训练模型，而是先把数据采集链路跑通：

```text
传感器稳定发布 ROS2 topic；
Octopus 或 ros2 bag 能录制这些 topic；
录制结果能输出为 MCAP；
后续再进入 FASTUMI 数据转换与训练流程。
```

## 3. FASTUMI 原始数据采集链路

FASTUMI 的原始数据采集可以理解为依赖三个核心 ROS 节点类别：

```text
1. GoPro 图像节点；
2. T265 位姿追踪节点；
3. 数据存储 / 同步节点。
```

其中：

| 节点 | 作用 |
| --- | --- |
| GoPro 节点 | 采集第一视角广角图像 |
| T265 节点 | 输出末端执行器位姿 |
| 存储 / 同步节点 | 聚合并同步多路数据，形成后续训练数据 |

这一结构对本项目的启发是：

```text
每个传感器节点可以独立运行；
所有传感器最终都应进入统一 ROS2 topic 空间；
采集程序只需要面向稳定、清晰命名的 topic；
后续可以继续增加触觉、夹爪宽度、机械臂状态等模态。
```

## 4. 本项目为什么引入 Baton Mini / RoboBaton MINI

原始 FASTUMI 使用的是 RealSense T265。T265 已经停产，后续采购、维护和复现都存在风险。

当前项目采用 Baton Mini / RoboBaton MINI 作为替代追踪模块：

```text
原始 FASTUMI：
GoPro + T265

本项目改造版：
GoPro + Baton Mini / RoboBaton MINI
```

Baton Mini 在本项目中的角色不是普通图像相机，而是承担追踪模块职责，提供：

```text
IMU；
里程计 / 位姿估计；
快速里程计；
双目图像。
```

这些数据最终需要进入 Octopus / MCAP / FASTUMI 数据处理链路。

## 5. 为什么需要两台 Baton Mini

本项目当前规划中，需要同时接入两台 Baton Mini，用于采集左右两侧相关的位姿、图像和 IMU 数据。

当前设备配置为：

| 设备 | 角色 | IP | 网关 | namespace |
| --- | --- | --- | --- | --- |
| Baton Mini 1 | right | `192.168.1.10` | 默认 | `baton_mini_right` |
| Baton Mini 2 | left | `192.168.2.10` | `192.168.2.1` | `baton_mini_left` |

这一步的背景是：多设备接入时必须避免两个冲突。

```text
IP 冲突：
两台设备不能都使用默认 IP 192.168.1.10。

topic / namespace 冲突：
两台设备不能都发布 /baton_mini/...，否则无法判断数据来源。
```

当前配置已经完成基础区分：

```text
右侧 Baton Mini → /baton_mini_right/...
左侧 Baton Mini → /baton_mini_left/...
```

## 6. 两种技术路线背景

围绕 Baton Mini，有两种可能路线。

### 6.1 路线 A：相机内部直接发布 ROS2 topic

逻辑是：

```text
Baton Mini 内部 ROS2 节点
    ↓
设备自己发布 topic
    ↓
Ubuntu 上位机直接订阅
```

这种路线的特点是：上位机不一定需要运行 SDK Demo，只要 ROS2 多机通信正常，就可以直接通过 `ros2 topic list` 看到设备内部发布的话题。

但它的问题是：

```text
1. 更依赖设备内部 ROS2 环境；
2. 多设备时需要处理 ROS_DOMAIN_ID、DDS、多网卡、namespace 等问题；
3. 出问题时，排查位置分散在“设备内部”和“上位机”两端。
```

### 6.2 路线 B：Ubuntu 上位机运行 SDK Demo，再由上位机发布 topic

逻辑是：

```text
Baton Mini 硬件
    ↓
USB / TCP / SDK 数据流
    ↓
Ubuntu 上位机运行 baton_mini_sdk_demo
    ↓
上位机发布 ROS2 topic
    ↓
FASTUMI / Octopus / ros2 bag 接收
```

Baton Mini SDK Demo 的架构说明中明确写到，它通过 TCP 接收 IMU、双目图像、快速里程计等数据，然后通过 `ros_interface` 发布成 ROS 消息。

也就是说，SDK Demo 不是简单地“订阅相机内部 topic 再转发”，而是：

```text
通过 SDK / TCP / HTTP 与相机硬件通信；
接收相机原始数据或算法结果；
在 Ubuntu 上重新包装成 ROS2 topic。
```

本地代码对应关系：

```text
baton_mini.cpp：
初始化 SDK、登录设备、启动算法和数据流。

src/sdk/imu_tcp.hpp：
通过 TCP:9996 接收 IMU 数据。

src/sdk/odom_tcp.hpp：
通过 TCP:9994 接收快速里程计数据。

src/sdk/image_tcp.hpp：
通过 TCP:9997 / 9998 接收双目图像数据。

src/io/ros_interface.cpp：
读取 topic 参数，并创建 ROS publisher 发布消息。
```

## 7. 本项目为什么选择路线 B

本项目选择路线 B：

```text
Ubuntu 上位机运行 SDK Demo，并由上位机统一发布 ROS2 topic。
```

核心原因有三点。

### 7.1 FASTUMI 本身是多节点数据采集系统

FASTUMI 的原始设计中，不是单一设备独立运行，而是多个 ROS 节点共同完成数据采集、同步和存储。

所以本项目也应该把 Baton Mini 当成传感器数据源，由上位机统一管理。

### 7.2 上位机统一发布 topic 更利于工程管理

后续系统中不止有 Baton Mini，还可能包括：

```text
1. GoPro 图像节点；
2. 触觉传感器节点；
3. 夹爪宽度计算节点；
4. 机械臂状态节点；
5. MCAP 录制节点。
```

如果所有 topic 都在 Ubuntu 上位机侧统一命名、统一启动、统一录制，会更方便写 launch 文件和调试脚本。

前期讨论中已经明确：

```text
.sh 更适合做环境准备和总入口；
launch 更适合负责多 ROS 节点组织、参数传递、topic 命名和日志管理。
```

### 7.3 后续要接入 Octopus / MCAP 录制

Octopus 项目本身是一个 ROS2 + Qt 的多模态数据采集应用，核心功能包括：

```text
1. 订阅实时 ROS2 topic；
2. 在桌面 UI 中显示数据；
3. 将选中的 ROS2 topic 录制为 .mcap 文件。
```

Octopus 架构文档还明确区分了显示链路和录制链路：

```text
显示链路：
ROS2 topic → MainWindow subscriptions → 页面组件 → UI 渲染

录制链路：
OpDockWidget → McapRecorder → generic ROS2 subscriptions → MCAP writer → .mcap 文件
```

因此，场景二需要优先保证：

```text
Ubuntu 上能稳定产生两组 Baton Mini ROS2 topic。
```

只要 topic 稳定存在，Octopus 或 `ros2 bag record` 才能继续接入并录制。

## 8. 场景二在整个 FASTUMI 复现项目中的位置

场景二不是完整 FASTUMI 系统，而是其中的一个中间基础场景。

它位于：

```text
硬件接入层
    ↓
ROS2 topic 发布层   ← 场景二当前重点
    ↓
MCAP 录制层
    ↓
FASTUMI 数据转换层
    ↓
模仿学习训练层
```

也就是说，场景二解决的是：

```text
两台 Baton Mini 的数据如何稳定进入 ROS2 系统。
```

它不直接解决：

```text
1. 数据同步算法；
2. HDF5 / Zarr 转换；
3. ACT / Diffusion Policy 训练；
4. 机械臂部署执行。
```

## 9. 场景二需要承接的上游约束

### 9.1 FASTUMI 需要位姿数据

FASTUMI 中的追踪节点需要提供末端执行器位姿，位姿通常表示为：

```text
x, y, z, qx, qy, qz, qw
```

其中：

| 字段 | 含义 |
| --- | --- |
| `x, y, z` | 位置 |
| `qx, qy, qz, qw` | 四元数姿态 |

Baton Mini 在本项目中承担的角色，就是替代原始 T265 追踪模块，向 ROS2 系统提供类似的位姿 / 里程计数据。

本地 SDK Demo 中，对应输出是：

```text
/baton_mini_right/odometry
/baton_mini_right/fast_odom
/baton_mini_left/odometry
/baton_mini_left/fast_odom
```

### 9.2 FASTUMI 需要多模态时间同步

FASTUMI 不只是录一个 topic，而是要将图像、位姿、夹爪宽度等多路数据对齐。

所以场景二发布 topic 时，需要尽量保证：

```text
1. topic 名称清楚；
2. 时间戳正常；
3. 数据流稳定；
4. 左右设备不会混在一起。
```

注意：时间同步策略不在本文中设计，但 topic 命名和稳定发布是后续同步的前提。

### 9.3 未来可能增加触觉等模态

后续系统可能继续增加触觉或力传感器，以支持更精细的操作任务。

因此场景二的设计不能只考虑“两台 Baton Mini 能跑起来”，还要为后续扩展预留清晰命名空间。

例如：

```text
/baton_mini_left/...
/baton_mini_right/...
/gopro_left/...
/gopro_right/...
/tactile_left/...
/tactile_right/...
```

## 10. 场景二的历史决策记录

本场景形成过程中已经完成以下判断：

```text
1. 识别出 Baton Mini 有两种使用方式：
   - 设备内部直接发布 ROS2 topic
   - Ubuntu 上位机运行 SDK Demo 后发布 ROS2 topic

2. 判断本项目更适合第二种：
   - 上位机统一运行 SDK
   - 上位机统一发布 topic
   - 上位机统一录制 MCAP

3. 识别出双设备接入的两个核心冲突：
   - IP 冲突
   - namespace / topic 名冲突

4. 完成当前设备配置：
   - right：192.168.1.10，baton_mini_right
   - left：192.168.2.10，192.168.2.1，baton_mini_left

5. 统一快速里程计命名：
   - 当前项目采用 fast_odom
   - 不使用 fast_odometry，除非后续明确修改源码或 launch 配置
```

## 11. 当前代码事实

当前 `baton_mini_sdk_demo` 的代码状态如下：

```text
launch/baton_mini.launch.py：
当前只声明 server_ip 与 local_ip，并启动单个 baton_mini 节点。

src/io/ros_interface.cpp：
支持读取 imu_topic、odom_topic、fast_odom_topic、image_left_topic、image_right_topic 参数。
```

因此，双节点场景还需要后续工程化实现：

```text
1. 让 launch 文件暴露 topic 参数；
2. 为 right / left 设置不同 node_name 或 namespace；
3. 同时启动两个 SDK 节点实例；
4. 确保两组 topic 不冲突；
5. 再交给 Octopus 或 ros2 bag 录制。
```

## 12. 背景总结

场景二产生的根本原因是：

```text
FASTUMI 需要一个稳定、可扩展、可录制的多传感器 ROS2 数据入口；
而本项目用 Baton Mini / RoboBaton MINI 替代 T265 后，
必须先解决双相机如何同时接入 Ubuntu、
如何区分左右设备、
如何把设备数据稳定发布成 ROS2 topic 的问题。
```

因此，场景二的背景可以压缩成一句话：

```text
为了把两台 Baton Mini 稳定接入 FASTUMI 数据采集链路，本项目选择在 Ubuntu 上位机运行两个 SDK 节点，由上位机统一发布 /baton_mini_right/... 与 /baton_mini_left/... 两组 ROS2 topic，作为后续 Octopus 录制 MCAP 和 FASTUMI 数据转换的基础输入。
```
