# Octopus 双链路架构总览

本页描述 Octopus 程序最核心的架构设计决策：显示链路与录制链路分离。理解这一点是理解整个采集程序运转逻辑的前提。

## 定位

本页回答：Octopus 程序的整体结构是什么？为什么"看到画面"不等于"录进 MCAP"？

本页是 `30_Octopus运转逻辑/` 的入口。显示和录制的细节分别见 `02_显示链路.md` 和 `03_录制链路.md`。

## Octopus 是什么

Octopus 是 ROS2 + Qt6 桌面应用，是阶段一唯一的"汇聚节点"。它做三件事：

1. 订阅实时 ROS2 topic，在桌面 UI 中渲染显示。
2. 把用户勾选的 topic 录制为 `.mcap` 文件（raw MCAP）。
3. 加载和保存本地运行配置（主题、语言、录制路径、压缩方式、默认 topic 列表）。

运行时的中心不是分层后端，而是 `MainWindow`——它组装 UI、持有显示订阅、把 ROS 消息直接路由到各页面面板。

## 核心设计决策：显示链路 ≠ 录制链路

Octopus 内部有**两个相互独立的 ROS2 节点**：

| | 显示链路 | 录制链路 |
|---|---|---|
| 节点名 | `octopus` | `recorder` |
| 归属对象 | `MainWindow` | `McapRecorder` |
| Executor | 独立 `SingleThreadedExecutor` | 独立 `SingleThreadedExecutor` |
| 线程 | 独立 `std::jthread` spin | 独立 `std::jthread` spin |
| 订阅方式 | typed subscription（固定 8 topic） | generic subscription（勾选 topic） |
| 用途 | 驱动 Qt 面板显示 | 写入 raw MCAP |
| 建立时机 | `MainWindow` 构造时立即 | 点击 Start 时 |

二者**不共享订阅、不共享 executor、不共享线程**。

### 为什么这样设计

- 显示链路要做图像格式转换、Resampler 缩放、面板 UI 更新，是重 UI 操作。
- 录制链路只需把序列化消息写盘，是轻 IO 操作。
- 分离后，一方的阻塞或异常不影响另一方。例如显示面板卡顿不会导致丢帧录制，录制写盘慢也不会卡住显示。

### 核心推论：看到画面 ≠ 录进 MCAP

这是使用 Octopus 最容易踩的坑：

- 显示面板有画面，只说明**显示节点**订阅成功。
- 是否录进 MCAP，取决于**录制节点**是否已通过 Operation 面板勾选 topic 并点击 Start。
- 两个节点独立，显示成功不传递到录制。

## 三条运行时流（flow）

Octopus 的运行时可拆解为三条 flow：

```text
1. Display flow（显示流）
   ROS topic → 显示节点回调 → 图像转换/队列 → Qt 面板更新

2. Recording flow（录制流）
   用户勾选 → Start → 录制节点 generic 订阅 → 序列化消息写 MCAP

3. Config flow（配置流）
   启动读 scanner.json → 运行期全局配置 → 退出写回 scanner.json
```

三条 flow 关联但不相同。Display 和 Recording 共享上游 topic，但各自独立消费。

## 启动顺序

程序启动链：

1. `src/main.cpp` —— 初始化日志、ROS2、创建 Qt 应用对象 `Scanner`、创建 `MainWindow`、进入 Qt 事件循环。
2. `src/scanner.cpp` —— 加载配置、加载字体、应用主题、安装翻译、退出时保存配置。
3. `src/mainwindow.cpp` —— 创建 dock 布局、创建显示节点和 executor 线程、建立固定订阅、连接消息到各 UI 面板。

运行时根不是服务容器或领域模型，而是 Qt 应用壳 `Scanner` 加 `MainWindow`。
