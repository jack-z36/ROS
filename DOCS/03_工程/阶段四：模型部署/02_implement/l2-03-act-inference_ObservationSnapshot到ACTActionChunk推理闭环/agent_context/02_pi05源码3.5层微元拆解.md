# Pi0.5 与 LeRobot ACT 源码 3.5 层拆解：L2-03

> [!info] 阅读目的
> 本文记录真实源码证据，回答“为什么 L2-03 被设计成三个同步阶段”。源码参考不能覆盖 `01_L2功能边界.md`。尤其不能因为 Pi0.5 把加载、推理和 worker 放得很近，就把这些职责重新合并到 ACT L2-03。

## 2. Pi0.5 纯推理链实际做了什么

Pi0.5 `Pi05PolicyRuntime.predict_action_chunk(observation)` 的有效业务顺序是：

```text
ObservationSnapshot
-> _build_batch
   -> encoded_state 转 float tensor
   -> state_normalizer.normalize
   -> 写 observation.state / task / observation.images.*
-> preprocessor(batch)
-> batch 搬到 device
-> policy.predict_action_chunk(batch)
-> detach / CPU / float32 / 取 batch[0]
-> 可选 clamp normalized action
-> action_normalizer.unnormalize
-> shape 检查
-> 截取 output_chunk_size
-> np.ndarray
```

这条链给 ACT L2-03 的有效启发只有：

1. snapshot 必须先适配成 policy batch。
2. state normalize 发生在 policy 前向之前。
3. policy 返回的是带 batch 维的 action chunk。
4. action unnormalize 发生在 policy 前向之后。
5. 下游应接收明确的 chunk 数据契约。

Pi0.5 链中的其他行为不能默认继承。

## 3. Pi0.5 各部分的边界归属

### 3.1 `policy_loader.py` 同时混合了两类职责

| 源码部分 | Pi0.5 行为 | 当前 ACT 归属 |
|---|---|---|
| `load_policy_runtime` | 校验 bundle、构建模型、加载 adapter、配置 device/eval、构建 processor、加载 normalizer | L2-01 |
| `Pi05PolicyRuntime` 稳定字段 | 持有 model/policy/preprocessor/normalizer/device | L2-01 创建资源；L2-03 service 只持有注入引用 |
| `_build_batch` | snapshot -> model batch | L2-03 一级阶段一 |
| `_move_tensors_to_device` | CPU tensor -> policy device | L2-03 一级阶段一 |
| `_predict_fn(batch)` | policy chunk 前向 | L2-03 一级阶段二 |
| unbatch/unnormalize/shape/array | raw model output -> physical chunk | L2-03 一级阶段三 |
| `_maybe_compile`、CUDA 全局设置 | 启动期模型配置 | L2-01 |

因此不能直接复制 `Pi05PolicyRuntime` 的完整职责。ACT L2-03 的 class 只保留“稳定持有已注入资源并编排一次同步计算”，不承担 loader/runtime 角色。

### 3.2 `inference_worker.py` 完全属于 L2-06

Pi0.5 `InferenceWorker` 包含：

```text
threading.Thread 生命周期
stop event
request/result latest-only queue
inference_hz 限速
request_id
infer_start/ready time
latency 和错误 metrics
异常捕获与日志
ActionChunk 运行元数据包装
```

这些微元回答“什么时候算、在哪个线程算、结果如何排队、失败后运行系统怎么办”，不是“snapshot 如何变成 actions”。当前 ACT 全部交给 L2-06，L2-03 不搬 `InferenceWorker` 的任何代码。

### 3.3 `ActionStateNormalizer` 是注入的计算能力

Pi0.5 `ActionStateNormalizer` 提供：

```text
normalize(data)
unnormalize(norm_data)
vector_dim
稳定统计参数
```

L2-03 只依赖该接口：

- 不读取 normalizer 文件。
- 不构造 normalizer。
- 不假定内部一定是 min-max、mean-std 或其他公式。
- state 只调用 `state_normalizer.normalize()`。
- action 只调用 `action_normalizer.unnormalize()`。
- 两个方向都只调用一次。

## 4. LeRobot ACT API 的决定性差异

### 4.1 必须使用 `predict_action_chunk`

`ACTPolicy.select_action(batch)` 的源码行为包括：

- policy 内部 `_action_queue`。
- queue 为空时才预测 chunk。
- 每次只 `popleft()` 一个 action。
- 配置 temporal ensemble 时维护跨调用 ensemble 状态。

这些都是 active chunk、cursor 或跨调用状态语义，属于 L2-06，不应隐藏在 L2-03 policy 调用里。

`ACTPolicy.predict_action_chunk(batch)` 的源码行为则是：

```text
eval
按 policy.config.image_features 的 key 从 batch 取图像
调用 ACT model
返回 actions tensor，shape 为 (B, chunk_size, action_dim)
```

因此 L2-03 只允许调用 `predict_action_chunk`，禁止调用 `select_action`。

### 4.2 ACT batch key 必须来自 policy 输入规格

LeRobot `PreTrainedConfig.image_features` 从 `input_features` 中筛选 `FeatureType.VISUAL` key。ACT policy 再按这些 key 读取 batch，而不是按 snapshot 字典插入顺序取图像。

当前适配规则：

```text
policy key: observation.images.<camera>
snapshot key: <camera>
```

L2-03 做精确 key 绑定；缺少必需相机时失败，不允许按“第一张/第二张”猜左右相机。

### 4.3 完整 ACT processor 不能原样套用

`make_act_pre_post_processors` 的输入 pipeline 同时包含：

```text
AddBatchDimensionProcessorStep
DeviceProcessorStep
NormalizerProcessorStep（input + output features）
```

输出 pipeline 同时包含：

```text
UnnormalizerProcessorStep
DeviceProcessorStep(cpu)
```

当前 L1 已明确向 L2-03 注入 state/action 两个 normalizer，并要求 L2-03 显式完成 state normalize 与 action unnormalize。如果再原样调用完整 processor，就会让归一化所有权不透明，并可能重复执行。

因此当前设计：

- 不把完整 LeRobot ACT pre/postprocessor 作为 L2-03 第五项稳定依赖。
- L2-03 自己做 batch 维和 device 适配。
- state/action 尺度转换只通过两个注入 normalizer。
- 图像在 `ObservationSnapshot` 中已经是模型就绪形态。

### 4.4 模型图像形态证据

LeRobot dataset 工具把 PIL/HWC uint8 图像转换为 `(C,H,W)`、`float32`、通常位于 `[0,1]` 的单帧 tensor。ACT model 的 backbone 接收每个视图的 `(B,C,H,W)` tensor。

这只说明标准 LeRobot 数据路径的常见形态。最终图像数值约定必须与实际训练/部署契约一致；L2-03 不凭源码默认值覆盖上游契约。

## 5. 源码微元到当前三级封装的映射

| 当前一级阶段 | 来源启发 | 保留内容 | 删除/改写内容 |
|---|---|---|---|
| Observation 批次准备 | Pi0.5 `_build_batch`、device 搬运；ACT image feature key | state tensor 化、state normalize、图像键绑定、batch 维、device | 去 task；不调用完整 processor；不做像素预处理 |
| ACT 前向推理 | 两个 policy 的 `predict_action_chunk` | inference-only 调用、返回完整 raw chunk | 禁止 `select_action`、queue、temporal ensemble 消费语义 |
| ActionChunk 后处理 | Pi0.5 unbatch/unnormalize/shape/array | raw 结构检查、action unnormalize、CPU float32、构造 chunk | 去 clamp、去 crop、去时间/request metadata |
| 总编排入口 | Pi0.5 runtime method 的固定调用顺序 | 三阶段顺序与异常传播 | 去 loader、worker、metrics、fallback |

## 6. 3.5 层源码微元判断

| 源码微元 | 3.5 类型 | 当前判断 |
|---|---|---|
| normalizer 稳定参数 | 数据 | L2-01 创建，L2-03 持有引用 |
| loaded policy/model weights | 数据 | L2-01 加载，L2-03 持有引用 |
| snapshot -> tensor/batch | 计算函数 | L2-03 保留并按 ACT 重写 |
| tensor -> device tensor | 计算函数 | L2-03 保留；产生新 tensor，不更新 queue/cache |
| policy chunk forward | 计算函数 | L2-03 核心计算 |
| unbatch/unnormalize/array | 计算函数 | L2-03 保留并严格化 |
| 三阶段串联 | 编排函数 | L2-03 总入口 |
| bundle/checkpoint 读取 | 数据读写函数 | L2-01，L2-03 为 0 |
| request/result queue 更新 | 内部状态更新函数 | L2-06，L2-03 为 0 |
| worker loop/限速/失败策略 | 编排函数 | L2-06，L2-03 不继承 |

按用户 3.5 层定义，L2-03 自身没有进程外数据读写函数，也没有 buffer/queue/cache 形式的内部状态更新函数。

## 7. Class 封装比较

| 对象 | 为什么是 class | 当前处理 |
|---|---|---|
| Pi0.5 `Pi05PolicyRuntime` | 同时持有模型、processor、normalizer、device、compile 函数和推理行为 | 不整体复用；职责过宽 |
| Pi0.5 `InferenceWorker` | 持有线程、event、queue、限速状态 | 完全归 L2-06 |
| LeRobot `ACTPolicy` | 持有模型权重和模型内部计算 | 由 L2-01 加载，L2-03 只调用 |
| 当前 inference service | 四项稳定依赖跨多次调用复用，需要一个对 L2-06 的统一入口 | L2-03 唯一新增 service class；不持有请求态 |
| 三个一级阶段 | 没有独立生命周期或可变状态 | 使用函数，不分别建 class |

## 8. 明确禁止继承的行为

- Pi0.5 的 bundle 校验、模型构建、adapter 加载、compile 和 CUDA 全局配置。
- Pi0.5 的 `task` 语言输入。
- Pi0.5 的完整 processor 依赖。
- Pi0.5 的 normalized action clamp。
- Pi0.5 的 `action_chunk[:output_chunk_size]` 截断。
- Pi0.5 的 `InferenceWorker`、request/result queue、限速、metrics 和异常吞吐策略。
- Pi0.5 `ActionChunk` 的 observation/inference/ready time、request ID、action dt 或对齐方法。
- LeRobot ACT `select_action` 的 queue 和 temporal ensemble 单步消费语义。
- 任何 14D action、26D state 或旧 action 段序。

这些差异不是实现优化选项，而是当前 L1 边界要求。
