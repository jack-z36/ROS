# 场景六：MCAP 数据清洗脚本与交互式启动器

## 一句话总结

将 Octopus 采集得到的 FASTUMI `.mcap` 文件，通过独立的 `data_clean` 离线清洗程序转换为后续可分析、回放和验证的清洗后 MCAP，并让用户能够用清晰的交互流程选择清洗文件数量。

## 核心目标

本场景目标是完善 `/home/hit/ROS/src/data_clean` 数据清洗程序及其启动方式，使用户可以稳定地完成以下操作：

- 从 `/home/hit/ROS/mcap` 中选择要清洗的 MCAP 文件。
- 默认清洗最近 1 个文件。
- 支持清洗最近 N 个文件或全部文件。
- 将结果输出到 `/home/hit/ROS/mcap_cleaned`。
- 在终端看到可理解的中文计划、进度、成功/失败摘要。
- 保留原始 JSON 输出模式，方便后续脚本化或机器读取。

## 目标用户流程

用户理想操作流程：

1. 进入工作区：

   ```bash
   cd /home/hit/ROS
   ```

2. 启动数据清洗：

   ```bash
   ./start_data_clean.sh
   ```

3. 在交互菜单中选择：

   - 回车：清洗最近 1 个 MCAP。
   - `n`：输入数量，清洗最近 N 个 MCAP。
   - `a`：清洗全部 MCAP。
   - `q`：退出。

4. 查看脚本展示的输入目录、输出目录、待清洗文件、文件大小、输出路径、topic 检查结果和标定参数提醒。

5. 确认后开始清洗，并在终端查看逐文件进度与最终汇总。

## 成功标准

场景六成功时应满足：

- `./start_data_clean.sh` 能直接调用 conda 环境运行清洗程序。
- 用户无需手写长 `PYTHONPATH` 命令。
- 默认只清洗最近 1 个文件，不会误批量处理全部数据。
- `--latest N`、`--all`、`--dry-run`、`--workers auto|N` 可用。
- 对首个待清洗 MCAP 进行 topic 检查，配置错误时给出清晰原因。
- 清洗成功后输出 MCAP 包含原始 topic，并新增夹爪宽度 topic：
  - `/gopro_left/gripper_width`
  - `/gopro_right/gripper_width`
- 失败文件的半成品输出会被清理，已成功文件保留。

## 与项目总目标的关系

场景六处于 Octopus 采集链路之后。场景三和场景四关注采集与显示，场景六关注采集产物 `.mcap` 的离线清洗，使原始 FASTUMI 采集结果转化为更适合后续处理和验证的数据文件。
