# 阶段二：数据清洗背景信息

## raw MCAP 的输入形态

raw MCAP 是多个 topic 各自的数据流：

- `/image_left`、`/image_right`：左右图像帧及时间戳。
- `/baton_left/pose`、`/baton_right/pose`：左右 Baton Mini 位姿及时间戳。
- `/tactile_left`、`/tactile_right`：左右触觉数据及时间戳。

各 topic 频率不一致，时间戳不天然对齐。raw MCAP 本身不区分 observation 和 action。

## 五场景的数据流关系

| 场景 | 输入 | 核心处理 | 输出 |
| --- | --- | --- | --- |
| 场景一 | raw MCAP | 提取夹爪宽度、common frame 相机位姿转换 | cleaned MCAP |
| 场景二 | cleaned MCAP | 滤波、异常值检测补全、IK/MuJoCo 验证 | validated MCAP |
| 场景三 | validated MCAP | 多 topic 统一时间轴对齐 | aligned MCAP + alignment_report |
| 场景四 | aligned MCAP + schema | episode/step 构建、action chunk 生成、masks/report | canonical_dataset_mcap |
| 场景五 | canonical_dataset_mcap | 按模型格式导出 | exports/ |

## 场景一：提取夹爪开合以及位姿转换

### 夹爪宽度提取

当前硬件配置中，夹爪宽度不在 MCAP 中直接记录。需要从 GoPro 图像中通过 ArUco 标记检测来估计夹爪宽度，生成 `/gopro_left/gripper_width` 和 `/gopro_right/gripper_width` 语义 topic。

### 位姿转换

左右 Baton Mini 各自处于独立局部坐标系中。需要通过标定得到的 6D 外参，把 `left_baton_pose_raw` 和 `right_baton_pose_raw` 转换到统一的 `common_frame` 下：

- `left_baton_pose_raw` → `left_camera_pose_common`
- `right_baton_pose_raw` → `right_camera_pose_common`

`common_frame` 是人为定义的外部统一坐标系，使左手和右手相机位姿处在同一个空间表达中。转换参数保存在 `config/data_clean_left_transform.yaml` 和 `config/data_clean_right_transform.yaml` 中；TCP 位姿后续可由 common-frame 相机位姿叠加相机到 TCP 外参得到。

## 场景二：硬件数据可靠性验证

### 为什么需要这一步

硬件传感器采集的原始信号存在噪声、突变和丢帧等问题。如果直接用于后续处理和模型训练，会引入错误信号。因此需要在进入时间对齐和 canonical dataset 构建之前，确保每条数据都真实可靠。

### 维度一：硬件信号滤波与异常值处理

对 cleaned MCAP 中的位姿和触觉数据执行：

- **滤波**：对位姿序列应用低通滤波（如 Butterworth、Savitzky-Golay），平滑高频噪声。
- **异常值检测**：检测位姿跳变、触觉突变等异常点。
- **异常值补全**：删除异常值后需要设计补全策略（插值、邻近值替换等），保证时间序列连续性。

### 维度二：IK 可行性验证与 MuJoCo 仿真

位姿数据不仅要反映真实物理运动，还要确保能被睿尔曼机械臂安全执行。具体步骤：

1. **IK 求解**：将 common frame 下的 TCP 位姿转换为睿尔曼机械臂的关节角。
2. **关节限制检查**：验证关节角是否在机械臂的旋转范围内。
3. **动力学检查**：验证关节速度和加速度是否在安全范围内，不会造成机械损伤。
4. **MuJoCo 物理仿真**：在 MuJoCo 仿真环境中播放位姿记录，发现无法执行或物理不可行的数据段。
5. **问题数据修复**：对仿真中发现的问题数据段，设计修复策略（如轨迹平滑、关键点插值等）。

### 硬件背景

- **位姿来源**：Baton Mini 双目相机提供的 6DoF odometry。
- **触觉来源**：触觉传感器阵列数据。
- **目标机械臂**：睿尔曼（RealMan）协作机械臂，需查阅其关节限制、速度限制和加速度限制参数。

## 场景三：MCAP 多 topic 时间轴对齐

### 为什么需要对齐

各 topic 以不同频率独立采集（例如图像 15Hz、位姿 100Hz、触觉 200Hz），时间戳不天然对齐。要构建 step 级训练样本，必须将所有 topic 统一到同一条时间轴。

### 对齐策略

- 选择统一采样频率（如 20Hz），生成固定间隔的 step 时间戳序列。
- 对每个 step，为每个 topic 找到最近邻消息或进行插值。
- 记录每个字段的对齐方式和时间误差。

## 场景四：构建标准 canonical dataset

### observation 定义

`observation_t` 是多模态状态包：`image_left`、`image_right`、`left_tcp_pose_common`、`right_tcp_pose_common`、`left_gripper_width`、`right_gripper_width`、`left_tactile`、`right_tactile`、`language_instruction`。

### action 定义

采用 UMI 风格 relative trajectory action：在当前推理起点 t，预测未来 K 步左右 TCP 相对于当前 TCP 位姿的目标相对轨迹，并包含夹爪宽度。

对单臂：`A_t+k = inverse(T_t) × T_t+k`。双臂左右分别计算。

### step_index 的职责

`step_index.parquet` 把 `data.mcap` 从 topic 世界映射到 step 世界，每行对应一个 step，记录该 step 的统一时间戳、各 observation 字段在 MCAP 中的定位引用、action chunk 的未来 step 范围。

### masks 和 reports 的职责

`masks.parquet` 记录每个 step 各字段的有效性。`alignment_report.json` 关注同步质量。`quality_report.json` 关注数据质量。`robot_constraint_report.json` 关注机器人执行约束。`processing_manifest.json` 关注处理可追溯性。

## 场景五：模型训练格式导出器

### 当前状态

最终使用的模型和数据格式尚未确定。常见的训练格式包括 LeRobot、HDF5、Zarr 等。

### 设计原则

- 导出器严格消费 canonical dataset 的 schema、step_index 和 masks。
- 即使删除 exports 目录，也应能从 canonical dataset 重新导出。
- 导出器设计应留有扩展接口，便于适配新模型的数据格式要求。

## common frame 说明

`common_frame` 是统一的外部坐标系，使左右 TCP 处在同一个空间表达中。它不必等同于 `robot_base`，但必须让模型正确理解双臂空间关系。`frame_schema.json` 定义 common frame 的原点、轴向、单位和四元数顺序。
