# 录制链路

本页描述 Octopus 录制链路（`recorder` 节点 + `McapRecorder` 类）的完整运转机理：从用户点击 Start 到 raw MCAP 落盘的全过程。

## 定位

本页回答：录制链路内部是怎么工作的？什么情况下勾选了 topic 却录不进去？

本页不涉及 raw MCAP 的产物契约（见 `10_数据流与产物/02_raw_MCAP产物语义.md`），不涉及显示（见 `02_显示链路.md`）。

## 完整时序

```text
OpDockWidget 构造
  → 读取 config::recording::mcap::topics，为每个默认 topic 创建可勾选 QListWidgetItem

用户点击 Start
  → OpDockWidget::start() 遍历列表，只把 checked 的 topic 放入 topics vector
  → 若为空，弹错误，不创建 recorder

创建 McapRecorder
  → 构造独立 rclcpp::Node("recorder")
  → 构造独立 SingleThreadedExecutor + 后台 jthread spin
  → 与显示链路的 octopus 节点完全分离

subscribe_topics(topics)
  → node_->get_topic_names_and_types() 查询当前 ROS graph
  → 只有此刻已存在的 topic 进入 topics_ map
  → 不存在的勾选项被静默跳过

record(filename, compression)
  → running_.exchange(true) 防重复开始
  → topics_ 为空时报 "no available topics to record"
  → 打开 McapWriter（profile=ros2, compression=配置值）
  → 对每个 topic: create_channel + create_subscription

create_channel
  → get_message_definition(type) 取手写 schema → addSchema（同类型只注册一次）
  → addChannel（每 topic 一个 channel）

create_subscription（generic）
  → node_->create_generic_subscription(topic, type, qos, callback)
  → callback 收到 SerializedMessage + MessageInfo

回调写入
  → fast_odom? 按 source_timestamp 60Hz 节流，跳过的不写
  → 构造 mcap::Message:
       channelId = channels_[topic]
       logTime   = received_timestamp
       publishTime = source_timestamp
       data 指针直接指向 serialized buffer（不反序列化）
  → writer_->write(msg)

用户点击 Stop
  → recorder_.reset() → McapRecorder 析构
  → cancel executor + join 线程 + close writer
```

## 关键机制详解

### topic 存在性过滤

`subscribe_topics()` 调用 `node_->get_topic_names_and_types()` 查询当前 ROS graph。**只有 Start 时刻已经存在的 topic 才会进入 `topics_` map**。

推论：

- Operation 列表中有 topic 不代表一定会录制。
- 如果某个传感器节点启动慢，Start 时该 topic 尚未在 ROS graph 中注册，会被静默跳过，不会报错也不会重试。
- 正确做法：先确认所有传感器 topic 都已发布（`ros2 topic list`），再点击 Start。

### QoS 策略

`qos_for_topic()` 决定每个 topic 的 QoS：

1. 默认 `rclcpp::QoS(KeepLast(10)).reliable()`。
2. 查询该 topic 的所有 publisher，若发现任一 publisher 是 BEST_EFFORT，则该订阅也用 BEST_EFFORT。
3. 特例：若 publishers 为空且类型是 `sensor_msgs/msg/Image` 或 `CompressedImage`，也用 BEST_EFFORT（兼容图像 publisher 尚未上线的场景）。

### fast_odom 60Hz 节流

topic 名包含 `fast_odom` 的消息，回调中按 `source_timestamp` 节流：

- `kFastOdomMinIntervalNs = 16,666,666 ns`（约 60Hz）。
- 连续两条 fast_odom 的 source_timestamp 差小于该值时，**后一条被丢弃，不写入 MCAP**。
- 目的：Baton Mini fast_odom 原始约 200Hz，录制时降为 60Hz 控制文件体积。

详见 `10_数据流与产物/02_raw_MCAP产物语义.md`。

### schema 手写维护

`get_message_definition()` 为每种消息类型返回**手写**的 ros2msg schema 文本。当前覆盖 5 种类型：

- `sensor_msgs/msg/Image`、`sensor_msgs/msg/CompressedImage`、`sensor_msgs/msg/JointState`
- `nav_msgs/msg/Odometry`
- `hwk_pressure_interfaces/msg/PressureFrame`

新增消息类型加入录制时，**必须在此函数补上手写 schema**，否则 MCAP 中 schema 为空，后续工具无法解码。

### Stop 的本质

点击 Stop 本质是 `recorder_.reset()`。`McapRecorder` 析构时：

1. `executor_->cancel()` —— 停止 spin。
2. `thread_.join()` —— 等待后台线程退出。
3. `writer_->close()` —— 关闭 MCAP writer，刷盘。

## 排障

- 勾选了 topic 但 MCAP 里没有：Start 时刻该 topic 不在 ROS graph 中，被静默跳过。先 `ros2 topic list` 确认。
- MCAP 无法被工具解析：新增了消息类型但没在 `get_message_definition()` 补 schema。
- 显示正常但录制为空：显示链路和录制链路是两个独立节点，显示正常不代表 recorder 已订阅。确认是否点了 Start。
