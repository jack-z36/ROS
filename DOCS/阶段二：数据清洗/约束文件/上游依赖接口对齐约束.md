# 上游依赖接口对齐约束

本文用于约束阶段二 L1/L2/L3 开发范式中的功能依赖检查。阶段二的多个功能模块是一环接一环的链路；开发功能 X 前，必须先确认它直接依赖的上游功能 Y 已经定义了可消费的接口，避免功能 2 和功能 3 分别完成后接口无法对接。

## 一、适用范围

本文适用于：

- 编写或修改 `功能模块清单.md`。
- 编写或修改任意 L2 能力模块说明。
- 从 L2 拆分任意 L3 微元任务。
- 执行任意会新增、修改或消费阶段二接口的 L3 任务。

本文不要求每次读取所有历史文档；只要求读取当前功能的直接上游依赖及其接口定义。

## 二、核心原则

开发功能 X 前，必须先回答：

```text
功能 X 依赖谁？
功能 X 从上游拿什么？
上游实际产出和 X 期望消费的接口是否一致？
如果不一致，是修改 X、修改上游，还是先新增接口对齐任务？
```

不得在未确认上游接口的情况下，让后续 Agent 自行猜测字段、路径、状态、错误对象、目录结构或调用返回值。

## 三、什么算上游依赖

以下任一情况都算上游依赖：

- 当前功能读取上游功能生成的数据对象、文件、目录、报告、manifest、schema、mask 或日志。
- 当前功能调用上游功能的函数、类、runner、service 或命令入口。
- 当前功能复用上游功能定义的状态、枚举、配置对象、错误对象或结果对象。
- 当前功能的执行顺序必须等待上游功能完成。
- 当前功能的验收依赖上游功能的输出样例或测试 fixture。

只做概念参考、不直接消费接口的文档不算直接上游依赖，可以作为背景文档读取，但不需要进入接口对齐表。

## 四、L2 编写前必须做的接口检查

编写 L2 能力模块说明前，必须先定位直接上游功能，并读取：

1. 上游 `L2能力模块/<能力名称>.md`。
2. 上游相关 `L2数据定义/` 原子文档。
3. 上游已存在的 L3 `task/active/<功能组>/`、`task/completed/<功能组>/` 任务或执行记录中与接口变更有关的内容。
4. 如果上游还没有 L2 文档，读取功能模块清单和对应 Harness 文档，并把“上游接口未稳定”写入当前 L2 的未知问题。

L2 文件必须包含或能够回答以下接口对齐表：

| 上游功能 | 上游接口 / 产物 | 当前功能如何消费 | 对齐状态 | 处理方式 |
|---|---|---|---|---|
|  |  |  | 已对齐 / 缺定义 / 有冲突 | 复用 / 调整当前功能 / 新增上游接口任务 / 暂停确认 |

## 五、L3 生成前必须做的接口检查

从 L2 生成 L3 前，必须确认：

- 本 L3 是否直接消费上游接口。
- 如果消费，上游接口定义文档必须列入 L3 的“必读任务文档”或“必读代码”。
- 如果上游接口尚未稳定，当前 L3 不得直接实现消费逻辑；应先生成“上游接口定义/对齐”的 L3，或在当前 L3 中明确只做接口占位与失败提示。
- L3 的验收命令必须覆盖至少一个上游接口兼容性检查，例如导入类型、读取样例、解析上游文件、调用上游返回值或验证字段映射。

## 六、执行 L3 前必须做的接口检查

执行 L3 前，Agent 必须先读本 L3 的上游依赖相关文档，并在开工前确认：

```text
本 L3 直接依赖的上游功能：
上游接口定义位置：
当前 L3 期望消费的字段 / 文件 / 返回值：
是否存在接口冲突：
如果有冲突，本次处理策略：
```

如果发现上游接口与当前 L3 期望不一致，必须暂停并说明冲突，不得擅自同时修改上下游两侧，除非 L3 明确允许。

## 七、禁止事项

- 不得跳过直接上游 L2 或数据定义文档，直接编写下游 L2/L3。
- 不得在下游功能中重新定义一个与上游相似但字段不同的数据对象。
- 不得在下游 L3 中偷偷兼容多个猜测版本的上游接口，除非该兼容策略已写入 L2。
- 不得为了让当前测试通过而修改上游接口，除非当前 L3 明确授权修改上游文件。
- 不得把“上游尚未定义”伪装成默认设计；必须写入未知问题或先拆出上游接口任务。

## 八、检查清单

```text
□ 是否识别了直接上游功能？
□ 是否读取了上游 L2、数据定义或接口相关 L3 记录？
□ 当前功能消费的字段、路径、返回值、状态或错误对象是否与上游一致？
□ 如果上游接口缺失，是否写入未知问题或拆出接口定义任务？
□ L3 验收是否覆盖了至少一个上游接口兼容性检查？
□ 是否避免同时无授权修改上下游两侧？
```
