# 时间戳与时钟模型

本页记录阶段一各传感器 topic 的时间戳来源，以及 raw MCAP 中的时间戳语义。这是阶段二跨 topic 时间对齐工作的前提。

## 定位

本页回答：每个 topic 的 `header.stamp` 是怎么打出来的？来源是同一个时钟吗？

阶段一的核心边界声明：**阶段一不负责跨 topic 时间同步。** 各 topic 各自打时间戳，时钟来源异构，对齐是阶段二的工作。但阶段一有责任如实记录各 topic 的时间戳来源，本页即此记录。

## 各 topic 的时间戳来源

| 模态 / topic | 时间戳来源 | 时钟域 | 说明 |
|---|---|---|---|
| GoPro 图像 `/gopro_*/image_raw` | v4l2 硬件缓冲区时间戳 | v4l2 内核时钟 | `use_v4l2_buffer_timestamps: true`，非 ROS 时钟 |
| Baton 图像 `/baton_mini_*/image_*` | IMU 关键帧同步 | SDK 内部时钟 | 由 Baton Mini 固件打，图像帧与对应 IMU 关键帧对齐 |
| Baton IMU `/baton_mini_*/imu` | SDK 内部时钟 | SDK 内部时钟 | 由 TCP 包携带 |
| Baton odom `/baton_mini_*/{odometry,fast_odom}` | SDK 内部时钟 | SDK 内部时钟 | 由 TCP 包携带 |
| 触觉 `/pressure/*` | `node.get_clock().now()` | ROS 时钟 | 由 `pressure_driver_node` 在发布时打 |

关键观察：

1. **时钟来源异构**：三类传感器的 `header.stamp` 来自三个不同的时钟域（v4l2 内核时钟、Baton SDK 时钟、ROS 时钟），它们之间没有公共时间基准。
2. **GoPro 与 Baton 图像都不是 ROS 时钟**：这两类图像的时间戳来自硬件/SDK，与触觉的 ROS 时钟不可直接比较。
3. **这是阶段二对齐难题的根源**：raw MCAP 里的 `header.stamp`（写入 `publishTime`）混合了多个时钟域。

## raw MCAP 中的双时间戳

raw MCAP 每条消息有两个时间戳，详见 `02_raw_MCAP产物语义.md`：

| 字段 | 来源 | 对齐用途 |
|---|---|---|
| `logTime` | `received_timestamp`（Octopus 收包时刻，ROS 时钟） | 所有 topic 共享同一接收时钟，**可用于跨 topic 近似对齐** |
| `publishTime` | `source_timestamp`（消息自带，异构时钟域） | 反映传感器真实采集时刻，**但跨模态不可直接比较** |

推论：阶段二若要做跨 topic 对齐，`logTime`（统一在 Octopus 接收时刻打）是相对可比较的基准；`publishTime` 反映各传感器自身时钟，需额外做时钟域转换。

## 阶段一不做的事

- 不做硬件级时间同步（无 PTP、无 NTP 对齐各传感器时钟）。
- 不做软件级 topic 重采样或插值对齐。
- 不保证 `publishTime` 跨 topic 可比较。
- 不修改传感器自带的原始时间戳（GoPro/Baton 的时间戳原样透传）。

## 对下游的影响

- **阶段二**：必须自行决定用 `logTime` 还是 `publishTime` 做对齐，并处理时钟域异构问题。
- **阶段三/四**：若部署时需要融合多模态数据，同样面对此异构时钟问题。阶段四读取触觉数据的代码可与阶段一共享 ROS 时钟语义，但读取图像/位姿时需注意其时间戳不是 ROS 时钟。
