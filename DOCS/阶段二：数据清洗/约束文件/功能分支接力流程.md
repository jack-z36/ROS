# 功能分支接力流程

本文约束阶段二 Win 主机与 Ubuntu 主机通过 Git feature 分支接力开发的固定流程。

## 一、核心规则

- `main` 是稳定分支，不作为日常工作台。
- 一个阶段二 L1 任务线对应一个长期 feature 分支。
- Win 主机负责在 feature 分支上写架构文档、L2 能力模块、L2 数据定义和 L3 微元任务。
- Ubuntu 主机负责在同一 feature 分支上执行 L3、修改代码和测试、更新当前 L3 文件并归档。
- 阶段性验收完成后，只由 Win 主机把 feature 分支合并回 `main`。

默认分支：

| L1 任务线 | feature 分支 |
|---|---|
| Runtime MVP | `runtime-mvp` |
| Service | `feature/stage2-service` |

## 二、Win 开始或继续 L1 设计分支

开始 Runtime MVP：

```powershell
git switch main
git pull --ff-only
git switch -c runtime-mvp
```

如果分支已存在：

```powershell
git fetch origin
git switch runtime-mvp
git pull --ff-only
```

写完规划、L2 或 L3 后：

```powershell
git add -A
git status
git commit -m "docs(runtime): plan <模块名>"
git push -u origin runtime-mvp
```

Service 分支把 `runtime-mvp` 替换为 `feature/stage2-service`，提交前缀使用 `docs(service): ...`。

## 三、Ubuntu 拉取同一 L1 分支执行 L3

Ubuntu 执行 Runtime MVP L3 前：

```bash
git fetch origin
git switch runtime-mvp || git switch -c runtime-mvp origin/runtime-mvp
git pull --ff-only
```

执行前必须确认：

- 当前分支是当前 L3 所属 L1 的 feature 分支。
- 当前 L3 文件位于 `DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/`。
- 当前 L3 文件列出的约束、上游 L3 和代码文件已经读取。

完成单个 L3 后：

```bash
git add -A
git status
git commit -m "feat(runtime): complete <L3任务名>"
git push
```

Ubuntu 完成 L3 后仍然只把执行记录写入当前 L3 文件末尾，并把该 L3 移到 `task/completed/<L1归档目录>/<功能组>/`；如果原 active 功能组目录为空，必须删除该空目录；不得新增集中执行记录文件。

## 四、Win 验收并合并回 main

Win 拉取 feature 分支最新内容并验收：

```powershell
git fetch origin
git switch runtime-mvp
git pull --ff-only
```

确认该 L1 阶段性结果稳定后，再合并到 `main`：

```powershell
git switch main
git pull --ff-only
git fetch origin
git merge --no-ff runtime-mvp
git push
```

合并完成后，Win 和 Ubuntu 后续继续开发必须重新切回对应 L1 feature 分支，不得留在 `main` 上继续写文档或代码。

## 五、禁止事项

- 禁止 Win 或 Ubuntu 把 `main` 当作日常工作台。
- 禁止 Ubuntu 直接提交或推送 `main`。
- 禁止两台机器在同一个 L1 feature 分支上长期保留未提交改动。
- 禁止省略 `--ff-only` 执行拉取。
- 禁止遇到分叉、冲突或远端领先时自动 merge/rebase/force push。
- 禁止把 Ubuntu L3 执行结果写入 `DOCS/阶段二：数据清洗/执行记录/`、各级 `当前进度.md`、共享 `执行记录.md` 或 `DOCS/总执行日志.md`。
