阶段二产物架构可视化

把 raw MCAP 逐级转换为 cleaned、validated、aligned、canonical dataset，并通过明确的层间数据流约束后续程序开发。

主数据产物 6 类 raw / cleaned / validated / aligned / canonical / exports
执行场景 5 个 清洗、验证、对齐、构建、导出
程序分层 6 层 Types -> Config -> Repo -> Service -> Runtime -> UI
标准交付 canonical dataset 阶段三训练前的唯一可信输入

产物流

主路径不是简单格式转换，而是数据语义逐级增强。每一级产物都必须能被下一级明确消费，并能通过报告解释自身质量。

→
场景三

场景四

场景五

exports

从 canonical dataset 可重复导出训练格式。

配置与标定

夹爪标定、common frame、滤波阈值、step 频率和导出映射按场景归属，随开发逐步增长。

报告与 masks

alignment、quality、robot constraint 和 invalid reason 决定哪些数据能进入训练。

manifest

记录输入、配置、软件版本、处理步骤和关键报告，让任意 episode 可追溯。

层间数据流

分层不只规定依赖方向，也规定数据如何进入、被校验、被读取、被处理、被写出，以及状态和错误如何回流。

UI

把用户意图转成 RunRequest，展示 RunSummary。

Runtime

创建 RunContext，编排配置、输入、处理、写出、日志和 manifest。

Service

执行清洗、验证、对齐、dataset 构建和导出业务逻辑。

Repo

封装 MCAP、Parquet、JSON、YAML 和目录读写。

Config

解析并校验配置、默认值、单位、坐标系、阈值和必需字段。

Types

定义 DTO、schema、report、artifact refs 和错误类型。

1

UI -> Runtime

提交 RunRequest(mode, scene, input, overrides)，不直接读写数据文件。

2

Runtime -> Config

加载配置和临时覆盖，得到 ValidatedConfig 或配置缺失定位。

3

Runtime -> Repo

检查输入输出路径，生成 InputInventory 和 OutputPlan。

4

Runtime -> Service

传入上下文、配置和产物引用，Service 只消费已解析的结构化对象。

5

Service <-> Repo

Repo 提供 typed streams/tables，Service 生成主产物、masks、reports 和 metrics。

6

Runtime -> UI

汇总 SceneResult，写日志和 manifest，再返回状态、路径和下一步动作。

请求与数据下行

UI 意图进入 Runtime，经过 Config 和 Repo 的边界校验后，Service 才能处理 typed input，并由 Repo 写出产物。

结果与错误回流

Config、Repo、Service 的错误统一回到 Runtime，写入结构化日志和报告，再由 UI 显示失败场景、步骤、摘要和日志路径。

五场景映射

每个场景都套用同一个层间数据流模板：UI 提交意图，Runtime 编排，Config 校验，Repo 读写，Service 转换，Runtime 回传结果。

场景一

raw -> cleaned

补齐基础语义。

  • 读入 raw MCAP topic inventory
  • 夹爪宽度提取
  • common frame 位姿转换
  • 写出 cleaned MCAP 和清洗报告
场景二

cleaned -> validated

验证可靠性和物理可执行性。

  • 滤波、异常检测和补全
  • IK、关节限制和仿真验证
  • 写出异常报告和修复记录
  • 不可执行片段进入下游 masks
场景三

validated -> aligned

统一 step 时间轴。

  • 生成目标 step 时间戳
  • 对齐图像、位姿、触觉、夹爪
  • 统计误差、缺失和插值比例
  • 写出 alignment report
场景四

aligned -> canonical

构建标准数据集。

  • 生成 schema 和 episode
  • 写 step_index 和 masks
  • 生成 action chunk
  • 写 reports 和 processing_manifest
场景五

canonical -> exports

导出训练格式。

  • 读取 schema、index 和 masks
  • 过滤不可训练 step
  • 映射字段、shape 和 dtype
  • 写导出报告和校验结果

canonical dataset 契约

canonical dataset 是阶段二交付给阶段三的标准中间态。后续 exporter 只消费它，不回头读取上游中间产物修复数据。

canonical_dataset_mcap/
├── dataset_meta.json
├── dataset_index.parquet
├── schema/
│   ├── observation_schema.json
│   ├── action_schema.json
│   ├── frame_schema.json
│   ├── topic_schema.json
│   └── quality_schema.json
├── episodes/
│   └── episode_xxxxxx/
│       ├── episode_meta.json
│       ├── data.mcap
│       ├── step_index.parquet
│       ├── masks.parquet
│       ├── alignment_report.json
│       ├── quality_report.json
│       ├── robot_constraint_report.json
│       └── processing_manifest.json
└── exports/

schema 解释所有 episode

observation、action、frame、topic、quality schema 必须能解释 dataset 下的每条 episode。

step_index 定位数据

step_index.parquet 把 step 世界映射到 data.mcap 消息或派生字段。

masks 阻止脏数据入训

必需字段缺失、不可对齐、不可执行或不可训练时，必须带 invalid reason。

action 可复现

relative trajectory action 必须能从 common-frame TCP 轨迹和夹爪宽度复现。

manifest 可追溯

输入、配置、软件版本、处理步骤和关键报告必须能追到来源。

exports 可再生成

删除 exports/ 后，应能从 canonical dataset 重新导出训练格式。

开发护栏

后续实现可以自由拆模块，但不能突破边界校验、结构化日志、单向依赖和可追溯产物契约。

边界校验
  • 输入路径、文件格式、topic/schema 必须显式校验。
  • 配置字段必须校验类型、单位、范围、坐标系和路径。
  • 输出目录、覆盖策略和报告可解析性必须提前检查。
日志与错误
  • 核心模块禁止裸 print。
  • 失败必须定位到场景、步骤、文件、episode、step 或字段。
  • Runtime 统一写结构化日志、失败摘要和 manifest。
分层纪律
  • UI 不直接读写 MCAP/Parquet/JSON。
  • Service 不解析命令行、不管理交互菜单。
  • Repo 不做业务判断，只封装持久化读写。
训练安全
  • 不可训练 step 必须被 masks 过滤。
  • 导出器不回头修复上游数据。
  • 机器人不可执行片段不能静默进入 exports。
