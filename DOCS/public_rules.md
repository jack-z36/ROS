# 公共规则

本文件记录 `.` 项目的公共协作规则。它服务于当前总目标、四个阶段和各阶段下的场景，是所有阶段共享的常驻规则文件。

## 当前主推进阶段

当前主推进阶段是：阶段二：数据清洗。次推进阶段是阶段一：因为我们迭代了一些硬件，因此会对ROS节点进行部分的修改。我们主要是把gopro进行了替代，会用另一款相机进行视频流的采集，因此，当你判别我是在开发新的相机节点时，自动化初始化在阶段一中创建场景流六文件夹，然后再进行相关工作。

这表示默认项目工作重心已经从 raw MCAP 采集推进到 canonical dataset 设计与生成。阶段一仍作为采集基础继续维护；阶段三模型训练和阶段四模型部署目前只建立阶段级方向，尚未正式启动具体场景。

每次处理任务时，必须先识别交互模式，再读取该模式需要的最小入口文档。阶段级文档和场景文档只在任务确实需要对应背景时读取，不因用户提到某个阶段就默认全部加载。

阶段二采用双机协作边界和 L1 feature 分支接力流程，详见 `DOCS/阶段二：数据清洗/约束文件/双机协作写入边界.md` 与 `DOCS/阶段二：数据清洗/约束文件/功能分支接力流程.md`。Runtime MVP 使用 `runtime-mvp` 分支，Service 使用 `feature/stage2-service` 分支；Ubuntu L3 执行端不得在 `main` 上执行 L3，不得写 `DOCS/总执行日志.md`、阶段二 `执行记录/`、阶段/场景 `当前进度.md` 或共享 `执行记录.md`。

## 一、项目最终目标

通过公司的数据采集平台程序 Octopus，实现 FASTUMI 数据采集，并将采集结果输出为 MCAP 文件；随后进入数据清洗、模型训练和模型部署阶段。

Octopus 的架构索引文件为：

- `DOCS/Octopus_architecture.md`

涉及 Octopus 采集链路、ROS2 topic、MCAP 录制、配置文件、显示与录制边界时，必须优先阅读该架构文件，再继续分析或修改。

## 三、项目边界

本项目当前关注从数据采集到数据清洗的链路打通，并以阶段二 canonical dataset 为当前重点；不把目标扩展为重新设计 Octopus、重构全部 ROS 节点或提前实现模型训练/部署。

核心边界如下：

- 数据来源：FASTUMI 相关 ROS2 节点输出的话题数据。
- 采集平台：公司的 Octopus 程序。
- 采集产物：可被后续处理、回放或验证的 `.mcap` 文件。
- 清洗产物：由 `data_clean` 生成或后续扩展生成的 `canonical_dataset_mcap`，包括 `data.mcap`、schema、step index、masks、report、manifest、夹爪宽度结果和坐标/TCP 配置。
- 关键验证：Octopus 能看到需要的 ROS2 topic，并能把选定 topic 正确录制进 MCAP；清洗程序能读取原始 MCAP 并输出符合配置约束的清洗结果。

## 四、固定文档职责

每个阶段固定维护以下四类阶段级文档：

- `阶段目标描述.md`
- `背景信息.md`
- `当前进度.md`
- `阶段产出.md`

阶段级文档的颗粒度必须较粗，作用是给后续 Agent 一个阶段方向和判断入口，不写成具体执行日志。需要了解脚本、配置、topic、命令、日志、问题历史时，应自动进入该阶段下对应场景目录读取细节文档。

### 阶段目标描述

说明该阶段最终要达成什么效果、在四阶段链路中的位置、阶段成功标准和与上下游的关系。

### 阶段背景信息

说明完成该阶段需要理解的粗粒度上下文，例如数据形态、关键概念、上下游契约和不应混淆的边界。

### 阶段当前进度

说明该阶段目前推进到哪里，哪些能力已经形成，哪些还没开始或尚未验证。

### 阶段产出

说明该阶段在执行过程中已经形成或依赖了哪些程序、脚本、launch、配置、软件模块和架构文档。它不负责描述阶段最终输出的数据是什么；阶段最终目标和数据产物应写入 `阶段目标描述.md`。`阶段产出.md` 必须尽量回答每个软件资产的功能、输入、输出，以及在哪里能看到更详细的软件信息。

每个具体场景固定维护以下五类文档：

- `目标描述.md`
- `背景信息.md`
- `执行约束.md`
- `执行记录.md`
- `当前进度.md`

各场景还应维护补充文档：

- `输出程序与文件.md`

### 目标描述

说明该场景最终要达成什么效果，应记录终极目标、成功时用户能做什么，以及与项目总目标的关系。

### 背景信息

说明完成该场景需要知道的上下文，应记录涉及的 ROS2 包、launch 文件、脚本、配置文件、设备、topic、数据类型和上下游关系。

### 执行约束

说明执行过程中必须遵守的限制，包括强制预读、配置边界、验证边界和不应算作成功的情况。

### 执行记录

说明某时某刻做了什么，遇到了什么问题，应记录日期时间、用户请求、命令或操作、观察结果、修复动作和结论。

### 当前进度

说明现在推进到了哪一步，应区分已完成、正在处理、未完成、风险和下次优先事项。

### 输出程序与文件

记录该场景已经形成或依赖的所有程序、脚本和配置文件，应包含输出清单、目标输出和使用边界。

## 五、DOCS 管理规则

`DOCS` 是本项目的文档中心。除已有代码包自带文档外，围绕本项目目标产生的新文档都必须放入该目录下对应阶段/场景。

规则：

- 公共规则、总架构、跨阶段信息放在 `DOCS` 根目录。
- 无法明确归入某个阶段/场景的零散执行事项，Win 文档规划端可以追加记录到 `DOCS/总执行日志.md`；Ubuntu L3 执行端不得写该文件。
- 每个阶段目录必须维护 `阶段目标描述.md`、`背景信息.md`、`当前进度.md`、`阶段产出.md` 四个阶段级文档。
- 阶段一数据采集的阶段级文档必须放入 `DOCS/阶段一：数据采集`，场景细节文档必须放入其下对应场景目录。
- 阶段二数据清洗的阶段级文档必须放入 `DOCS/阶段二：数据清洗`，场景细节文档必须放入其下对应场景目录。
- 阶段三模型训练的阶段级文档必须放入 `DOCS/阶段三：模型训练`，后续场景细节文档必须放入其下对应场景目录。
- 阶段四模型部署的阶段级文档必须放入 `DOCS/阶段四：模型部署`，后续场景细节文档必须放入其下对应场景目录。
- 不把新的项目文档散落到 `.` 根目录、`src` 目录、`config` 目录、`log` 目录或临时目录。
- 新文档必须能被 `AGENTS.md`、对应工作流、对应 L3 任务文件或相关 README 索引到。
- 废弃但仍有参考价值的内容不直接删除，优先移动到对应阶段/场景目录下的归档文档或在执行记录中注明。

## 六、架构文档要求

除输出清单中的简表外，每个程序、脚本或独立模块必须配备一份独立的架构说明文档（`*_architecture.md` 或 `*_架构说明.md`），放在该程序所属的代码包目录下。

架构文档必须包含以下内容，使毫无上下文记忆的后续 Agent 能够快速理解该程序的设计与运行方式：

1. 概述：该程序的用途、所属阶段/场景、解决什么问题。
2. 目录结构：源码文件清单及每个文件的职责。
3. 数据流：输入来源、内部工作机理、处理逻辑、输出目标。
4. 依赖与运行：依赖的系统环境、ROS2 包、Python 库等；启动命令和参数说明。
5. 配置项说明：关键配置参数、默认值、可调范围和含义。
6. 与上下游的关系：该程序被谁调用、调用了谁、共享哪些 topic 或文件。

更新规则：

- 新增程序或脚本时，必须在对应场景的输出清单中追加条目，并同步创建架构文档。
- 修改已有程序的行为时，必须同步更新其架构文档。
- 架构文档的文件名和路径必须在输出清单表格中明确列出。

## 七、执行纪律

处理本项目问题时，默认遵守以下纪律：

- 先判断交互模式：Win 文档规划、Ubuntu L3 执行、普通代码维护、Git 操作或其他任务。
- Win 文档规划模式按 `DOCS/工作流/阶段二开发范式.md` 读取最小上下文。
- Ubuntu L3 执行模式只按当前 L3 文件列出的必读上下文执行。
- 如果任务无法明确归入某个阶段/场景，或属于跨阶段零散维护，Win 文档规划端可以阅读并追加 `DOCS/总执行日志.md`；Ubuntu L3 执行端不得写该文件。
- 涉及 Git 状态、提交、推送、拉取、远端、账号、分支或仓库同步时，先阅读 `DOCS/git操作约束.md`。
- 涉及 Octopus 采集程序时，先阅读 `DOCS/Octopus_architecture.md`。
- 涉及 `src/gopro_camera_launch` 时，先阅读该包的架构和运行指南。
- 涉及 `src/baton_mini_sdk_demo` 时，先阅读该包的架构和运行指南。
- 涉及 `src/data_clean` 或 `start_data_clean.sh` 时，优先判断是否为 Ubuntu L3 执行：如果是，只读当前 L3 指定上下文；如果不是，再按实际问题读取必要的阶段二文档。
- 修改代码或脚本前，先确认它服务的是逐个启动、批量启动、Octopus 录制验证，还是 MCAP 数据清洗。
- 运行命令后，如结果会影响阶段/场景判断，Ubuntu L3 执行端只写入当前 L3 执行摘要；Win 文档规划端再统一整理共享文档。
- 当用户明确给出新的事实、约束或阶段性结论时，优先判断写入端：Win 端可沉淀到对应阶段/场景文档，Ubuntu L3 执行端只记录到当前 L3 摘要并建议 Win 端同步。

## 八、AGENTS.md 维护规则

`AGENTS.md` 是项目入口索引文件，只放模式分流、少量目录索引和强制边界，不承载详细任务内容。

维护规则：

- 新增阶段或场景时，先在 `DOCS` 下创建对应目录。
- 每个新场景至少包含目标描述、背景信息、执行约束、执行记录、当前进度五类固定文档，并维护输出程序与文件清单。

- 详细内容写入 DOCS 下对应文档，不写入 `AGENTS.md`。

## 九、交互模式识别与工作流加载

每次交互开始时，必须先识别用户请求属于哪种交互模式。识别到匹配的模式后，自动加载对应的工作流文档并按工作流执行。工作流文档存放在 `DOCS/工作流` 目录下。

### 交互模式与对应工作流

| 交互模式     | 识别信号                                                         | 工作流文档                      |
| ------------ | ---------------------------------------------------------------- | ------------------------------- |
| 从零编写程序 | 用户要求创建新程序、新脚本、新模块、新功能，且当前不存在对应代码 | `DOCS/工作流/从零编写程序.md` |
| 阶段二开发范式 | 用户提到阶段二 pipeline、L1/L2/L3、功能模块拆解、功能模块说明文档、微元任务，或要求根据功能模块说明生成任务 | `DOCS/工作流/阶段二开发范式.md` |

### 识别规则

1. 如果用户明确说"写一个新程序"、"新建一个脚本"、"从零开始实现"等表述，匹配"从零编写程序"模式。
2. 如果用户描述了一个不存在的功能需求（代码库中无对应文件），匹配"从零编写程序"模式。
3. 如果用户围绕阶段二数据清洗 pipeline 讨论 L1/L2/L3 拆解、功能模块说明或微元任务生成，匹配"阶段二开发范式"模式。
4. "阶段二开发范式"只负责生成 L2 功能模块说明和 L3 微元任务文档，不直接执行代码开发。
5. 对已有代码的小修小补、配置调整、bug 修复不匹配"从零编写程序"模式，按常规流程处理。
6. 匹配到模式后，必须先完整阅读对应工作流文档，再按工作流步骤执行。
7. 如果后续新增更多交互模式，在本表中追加条目。
