# 架构边界与机械约束原则

## 适用范围

- 阶段：全局，重点覆盖阶段二数据清洗和阶段四模型部署
- 任务模式：架构改造、跨层修改、公共类型 / schema / provider / adapter 变更、代码类 L3、长期维护规则沉淀
- 适用对象：源码分层、依赖方向、数据 shape、横切能力接入、结构化日志、测试和 lint 约束
- 不适用对象：只读解释、纯执行记录、一次性实验草稿

## 来源与采用口径

本文吸收 OpenAI《Harness engineering》中 “Enforcing architecture and taste” 的工程原则：文档是入口，但稳定 Agent 产出更依赖清晰边界、可机械检查的不变量、结构化反馈回写，以及“中央约束、局部自由”的工程模型。来源：https://openai.com/index/harness-engineering/

本文也吸收本仓库既有阶段二 Runtime / Service 开发范式和阶段四 `Types -> Config -> Repo -> Service -> Runtime -> UI` 分层改造模型。

## 一、文档规则要逐步升级为机械检查

文档不能单独保证长期一致性。反复违反、影响面大或可被稳定判定的规则，应优先升级为：

- lint 规则。
- import / 依赖方向结构测试。
- schema / type contract test。
- 配置校验脚本。
- smoke test 或验收命令。
- CI 或本地 preflight 检查。

如果某条架构或 taste 规则已经被脚本、lint、结构测试或验收命令表达，执行和验收以机械检查为准；文档用于解释意图和修复方向。

本轮规则沉淀不要求立即实现新的 linter 或结构测试。新增机械检查应作为后续 L3 或维护任务单独拆出。

## 二、约束不变量，不微观管理实现

仓库级约束应规定必须保持的边界和不变量，而不是规定每个函数的内部写法。

Agent 在边界内可以自由选择局部实现方式，但不得突破：

- 依赖方向。
- 数据 shape 契约。
- 文件落点。
- 运行入口和验收入口。
- 日志、错误、配置和硬件接口的显式接入方式。

当局部最优实现会破坏全局不变量时，以全局不变量为准。

## 三、数据 shape 必须在边界解析或校验

跨层、跨进程、跨文件、跨 ROS topic、跨模型 bundle 或跨配置中心的数据不得靠下游猜测。

必须在边界处完成以下动作之一：

- 解析为明确 type / schema / dataclass / Pydantic model / TypedDict。
- 校验必需字段、shape、dtype、单位、坐标系、频率和值域。
- 对不完整数据生成结构化错误，而不是继续向下游传播。

下游代码不应反复猜测同一个输入结构。重复出现的 shape 判断应上移为边界校验或公共 contract test。

## 四、默认层次模型

### 阶段二：数据清洗

阶段二默认采用：

```text
Types / Config / Repo / Service / Runtime / Web或入口层
```

- Types / Schemas：定义稳定数据结构、枚举、结果对象和错误引用，不依赖 Config、Repo、Service、Runtime、Web。
- Config：读取、合并、校验配置，产出可被下游消费的有效配置对象。
- Repo：负责文件系统、MCAP、Parquet、LeRobot dataset 等外部存储读写边界。
- Service：实现单一业务场景的数据处理能力，消费明确输入，产出明确结果。
- Runtime：负责运行上下文、调度、run 目录、日志、manifest、错误摘要和场景编排。
- Web 或入口层：负责人机入口、菜单、参数传入和结果展示，不承载核心业务计算。

阶段二 Runtime / Service 代码应沿用现有开发范式：Service 不反向控制 Runtime，入口层不绕过 Runtime 直接拼业务链路。

### 阶段四：模型部署

阶段四沿用：

```text
Types -> Config -> Repo -> Service -> Runtime -> UI
```

- Types：状态、action、observation、metrics、错误和 contract 数据结构。
- Config：部署配置、topic、维度、安全阈值、bundle 路径和运行模式。
- Repo：模型 bundle、normalizer、文件和外部资源读取边界。
- Service：policy loader、observation 装配、action 转换、安全 gate 等可测试能力。
- Runtime：ROS node、控制循环、线程、topic 订阅发布、真机 / shadow-run 编排。
- UI：人工操作入口、状态展示或外部启动封装。

阶段四 L3 是已有代码上的最小可验证改造，不得为了通过单个 L3 绕过既定分层。

## 五、横切能力必须显式接入

横切能力不得隐式穿透各层。以下能力应通过明确 provider、adapter、gateway 或入口契约接入：

- 结构化日志和 metrics。
- 硬件 SDK、机械臂、夹爪、相机、触觉设备。
- ROS topic 订阅、发布和 message 转换。
- 模型 bundle、normalizer、checkpoint 和推理 backend。
- 配置中心、环境变量和路径解析。
- 错误码、错误摘要和运行 manifest。

业务层不得散落读取环境变量、直接访问硬件、直接解析 ROS message 或直接打开模型 bundle，除非该层本身就是对应 adapter / provider。

## 六、依赖方向必须可解释、可检查

新增 import、调用或文件依赖时，必须能说明它属于哪一层、为什么允许从当前层依赖目标层。

禁止常见反向依赖：

- Types 依赖 Config、Service、Runtime 或 UI。
- Config 依赖 Runtime 或 UI。
- Repo 依赖 UI。
- Service 隐式启动 Runtime 或直接控制入口层。
- UI / 入口层复制核心业务计算。

如果现有代码已经存在历史例外，当前任务不得扩大例外；需要修复时应单独拆分任务并补结构检查。

## 七、Taste invariants 应逐步机械化

以下 taste 规则如果在 review 中反复出现，应沉淀为工具检查：

- 命名稳定：schema/type/config/error code/log event 命名一处定义，多处复用。
- 结构化日志：关键运行步骤有统一字段，避免自由文本成为唯一证据。
- 文件大小和职责边界：过大文件要按层或职责拆分，不能继续堆叠横切逻辑。
- 平台可靠性：命令、路径、Python 入口、ROS 环境和硬件缺失状态要可诊断。
- schema/type 命名和字段单位：单位、坐标系、shape、dtype 不靠注释猜测。

这些规则先以文档约束表达；当稳定、重复、可判定时，升级为 lint、结构测试或验收脚本。

## 八、反馈回写

Review 反馈、bug、重构经验和验收失败不能只停留在对话里。

- 单次偶发问题：记录在任务交接或验收反馈。
- 重复出现的问题：回写为对应约束文档规则。
- 反复违反的文档规则：升级为机械检查候选。
- 已机械化的规则：后续执行和验收优先看检查结果。

回写规则时只沉淀稳定约束，不把具体执行日志、当前进度或一次性 debug 过程写入约束文档。
