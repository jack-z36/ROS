# 阶段一：数据采集 总览

阶段一位于项目数据链路的最前端，负责把物理世界的传感器信号采集为可回放、可追溯的原始数据日志。

```text
硬件传感器 -> ROS2 topic -> Octopus(显示链路 + 录制链路) -> raw MCAP
```

## 核心边界

阶段一只保证原始采集链路正确，明确不负责以下事项：

- **不承诺 topic 之间的时间同步**：各 topic 各自打时间戳，跨 topic 对齐是阶段二的工作。
- **不生成训练语义产物**：不产出 canonical dataset、LeRobot dataset、训练 action 或归一化数据。
- **不混入清洗/对齐逻辑**：不滤波、不对齐、不构造坐标系统一。
- **不把"显示成功"等同于"录制成功"**：Octopus 的显示链路与录制链路是两条相互独立的 ROS 节点，看到画面不代表已经录进 MCAP。

## 五个 ROS 包角色一览

阶段一的源码全部位于 `src/data_collection/`，由 5 个 ROS 包组成：

| ROS 包 | 语言 | 职责 | 产物/发布的 topic |
|---|---|---|---|
| `hwk_pressure_interfaces` | C++ 接口包 | 定义触觉消息契约 | `msg/PressureFrame.msg` |
| `hwk_pressure_driver` | Python | 华威科压力传感器串口驱动 | `/pressure/{left,right}_hand/gripper_{1,2}` |
| `gopro_camera_launch` | Python launch | 相机启动包（v4l2） | `/gopro_{left,right}/image_raw` + `/camera_info` |
| `baton_mini_sdk_demo` | C++ | Baton Mini 双目 VIO 相机 SDK | `/baton_mini/{imu,odometry,fast_odom,image_left,image_right}` |
| `VTLA_octopus-master/octopus` | C++/Qt6 | 桌面采集与录制平台 | 显示 UI + raw MCAP 文件 |

其中 Octopus 是阶段一唯一的"汇聚节点"，它消费前 4 个包发布的 topic，是 raw MCAP 的唯一生产者。

## 本目录阅读顺序

本目录按维度组织，推荐按编号顺序阅读：

1. **`10_数据流与产物`** — 先建立全局链路与产物语义的心智模型。理解数据从哪来、到哪去、raw MCAP 里到底有什么。
2. **`20_传感器模态语义`** — 再看每条传感器链路的契约（topic、消息字段、帧率、坐标系）。这是下游阶段二/三/四最常复用的前置知识。
3. **`30_Octopus运转逻辑`** — 然后理解采集程序本身如何运转。重点是"显示链路与录制链路是两个独立节点"这一核心设计。
4. **`40_身份与稳定性`** — 最后看如何保证"同一物理设备始终映射到同一 topic"。这是阶段四部署的核心痛点。
5. **`50_采集场景语义`** — 阶段一验证过哪些传感器组合（场景一到五），命令与进度归工程区。
6. **`90_历史边界`** — 已移除的功能与受限用法，避免重走老路。

## 与其他阶段的关系

- **向阶段二**：阶段二读取 raw MCAP 后，逐步生成 cleaned MCAP、MCAP_A、aligned MCAP 和训练格式桥接产物。阶段一不得提前把阶段二的清洗、滤波、对齐或 action 语义混入采集层。
- **向阶段三/四**：阶段四模型部署同样需要读取传感器数据（尤其是触觉 PressureFrame），其读取代码与阶段一采集端共享同一套消息契约。本目录的 `20_传感器模态语义` 是跨阶段复用的关键。
