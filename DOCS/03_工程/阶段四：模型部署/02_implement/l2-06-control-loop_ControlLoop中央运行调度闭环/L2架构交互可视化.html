固定节拍把 observation、异步推理、单步安全与发布组织成可观测的最小运行闭环。

先读 agent_context/01_L2功能边界.md#运行责任与边界

功能边界：中央总控，不是又一个业务计算器

每个 tick 只决定“现在该拿什么、叫谁做、失败后怎样安全地不做”；模型、安全与硬件细节仍在各自 L2。

✓ 负责

timer 节拍、latest request/result、active chunk/cursor、prefetch、fallback reason、汇总 metrics。

✗ 不负责

ACT batch/前向、安全算法、ROS callback、topic/hardware 适配，也不做平滑或跨 chunk 融合。

任何无 observation、无可用 chunk、推理错误、chunk 过期或 safety 拒绝，都必须落到 L2-05 fallback 与 status；不能伪装成已发布。

Pi0.5 如何运作：旧程序的一次“接力跑”

旧代码已经证明了“timer 不等 GPU”的结构：timer 写请求，后台 worker 算 chunk，下一次 timer 取最新结果。我们借这条骨架，不借它的平滑策略和旧维度。

开发蓝图：真实 tick 调用方向

横向泳道展示运行时调用，不是创建顺序。虚线横幅是启动期注入；红虚线是任何一个失败分支停止正常发布。

关键事实：driver 是 runtime 的 `tick()`；active chunk/cursor 只归 L2-06；L2-04/L2-05 没有编排函数；worker 错误经 result/status 进入下一 tick 的 fallback。
types：无新增

消费既有 public contracts；验收以 import/shape 断言确认，不复制类型。

config：无新增

只注入 L2-01 的 DeployConfig；非法参数必须在 timer 前失败。

repo：无新增

ControlLoop 不读文件、模型或硬件；mock 测试应证明无 repo import。

service：无新增

只调用 L2-04/L2-05；安全计算和 topic 适配保持在其 L2。
