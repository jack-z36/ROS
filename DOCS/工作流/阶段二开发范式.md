# 工作流：阶段二开发范式

本工作流适用于阶段二数据清洗 pipeline 的 L1/L2/L3 开发范式整理。它负责把阶段二的开发想法逐层清洗为功能模块清单、数据定义文件、L2 能力模块说明和可执行任务文档，终点是生成 `03_tasks/active/` 下的 L3 微元任务；不负责直接执行代码开发、测试修复、Git 提交或任务归档。

当用户提到“阶段二 pipeline”“L1/L2/L3”“功能模块拆解”“功能模块说明文档”“微元任务”“根据模块说明生成任务”等信号时，必须加载本工作流。

## 核心分层

### L1：阶段二一级开发任务

阶段二 L1 固定为以下六条任务线：

1. `runtime_mvp`：Runtime MVP 开发。
2. `service_s1`：Service 场景一，提取夹爪开合以及位姿转换。
3. `service_s2`：Service 场景二，硬件数据可靠性验证。
4. `service_s3`：Service 场景三，MCAP 多 topic 时间轴对齐。
5. `service_s4`：Service 场景四，构建标准 canonical dataset。
6. `service_s5`：Service 场景五，模型训练格式导出器。


### L2：功能模块说明文档

L2 是某个 L1 内部的功能模块说明。L2 阶段不只产出单个功能模块说明文件，还必须先产出该 L1 一共需要实现多少个功能模块的清单，再围绕这些功能模块定义必要的数据契约、schema、types 和 config，最后才逐个生成能力模块说明文件。

L2 阶段的产出分三类：

1. `功能模块清单.md`：说明该 L1 下需要实现多少个功能模块、每个模块的名称、目标、上下游和优先级。
2. `数据定义文件`：说明上游/下游数据产物契约、机器可读 schema、程序内部 types、配置项和配置 schema。
3. `能力模块说明文件`：说明某个功能模块的输入、输出、数据语义、处理流程、交互逻辑、边界和可拆分 L3 任务。

功能模块清单统一命名为：

```text
功能模块清单.md
```

单个能力模块说明文件建议放入 `L2能力模块/` 子目录，按功能命名，例如：

```text
L2能力模块/夹爪开合提取.md
L2能力模块/common_frame位姿转换.md
L2能力模块/夹爪开合配置文件自动生成.md
L2能力模块/位姿转换配置文件自动生成.md
```

落点规则：

- Runtime 功能模块清单：`DOCS/阶段二：数据清洗/01_runtime_mvp/功能模块清单.md`
- Runtime 能力模块说明：`DOCS/阶段二：数据清洗/01_runtime_mvp/L2能力模块/<能力名称>.md`
- Service 场景功能模块清单：放入对应场景目录，例如 `DOCS/阶段二：数据清洗/02_service/场景一/功能模块清单.md`
- Service 场景能力模块说明：放入对应场景的 `L2能力模块/` 子目录，例如 `DOCS/阶段二：数据清洗/02_service/场景一/L2能力模块/夹爪开合提取.md`

生成 L2 时，不要在交互一开始加载模板。只有当 Agent 已经和用户完成深入交流、整理出某个 L2 功能蓝图，并准备把蓝图落成正式 L2 能力模块说明文件时，才加载 `DOCS/工作流/attachments/L2能力模块说明文件模板.md`。如果用户在当前任务中提供新版 L2 模板，以用户提供的模板为准；如果模板字段仍不足以填写，围绕目标、输入输出、上下游、边界、验收和风险继续追问。

### 数据定义文件

每开发一个功能模块前，必须先定义清楚它依赖和产出的数据。不要把所有数据定义都放进 types 目录，应分为三类：

| 类别          | 内容                                                                               | 建议位置                       | 使用者          |
| ----------- | -------------------------------------------------------------------------------- | -------------------------- | ------------ |
| 数据产物契约      | raw MCAP、cleaned MCAP、validated MCAP、aligned MCAP、canonical dataset 等文件/数据产物长什么样 | `DOCS/阶段二：数据清洗/01_数据产物契约/` | 人、Agent、后续设计 |
| 机器可读 schema | JSON Schema / YAML Schema，描述字段、topic、单位、必填项和配置结构                                 | `schemas/` 或 `contracts/`  | 程序、测试、Agent  |
| 代码 Types    | Python dataclass / Pydantic model / TypedDict 等程序内部对象                            | `src/data_clean/types/`    | 程序内部         |


判断规则：

- raw MCAP 应该有哪些 topic：写入数据产物契约。
- cleaned MCAP 比 raw 多哪些 topic：写入数据产物契约。
- 某个功能模块吃什么、吐什么：写入该模块的 L2 能力模块说明。
- topic 名、marker id、标定参数、failure policy：写入 config 和 schema。
- `GripperWidthSample`、`PoseSample`、`Report` 等程序内部对象：写入 `src/data_clean/types/`。
- 如何读写 MCAP：属于 Repo 层。
- 如何计算夹爪宽度、位姿转换、异常检测：属于 Service 层。
- 如何调度整个流程：属于 Runtime 层。

定义流程固定为：

```text
1. 定义上游数据产物契约
2. 定义下游数据产物契约
3. 定义本模块输入输出
4. 定义需要的 Types
5. 定义需要的 Config / Schema
```

### L3：微元任务文档

L3 是交给一个没有长期上下文、上下文窗口有限的 Agent 执行的任务文件。一个 L3 微元任务应满足：单个 Agent 在一轮任务中可以读完上下文、完成实现或文档动作、执行验收并更新必要记录。

L3 文档统一放入：

```text
DOCS/阶段二：数据清洗/03_tasks/active/
```

命名规则按 L1 前缀编号：

```text
runtime_mvp_001_<短任务名>.md
service_s1_001_<短任务名>.md
service_s2_001_<短任务名>.md
service_s3_001_<短任务名>.md
service_s4_001_<短任务名>.md
service_s5_001_<短任务名>.md
```

同一 L1 内编号递增，不同 L1 之间编号互不共享。

生成 L3 时，不要在交互一开始加载模板。只有当某个 L2 能力模块说明已经稳定，并准备从它拆出正式 L3 active task 时，才加载 `DOCS/工作流/attachments/L3微元任务文件模板.md`。如果用户在当前任务中提供新版 L3 模板，以用户提供的模板为准；如果模板字段仍不足以填写，先整理待确认问题。

## 工作流步骤

### 步骤一：定位 L1

根据用户描述判断任务属于哪个 L1：

- 提到 Runtime、调度、run 目录、manifest、入口菜单、fake service，优先归入 `runtime_mvp`。
- 提到夹爪开合、位姿转换、raw 到 cleaned，归入 `service_s1`。
- 提到滤波、异常值、IK、MuJoCo、可靠性验证，归入 `service_s2`。
- 提到多 topic、时间轴、step 时间戳、插值、对齐，归入 `service_s3`。
- 提到 episode、step index、canonical dataset、schema、mask、manifest，归入 `service_s4`。
- 提到 HDF5、LeRobot、Zarr、训练格式、export，归入 `service_s5`。

如果用户描述跨多个 L1，先确认主 L1；不要在一个 L3 微元任务中混合多个 L1 的实现目标。

### 步骤二：追问并生成 L2 功能模块说明

如果用户要求生成或完善 L2，必须按以下顺序执行：

1. 先与用户交互，确认该 L1 下总共需要实现多少个功能模块，并生成 `功能模块清单.md`。
	   例如：场景一可拆为：夹爪开合提取、common frame 位姿转换、夹爪开合配置文件自动生成、位姿转换配置文件自动生成。
2. 围绕功能模块清单，定义必要的数据文件：上游数据产物契约、下游数据产物契约、本模块输入输出、需要的 Types、需要的 Config / Schema。
3. 与用户深入交流，整理出某个功能模块的功能蓝图；此阶段只围绕目标、输入、输出、核心数据语义、用户交互逻辑、上下游、成功标准、禁止事项和验收方式追问，不加载 L2 模板全文。
4. 当功能蓝图已经稳定、准备写入正式 L2 文档时，再读取 `DOCS/工作流/attachments/L2能力模块说明文件模板.md`；如果用户提供新版模板，则使用新版模板。
5. 根据模板检查功能蓝图是否缺字段；如有缺口，只追问缺口字段。
6. 将确认后的内容写入对应 `L2能力模块/<能力名称>.md`。
7. L2 文档可以说明能力、边界和验收，但不得在用户未要求时提前锁死具体 `.py` 文件名、类名、函数名或配置文件名。

### 步骤三：根据 L2 生成 L3 微元任务

如果用户要求从某个功能模块生成 L3：

1. 先读取对应 L2 能力模块说明文件。
2. 与用户确认要拆出的 L3 任务边界，确保每个 L3 只解决一个核心目标。
3. 当准备写入正式 L3 active task 时，再读取 `DOCS/工作流/attachments/L3微元任务文件模板.md`；如果用户提供新版模板，则使用新版模板。
4. 读取与该 L1 对应的 Harness 文档和当前进度。
5. 将功能模块拆成一个或多个“一轮 Agent 可完成”的任务。

L3 文档只列必读链接和必要任务边界，不完整复制上游文档。
L3 文档不得把通用实现约束、文件存放规则、Git 同步规则或技术栈规则整段复制进任务卡片；这些规则必须沉淀为独立约束文档，并在 L3 的“必读约束文档”中引用。具体 L3 只保留与本任务强相关的目标、输入输出、修改边界、验收命令和交接要求。
L3 执行完成后的执行记录和当前状态快照，统一写入 `DOCS/阶段二：数据清洗/执行记录/`。文件名统一使用 `MMDDHH_<简短主题>.md`；如果记录来自明确的 L3 微元任务，则使用 `MMDDHH_<L3微元任务名>.md`。同一个文件内同时记录执行过程、当前状态、未完成事项和下一步建议。

### 步骤四：投递到 active 任务池

生成的 L3 文档必须写入：

```text
DOCS/阶段二：数据清洗/03_tasks/active/
```

写入前检查同前缀最大编号，按 L1 前缀递增。

写入后，向用户报告：

- 新增了哪些 L3 任务文件。
- 每个任务对应哪个 L1 和哪个 L2 功能模块。
- 哪些模板字段仍为空或被标记为待确认。

本工作流到此结束。后续实际执行 L3 任务时，应按 `03_tasks/README.md` 的 active/completed 机制处理。

## 禁止事项

- 不得跳过 `功能模块清单.md` 直接生成零散 L2 能力模块说明。
- 不得跳过数据产物契约、schema、types、config 的定义，让 Codex 在代码实现阶段自行猜数据语义。
- 不得把 L3 微元任务写入 L2 模块目录。
- 不得绕过 `03_tasks/active/` 直接让 Agent 执行口头任务。
- 不得在未获得用户 L2/L3 模板时自行创造模板并落盘。
- 不得把多个 L1 的实现混入一个 L3 微元任务。
- 不得在本工作流中直接实现代码、运行会改写源码的格式化命令、移动任务到 completed 或执行 Git 提交。
- 不得为了适配工作流新增 `service_s6`，除非用户明确要求重构阶段二 L1 边界。
