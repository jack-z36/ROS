## 3. 显示链路与录制链路必须解耦

根据 Octopus 架构，显示链路和录制链路是两条不同路径：

```text
显示链路：
ROS2 topic -> MainWindow subscriptions -> 页面组件 -> UI 渲染

录制链路：
OpDockWidget -> McapRecorder -> generic ROS2 subscriptions -> MCAP writer -> .mcap 文件
```

场景四主要改显示和操作界面，不应让 MCAP 录制依赖某个显示 widget。

如果为了显示新增订阅或转换逻辑，也必须确认：

- 录制 topic 列表不被误删；
- `McapRecorder` 仍按 topic 和类型写入 MCAP；
- GoPro Best Effort QoS 兼容修复不被破坏；
- `nav_msgs/msg/Odometry` 和 `hwk_pressure_interfaces/msg/PressureFrame` 的 schema 支持不被回退。

## 4. UI 验证边界

操作页面的成功标准是用户能直接看到全部 8 个目标 topic。

不应把以下情况算作完成：

- 只把滚动条隐藏，但仍有 topic 实际不可见；
- 只修改字体或间距，目标窗口尺寸下仍需要滚轮才能查看全部 topic；
- 只硬编码截图中的 topic 文本，但没有保留真实订阅 / 录制状态；
- 只改面板标题，没有把真实 ROS2 数据接入对应显示组件。

主显示区的成功标准是当前目标数据可视化真实可用。

不应把以下情况算作完成：

- 旧的左右手触觉、左右手视觉、头部视觉布局仍作为主界面存在；
- GoPro 面板没有显示 `/gopro_left/image_raw` 和 `/gopro_right/image_raw`；
- 位姿面板没有使用 `/baton_mini_left/odometry` 和 `/baton_mini_right/odometry`；
- 触觉面板没有使用四路 `/pressure/...` topic；
- UI 能显示，但场景三 MCAP 录制能力被破坏。

## 5. MCAP 和 topic 验证规则

完成 UI 改造后，仍必须保留场景三的 MCAP 验证：

```text
1. 启动 8 路目标数据源；
2. 启动 Octopus；
3. 在 GUI 中确认 8 个目标 topic 可见；
4. 点击开始采集；
5. 采集一段真实数据；
6. 点击结束采集；
7. 对生成的 .mcap 执行 ros2 bag info；
8. 确认 8 个目标 topic 均存在且消息数大于 0。
```

场景四完成时，必须区分：

- 已部署：代码已修改并构建到可运行位置；
- 已测试：Octopus GUI 已启动并观察过 UI；
- 已验证：8 个目标 topic 显示和 MCAP 内容均通过实测。
