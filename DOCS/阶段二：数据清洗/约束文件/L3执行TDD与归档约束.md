# L3 执行 TDD 与归档约束

本文约束阶段二 L3 微元任务的实际执行方式。只要 L3 涉及代码新增、代码修改、bug 修复或行为变更，执行 Agent 必须按本文执行。

执行阶段二 L3 前必须先确认当前分支是该 L3 所属 Runtime 分支或 Service 场景分支。Runtime MVP 使用 `runtime-mvp`；Service 场景一到五分别使用 `service-s1`、`service-s2`、`service-s3`、`service-s4`、`service-s5`。如果当前分支是 `main` 或其他不匹配分支，必须停止并提示切换，不得继续执行。

执行阶段二 L3 前还必须先完成 `DOCS/阶段二：数据清洗/约束文件/L3任务文件身份校验约束.md` 中规定的身份校验。用户指定路径、实际读取路径、文件名编号和正文 `L3 编号` 必须一致；任何一项不一致或读取失败，都必须停止，不得自行改读同目录其他 L3。

执行阶段二 L3 前还必须读取并遵守 `DOCS/阶段二：数据清洗/约束文件/L3调度元数据约束.md`。当前 L3 文件中的 `dispatch` YAML 必须与任务定位一致；如果 `depends_on` 中存在尚未完成并归档的 L3，或 `dispatch_status` 为 `blocked` / `waiting_user`，必须停止并汇报，不得抢跑。

执行阶段二代码类 L3 前必须运行阶段二开工自检：

```bash
bash scripts/init_data_clean_dev.sh
```

自检失败时必须停止并汇报环境缺口，不得进入代码修改，不得把环境问题当成业务代码问题修。

Service 场景一到场景五的 L3 还必须遵守 `DOCS/阶段二：数据清洗/约束文件/开发者验收入口约束.md`。L3 自动化验收命令只证明局部实现正确；场景最终验收必须由用户本人运行 `./start_data_clean.sh --dev`，选择对应场景和功能检验项或场景完整 smoke test 后确认。

## 一、执行前必须确认任务文件身份

执行 Agent 必须先校验当前 L3 文件身份，再读取其他上下文或使用 `$tdd`：

1. 原样记录用户输入的 L3 路径。
2. 只打开用户指定路径。
3. 读取失败时立即停止，不得搜索替代任务。
4. 对比用户路径、实际读取路径、文件名编号和正文 `L3 编号`。
5. 校验通过后，才能继续执行。

如果当前任务由主 Agent 分发给 sub-agent，sub-agent 仍必须执行上述身份校验；不得因为主 Agent 已分发路径就跳过校验。

## 二、执行前必须确认调度状态

执行 Agent 必须读取当前 L3 的 `dispatch` YAML，并完成以下检查：

1. `task_id` 与正文 `L3 编号` 一致。
2. `task_file` 与用户指定路径、实际读取路径一致。
3. `group` 与当前文件所在 `task/active/<功能组>/` 一致。
4. `branch` 与当前 Git 分支一致。
5. `dispatch_status` 为 `ready`。
6. `depends_on` 中的每个 L3 都已经移动到 `task/completed/<L1归档目录>/<功能组>/` 或其指定完成位置。

任一检查失败时必须停止并汇报，不得自行改读同目录其他 L3，不得自行修改 `task/dispatch/<功能组>.yaml`。

## 三、执行前必须运行开工自检

代码类 L3 进入 `$tdd` 前，必须先运行：

```bash
bash scripts/init_data_clean_dev.sh
```

该自检只证明工作区具备基本开发前提，不替代当前 L3 的验收命令。自检失败时，执行摘要只记录环境缺口和阻塞原因，不继续修改代码。

## 四、必须使用 TDD 技能

执行代码类 L3 前，必须读取并使用 Codex 环境中可用的 `$tdd` 技能：

```text
$tdd
```

执行方式采用垂直切片 TDD：

1. 先为一个可观察行为写测试或最小复现。
2. 确认测试失败，或说明当前环境无法运行失败验证的具体原因。
3. 写最少代码让该行为通过。
4. 运行对应测试。
5. 只在测试为 green 后做必要整理。
6. 再进入下一个行为。

不得一次性写完大量测试后再整体实现；不得绕过公共接口直接测试内部实现细节；不得借 TDD 名义扩大 L3 范围。

## 五、Python 命令统一使用 python3

代码执行环境不保证存在 `python` 指令。阶段二 L3 中所有 Python 执行命令、验收命令、示例命令和交接记录必须使用：

```bash
python3
```

不得写成：

```bash
python
```

如果某个工具链只能通过 `python` 调用，必须先在交接中说明原因，并优先寻找等价的 `python3` 调用方式。

## 六、项目文件路径统一使用相对路径

阶段二 L3 文档、执行记录和交接摘要中，凡是引用仓库内文件或目录，都必须使用相对仓库根目录的路径，例如：

```text
DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/
DOCS/阶段二：数据清洗/03_tasks/task/completed/<L1归档目录>/<功能组>/
src/data_clean/
```

不得写入开发者本机的绝对路径、Windows 盘符路径或某台机器特有的工作区路径。

外部 Agent 技能只写技能名，例如 `$tdd`，不写技能在某台机器上的安装路径。

## 七、执行前必须读取相关微元任务记录

执行 L3 前，除当前 L3 文件列出的必读文档外，还必须读取与当前任务直接相关的历史记录：

1. `DOCS/阶段二：数据清洗/03_tasks/README.md`
2. 当前 L3 所属 L2 能力模块说明。
3. `DOCS/阶段二：数据清洗/约束文件/L3调度元数据约束.md`。
4. 当前 L3 直接依赖的上游 L3 文件，优先同时检查 `task/active/<上游功能组>/` 与 `task/completed/<L1归档目录>/<上游功能组>/`。
5. 同一功能组下已经完成的 L3 任务文件。
6. 当前 L3 文件明确列出的其他必读历史记录。

如果找不到相关记录，必须在执行摘要中写明“未找到相关 L3 历史记录”，不能假装已经对齐。

## 八、完成后必须更新任务文件

L3 完成后，必须先更新当前 L3 任务文件，再移动归档：

1. 在“成功标准”中，把已经实际验证通过的条目从 `- [ ]` 改为 `- [x]`。
2. 未验证或未完成的条目保持 `- [ ]`，并在执行摘要中说明原因。
3. 在任务文件末尾追加“执行摘要”，写明实际修改文件、测试/验收命令、结论和遗留风险。
4. 只有成功标准已经处理完毕后，才能把任务文件从 `DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/` 移到 `DOCS/阶段二：数据清洗/03_tasks/task/completed/<L1归档目录>/<功能组>/`。
5. 移动任务文件后，如果原 `DOCS/阶段二：数据清洗/03_tasks/task/active/<功能组>/` 已经没有任何任务文件或其他保留文件，必须删除该空目录。

不得完成代码后只口头交接；不得让已完成 L3 长期停留在 `task/active/<功能组>/`；不得移动到错误的 `task/completed/<L1归档目录>/<功能组>/` 后仍留下未解释的空成功标准。

Ubuntu L3 执行端禁止写入 `DOCS/阶段二：数据清洗/执行记录/`、阶段/场景 `当前进度.md`、共享 `执行记录.md` 或 `DOCS/总执行日志.md`。如需阶段汇总，只能在当前 L3 执行摘要中建议 Win 端后续整理。

如果当前任务由 sub-agent 执行，sub-agent 禁止修改 `DOCS/阶段二：数据清洗/03_tasks/task/dispatch/<功能组>.yaml`。调度索引只由 Win 规划端或主 Agent 维护。

## 九、交接摘要最低要求

交接摘要必须包含：

1. 任务文件身份校验结论：用户指定路径、实际读取路径、文件名编号、正文 `L3 编号` 是否一致。
2. 调度元数据校验结论：`task_id`、`task_file`、`group`、`branch`、`depends_on` 和 `dispatch_status` 是否允许执行。
3. 本次读取了哪些相关 L3 任务文件或执行记录。
4. 阶段二开工自检是否通过；如果失败，说明环境缺口。
5. 本次使用 TDD 的 red / green / refactor 过程；如果无法完整执行，说明具体阻塞。
6. 实际修改了哪些文件。
7. 新增或修改了哪些函数、类、配置或测试。
8. 运行了哪些验收命令，命令必须使用 `python3`。
9. 哪些成功标准已勾选，哪些未勾选以及原因。
10. 是否已从 `task/active/<功能组>/` 移动到 `task/completed/<L1归档目录>/<功能组>/`。
11. 如果原 active 功能组目录已为空，是否已删除该空目录。
12. Service 场景 L3 对 `./start_data_clean.sh --dev` 下哪个场景菜单、功能检验项或场景完整 smoke test 有影响。
13. 建议用户后续运行 `./start_data_clean.sh --dev` 的哪个场景、哪个功能检验项或 smoke test 做最终人工验收。
