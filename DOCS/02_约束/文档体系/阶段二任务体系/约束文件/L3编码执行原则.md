# 阶段二 L3 编码执行原则

## 适用范围

- 阶段：阶段二：数据清洗
- 任务模式：Ubuntu 端执行阶段二代码类 L3 微元任务
- 适用对象：阶段二 Runtime MVP、Service 场景一到五的 L3 代码、测试、配置和任务文件更新
- 不适用对象：阶段四 L3、普通非 L3 代码维护、纯文档规划

本文是阶段二专属 wrapper。通用编码行为以 `DOCS/02_约束/编程执行/Agent编程执行原则.md` 为准；架构边界和机械约束以 `DOCS/02_约束/编程执行/架构边界与机械约束原则.md` 为准。本文只补充阶段二 L3 的身份校验、dispatch、TDD、自检、归档和交接要求。

## 开工校验

执行前必须先校验当前 L3 任务文件身份：

- 用户指定路径。
- 实际读取成功的 L3 文件路径。
- 文件名中的 L3 编号和任务短名。
- 正文标题、任务定位和 `L3 编号`。

四项必须一致；找不到或不一致时必须停止，不得改读同目录其他 L3。

随后读取并校验当前 L3 的 `dispatch` YAML：

- `task_id`、`task_file`、`group`、`branch` 必须与当前任务一致。
- `depends_on` 中的 L3 必须已完成并归档。
- `dispatch_status` 必须允许当前执行。
- 当前 Git 分支必须是当前 L3 所属 Runtime 分支或 Service 场景分支。

Runtime MVP 使用 `runtime-mvp`；Service 场景一到五分别使用 `service-s1`、`service-s2`、`service-s3`、`service-s4`、`service-s5`。

## TDD 与最小切片

只要任务涉及代码新增、代码修改、bug 修复或行为变更，就必须按 TDD 垂直切片推进：

```text
一个行为测试或最小复现 -> 最少实现 -> 验证通过 -> 必要整理 -> 下一个行为
```

代码执行环境中的 Python 命令统一使用 `python3`。所有验收命令、示例命令和交接记录不得写成 `python`。

代码类 L3 在进入实现前必须运行：

```bash
bash scripts/init_data_clean_dev.sh
```

如果开工自检失败，必须停止并汇报环境缺口，不得把环境问题当成业务代码问题修。

## 阶段二分层边界

阶段二代码默认按 `Types / Config / Repo / Service / Runtime / Web或入口层` 组织。执行 L3 时必须遵守：

- Types / Schemas 层不依赖 Config、Repo、Service、Runtime、Web。
- Service 不反向控制 Runtime。
- Web 或入口层不绕过 Runtime 直接拼业务链路。
- 数据 shape 必须在边界解析或校验，不向下游传播猜测。

如果当前 L3 发现历史代码已存在分层例外，不得扩大例外；需要修复时在交接摘要中提出后续任务建议。

## 开发者入口要求

Service 场景一到场景五的 L3 必须说明本任务对 `./start_data_clean.sh --dev` 开发者验收入口的影响。

单个 L3 的自动化测试不能替代场景最终验收；场景最终验收必须由用户本人运行开发者入口、选择场景和功能检验项或场景完整 smoke test 后确认。

如果本 L3 不直接接入开发者入口，必须写明“不直接接入开发者入口，但由 `<功能检验项或 smoke test>` 间接覆盖”。

## 归档与写入边界

完成后必须：

- 勾选当前 L3 文件中已验证的成功标准。
- 在当前 L3 文件末尾追加执行摘要。
- 将完成的 L3 文件从 `03_tasks/task/active/<功能组>/` 移动到 `03_tasks/task/completed/<L1归档目录>/<功能组>/`。
- 如果原 active 功能组目录为空，删除该空目录。

Ubuntu L3 执行端不得写集中执行记录或阶段进度文件，不得修改 `task/dispatch/<功能组>.yaml`，除非当前 L3 明确授权。

## 交接要求

阶段二 L3 执行摘要必须说明：

1. 执行前读取了哪些相关 L3 任务文件或执行记录。
2. 任务文件身份校验结论。
3. 调度元数据校验结论。
4. 阶段二开工自检是否通过；如果失败，说明环境缺口。
5. 修改了哪些文件。
6. 新增或修改了哪些函数、类、配置或测试。
7. TDD red / green / refactor 如何执行；如果无法完整执行，说明具体原因。
8. 运行了哪些验收命令，命令必须使用 `python3`。
9. 哪些成功标准已勾选，哪些未勾选以及原因。
10. Service 场景 L3 对 `./start_data_clean.sh --dev` 开发者入口、功能检验项或场景完整 smoke test 的影响。
11. 当前明确没做什么。
12. 后续如果继续推进，下一步建议是什么。

如果需要阶段级汇总或规划记录，只能在当前 L3 执行摘要中提出建议，由 Win 主机后续统一整理。
