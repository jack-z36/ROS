# 阶段四 L3 微元改造任务模板

本模板用于生成阶段四模型部署程序的 L3 微元改造任务。它可以参考阶段二 L3 模板的结构骨架，但不得复用阶段二的任务类别、Service 验收入口、阶段二开工自检、功能组归档规则或数据清洗专属约束。

阶段四 L3 的核心不是“从零实现一个功能”，而是：

```text
在同事已有部署程序上，完成一次最小、可验证、可回滚的代码改造。
```

## 使用前提

生成阶段四 L3 前，必须已经存在或明确草拟：

1. AS-IS Contract。
2. TO-BE Contract。
3. Contract Delta。
4. 当前 L3 所属的 L2 改造工作包。
5. 当前 L3 涉及的现有代码路径。

如果现有代码尚未盘点，不得生成正式 L3。

## 改造类型

阶段四 L3 不使用阶段二的数据定义 / 数据读写 / 数据计算 / 流程编排四类模板。阶段四 L3 可按改造意图标注为以下类型之一：

| 改造类型 | 适用任务 |
|---|---|
| `contract-adapter` | 在旧接口外包一层 adapter，使其满足目标契约 |
| `behavior-change` | 修改已有行为，但必须保护默认旧路径或写明破坏性原因 |
| `safety-gate` | 在真机发送链路前增加安全检查或阻断策略 |
| `observability` | 增加日志、运行记录、可复现产物或错误上下文 |
| `compatibility` | 保留旧入口、旧参数、旧返回值或回滚开关 |
| `test-coverage` | 为已有行为或新增改造补测试 / smoke 验证 |
| `runbook-doc` | 补充 dry-run、fake-policy、real-policy、real-robot 运行说明 |

如果一个 L3 同时符合多个类型，优先拆成多个 L3；只有在拆分会破坏同一个最小行为闭环时，才允许写两个类型。

## 2. 调度元数据

本节用于主 Agent 判断当前 L3 在阶段四任务池中的并行 / 串行关系。必须使用 YAML；所有路径必须是相对仓库根目录路径。

```yaml
dispatch:

  task_file: DOCS/03_工程/阶段四：模型部署/03_tasks/task/active/<工作包组>/<文件名>.md

  integration_branch: model_deploy
  acceptance_dir: DOCS/03_工程/阶段四：模型部署/05_acceptance/<工作包组>
  acceptance_scenarios: []
  acceptance_card: DOCS/03_工程/阶段四：模型部署/03_tasks/cards/<工作包组>/<deploy_id>_验收卡片.md
  acceptance_mode: <direct-local / static-review / downstream-l2 / hardware-blocked / env-blocked>
  acceptance_secondary_modes: []
  local_acceptance_required: <true / false>
  acceptance_round_limit: 3
  acceptance_feedback_dir: DOCS/03_工程/阶段四：模型部署/05_acceptance/<工作包组>/logs
  wave: 1
  parallel_group: <工作包组>-p1
  depends_on: []
  must_run_after: []
  can_run_parallel_with: []
  blocks: []
  conflict_scope:
    files: []
    modules: []
    runtime_modes: []
    hardware_paths: []
  robot_risk: <none / dry-run-only / hardware-blocked / real-robot>
  dispatch_status: ready
```

`dispatch_status` 只允许 `ready`、`blocked`、`waiting_user`。如果 `robot_risk` 是 `real-robot`，必须在验收方式中写明人工确认、急停准备、限幅策略和回滚路径。
`branch` 必须是当前 L3 所属 L2 分支，不得写集成分支 `model_deploy`。`integration_branch` 固定为 `model_deploy`。

### Agent 执行 / 验收边界

本 L3 文件主要供执行 sub-agent 使用；对应验收卡片主要供验收 sub-agent 使用。生成 L3 时必须让两者边界清晰：

- 执行 sub-agent 只负责本 L3 的实现、局部验证和执行摘要。
- 执行 sub-agent 可以阅读验收卡片理解通过标准，但不得替验收 sub-agent 修改验收结论。
- 验收 sub-agent 只能读取验收卡片、L3 文件、执行摘要、允许查看的 diff / 日志，并按 `acceptance_mode` 输出结论。
- 验收 sub-agent 不得改源码、测试、dispatch、任务状态或 Git。
- `FAIL_LOCAL` 反馈最多回到执行 sub-agent 迭代 3 轮；超过 3 轮必须由主 Agent 停止自动推进并要求人工介入。
- `downstream-l2`、`hardware-blocked`、`env-blocked` 不是免验收，而是要求写清由哪个 L2 场景覆盖、缺什么环境或缺什么硬件。

## 12. 执行要求

执行前必须完成任务文件身份校验：

```text
用户指定任务路径：
实际读取任务路径：
文件名编号：
正文 L3 编号：

```

执行前必须读取 `dispatch` YAML，确认：

- `task_id` 与正文 L3 编号一致。
- `task_file` 与当前文件路径一致。
- `branch` 是当前 L2 分支，且符合 `model_deploy-l2-xx-*`。
- `integration_branch` 是 `model_deploy`。
- `acceptance_dir` 指向所属 L2 的 `05_acceptance` 子目录。
- `acceptance_scenarios` 指向所属 L2 `验收结果.md` 中存在的运行验收场景。
- `acceptance_card` 指向当前 L3 的验收卡片。
- `acceptance_mode` 已明确，且与无硬件验收能力一致。
- `acceptance_round_limit` 固定为 `3`。
- `depends_on` 已完成或明确无需等待。
- `dispatch_status` 不是 `blocked` 或 `waiting_user`。
- `robot_risk` 与验收方式一致。

如果本 L3 涉及代码新增、代码修改、bug 修复或行为变更，必须采用测试优先或最小复现优先：

```text
最小复现 / 测试
→ 最小实现
→ 验证通过
→ 必要整理
```

不得为了通过当前 L3 验收而擅自扩大修改范围。

## 合格 L3 判断

生成完成后，必须能回答：

1. 这个 L3 来自哪个 Delta 和哪个 L2 改造工作包？
2. 它改的是哪段已有代码？
3. 现有代码已经做到了什么？
4. 本次只改什么？
5. 什么明确不能改？
6. 是否保护了同事原始可运行路径？
7. 是否有 dry-run 或 fake-policy 验证路径？
8. 是否涉及 real-robot 风险？
9. 如何自动验收？
10. 如何回滚？
