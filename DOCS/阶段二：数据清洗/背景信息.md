# 阶段二：数据清洗背景信息

## raw MCAP 的输入形态

raw MCAP 的本质是多个 topic 各自的数据流。

例如：

- `/image_left` 保存左图像帧及其时间戳。
- `/image_right` 保存右图像帧及其时间戳。
- `/baton_left/pose` 保存左 Baton Mini 位姿及其时间戳。
- `/baton_right/pose` 保存右 Baton Mini 位姿及其时间戳。
- `/tactile_left` 保存左触觉数据及其时间戳。
- `/tactile_right` 保存右触觉数据及其时间戳。

raw MCAP 的特点是：数据按 topic 存储，各 topic 频率不一定一致，各 topic 时间戳不一定天然对齐，而且 raw MCAP 本身并不会告诉模型什么是 observation、什么是 action。

## canonical dataset 的完整含义

canonical dataset 是 raw MCAP 和训练格式之间的标准中间层。它的核心不是把所有数据提前展开成数组，而是用 `data.mcap` 保留时间序列数据本体，再用 schema、index、masks、report 和 manifest 明确训练语义。

它至少包含四层信息：

- 数据本体层：每个 episode 内的 `data.mcap`，保存可回放、可追溯的多模态时间序列。
- 语义契约层：`schema/`，定义 observation、action、frame、topic 和 quality 的全局规则。
- step 映射层：`step_index.parquet`，把异步 topic 消息映射到统一 step，并记录 action chunk 的未来 step 范围。
- 质量和追溯层：`masks.parquet`、`alignment_report.json`、`quality_report.json`、`robot_constraint_report.json`、`processing_manifest.json`，说明哪些 step 能训练、对齐质量如何、机器人约束风险如何、处理过程如何复现。

因此 canonical dataset 不是“训练框架格式”，而是 exporter 的稳定输入。LeRobot、HDF5、Zarr 等都应从 canonical dataset 派生出来。

## canonical dataset 的最终目录结构

最终结构固定如下：

- `canonical_dataset_mcap/dataset_meta.json`
- `canonical_dataset_mcap/dataset_index.parquet`
- `canonical_dataset_mcap/schema/observation_schema.json`
- `canonical_dataset_mcap/schema/action_schema.json`
- `canonical_dataset_mcap/schema/frame_schema.json`
- `canonical_dataset_mcap/schema/topic_schema.json`
- `canonical_dataset_mcap/schema/quality_schema.json`
- `canonical_dataset_mcap/episodes/episode_000001/episode_meta.json`
- `canonical_dataset_mcap/episodes/episode_000001/data.mcap`
- `canonical_dataset_mcap/episodes/episode_000001/step_index.parquet`
- `canonical_dataset_mcap/episodes/episode_000001/masks.parquet`
- `canonical_dataset_mcap/episodes/episode_000001/alignment_report.json`
- `canonical_dataset_mcap/episodes/episode_000001/quality_report.json`
- `canonical_dataset_mcap/episodes/episode_000001/robot_constraint_report.json`
- `canonical_dataset_mcap/episodes/episode_000001/processing_manifest.json`
- `canonical_dataset_mcap/exports/lerobot/`
- `canonical_dataset_mcap/exports/hdf5/`
- `canonical_dataset_mcap/exports/zarr/`

其中 `exports/` 只是派生目录。canonical dataset 的主定义由 dataset 级 metadata/schema 和 episode 级 `data.mcap`、`step_index`、`masks`、reports、manifest 共同组成。

需要特别注意：`schema/` 目录最终只包含 `observation_schema.json`、`action_schema.json`、`frame_schema.json`、`topic_schema.json`、`quality_schema.json` 五个文件。统一时间轴和同步策略不单独放入 `sync_schema.json`，而是由 `alignment_report.json` 记录实际对齐结果，由 `processing_manifest.json` 记录处理参数，并由 `quality_schema.json` 解释同步误差等质量字段。

## schema 的职责

`observation_schema.json` 必须说明当前模型看到什么。当前项目的 observation 至少包括左右图像、左右 common-frame TCP pose、左右夹爪宽度、左右触觉和语言指令。每个字段都要说明来源、shape、单位、是否必需、是否参与训练和预处理方式。

`action_schema.json` 必须说明模型要预测什么。当前项目的 action 是 UMI 风格 relative trajectory action：未来 K 步 TCP 目标都相对于同一个当前推理起点，而不是逐步 delta。

`frame_schema.json` 必须说明位姿数值相对于谁。它要定义 `common_frame`，并说明左右 Baton Mini raw pose 如何转换为 `left_tcp_pose_common` 和 `right_tcp_pose_common`。

`topic_schema.json` 必须说明 `data.mcap` 中 topic 和训练语义字段之间的映射关系。它既要能指向 raw topic，也要能描述 processed field。

`quality_schema.json` 必须说明 masks 和质量字段如何解释，避免 exporter 或训练脚本各自猜测字段含义。

## step_index 的职责

`step_index.parquet` 是 canonical dataset 中最关键的索引表。

它的职责不是复制所有数据，而是记录每个 step 如何从 `data.mcap` 中取到 observation，以及如何定位未来 action chunk。

每行通常对应一个 `step_t`，应能表达：

- 该 step 属于哪个 episode。
- 该 step 的统一时间戳。
- `image_left`、`image_right`、pose、tactile、gripper 等字段对应 `data.mcap` 中哪条消息或哪个派生字段。
- 对齐方式是最近邻还是插值。
- 每个字段相对 step 时间的误差。
- action chunk 的 horizon 和未来 step 范围。

换句话说，`step_index.parquet` 把 `data.mcap` 从 topic 日志变成 step 级训练样本。

## masks 和 reports 的职责

不是每个 step 都适合训练。`masks.parquet` 必须显式告诉 exporter 哪些 step 能用，哪些不能用。

典型 mask 包括：

- 图像是否有效。
- 左右位姿是否有效。
- 左右触觉是否有效。
- 左右夹爪宽度是否有效。
- action chunk 是否能完整构造。
- language instruction 是否有效。
- 该 step 是否最终可用于训练。

`alignment_report.json` 关注时间同步质量，`quality_report.json` 关注数据质量，`robot_constraint_report.json` 关注离线可检查的机器人执行约束风险，`processing_manifest.json` 关注处理过程可追溯性。四者共同保证后续发现训练或部署问题时，能回到 episode 级别查原因。

`robot_constraint_report.json` 不等于部署阶段的在线安全检查。它只记录清洗阶段能离线判断的约束，例如 TCP 轨迹是否超出预设 workspace、单步位移/旋转是否异常、夹爪宽度是否越界、左右手距离或轨迹是否存在明显不可执行风险。

## 统一时间轴

数据清洗需要把异步 topic 统一到固定 step 频率。例如统一到 20Hz 时，每个 step 间隔是 0.05 秒。

对每个 step，清洗程序需要找到或插值出同一时刻附近的图像、位姿、触觉、夹爪宽度等数据，并记录它们与 `data.mcap` 中消息的对应关系。

这个映射由 `step_index.parquet` 表达。它把 `data.mcap` 从 topic 世界映射到 step 世界。

## common frame

阶段二最关键的数据清洗步骤之一，是把左右 Baton Mini 位姿统一到 common frame。

Baton Mini 左右设备默认可能各自处在独立局部坐标系中。如果直接把 `left_baton_pose_raw` 和 `right_baton_pose_raw` 喂给模型，模型看到的双臂空间关系会混乱。

因此清洗阶段需要把：

- `left_baton_pose_raw` 转成 `left_tcp_pose_common`。
- `right_baton_pose_raw` 转成 `right_tcp_pose_common`。

`common_frame` 是人为定义的外部统一坐标系，可先理解为左手和右手之间的共同原点。它不必在第一版就强行等同于 `robot_base`，但必须让左手 TCP 和右手 TCP 处在同一个空间表达中。

## observation 定义

当前阶段定义的 `observation_t` 是多模态状态包，而不是原始 topic 的简单堆叠：

- `image_left`
- `image_right`
- `left_tcp_pose_common`
- `right_tcp_pose_common`
- `left_gripper_width`
- `right_gripper_width`
- `left_tactile`
- `right_tactile`
- `language_instruction`

每个字段的来源 topic、数据类型、shape、单位、是否参与训练、预处理方式，应由 `observation_schema.json` 明确。

## action 定义

阶段二采用 UMI 风格的 relative trajectory action。

action 不是原始 Baton Mini pose，不是 robot_base 下绝对 TCP 位姿，不是机械臂关节角，也不是逐步 delta action。

它表示：在当前推理起点 t，模型要预测未来 K 步左右 TCP 相对于当前 TCP 位姿的目标相对轨迹，并包含夹爪宽度。

对单臂来说，当前 TCP 位姿为 `T_t`，未来第 k 步 TCP 目标位姿为 `T_t+k`，则相对 action 为 `A_t+k = inverse(T_t) × T_t+k`。一个 action chunk 中的每个未来目标都相对于同一个起点 `T_t`，不是相对于前一个未来目标。

对双臂来说，左手和右手分别计算：

- `A_left_t+k = inverse(T_left_t) × T_left_t+k`
- `A_right_t+k = inverse(T_right_t) × T_right_t+k`

最终 action chunk 包含左右相对 TCP 轨迹和左右夹爪轨迹。
