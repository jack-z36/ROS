# L2 能力模块与数据定义约束

本文是阶段二开发范式下编写 L2 功能模块说明和数据定义文件时的强制约束。凡是进入阶段二 L1/L2/L3 开发范式，尤其是编写 `runtime_mvp` 或 Service 场景的 L2 能力模块说明时，都必须先阅读并遵守本文。

## 一、适用范围

本文适用于：

- `DOCS/阶段二：数据清洗/01_runtime_mvp/L2能力模块/`
- `DOCS/阶段二：数据清洗/01_runtime_mvp/L2数据定义/`
- `DOCS/阶段二：数据清洗/02_service/**/L2能力模块/`
- `DOCS/阶段二：数据清洗/02_service/**/L2数据定义/`
- 后续由 L2 能力模块说明生成的 L3 微元任务文档。

本文不替代 `文件存放规范.md`，只补充 L2 文档和数据原子笔记的写法约束。

## 二、先 grill-me，再写 L2

每次编写、补全或重写 L2 能力模块说明文件之前，必须使用 `grill-me` 技能确认用户意图。

执行要求：

1. 先围绕本次 L2 的目标、输入、输出、上下游、边界、验收方式和未知问题与用户对齐。
2. 每次只问一个高影响问题。
3. 如果问题可以通过阅读仓库已有文档或代码回答，先自行检索，不把可发现问题丢给用户。
4. 用户意图没有稳定前，不得直接写正式 L2 能力模块文件。
5. 当意图已经清楚、无必要追问时，必须在执行记录或回复中说明“已按 grill-me 约束完成意图澄清”。

禁止事项：

- 不得拿到一个粗略功能名就直接套模板写 L2。
- 不得在没有确认边界的情况下替用户决定功能是否跨 L1、跨场景或跨模块。
- 不得把尚未确认的问题伪装成默认设计。

## 三、数据定义必须原子化

L2 能力模块说明中出现的每一个数据概念，都必须在对应 `L2数据定义/` 目录下拥有一个独立原子文档。

这里的数据概念包括但不限于：

- 程序内部语义对象，例如 `RunContext`、`SceneResult`。
- 状态或枚举概念，例如 `RunStatus`、`RunMode`、`SceneName`。
- 配置对象，例如某个场景配置、临时覆盖配置。
- 报告对象，例如 `RuntimeErrorRef`、`PipelineResult`。
- 产物索引对象，例如 run result、manifest summary。

### 原子文档命名

原子数据定义文档统一放在对应 L1 或场景的 `L2数据定义/` 目录下。

Runtime MVP 示例：

```text
DOCS/阶段二：数据清洗/01_runtime_mvp/L2数据定义/RunContext.md
DOCS/阶段二：数据清洗/01_runtime_mvp/L2数据定义/RunStatus.md
DOCS/阶段二：数据清洗/01_runtime_mvp/L2数据定义/SceneName.md
```

Service 场景示例：

```text
DOCS/阶段二：数据清洗/02_service/场景一/L2数据定义/GripperWidthSample.md
DOCS/阶段二：数据清洗/02_service/场景一/L2数据定义/CommonFramePose.md
```

如果同名概念在多个 L1 或场景中复用，应优先复用上游定义并通过 Obsidian 双向链接引用；不得复制一份含义相近但字段不同的新定义。

## 四、功能模块文件必须使用 Obsidian 双向链接引用数据

L2 能力模块说明中凡是提到已经定义或需要定义的数据概念，必须使用 Obsidian wikilink。

正确写法：

```md
- 一份结构化 [[RunContext]] 语义对象。
- 单场景执行后生成 [[SceneResult]]。
- 全流程结束后汇总为 [[PipelineResult]]。
```

错误写法：

```md
- 一份结构化 `RunContext` 语义对象。
- 单场景执行后生成 SceneResult。
- 全流程结束后汇总为 PipelineResult。
```

如需显示中文名称，可以使用别名：

```md
- 本次运行状态由 [[RunStatus|运行状态]] 表达。
```

## 五、原子数据定义文档必须回答的问题

每个原子数据定义文档至少包含以下内容：

```md
# <数据概念名>

## 定义

一句话说明这个数据概念是什么。

## 所属位置

说明它属于哪个 L1、哪个 L2 或哪个 Service 场景。

## 现实语义

说明它在真实运行或数据流中指代什么。

## 字段或取值

如果是对象，列出字段；如果是枚举，列出取值。

## 有效性规则

说明什么情况算有效、什么情况必须失败或进入报告。

## 上游来源

说明它由谁创建、谁填充或谁首次定义。

## 下游消费者

说明谁会读取、引用或依赖它。

## 不负责

说明它不承载哪些语义，避免任务膨胀。

## 相关链接

- [[相关数据概念]]
- [[相关能力模块]]
```

字段或取值未知时，必须写入“当前未知问题”，不得让后续 Agent 自行猜测。

## 六、聚合式数据定义文件的限制

禁止把多个重要数据概念长期堆在一个大文档里。

允许存在的聚合文档只有两类：

1. 索引文档：用于列出本 L2 或本场景有哪些原子数据定义。
2. 迁移文档：用于临时记录尚未拆分的旧定义，并明确下一步拆分计划。

聚合文档中出现的每个数据概念，仍必须最终拆成独立原子文档。

## 七、L2 能力模块说明的写作顺序

每次编写 L2 能力模块说明时，必须按以下顺序执行：

1. 阅读阶段二开发范式和本文。
2. 使用 `grill-me` 技能澄清用户意图。
3. 整理本 L2 会提到的数据概念清单。
4. 先在 `L2数据定义/` 中创建或复用每个数据概念的原子文档。
5. 再编写 L2 能力模块说明，并用 `[[数据概念名]]` 引用这些原子文档。
6. 检查 L2 文档中是否仍存在未链接的数据概念。
7. 将新增文档写入对应输出清单或执行记录。

## 八、检查清单

编写完成后必须自查：

```text
□ 是否已经使用 grill-me 澄清用户意图？
□ L2 文件中出现的每个数据概念是否都有原子文档？
□ L2 文件是否用 [[wikilink]] 引用数据概念？
□ 是否避免了把多个核心数据概念塞进一个大数据定义文档？
□ 每个原子数据定义是否说明定义、现实语义、字段/取值、有效性、上下游和不负责？
□ 未确认问题是否显式写入“当前未知问题”？
□ 新增约束或文档是否已被阶段二开发范式或输出清单索引？
```
