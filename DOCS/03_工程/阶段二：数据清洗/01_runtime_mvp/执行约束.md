## 架构约束

- Runtime 只能编排流程，不写真实业务算法。
- Runtime 调用 Service，不反向依赖 UI。
- 输入检查、run 目录、日志、manifest 和错误摘要必须统一处理。
- fake service 只用于验证流程，不代表真实清洗能力完成。
- Types、Config、Repo 是支撑层，不是 Service 的附属品；不得让它们反向依赖 Service、Runtime 或 UI。
- 未来开发者入口先规划为 `./start_data_clean.sh --dev`，但本轮不修改启动脚本。

## 数据约束

- 不覆盖 raw MCAP。
- 调试运行和正式产物必须隔离。
- 默认真实数据产物落点是 `asset/阶段二：数据清洗/`。

## 验收边界

不能把以下情况算作 Runtime MVP 完成：

- 只创建入口文件，没有 fake pipeline smoke test。
- 运行失败没有 error summary。
- 成功运行没有 run log 或 processing manifest。
- Runtime 内部混入场景一到场景五的业务算法。

## 对话确认约束

- 进入 `task/active/<功能组>/` 下的 L3 任务前，必须先阅读任务文件的“对话确认区”。
- 如果用户意图、成功标准、范围边界或入口机制不清楚，先向用户确认。
- 用户确认后的关键结论应写回对应 L3 task 或对应 Runtime 文档。
