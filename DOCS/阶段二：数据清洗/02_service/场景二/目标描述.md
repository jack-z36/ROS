# 阶段二场景二：硬件数据可靠性验证（滤波、异常值处理与 IK 仿真）

## 一句话总结

从 cleaned MCAP 生成 validated MCAP，对位姿、触觉、夹爪等数据做可靠性处理，并判断轨迹是否具备机器人执行可行性。

## 核心目标

本场景负责阶段二的第二步：确保进入时间对齐的数据不是明显噪声、异常跳变或物理不可执行轨迹。

validated MCAP 应尽量保留真实物理运动，同时对以下问题进行修复或标记：

- 高频噪声。
- 位姿突变或漂移。
- 触觉异常尖峰。
- 缺失或不可可靠补全的数据段。
- IK 无解或机器人约束不可满足的数据段。
- 仿真检查中发现的物理不可行片段。

## 软件能力产出

本场景应形成以下中粒度软件能力：

- 数据可靠性验证入口：用户可以对 cleaned MCAP 执行可靠性验证。
- 滤波能力：对位姿、触觉、夹爪宽度等序列进行平滑处理。
- 异常检测能力：发现跳变、缺失、非法值、速度/加速度异常、触觉突变等问题。
- 异常补全能力：对可修复片段进行插值、邻近补全或其他策略处理。
- 机器人约束验证能力：通过 IK、关节限制、速度/加速度限制、workspace 限制等判断轨迹是否可执行。
- 仿真验证能力：在 MuJoCo 或等价仿真环境中回放或检查轨迹。
- 报告能力：记录异常、修复、丢弃、不可执行片段和判断依据。

具体脚本名、模块名、配置名和代码结构在实现时决定，不在本目标描述中提前固定。

## 自动化处理目标

用户运行本场景入口后，理想情况下应自动完成：

1. 读取 cleaned MCAP 中需要验证的序列。
2. 执行滤波和异常检测。
3. 对可修复异常进行补全，对不可修复异常保留标记。
4. 执行 IK 和机器人运动约束检查。
5. 执行仿真验证或生成仿真检查摘要。
6. 写出 validated MCAP 和验证报告。

## 数据输出

| 输出 | 用途 |
| --- | --- |
| validated MCAP | 场景三的输入。 |
| 异常报告 | 说明哪些数据点或片段有问题。 |
| 修复记录 | 说明哪些数据被补全、平滑或替换。 |
| 机器人约束报告 | 场景四质量报告和 masks 的来源之一。 |
| 仿真验证摘要 | 人工复查和安全判断。 |

## 成功标准

- validated MCAP 可作为时间对齐输入。
- 每个被修改、补全、丢弃或标记的数据段都可追溯。
- 不可修复或不可执行片段不会静默进入后续训练数据。
- 验证报告能被场景四继承，用于生成 quality report、robot constraint report 和 masks。

## 最终开发者检验方式

本场景最终不只要求自动化测试通过，还要求开发者可以通过统一开发者引导入口，按功能模块检验场景二各能力是否正常运行。开发者检验入口应面向“场景”和“功能”，而不是要求开发者记住内部脚本路径、模块名和参数组合。

### 开发者端交互逻辑

开发者端通过统一入口进入开发调试模式：

```text
./start_data_clean.sh --dev
```

`--dev` 表示进入开发者引导界面，不直接执行正式生产流程。当前开发者引导界面的一级菜单只呈现已经开发或正在规划的阶段二 Service 场景：

```text
开发者引导界面
  1. 场景一：提取夹爪开合以及位姿转换
  2. 场景二：硬件数据可靠性验证
```

场景三、场景四、场景五尚未开发，不应在当前开发者引导界面中作为可选项暴露。后续对应场景进入开发后，再扩展一级菜单。

选择场景二后，进入场景二功能检验菜单。该菜单按功能组织，不按脚本文件组织。具体检验项在 L2/L3 实现时固化，但本场景至少必须保留一个“场景完整 smoke test”选项，用于按场景二内部主要处理链路跑通一次最小样本。

开发者端每个功能检验或场景 smoke test 的输出只要求两类：

- **测试产物**：用于判断该功能是否按预期运行的调试输出、中间结果或小样本结果。
- **运行日志**：记录输入、配置、执行步骤、关键状态、错误信息和输出位置。

开发者端输出必须与正式生产输出隔离。每次功能检验应保留独立运行目录，目录内至少包含测试产物和运行日志。调试产物不写入正式 canonical dataset 目录，也不污染正式生产输出。

开发者端默认读取用户端生产配置，以保证功能检验接近真实生产契约；同时允许在引导界面临时覆盖部分参数。临时覆盖只对本次开发调试运行生效。只有开发者明确选择“保存到配置文件”时，才允许把覆盖结果写回正式配置。

开发者端交互闭环为：

```text
./start_data_clean.sh --dev
  -> 选择场景二：硬件数据可靠性验证
  -> 选择场景二下的功能检验项或完整 smoke test
  -> 选择小样本输入和调试输出位置
  -> 可选：临时覆盖配置
  -> 执行检验
  -> 查看测试产物和运行日志
  -> 判断功能是否正确
```

开发者端交互应呈现为“页面/终端向导调用脚本”的体验。开发者只需要知道自己要检验场景二的哪个功能；入口程序负责根据选择调用对应脚本、传递配置、创建调试输出目录并写入运行日志。

### 场景二功能检验菜单

场景二功能检验菜单应围绕硬件数据可靠性验证链路组织。首版菜单至少应覆盖：

```text
场景二：硬件数据可靠性验证
  1. 检查 cleaned MCAP 输入契约
  2. 检查异常检测与补全
  3. 检查位姿 / 触觉滤波
  4. 检查 MCAP_A 生成
  5. 检查 IK 求解与 MCAP_B 生成
  6. 检查关节限制标注
  7. 检查 MuJoCo 仿真标注
  8. 检查 annotations.parquet 生成
  9. 场景二完整 smoke test
```

其中，“场景二完整 smoke test”是本场景必须保留的完整 smoke test。它应使用最小 cleaned MCAP 样本跑通：

```text
cleaned MCAP
  -> 异常检测 / 补全 / 滤波
  -> MCAP_A
  -> IK 求解
  -> MCAP_B
  -> 关节限制检查
  -> MuJoCo 仿真检查
  -> annotations.parquet
```

完整 smoke test 不要求真实大数据集，也不要求覆盖所有异常类型；它只要求证明场景二主链路能在最小样本上完成输入读取、关键中间产物生成、问题标注生成、运行日志写入和输出目录隔离。

本场景开发者检验的输出应至少包含：

- 测试产物：小样本 MCAP_A、MCAP_B、`annotations.parquet`、必要的摘要报告或可人工复查的中间结果。
- 运行日志：本次使用的输入 MCAP、生产配置、临时覆盖参数、实际执行步骤、关键状态、失败原因和输出目录。

本场景开发者检验不得把调试输出写入正式 canonical dataset 目录，也不得覆盖生产配置。只有开发者在引导界面中明确选择保存配置时，才允许把本次临时覆盖固化到正式配置文件。
